A **session** allows Flask to remember information about a user across multiple HTTP requests.

This is extremely important for login systems because HTTP itself is **stateless**.

For example, without a session:

```
Login request
    ↓
Server verifies password
    ↓
Response sent

Next request
    ↓
Server doesn't automatically know
who the user is
```

A session solves this problem.

---

# 1. What is a Session?

A **session** is a mechanism for maintaining user-specific state across multiple requests.

For authentication, a session can remember:

```
User has logged in
        ↓
User ID
        ↓
Available to later requests
```

For example:

```
Login
  ↓
session["user_id"] = 10
  ↓
Dashboard
  ↓
Profile
  ↓
Settings
```

The application can use the session to identify the logged-in user.

---

# 2. Why Do We Need Sessions?

HTTP is stateless.

Suppose a user sends:

```
POST /login
```

Then later:

```
GET /dashboard
```

These are two separate HTTP requests.

The server needs some way to associate the second request with the authenticated user.

A session provides that connection.

```
Request 1
Login
  ↓
Create session
  ↓
Request 2
Dashboard
  ↓
Read session
  ↓
Identify user
```

---

# 3. Flask Session

Flask provides a built-in `session` object.

Import it:

```
from flask import session
```

Then you can store data:

```
session["user_id"] = 10
```

And retrieve it later:

```
user_id = session.get("user_id")
```

You can think of it as a small user-specific dictionary:

```
session["user_id"]
session["role"]
session["logged_in"]
```

---

# 4. Secret Key

Flask sessions require a **secret key**.

Example:

```
app.secret_key = "your-secret-key"
```

Or:

```
app.config["SECRET_KEY"] = "your-secret-key"
```

The second style is generally preferred because Flask configuration is centralized.

```
from flask import Flask

app = Flask(__name__)

app.config["SECRET_KEY"] = "your-secret-key"
```

### Why is the secret key important?

Flask uses the secret key to securely sign session data.

If an attacker can obtain your application's secret key, they may be able to forge valid signed session data.

Therefore:

> **Never expose your production `SECRET_KEY`.**

---

# 5. Don't Hardcode Production Secrets

For learning:

```
app.config["SECRET_KEY"] = "dev-secret-key"
```

is okay.

For a real application, use an environment variable.

For example:

```
import os

app.config["SECRET_KEY"] = os.environ.get(
    "SECRET_KEY"
)
```

Environment:

```
SECRET_KEY=some-long-random-secret
```

This keeps secrets outside your source code.

# 7. Login + Session

Let's connect this with the previous topics.

```
from flask import Flask, request, session
from werkzeug.security import check_password_hash

app = Flask(__name__)

app.config["SECRET_KEY"] = "dev-secret-key"


@app.route("/login", methods=["POST"])
def login():

    email = request.form.get("email")
    password = request.form.get("password")

    user = User.query.filter_by(
        email=email
    ).first()

    if not user:
        return "Invalid credentials", 401

    if not check_password_hash(
        user.password_hash,
        password
    ):
        return "Invalid credentials", 401

    session["user_id"] = user.id

    return "Login successful"
```

The important sequence is:

```
Find User
   ↓
Verify Password
   ↓
Password correct?
   ↓
session["user_id"] = user.id
```

# 9. Check Whether User Is Logged In

A common pattern:

```
if "user_id" not in session:
    return "Please login"
```

Or:

```
user_id = session.get("user_id")

if user_id is None:
    return "Please login"
```

Example:

```
@app.route("/dashboard")
def dashboard():

    user_id = session.get("user_id")

    if user_id is None:
        return "Please login", 401

    return "Welcome to your dashboard"
```

# 10. Protecting a Route

A route that should only be accessible to authenticated users is called a **protected route**.

Example:

```
@app.route("/profile")
def profile():

    user_id = session.get("user_id")

    if user_id is None:
        return "Login required", 401

    return "Your profile"
```

The flow:

```
GET /profile
      ↓
Is user_id in session?
      │
   ┌──┴──┐
   ↓     ↓
  Yes    No
   ↓     ↓
Allow   Reject
```

# 11. Retrieve the Actual User

The session usually contains an identifier rather than the entire database user object.

For example:

```
session["user_id"] = user.id
```

Then:

```
user_id = session.get("user_id")
```

And:

```
user = db.session.get(User, user_id)
```

Complete example:

```
@app.route("/profile")
def profile():

    user_id = session.get("user_id")

    if user_id is None:
        return "Login required", 401

    user = db.session.get(User, user_id)

    if user is None:
        session.clear()
        return "User not found", 401

    return f"Hello, {user.name}"
```

This gives us:

```
Session
  ↓
user_id
  ↓
Database
  ↓
User object
```

---

# 12. Why Store the User ID Instead of the Whole User?

A common approach is:

```
session["user_id"] = user.id
```

rather than:

```
session["user"] = user
```

The user object contains database-related information and isn't appropriate session data.

A small identifier is much cleaner:

```
Session:
{
    "user_id": 25
}
```

Then retrieve the current user from the database when needed.

---

# 13. Session as a User Identity Marker

Think of:

```
session["user_id"] = 25
```

as saying:

> "The current authenticated session belongs to user 25."

Then:

```
user = db.session.get(User, 25)
```

gets the actual user.

Mental model:

```
Browser
   ↓
Session
   ↓
user_id = 25
   ↓
Database
   ↓
User #25
```

---

# 14. Session Data

You can store other small pieces of information.

For example:

```
session["user_id"] = user.id
session["role"] = user.role
```

Then:

```
role = session.get("role")
```

However, be careful about storing authorization information in sessions.

For important authorization decisions, you should consider the source of truth and whether role changes need to take effect immediately.

For example, if an administrator changes a user's role in the database, an old session containing:

```
role = "admin"
```

could become stale.

A common approach is to store the user ID and retrieve the current user's role from the database when making important authorization decisions.

---

# 15. Session Cookies

Flask's default session mechanism uses a **session cookie**.

Conceptually:

```
Browser
   │
   │ Cookie
   ↓
Flask
   │
   ↓
Session data
```

The browser stores a cookie associated with the Flask session.

Flask signs session data using the application's secret key so that modifications can be detected.

### Important distinction

Flask's default session is generally **cookie-based**.

That means you should not treat it as though all session data is stored only on the server.

---

# 16. Can the User See Session Data?

With Flask's default cookie-based session system, session data is stored in the browser in a signed cookie.

Therefore, don't put sensitive secrets directly into the session.

For example, avoid storing:

```
Database password
API secret
Private encryption key
Credit card information
```

A good session might contain:

```
{
    "user_id": 25
}
```

rather than sensitive credentials.

---

# 17. Signed Does Not Mean Encrypted

This distinction is important.

Flask's default session cookie is **signed**, which helps detect tampering.

Signing provides integrity/authenticity of the session data.

It should not be treated as a general-purpose encrypted storage mechanism for secrets.

Therefore:

```
Signed ≠ encrypted
```

Do not put highly sensitive information into a normal Flask session just because the session is signed.

# 18. Session Lifecycle

A typical authentication session looks like:

```
                User
                  │
                  ↓
                Login
                  │
                  ↓
          Verify Credentials
                  │
                  ↓
       session["user_id"] = ID
                  │
                  ↓
            Authenticated
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
    Dashboard  Profile   Settings
        │         │         │
        └─────────┼─────────┘
                  ↓
                Logout
                  │
                  ↓
          Session Removed
```

This is the core authentication lifecycle.

# 19. Removing Session Data

There are several ways to remove session information.

### Remove one value

```
session.pop("user_id", None)
```

This removes:

```
user_id
```

while leaving other session values.

### Clear the whole session

```
session.clear()
```

This removes all session data.

This is commonly useful during logout.

We'll cover logout specifically in **9.7**.

---

# 20. Session vs Local Storage

Don't confuse Flask sessions with browser `localStorage`.

|Flask Session|`localStorage`|
|---|---|
|Part of server-side application authentication design|Browser storage API|
|Flask manages session cookie|JavaScript manages storage|
|Can be used by Flask authentication|Not automatically authentication|
|Session cookie is sent with requests|Not automatically sent to server|
|Server can identify session|Frontend must explicitly send data|

For example:

```
localStorage.setItem("userId", "25");
```

does **not** automatically make the user authenticated to Flask.

Authentication requires a properly designed server-side mechanism.

---

# 21. Session vs Cookies

A **cookie** and a **session** are related but not identical concepts.

### Cookie

A cookie is data stored by the browser and associated with a website.

### Session

A session is an application-level mechanism for maintaining state across requests.

Flask's default session implementation uses a cookie to carry signed session data.

Think:

```
Cookie = transport/storage mechanism in the browser

Session = application concept for remembering state
```

# 22. Session Configuration

Flask provides several session-related configuration options.

Some important ones include:

```
app.config["SESSION_COOKIE_SECURE"] = True
app.config["SESSION_COOKIE_HTTPONLY"] = True
app.config["SESSION_COOKIE_SAMESITE"] = "Lax"
```

Let's understand them.

---

## `SESSION_COOKIE_SECURE`

```
app.config["SESSION_COOKIE_SECURE"] = True
```

The browser should only send the session cookie over HTTPS.

Therefore:

```
HTTP  ❌
HTTPS ✅
```

This is appropriate for HTTPS production environments.

During local development without HTTPS, setting this to `True` can prevent the cookie from being sent.

---

## `SESSION_COOKIE_HTTPONLY`

```
app.config["SESSION_COOKIE_HTTPONLY"] = True
```

This tells the browser that JavaScript should not normally access the cookie through `document.cookie`.

This helps reduce the impact of certain XSS scenarios involving cookie theft.

---

## `SESSION_COOKIE_SAMESITE`

Example:

```
app.config["SESSION_COOKIE_SAMESITE"] = "Lax"
```

This controls when the browser sends the cookie in cross-site contexts.

Common values include:

```
Strict
Lax
None
```

`SameSite` is an important part of modern cookie security.

---

# 23. Basic Secure Configuration

A common production-oriented configuration may look like:

```
app.config["SESSION_COOKIE_SECURE"] = True
app.config["SESSION_COOKIE_HTTPONLY"] = True
app.config["SESSION_COOKIE_SAMESITE"] = "Lax"
```

Remember:

```
SECURE
HTTPONLY
SAMESITE
```

These settings don't replace proper authentication and authorization design, but they strengthen cookie handling.

---

# 24. Session Expiration

Sessions can also have a lifetime.

Flask provides:

```
from datetime import timedelta

app.permanent_session_lifetime = timedelta(
    days=7
)
```

Then:

```
session.permanent = True
```

This tells Flask to use the configured permanent-session lifetime for that session.

Without making a session permanent, Flask's session cookie behavior is tied to the browser session.

# 25. Complete Simple Example

Let's put everything together.

```
from flask import Flask, request, session
from werkzeug.security import check_password_hash

app = Flask(__name__)

app.config["SECRET_KEY"] = "dev-secret-key"


@app.route("/login", methods=["POST"])
def login():

    email = request.form.get("email")
    password = request.form.get("password")

    user = User.query.filter_by(
        email=email
    ).first()

    if not user:
        return "Invalid credentials", 401

    if not check_password_hash(
        user.password_hash,
        password
    ):
        return "Invalid credentials", 401

    session["user_id"] = user.id

    return "Login successful"


@app.route("/dashboard")
def dashboard():

    user_id = session.get("user_id")

    if user_id is None:
        return "Login required", 401

    user = db.session.get(User, user_id)

    if user is None:
        session.clear()
        return "User not found", 401

    return f"Welcome, {user.name}"
```

```

   ↓
Database
   ↓

   ↓
Session
   ↓
user_id
   ↓
Protected Route
   ↓
Database User
```

# 26. Session Security Checklist 🔒

For a production application:

### 1. Use a strong secret key

```
SECRET_KEY
```

should be unpredictable.

### 2. Don't commit secrets

Avoid putting real production secrets directly into Git.

### 3. Use HTTPS

Especially for authentication.

### 4. Use `HttpOnly`

```
SESSION_COOKIE_HTTPONLY = True
```

### 5. Configure `SameSite`

For example:

```
SESSION_COOKIE_SAMESITE = "Lax"
```

### 6. Use `Secure` with HTTPS

```
SESSION_COOKIE_SECURE = True
```

### 7. Keep session data minimal

Prefer:

```
session["user_id"] = user.id
```

instead of storing lots of sensitive information.

# 27. Common Mistakes ❌

### Mistake 1: No secret key

```
session["user_id"] = 10
```

without configuring the Flask secret key.

This causes session functionality problems.

---

### Mistake 2: Putting secrets in the session

Don't store:

```
Database password
API keys
Private keys
```

in the normal Flask session.

---

### Mistake 3: Assuming session means database storage

Flask's default session is cookie-based.

Don't assume:

```
session data = database row
```

They are different things.

---

### Mistake 4: Trusting a client-controlled role blindly

For example:

```
session["role"] = "admin"
```

and then blindly trusting that value for sensitive authorization decisions can create stale or poorly controlled authorization state.

The database should generally remain the authoritative source for current user permissions.

---

### Mistake 5: Forgetting to protect routes

Having a login system does not automatically protect every route.

You must explicitly check authentication on protected resources.
