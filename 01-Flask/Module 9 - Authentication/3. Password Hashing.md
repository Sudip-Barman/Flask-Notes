Password hashing is one of the **most important security concepts** in authentication.

When a user registers, we should **never store their original password directly in the database**.

Instead:

```
User Password
      ↓
Password Hashing Algorithm
      ↓
Password Hash
      ↓
Database
```

When the user logs in:

```
Entered Password
      ↓
Password Verification
      ↓
Stored Password Hash
      ↓
Match?
```

---

# 1. What is Password Hashing?

**Password hashing** is the process of converting a password into a fixed-format value called a **hash** using a one-way password hashing algorithm.

For example, the user enters:

```
secret123
```

The database might store something like:

```
scrypt:32768:8:1$...$...
```

The exact hash depends on the hashing algorithm and parameters.

The important idea is:

```
secret123
    ↓
Hashing
    ↓
Hash value
```

The original password should not be stored.

---

# 2. Why Do We Hash Passwords?

Imagine a database contains:

|User|Password|
|---|---|
|Rahul|secret123|
|Priya|password456|
|Amit|mypassword|

This is extremely dangerous.

If an attacker obtains the database, they immediately have the users' passwords.

With hashing:

|User|Password Hash|
|---|---|
|Rahul|`$...`|
|Priya|`$...`|
|Amit|`$...`|

The database does not contain the original passwords.

Therefore:

> **Never store plaintext passwords in a production application.**

---

# 3. Hashing vs Encryption

This distinction is very important.

### Encryption

Encryption is designed to be reversible.

```
Plain Data
    ↓
Encryption
    ↓
Encrypted Data
    ↓
Decryption
    ↓
Plain Data
```

You can decrypt encrypted data if you have the appropriate key.

### Hashing

Hashing is designed to be one-way.

```
Password
    ↓
Hash
    ↓
Hash Value
```

You don't normally "decrypt" a password hash to get the original password.

### Comparison

|Hashing|Encryption|
|---|---|
|Generally one-way|Reversible with a key|
|Used for passwords|Used for data that needs recovery|
|No decryption step|Has decryption|
|Password verification|Secure communication/storage|

For passwords:

```
Hashing ✅
Encryption as password storage ❌
Plain text ❌
```

---

# 4. Hashing Is Not Simply "Converting Text"

A common beginner misunderstanding is:

> "A hash is just an encrypted version of the password."

Not exactly.

A secure password hashing system is designed specifically to make password guessing expensive.

Modern password hashing algorithms can intentionally require substantial:

- CPU work
- Memory
- Time

This makes large-scale password guessing more difficult.

# 6. `generate_password_hash()`

Example:

```
from werkzeug.security import generate_password_hash

password = "secret123"

```

The result will be a long hash string.

Conceptually:

```
secret123
     ↓

     ↓

```

You store the **hash** in the database.


# 9. Registration with Password Hashing

Now let's improve the registration code from Topic 9.1.

```
from flask import request
from werkzeug.security import generate_password_hash


@app.route("/register", methods=["POST"])
def register():

    name = request.form.get("name")
    email = request.form.get("email")
    password = request.form.get("password")

    if not name or not email or not password:
        return "All fields are required"

    existing_user = User.query.filter_by(
        email=email
    ).first()

    if existing_user:
        return "Invalid registration"

    password_hash = generate_password_hash(password)

    user = User(
        name=name,
        email=email,
        password_hash=password_hash
    )

    db.session.add(user)
    db.session.commit()

    return "Registration successful"
```

The important part is:

```
password_hash = generate_password_hash(password)
```

and:

```
password_hash=password_hash
```

# 11. What is a Salt?

A **salt** is additional random data incorporated into password hashing so that identical passwords do not normally produce identical stored hashes.

For example:

```
Password A:
secret123

Salt:
random value

       ↓

Password Hash
```

Another user can have the same password:

```
Password B:
secret123

Different Salt:
another random value

       ↓

Different Password Hash
```

So two users with the same password can have different stored hashes.

Modern password hashing utilities generally handle salt generation for you.

You don't normally need to manually create and manage a salt when using Werkzeug's password hashing functions.

---

# 12. Why Salt Is Important

Suppose 3 users all choose:

```
secret123
```

Without proper salting, a simplistic hash system might produce:

```
User A → same hash
User B → same hash
User C → same hash
```

With salts:

```
User A → hash A
User B → hash B
User C → hash C
```

even though:

```
Password A = Password B = Password C
```

This helps defend against precomputed password-hash attacks such as rainbow tables.

# 13. Password Verification

Now comes the login process.

Suppose the database contains:

```
password_hash = stored hash
```

The user enters:

```
secret123
```

We use:

```
check_password_hash(
    stored_hash,
    entered_password
)
```

Example:

```
from werkzeug.security import check_password_hash

is_valid = check_password_hash(
    user.password_hash,
    password
)
```

It returns:

```
True
```

or:

```
False
```

---

# 14. Login with Password Verification

A complete simplified login:

```
from flask import request
from werkzeug.security import check_password_hash


@app.route("/login", methods=["POST"])
def login():

    email = request.form.get("email")
    password = request.form.get("password")

    user = User.query.filter_by(
        email=email
    ).first()

    if not user:
        return "Invalid credentials", 401

    if not check_password_hash(
        user.password_hash,
        password
    ):
        return "Invalid credentials", 401

    return "Login successful"
```

Notice the important difference.

We don't do:

```
password == user.password_hash
```

Instead:

```
check_password_hash(
    user.password_hash,
    password
)
```

# 15. How Password Verification Works

Conceptually:

```
                    Registration

User password
     │
     ↓
Hash function
     │
     ↓
Password hash
     │
     ↓
Database
```

Then:

```
                     Login

User enters password
        │
        ↓
Password verification
        │
        ↓
Compare against stored hash
        │
     ┌──┴──┐
     ↓     ↓
   Match  Wrong
     ↓     ↓
  Login   Reject
```

The application doesn't need to retrieve the original password from the database.

# 16. You Don't Need to Hash the Login Password Yourself

A common mistake is doing something like:

```
entered_hash = generate_password_hash(password)

if entered_hash == user.password_hash:
    ...
```

❌ Don't do this.

Why?

Password hashing uses a salt, so hashing the same password again can produce a different hash.

Instead, use:

```
check_password_hash(
    user.password_hash,
    password
)
```

The verification function knows how to use the information contained in the stored hash.

---

# 17. Same Password, Different Hash

For example:

```
generate_password_hash("secret123")
```

might produce one hash.

Calling it again:

```
generate_password_hash("secret123")
```

can produce a different hash.

Conceptually:

```
secret123
   ↓
Hashing
   ↓
Hash A


secret123
   ↓
Hashing
   ↓
Hash B
```

Yet:

```
check_password_hash(hash_a, "secret123")
```

returns:

```
True
```

and:

```
check_password_hash(hash_b, "secret123")
```

also returns:

```
True
```

That's one reason verification should use the dedicated function.

---

# 18. Password Hashing Algorithms

Password hashing is different from ordinary fast hashing.

You may encounter algorithms such as:

- PBKDF2
- scrypt
- Argon2
- bcrypt

These are designed for password storage and verification.

### Important idea

A general-purpose hash such as:

```
SHA-256
```

is designed to be extremely fast.

That's usually **not what you want for password storage by itself**.

An attacker can potentially test huge numbers of password guesses very quickly.

Password hashing algorithms deliberately make guessing more expensive.

---

# 19. Why Not Just Use SHA-256?

You might see:

```
hashlib.sha256(password.encode()).hexdigest()
```

This produces a hash, but using plain SHA-256 directly for password storage is generally not the recommended approach.

The problem is speed.

```
Fast hash
   ↓
Millions/billions of guesses become easier
```

Password hashing algorithms are designed differently:

```
Password
   ↓
Slow / memory-intensive password hashing
   ↓
Hash
```

This increases the cost of guessing attacks.

For Flask applications, use a proper password hashing utility such as Werkzeug's password helpers rather than inventing your own password-storage scheme.

# 21. Never Log Passwords

Avoid:

```
print(password)
```

and:

```
app.logger.info(password)
```

Passwords should not appear in:

- Console logs
- Application logs
- Error messages
- Database records
- Analytics
- Debug output

Even during development, getting into the habit of treating passwords as sensitive data is important.

---

# 22. Password Hashing Does Not Mean Passwords Are Unbreakable

Hashing greatly improves security, but it doesn't make weak passwords magically strong.

Suppose someone chooses:

```
123456
```

An attacker can try common passwords.

Therefore a good authentication system should combine:

```
Strong password policy
        +
Secure password hashing
        +
Secure authentication
        +
Rate limiting
        +
Secure session management
```

Password hashing protects stored passwords. It does not solve every authentication security problem.

---

# 23. Password Hashing and Database Breach

Imagine an attacker obtains:

```
users
├── email
├── name
└── password_hash
```

They don't immediately have the original passwords.

They may still attempt offline password guessing:

```
Guess password
      ↓
Hash guess
      ↓
Compare
      ↓
Repeat
```

This is why password hashing algorithms are intentionally designed to make each guess expensive.

And this is why users should choose strong, unique passwords.

# 26. Common Mistakes ❌

### Mistake 1: Plain-text password

```
user.password = password
```

❌ Don't store the original password.

---

### Mistake 2: Encrypting passwords instead of hashing them

Passwords generally don't need to be recovered.

Use a proper password hashing system.

---

### Mistake 3: Using a fast hash directly

```
sha256(password)
```

❌ Don't design your own password-storage system using a general-purpose hash.

Use a password hashing algorithm/library.

---

### Mistake 4: Hashing again during login

```
generate_password_hash(password) == user.password_hash
```

❌ Don't do this.

Use:

```
check_password_hash(
    user.password_hash,
    password
)
```

---

### Mistake 5: Logging passwords

```
print(password)
```

❌ Avoid this.

---

### Mistake 6: Storing `confirm_password`

You might receive:

```
password
confirm_password
```

The confirmation field is for validation.

You normally store only:

```
password_hash
```

```
                  REGISTER

                     ↓

     generate_password_hash()

                     ↓
              Password Hash
                     │
                     ↓
                  Database
                     │
                     │
─────────────────────┼─────────────────────
                     │
                     ↓
                   LOGIN
                     │
                     ↓
             Entered Password
                     │
                     ↓
       check_password_hash()
                     │
                     ↓
              Stored Hash
                     │
                ┌────┴────┐
                ↓         ↓
              Match     Wrong
                ↓         ↓
          Authenticated  Reject
```

The golden rule:

> **Hash when storing. Verify when logging in. Never decrypt or compare plaintext passwords.**
