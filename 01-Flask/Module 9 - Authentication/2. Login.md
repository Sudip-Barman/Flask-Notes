**Login** is the process of verifying an existing user's identity.

Registration creates the account. Login proves that the person trying to use the account knows the correct credentials.

```
Register
   ↓
Account created
   ↓
Login
   ↓
Verify credentials
   ↓
User authenticated
   ↓
Create session
   ↓
Access protected resources
```

---

# 1. What is Login?

A login system usually asks for:

```
Email
Password
   ↓
Login
```

The server then:

1. Receives the email and password.
2. Finds the user in the database.
3. Checks whether the password is correct.
4. If correct, authenticates the user.
5. Creates an authenticated session.

---

# 2. Login vs Registration

|Registration|Login|
|---|---|
|Creates a new account|Accesses an existing account|
|Usually done once|Can be done many times|
|Saves user information|Verifies user information|
|Creates password hash|Checks password against hash|
|Creates database record|Usually does not create a new user|

Think of it like:

```
Registration = Get an ID card

Login = Prove that the ID card belongs to you
```

# 4. Login Database Data

Suppose the database contains:

|id|name|email|password_hash|
|---|---|---|---|
|1|Rahul|[rahul@example.com](mailto:rahul@example.com)|`$...hashed value...`|
|2|Priya|[priya@example.com](mailto:priya@example.com)|`$...hashed value...`|

The user enters:

```
Email: rahul@example.com
Password: secret123
```

The application does **not** compare:

```
password == user.password
```

because the database should not contain the original password.

Instead:

```
Entered Password
       ↓
Password Verification
       ↓
Stored Password Hash
       ↓
Match?
```

Password verification will be covered in detail in **9.3 Password Hashing**.

# 7. Find the User

After receiving the email, we search the database.

```
user = User.query.filter_by(
    email=email
).first()
```

If a matching user exists:

```
if user:
    print("User found")
```

If no user exists:

```
if not user:
    return "Invalid credentials"
```

A better authentication flow avoids revealing whether the email itself exists.

---

# 8. Verify the Password

Once the user is found, the application must verify the entered password against the stored hash.

Conceptually:

```
Entered Password
       ↓
   Verify
       ↓
Stored Password Hash
       ↓
   True / False
```

For example, using Werkzeug:

```
from werkzeug.security import check_password_hash
```

Then:

```
check_password_hash(
    user.password,
    password
)
```

If the password is correct:

```
if check_password_hash(user.password, password):
    print("Password correct")
```

If incorrect:

```
if not check_password_hash(user.password, password):
    return "Invalid credentials"
```

We'll study `generate_password_hash()` and `check_password_hash()` properly in **9.3**.

# 9. Complete Basic Login

Putting the pieces together:

```
from flask import Flask, request
from werkzeug.security import check_password_hash

app = Flask(__name__)


@app.route("/login", methods=["GET", "POST"])
def login():

    if request.method == "POST":

        email = request.form.get("email")
        password = request.form.get("password")

        user = User.query.filter_by(
            email=email
        ).first()

        if not user:
            return "Invalid credentials"

        if not check_password_hash(
            user.password,
            password
        ):
            return "Invalid credentials"

        return "Login successful"

    return "Login form"
```

At this point, we have verified the user.

But there is still a problem.

# 10. How Does Flask Remember the Login?

Suppose the user successfully logs in.

The next request might be:

```
GET /dashboard
```

How does Flask know that this request came from the user who just logged in?

HTTP is fundamentally **stateless**.

Each request is independent:

```
Request 1 → Login
Request 2 → Dashboard
Request 3 → Profile
Request 4 → Settings
```

The server needs a mechanism to remember authentication between requests.

That mechanism is usually a **session**.

```
Login
  ↓
Authentication successful
  ↓
Session created
  ↓
Future requests
  ↓
Flask knows the user is authenticated
```

Sessions are Topic **9.4**.

---

# 11. Login with Session

Flask provides:

```
from flask import session
```

Before using sessions, you need a secret key:

```
app.secret_key = "your-secret-key"
```

After successful authentication:

```
session["user_id"] = user.id
```

Now the application has information indicating which user is logged in.

Example:

```
@app.route("/login", methods=["POST"])
def login():

    email = request.form.get("email")
    password = request.form.get("password")

    user = User.query.filter_by(
        email=email
    ).first()

    if not user:
        return "Invalid credentials"

    if not check_password_hash(
        user.password,
        password
    ):
        return "Invalid credentials"

    session["user_id"] = user.id

    return "Login successful"
```

We'll go much deeper into this in **9.4 Sessions**.

# 12. Login Mental Model

Think of authentication as two separate questions.

### Question 1: Who are you?

This is **authentication**.

```
Email + Password
       ↓
     Login
       ↓
Identity verified
```

### Question 2: What can you do?

This is **authorization**.

```
Authenticated User
       ↓
     Role
       ↓
   Permissions
       ↓
Allowed actions
```

For example:

```
Login successful
      ↓
     User
      ↓
Can access dashboard
      ↓
Cannot access admin settings
```

We'll study roles and permissions later.

---

# 13. Authentication vs Authorization

This distinction is extremely important.

|Authentication|Authorization|
|---|---|
|Who are you?|What are you allowed to do?|
|Verifies identity|Verifies access|
|Login|Role/permission checks|
|Password|Permissions|
|Happens first|Happens after authentication|

Example:

```
User logs in
    ↓
Authentication
    ↓
"Yes, this is Rahul."
    ↓
Authorization
    ↓
"Rahul is a normal user."
    ↓
"Can access user dashboard."
```

# 14. Login API

Login can also be implemented as a JSON API.

Request:

```
{
    "email": "rahul@example.com",
    "password": "secret123"
}
```

Flask:

```
@app.route("/api/login", methods=["POST"])
def login():

    data = request.get_json()

    email = data.get("email")
    password = data.get("password")

    user = User.query.filter_by(
        email=email
    ).first()

    if not user:
        return {
            "error": "Invalid credentials"
        }, 401

    if not check_password_hash(
        user.password,
        password
    ):
        return {
            "error": "Invalid credentials"
        }, 401

    return {
        "message": "Login successful"
    }
```

Here:

```
401
```

means:

**Unauthorized**

More precisely, the server did not accept the supplied authentication credentials.

---

# 15. HTTP Status Codes for Login

Common responses:

|Status|Meaning|Example|
|---|---|---|
|`200`|Success|Login successful|
|`400`|Bad request|Missing required fields|
|`401`|Authentication failed|Invalid credentials|
|`403`|Forbidden|Authenticated but not allowed|
|`500`|Server error|Unexpected server problem|

Important distinction:

```
401 → You are not successfully authenticated

403 → You are authenticated, but you don't have permission
```

For example:

```
@app.route("/login", methods=["POST"])

    password = request.form.get("password")

    if not email or not password:
        return "Email and password are required"

```

# 17. Don't Trust Client-Side Validation

You might have HTML:

```
<input
    type="email"
    required
>
```

This is useful for the user experience.

But Flask must still validate the input.

Why?

Because a user can bypass browser validation and directly send a request to:

```
POST /login
```

Therefore:

```
Frontend validation
       +
Backend validation
       =
Better validation
```

The backend is the final authority.

# 19. Common Login Mistakes ❌

### Mistake 1: Comparing plain passwords

Bad:

```
if password == user.password:
```

If `user.password` contains a hash, this will not work correctly.

Use a password verification function.

---

### Mistake 2: Storing plain-text passwords

Never do:

```
user.password = password
```

with the original password.

Use hashing.

---

### Mistake 3: Forgetting the session

Successfully verifying the password does not automatically make the user authenticated for future requests.

You need a mechanism such as:

```
session["user_id"] = user.id
```

or, for API architectures, another appropriate authentication mechanism.

---

### Mistake 4: Trusting the frontend

Don't assume that because the login page validates the email, the backend doesn't need to.

Always validate server-side.

---

### Mistake 5: Revealing too much information

Avoid authentication responses such as:

```
Email does not exist
```

versus:

```
Password is incorrect
```

A generic:

```
Invalid credentials
```

is often safer.
