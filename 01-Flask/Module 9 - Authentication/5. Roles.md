
A **role** defines the general type or level of access a user has within an application.

For example:

```
Users
  ├── Admin
  ├── Manager
  ├── Staff
  └── Customer
```

Roles become useful **after authentication**.

Remember:

```
Authentication
      ↓
Who are you?
      ↓
Role
      ↓
What type of user are you?
      ↓
Permissions
      ↓
What can you do?
```

---

# 1. What is a Role?

A **role** is a label assigned to a user that represents their general responsibilities or access level.

Examples:

|Role|Typical purpose|
|---|---|
|Admin|Manage the application|
|Manager|Manage specific business operations|
|Staff|Perform assigned tasks|
|Customer|Use customer-facing features|

For example:

```
Rahul → Admin
Priya → Staff
Amit  → Customer
```

The role itself doesn't necessarily define every individual action. It usually acts as a **grouping mechanism for permissions**.

---

# 2. Why Do We Need Roles?

Imagine an application has these pages:

```
Dashboard
Users
Reports
Settings
Orders
```

You probably don't want every authenticated user to access everything.

For example:

```
Admin
 ├── Dashboard
 ├── Users
 ├── Reports
 ├── Settings
 └── Orders

Staff
 ├── Dashboard
 ├── Orders
 └── Reports

Customer
 ├── Dashboard
 └── Orders
```

Roles make this easier to manage.

---

# 3. Authentication vs Role

Authentication answers:

> **Who are you?**

Example:

```
Email + Password
       ↓
User verified
```

Role answers:

> **What type of user are you?**

Example:

```
Authenticated User
       ↓
role = "admin"
```

So:

```
Login
  ↓
Authentication
  ↓
User identified
  ↓
Role identified
```

---

# 4. Role vs Permission

This distinction is extremely important.

### Role

A role is a **group/category**.

```
Admin
Staff
Customer
```

### Permission

A permission is a **specific action or access right**.

```
create_user
delete_user
view_reports
edit_order
```

Therefore:

```
Role
 ↓
Group of users
 ↓
Associated permissions
```

For example:

```
Admin
 ├── create_user
 ├── delete_user
 ├── view_reports
 └── edit_settings
```

Permissions are covered in **9.6**.

# 5. Adding a Role to the User Model

A simple approach is to add a `role` column.

```
class User(db.Model):
    __tablename__ = "users"

    id = db.Column(
        db.Integer,
        primary_key=True
    )

    name = db.Column(
        db.String(100),
        nullable=False
    )

    email = db.Column(
        db.String(120),
        unique=True,
        nullable=False
    )

    password_hash = db.Column(
        db.String(255),
        nullable=False
    )

    role = db.Column(
        db.String(50),
        nullable=False,
        default="customer"
    )
```

Now a user might look like:

|id|name|email|role|
|---|---|---|---|
|1|Rahul|[rahul@example.com](mailto:rahul@example.com)|admin|
|2|Priya|[priya@example.com](mailto:priya@example.com)|staff|
|3|Amit|[amit@example.com](mailto:amit@example.com)|customer|

# 6. Creating a User with a Role

When creating a user:

```
user = User(
    name="Rahul",
    email="rahul@example.com",
    password_hash=password_hash,
    role="admin"
)
```

Or:

```
user = User(
    name="Priya",
    email="priya@example.com",
    password_hash=password_hash,
    role="staff"
)
```

The role is stored in the database.

---

# 7. Default Role

You can define a default role:

```
role = db.Column(
    db.String(50),
    nullable=False,
    default="customer"
)
```

Then:

```
user = User(
    name="Amit",
    email="amit@example.com",
    password_hash=password_hash
)
```

The database/model will use:

```
customer
```

as the default role.

This is useful because newly registered users shouldn't accidentally become administrators.

---

# 8. Very Important Security Rule 🚨

**Do not allow a normal user to freely choose an administrative role during registration.**

For example, this is dangerous:

```
<select name="role">
    <option value="customer">Customer</option>
    <option value="staff">Staff</option>
    <option value="admin">Admin</option>
</select>
```

If your backend blindly accepts:

```
role = request.form.get("role")
```

a malicious user could submit:

```
role=admin
```

and create an administrator account.

❌ Very dangerous.

---

# 9. Safer Registration

For public registration, assign the role on the server:

```
user = User(
    name=name,
    email=email,
    password_hash=password_hash,
    role="customer"
)
```

The client doesn't control the role.

If an administrator needs to promote someone:

```
Admin
  ↓
User Management
  ↓
Change Role
  ↓
Staff
```

That should be a protected administrative operation.

# 11. Role-Based Route Protection

Suppose only administrators should access:

```
/admin
```

A basic route:

```
@app.route("/admin")
def admin():

    user_id = session.get("user_id")

    if user_id is None:
        return "Login required", 401

    user = db.session.get(User, user_id)

    if user is None:
        return "User not found", 401

    if user.role != "admin":
        return "Access denied", 403

    return "Admin dashboard"
```

The flow is:

```
Request /admin
       ↓
Is user logged in?
       │
   ┌───┴───┐
   ↓       ↓
  No      Yes
   ↓       ↓
  401    Find User
             ↓
          Check Role
             ↓
       role == admin?
          │       │
         Yes      No
          ↓       ↓
        Allow    403
```

---

# 12. Why `403` Instead of `401`?

This connects with the previous topic.

### `401 Unauthorized`

The user isn't successfully authenticated.

```
Not logged in
    ↓
401
```

### `403 Forbidden`

The user is authenticated but doesn't have the required access.

```
Logged in
   ↓
role = customer
   ↓
Trying to access admin page
   ↓
403
```

So:

```
401 → Authentication problem
403 → Authorization problem
```

# 13. Role Decorators

If you have many admin routes, repeatedly writing:

```
if user.role != "admin":
    return "Access denied", 403
```

becomes repetitive.

A better approach is to create a **decorator**.

For example:

```
from functools import wraps
from flask import session


def admin_required(view):

    @wraps(view)
    def wrapped_view(*args, **kwargs):

        user_id = session.get("user_id")

        if user_id is None:
            return "Login required", 401

        user = db.session.get(User, user_id)

        if user is None:
            return "User not found", 401

        if user.role != "admin":
            return "Access denied", 403

        return view(*args, **kwargs)

    return wrapped_view
```

Then:

```
@app.route("/admin")
@admin_required
def admin():
    return "Admin dashboard"
```

Now:

```
GET /admin
      ↓
@admin_required
      ↓
Authentication check
      ↓
Role check
      ↓
Admin?
   ┌──┴──┐
   ↓     ↓
  Yes    No
   ↓     ↓
 Route   403
```

---

# 14. Why Use Decorators?

Suppose you have:

```
/admin
/admin/users
/admin/settings
/admin/reports
/admin/logs
```

Without a decorator, every route needs the same authorization code.

With:

```
@admin_required
```

you can reuse the logic.

```
Authentication / Authorization Logic
              ↓
        admin_required()
              ↓
       ┌──────┼──────┐
       ↓      ↓      ↓
    /admin /users /reports
```

This is cleaner and easier to maintain.

# 15. Multiple Roles

Sometimes a route should be available to multiple roles.

For example:

```
Admin
Manager
```

could both access reports.

We can create:

```
def roles_required(*allowed_roles):

    def decorator(view):

        @wraps(view)
        def wrapped_view(*args, **kwargs):

            user_id = session.get("user_id")

            if user_id is None:
                return "Login required", 401

            user = db.session.get(User, user_id)

            if user is None:
                return "User not found", 401

            if user.role not in allowed_roles:
                return "Access denied", 403

            return view(*args, **kwargs)

        return wrapped_view

    return decorator
```

Then:

```
@app.route("/reports")
@roles_required("admin", "manager")
def reports():
    return "Reports page"
```

Now:

```
Admin    → ✅
Manager  → ✅
Staff    → ❌
Customer → ❌
```

# 16. Role Hierarchy

Sometimes roles have a rough hierarchy:

```
Admin
  ↓
Manager
  ↓
Staff
  ↓
Customer
```

But don't assume that roles automatically form a hierarchy.

For example:

```
Doctor
Nurse
Accountant
```

These aren't necessarily higher or lower than each other.

They simply have **different responsibilities**.

Therefore, role systems should reflect your application's actual authorization requirements.

# 17. Role Stored in Session vs Database

You might see:

```
session["role"] = user.role
```

This can be convenient.

For example:

```
if session.get("role") == "admin":
    ...
```

But there is a potential problem.

Suppose:

```
Database:
Rahul → staff
```

but the old session still contains:

```
session["role"] = "admin"
```

Now the session contains stale authorization information.

For important authorization checks, a safer pattern is often:

```
Session
   ↓
user_id
   ↓
Database
   ↓
Current role
   ↓
Authorization decision
```

This means role changes in the database can take effect without relying on stale session role data.

# 19. Role Enumeration

You could simply use strings:

```
role = "admin"
```

This is easy, but strings can lead to typos:

```
"admin"
"Admin"
"administrator"
```

These are different strings.

For a small application, simple strings can be enough if you validate them carefully.

For larger systems, you may use constants or an enum.

Example:

```
from enum import Enum


class UserRole(Enum):
    ADMIN = "admin"
    STAFF = "staff"
    CUSTOMER = "customer"
```

Then:

```
role = UserRole.ADMIN.value
```

This can make role values more consistent.

---

# 20. Role Column with an Enum

Depending on your SQLAlchemy setup and database requirements, you can use an enum-like column.

For example:

```
role = db.Column(
    db.Enum(
        "admin",
        "staff",
        "customer"
    ),
    nullable=False,
    default="customer"
)
```

This can restrict values at the database level.

However, database enum behavior and migrations can require additional care, especially when role values change.

For learning and smaller projects, a `String` column is often easier to understand:

```
role = db.Column(
    db.String(50),
    nullable=False,
    default="customer"
)
```

```
User Management
────────────────────

────────────────────

Changing a role is itself a **protected action**.

For example:

```

Cannot change own role to admin

   ↓

# 22. Roles Are Not Enough for Large Systems

Imagine you have:

```
Admin
Manager
Staff
Customer
```

But the manager needs:

```
view_reports
edit_orders
```

while another manager needs:

```
view_reports
```

A simple role system becomes restrictive.

You may eventually need:

```
Users
  ↓
Roles
  ↓
Permissions
```

For example:

```
Admin
 ├── users.create
 ├── users.update
 ├── users.delete
 ├── reports.view
 └── settings.update

Staff
 ├── orders.view
 └── orders.update

Customer
 └── orders.view
```

That's the purpose of **permissions**.

# 23. Role-Based Access Control

The overall approach is commonly called **RBAC**:

> **Role-Based Access Control**

The idea:

```
User
 ↓
Role
 ↓
Permissions
 ↓
Resource / Action
```

For example:

```
Rahul
  ↓
Admin
  ↓
delete_user
  ↓
DELETE /users/25
  ↓
Allowed
```

RBAC is widely used because it makes access rules easier to organize.

# 24. Common Mistakes ❌

### Mistake 1: Trusting role from the client

Never blindly accept:

```
role = request.form.get("role")
```

especially during public registration.

A malicious client can change the request.

---

### Mistake 2: Checking only the frontend

Hiding an admin button:

```
if (role === "admin") {
    showAdminButton();
}
```

does **not** protect the backend.

A user can still directly request:

```
/admin
```

Backend authorization is mandatory.

---

### Mistake 3: Confusing authentication and authorization

```
Logged in ≠ allowed to do everything
```

A customer can be authenticated while still being forbidden from accessing admin functionality.

---

### Mistake 4: Treating role names as hierarchy automatically

Don't assume:

```
manager > staff
```

unless your application explicitly defines that relationship.

---

### Mistake 5: Relying on stale session roles

If roles can change, important authorization decisions should use current authoritative data.

# 26. Quick Revision 📝

### What is a role?

A category representing a user's general access/responsibilities.

### Examples?

```
admin
manager
staff
customer
```

### Where can the role be stored?

Usually in the user's database record:

```
role = db.Column(
    db.String(50),
    nullable=False,
    default="customer"
)
```

### How do you check a role?

```
if user.role != "admin":
    return "Access denied", 403
```

### What is RBAC?

**Role-Based Access Control**, where roles determine which permissions users receive.

### Should frontend role checks protect an application?

No.

```
Frontend check → UI convenience
Backend check  → actual security
```

### `401` vs `403`

```
401 → Not successfully authenticated
403 → Authenticated but not allowed
```

### Should a public registration form allow `role="admin"`?

**No.** Assign safe default roles on the server.
