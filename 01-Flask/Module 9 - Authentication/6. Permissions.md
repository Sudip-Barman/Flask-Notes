A **permission** defines a specific action that a user is allowed to perform in an application.

For example:

- `users.create` → Can create users
- `users.read` → Can view users
- `users.update` → Can update users
- `users.delete` → Can delete users

Permissions are more specific than roles.

---

## 1. What is a Permission?

A permission answers:

> **"What is this user allowed to do?"**

Example:

```
User: Rahul
Role: Admin

Permissions:
✓ users.create
✓ users.read
✓ users.update
✓ users.delete
✓ reports.read
```

Another user:

```
User: Priya
Role: Staff

Permissions:
✓ users.read
✓ reports.read
✗ users.delete
```

So, a role gives a general category, while permissions define the actual actions.

---

# 2. Role vs Permission

This distinction is very important.

|Concept|Meaning|Example|
|---|---|---|
|Authentication|Who are you?|Rahul|
|Role|What type of user are you?|Admin|
|Permission|What can you do?|Delete users|

Think of it like this:

```
User
  ↓
Role
  ↓
Permissions
  ↓
Allowed Actions
```

For example:

```
Rahul
  ↓
Admin
  ↓
users.create
users.read
users.update
users.delete
  ↓
Can manage users
```

---

# 3. Why Do We Need Permissions?

Suppose your application has these users:

```
Admin
Manager
Staff
Customer
```

You could simply check roles:

```
if user.role == "admin":
    allow()
```

But this becomes difficult when the application grows.

For example:

```
Manager
    ✓ View reports
    ✓ Create reports
    ✗ Delete users
    ✗ Change system settings

Staff
    ✓ View reports
    ✗ Create reports
    ✗ Delete users
```

Roles alone can become too broad.

Permissions allow much more precise control.

|Operation|Permission|

A user with only:


# 6. Simple Permission System

For a small Flask application, we can create a permission mapping in Python.

```
ROLE_PERMISSIONS = {
    "admin": {
        "users.create",
        "users.read",
        "users.update",
        "users.delete",
        "reports.read",
    },

    "manager": {
        "users.read",
        "users.update",
        "reports.read",
    },

    "staff": {
        "users.read",
        "reports.read",
    },

    "customer": {
        "reports.read",
    }
}
```

Now each role has a set of permissions.

---

# 7. Checking a Permission

Create a helper function:

```
def has_permission(user, permission):
    permissions = ROLE_PERMISSIONS.get(user.role, set())

    return permission in permissions
```

Usage:

```
if has_permission(user, "users.delete"):
    print("User can delete users")
else:
    print("Access denied")
```

### How it works

Suppose:

```
user.role = "staff"
```

The application gets:

```
ROLE_PERMISSIONS["staff"]
```

which contains:

```
users.read
reports.read
```

Then:

```
has_permission(user, "users.delete")
```

becomes:

```
"users.delete" in {"users.read", "reports.read"}
```

Result:

```
False
```

Therefore:

```
403 Forbidden
```

# 8. Permission Decorator

Checking permissions manually on every route can become repetitive.

Instead, we can create a decorator.

```
from functools import wraps
from flask import session

def permission_required(permission):

    def decorator(view):

        @wraps(view)
        def wrapped_view(*args, **kwargs):

            user_id = session.get("user_id")

            if user_id is None:
                return "Login required", 401

            user = db.session.get(User, user_id)

            if user is None:
                return "User not found", 401

            if not has_permission(user, permission):
                return "Access denied", 403

            return view(*args, **kwargs)

        return wrapped_view

    return decorator
```

Now we can protect routes easily.

---

# 9. Using the Permission Decorator

For example:

```
@app.route("/users/delete/<int:user_id>")
@permission_required("users.delete")
def delete_user(user_id):

    return f"Deleting user {user_id}"
```

Another route:

```
@app.route("/reports")
@permission_required("reports.read")
def reports():

    return "Reports page"
```

Now Flask checks the permission before executing the route.

# 10. Permission Checking Flow

The complete process looks like this:

```
User sends request
        ↓
Session exists?
        ↓
      Yes
        ↓
Find user
        ↓
Read user's role
        ↓
Find role permissions
        ↓
Check requested permission
        ↓
   ┌────┴────┐
   ↓         ↓
Allowed    Denied
   ↓         ↓
Execute    403
route
```

For example:

```
GET /reports
       ↓
Session
       ↓
User = Priya
       ↓
Role = Staff
       ↓
Staff permissions
       ↓
reports.read?
       ↓
      Yes
       ↓
Show reports
```

# 11. Permission vs Role Decorator

Earlier we created:

```
@roles_required("admin")
```

Now we have:

```
@permission_required("users.delete")
```

They serve different purposes.

### Role-based

```
@app.route("/admin")
@roles_required("admin")
def admin():
    return "Admin dashboard"
```

This asks:

> Is the user an admin?

### Permission-based

```
@app.route("/users/delete/<int:user_id>")
@permission_required("users.delete")
def delete_user(user_id):
    return "Delete user"
```

This asks:

> Does the user have permission to delete users?

---

# 12. Why Permissions Are More Flexible

Imagine:

```
Admin
Manager
Staff
```

Suppose both Admin and Manager should be able to export reports.

With role checking:

```
if user.role in ["admin", "manager"]:
```

But with permissions:

```
@permission_required("reports.export")
```

Both roles can simply have:

```
reports.export
```

The route does not need to know which roles have that permission.

This is one of the major advantages of permission-based authorization.

---

# 13. Backend Permission Checking Is Mandatory

Never rely only on frontend checks.

For example, React might hide:

```
Delete User
```

from staff users.

That's useful for the UI, but it is **not security**.

A malicious user could still manually send:

```
DELETE /users/10
```

Therefore, Flask must check:

```
@permission_required("users.delete")
```

The backend is the final security boundary.

```
Frontend
   ↓
UI permission check
   ↓
Backend
   ↓
Actual permission check
   ↓
Database
```

Frontend controls **what the user sees**.

Backend controls **what the user can actually do**.

# 14. Database-Based Permissions

For larger applications, permissions can be stored in the database instead of a Python dictionary.

A common design is:

```
users
roles
permissions
user_roles
role_permissions
```

Relationship:

```
User
 ↓
Role
 ↓
Permissions
```

Example:

```
users
----------------
1  Rahul
2  Priya
3  Amit


roles
----------------
1  admin
2  staff
3  customer


permissions
----------------
1  users.read
2  users.create
3  users.update
4  users.delete
5  reports.read
```

Then a mapping table connects roles and permissions.

```
role_permissions

role_id | permission_id
--------|--------------
1       | 1
1       | 2
1       | 3
1       | 4
1       | 5
2       | 1
2       | 5
```

So:

```
Admin
 ↓
users.read
users.create
users.update
users.delete
reports.read
```

while:

```
Staff
 ↓
users.read
reports.read
```

---

# 15. Simple vs Database-Based Permissions

|Approach|Best for|
|---|---|
|Python dictionary|Small projects|
|Database permissions|Large applications|
|Hardcoded role checks|Very simple authorization|
|Permission system|Complex authorization|

For learning and small Flask applications, this is perfectly reasonable:

```
ROLE_PERMISSIONS = {
    "admin": {...},
    "staff": {...},
}
```

For a larger production system, database-backed permissions can provide much more flexibility.

---

# 16. Important Security Rule

Never allow the client to decide its own permissions.

Bad:

```
permission = request.json.get("permission")

if permission == "users.delete":
    delete_user()
```

The client could simply send:

```
{
    "permission": "users.delete"
}
```

Instead:

```
if not has_permission(user, "users.delete"):
    return "Access denied", 403
```

The server determines the permission from trusted server-side information.

---

# 17. 401 vs 403

Permissions are closely related to HTTP status codes.

### `401 Unauthorized`

The user is not authenticated.

```
No valid login/session
        ↓
401
```

Example:

```
if user_id is None:
    return "Login required", 401
```

### `403 Forbidden`

The user is authenticated but doesn't have permission.

```
Logged in
   ↓
Permission missing
   ↓
403
```

Example:

```
if not has_permission(user, "users.delete"):
    return "Access denied", 403
```

Remember:

```
401 → Who are you?
403 → I know who you are, but you cannot do this.
```

# 18. Role-Based Access Control

The permission approach we discussed is part of **RBAC**.

**RBAC = Role-Based Access Control**

The basic model is:

```
User
 ↓
Role
 ↓
Permissions
 ↓
Resources / Actions
```

Example:

```
Rahul
 ↓
Admin
 ↓
users.create
users.read
users.update
users.delete
 ↓
User Management
```

This makes authorization easier to manage as the application grows.

# 19. Common Mistakes

### Mistake 1: Only checking frontend permissions

❌ Not secure.

Always check permissions on the backend.

---

### Mistake 2: Giving every user all permissions

❌ Dangerous.

Use the principle of **least privilege**.

Give users only the permissions they actually need.

---

### Mistake 3: Trusting permission data from the client

❌ Never trust:

```
request.json["role"]
```

or:

```
request.json["permission"]
```

for authorization decisions.

---

### Mistake 4: Using only roles for everything

Roles are useful, but permissions provide finer control.

Instead of:

```
if user.role == "admin":
```

sometimes use:

```
if has_permission(user, "reports.export"):
```

---

### Mistake 5: Forgetting to protect API endpoints

Even if the web page is protected:

```
/admin
```

you must also protect sensitive API endpoints:

```
/api/users/delete
/api/settings/update
/api/reports/export
```

Every sensitive backend operation needs authorization.
