**Flask-Migrate** is a Flask extension that helps manage **database schema changes** using migrations.

It provides a convenient Flask interface for **Alembic**, which is the migration tool used with SQLAlchemy.

### Simple definition

> **Flask-Migrate = A Flask extension that manages SQLAlchemy database migrations.**

The relationship is:

```
Flask
  ↓
Flask-Migrate
  ↓
Alembic
  ↓
SQLAlchemy
  ↓
MySQL
```

---

# 2. Why Do We Need Flask-Migrate?

Suppose you initially have this model:

```
class Student(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
```

The database contains:

```
students
----------------
id
name
```

Later, you add:

```
email = db.Column(db.String(120))
```

Your Python model now expects:

```
students
----------------
id
name
email
```

But the existing database still has:

```
students
----------------
id
name
```

Flask-Migrate helps you synchronize the database schema with the changed models through a migration.

---

# 3. Flask-Migrate vs Flask-SQLAlchemy

These two have different jobs.

|Tool|Main purpose|
|---|---|
|Flask-SQLAlchemy|Work with the database using SQLAlchemy|
|Flask-Migrate|Manage changes to the database schema|

Think of it this way:

```
Flask-SQLAlchemy
        ↓
"How do I work with my database?"

Flask-Migrate
        ↓
"How do I change my database structure safely?"
```


You will typically have:

```
pip install flask flask-sqlalchemy flask-migrate pymysql
```

Here:

- `flask-sqlalchemy` → SQLAlchemy integration
- `flask-migrate` → migration management
- `pymysql` → MySQL driver

# 5. Basic Configuration

Start with Flask and SQLAlchemy:

```
from flask import Flask
from flask_sqlalchemy import SQLAlchemy

app = Flask(__name__)

app.config["SQLALCHEMY_DATABASE_URI"] = (
    "mysql+pymysql://root:password@localhost/school"
)

db = SQLAlchemy(app)
```

Now import Flask-Migrate:

```
from flask_migrate import Migrate
```

Create the migration object:

```
migrate = Migrate(app, db)
```

Complete basic setup:

```
from flask import Flask
from flask_sqlalchemy import SQLAlchemy
from flask_migrate import Migrate

app = Flask(__name__)

app.config["SQLALCHEMY_DATABASE_URI"] = (
    "mysql+pymysql://root:password@localhost/school"
)

db = SQLAlchemy(app)

migrate = Migrate(app, db)
```

The important line is:

```
migrate = Migrate(app, db)
```

It connects Flask-Migrate with:

- Flask application
- SQLAlchemy database object

# 6. How Flask-Migrate Works

The overall flow is:

```
SQLAlchemy Model
       ↓
Change Model
       ↓
Flask-Migrate
       ↓
Alembic
       ↓
Migration File
       ↓
Apply Migration
       ↓
MySQL Database
```

For example:

```
Model:
Student
 ├── id
 ├── name
 └── email

        ↓

Migration detects schema change

        ↓

Migration file created

        ↓

Migration applied

        ↓

MySQL table updated
```

# 7. Initialize Migrations

After configuring Flask-Migrate, initialize the migration system.

From your project directory:

```
flask db init
```

This creates a migration directory:

```
project/
│
├── app.py
├── models.py
├── requirements.txt
└── migrations/
    ├── versions/
    ├── alembic.ini
    ├── env.py
    ├── script.py.mako
    └── README
```

The exact files can vary by setup/version, but the important directory is:

```
migrations/
```

### Important

You normally run:

```
flask db init
```

**only once for a project.**

After that, you generate individual migrations as your models change.

---

# 8. Create a Model

Suppose we have:

```
class Student(db.Model):
    __tablename__ = "students"

    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100), nullable=False)
    age = db.Column(db.Integer)
```

Now Flask-Migrate needs to create the corresponding database structure.

---

# 9. Generate the First Migration

Run:

```
flask db migrate -m "create students table"
```

The `-m` option provides a description of the migration.

For example:

```
create students table
```

Flask-Migrate/Alembic examines the models and generates a migration file.

Conceptually:

```
migrations/
└── versions/
    └── abc123_create_students_table.py
```

The generated file contains instructions describing the schema change.

---

# 10. Review the Migration

A very important practice is to **review generated migration files**.

Do not blindly assume that automatic migration detection is always perfect.

For example, the migration may contain something conceptually like:

```
def upgrade():
    op.create_table(
        "students",
        sa.Column("id", sa.Integer(), nullable=False),
        sa.Column("name", sa.String(length=100), nullable=False),
        sa.Column("age", sa.Integer()),
        sa.PrimaryKeyConstraint("id")
    )
```

And a downgrade:

```
def downgrade():
    op.drop_table("students")
```

You don't normally need to write this manually for simple changes, because Flask-Migrate can generate it.

---

# 11. Apply the Migration

Generating a migration does **not** change the database yet.

You need:

```
flask db upgrade
```

The flow is:

```
flask db migrate
        ↓
Migration file created
        ↓
flask db upgrade
        ↓
Database changed
```

This distinction is extremely important.

### `migrate`

Creates a migration file.

### `upgrade`

Actually applies the migration to the database.

---

# 12. The Complete Basic Workflow

The standard workflow is:

```
1. Create/change model
          ↓
2. flask db migrate
          ↓
3. Review migration
          ↓
4. flask db upgrade
          ↓
5. Database updated
```

In commands:

```
flask db migrate -m "create students table"
```

then:

```
flask db upgrade
```

# 14. Modifying a Model

Suppose:

```
name = db.Column(db.String(100))
```

becomes:

```
name = db.Column(db.String(150))
```

Run:

```
flask db migrate -m "increase student name length"
```

Then:

```
flask db upgrade
```

The migration records the schema change.

---

# 15. Removing a Column

Suppose you remove:

```
age = db.Column(db.Integer)
```

from the model.

Generate:

```
flask db migrate -m "remove student age"
```

Then:

```
flask db upgrade
```

The database schema is updated accordingly.

⚠️ **Be careful with destructive migrations.**

Removing a column can permanently remove its stored data.

---

# 16. Upgrade and Downgrade

Flask-Migrate provides commands for moving between migration states.

### Upgrade

```
flask db upgrade
```

Moves the database forward.

```
V1 → V2 → V3
```

### Downgrade

```
flask db downgrade
```

Moves the database backward by one migration.

```
V3 → V2
```

You can think of it as:

```
          upgrade →
V1 → V2 → V3 → V4

          ← downgrade
```

---

# 17. Migration History

You can inspect migration history using:

```
flask db history
```

This shows the migration chain.

Conceptually:

```
V1 → create students
V2 → add email
V3 → add age
V4 → add index
```

You can also check the current database migration state:

```
flask db current
```

This is useful when working with different environments.

# 19. Application Factory Setup

For larger Flask applications, you may use the application factory pattern.

Instead of:

```
db = SQLAlchemy(app)
migrate = Migrate(app, db)
```

you can create extensions separately:

```
from flask_sqlalchemy import SQLAlchemy
from flask_migrate import Migrate

db = SQLAlchemy()
migrate = Migrate()
```

Then:

```
def create_app():
    app = Flask(__name__)

    app.config["SQLALCHEMY_DATABASE_URI"] = (
        "mysql+pymysql://root:password@localhost/school"
    )

    db.init_app(app)
    migrate.init_app(app, db)

    return app
```

This approach is useful for larger applications and testing.

The important relationship is:

```
db.init_app(app)
migrate.init_app(app, db)
```

Some important Flask-Migrate commands are:

|Command|Purpose|
|---|---|
|`flask db init`|Initialize migration system|
|`flask db migrate`|Generate migration|
|`flask db upgrade`|Apply migrations|
|`flask db downgrade`|Reverse migration|
|`flask db current`|Show current migration|
|`flask db history`|Show migration history|
|`flask db stamp`|Mark database with a migration revision|

### Most commonly used

In normal development, you will frequently use:

```
flask db migrate -m "description"
```

and:

```
flask db upgrade
```

---

# 21. `flask db migrate` Does Not Apply Changes

This is one of the most important things to remember.

If you run:

```
flask db migrate -m "add email"
```

you have only generated a migration file.

The database has **not necessarily been updated**.

You then need:

```
flask db upgrade
```

So:

```
migrate = prepare the change
upgrade = apply the change
```

---

# 22. `flask db init` vs `migrate`

These are also different.

### `flask db init`

Creates the migration infrastructure.

Usually:

```
flask db init
```

once per project.

### `flask db migrate`

Creates a new migration after a model change.

For example:

```
flask db migrate -m "add email"
```

So:

```
init
 ↓
Migration system created

migrate
 ↓
New migration generated
```

---

# 23. Flask-Migrate and Git

Migration files should generally be committed to Git.

For example:

```
git add migrations/
git commit -m "Add student email migration"
```

Then another developer can pull the changes:

```
git pull
```

and run:

```
flask db upgrade
```

Their database can then be brought to the same schema version.

This is one of the biggest advantages of migrations in team projects.

# 25. Important Safety Point: Review Migrations

Automatic migration generation is useful, but it is not perfect.

For example, renaming:

```
old_name → new_name
```

can sometimes be interpreted as:

```
delete old_name
+
create new_name
```

instead of:

```
rename old_name
```

That could result in data loss.

Therefore:

```
Model change
    ↓
Generate migration
    ↓
👀 Review migration
    ↓
Apply migration
```

is a good habit.

# 26. Flask-Migrate vs `db.create_all()`

|Situation|Recommended|
|---|---|
|Quickly creating tables in a simple experiment|`db.create_all()`|
|Schema changes over time|Flask-Migrate|
|Team project|Flask-Migrate|
|Production application|Flask-Migrate|
|Need migration history|Flask-Migrate|
|Need upgrade/downgrade|Flask-Migrate|

A useful rule:

> **`create_all()` creates. Flask-Migrate evolves.**

# 27. Common Mistakes

### Mistake 1: Forgetting `flask db upgrade`

You generate:

```
flask db migrate -m "add email"
```

but don't run:

```
flask db upgrade
```

Result:

```
Migration file exists
        ↓
Database unchanged
```

---

### Mistake 2: Running `flask db init` repeatedly

Usually:

```
flask db init
```

is performed once.

Don't initialize a new migration repository every time you change a model.

---

### Mistake 3: Not committing migration files

Don't ignore:

```
migrations/
```

when your project relies on it.

Migration files are part of the application's database history.

---

### Mistake 4: Blindly trusting generated migrations

Always inspect important schema changes, particularly:

- Renames
- Data type changes
- Dropping columns
- Dropping tables
- Changes involving constraints

# 29. Quick Revision

### What is Flask-Migrate?

A Flask extension for managing SQLAlchemy database migrations.

### What is it based on?

**Alembic.**

### What does `flask db init` do?

Initializes the migration repository.

### What does `flask db migrate` do?

Generates a migration based on detected model/schema changes.

### What does `flask db upgrade` do?

Applies pending migrations to the database.

### What does `flask db downgrade` do?

Reverts a migration.

### Does `flask db migrate` change the database?

**No.** It generates a migration file.

### Does `flask db upgrade` change the database?

**Yes.** It applies the migration.

### Should migrations be committed to Git?

**Yes, generally.**

# 30. One-Line Memory Trick

```
INIT → Set up migrations
MIGRATE → Create migration
UPGRADE → Apply migration
DOWNGRADE → Reverse migration
```

So the most important workflow to remember is:

```
flask db init

flask db migrate -m "describe the change"

flask db upgrade
```

After this, whenever you modify your SQLAlchemy models:

```
flask db migrate -m "describe the change"
flask db upgrade
```
