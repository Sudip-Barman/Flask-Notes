A **transaction** is a group of database operations treated as **one unit of work**.

Either all required operations succeed, or the changes can be rolled back.

### Simple definition

> **Transaction = A group of database operations that should be completed together as one logical unit.**

For example, imagine transferring money:

```
Account A
₹10,000
   ↓
Transfer ₹1,000
   ↓
Account B
₹5,000
```

Two operations are required:

```
1. Remove ₹1,000 from Account A
2. Add ₹1,000 to Account B
```

These operations should belong to the same transaction.

You don't want:

```
Account A → ₹9,000
Account B → ₹5,000
```

because the money disappeared.

You want either:

```
Both operations succeed
        ↓
COMMIT
```

or:

```
Something fails
        ↓
ROLLBACK
        ↓
Database returns to previous state
```

---

# 2. Why Are Transactions Important?

Without transactions, multiple related database operations can leave the database in an inconsistent state.

Suppose:

```
Operation 1 → Successful
Operation 2 → Successful
Operation 3 → Failed
```

If all three belong to one transaction:

```
Operation 1 ─┐
Operation 2 ─┼── Transaction
Operation 3 ─┘
                 ↓
               Failure
                 ↓
              ROLLBACK
```

The database can return to its previous state.

---

# 3. Real-World Example

Consider an order system.

Creating an order might require:

```
1. Create order
2. Add order items
3. Reduce product stock
4. Create payment record
```

These operations are related.

Imagine:

```
Create order        ✅
Add order items     ✅
Reduce stock        ❌
Payment record      ❌
```

If the first two operations were permanently saved, you could end up with an incomplete order.

A transaction allows:

```
All successful
      ↓
COMMIT

Any critical failure
      ↓
ROLLBACK
```

# 4. ACID Properties

Database transactions are commonly described using **ACID**.

```
A → Atomicity
C → Consistency
I → Isolation
D → Durability
```

These are fundamental transaction concepts.

---

# 5. Atomicity

**Atomicity** means:

> A transaction is treated as one unit. It either completes successfully or its changes are rolled back.

Imagine:

```
Transaction
├── Operation A ✅
├── Operation B ✅
└── Operation C ❌
```

With atomicity:

```
Operation A → Rolled back
Operation B → Rolled back
Operation C → Failed
```

The transaction does not leave partial changes behind.

### Mental model

```
ALL
 ↓
COMMIT

OR

NONE
 ↓
ROLLBACK
```

---

# 6. Consistency

**Consistency** means a transaction should move the database from one valid state to another valid state while respecting its rules and constraints.

For example, suppose:

```
students.email
```

has a `UNIQUE` constraint.

If you try to insert a duplicate email:

```
Existing:
rahul@example.com

New:
rahul@example.com
```

the database can reject the operation.

The transaction can then be rolled back.

So database constraints help maintain valid data.

---

# 7. Isolation

**Isolation** deals with multiple transactions happening at the same time.

Imagine:

```
Transaction A
Transaction B
```

both are accessing the database simultaneously.

Isolation controls how their intermediate changes interact.

For example:

```
User A → Updating product stock
User B → Reading product stock
```

The database needs rules about what each transaction can see.

This becomes particularly important in systems with many concurrent users.

---

# 8. Durability

**Durability** means that once a transaction has been successfully committed, its changes should persist.

For example:

```
Transaction
   ↓
COMMIT
   ↓
Success
```

After the commit, the changes should remain available even if the application later restarts.

So:

```
COMMIT
   ↓
Changes become permanent
```

subject to the database system's durability guarantees and configuration.

---

# 9. ACID Summary

|Property|Meaning|
|---|---|
|**Atomicity**|All operations succeed or are rolled back|
|**Consistency**|Database remains valid|
|**Isolation**|Concurrent transactions are controlled|
|**Durability**|Committed changes persist|

### Memory trick

```
A → All or nothing
C → Correct state
I → Independent transactions
D → Data survives commit
```

---

# 10. `COMMIT`

A **commit** permanently saves the changes made by the current transaction.

In Flask-SQLAlchemy:

```
db.session.commit()
```

For example:

```
student = Student(
    name="Rahul",
    age=20
)

db.session.add(student)

db.session.commit()
```

The sequence is:

```
Create object
     ↓
Add to session
     ↓
Commit
     ↓
Database changes saved
```

---

# 11. `ROLLBACK`

A **rollback** cancels uncommitted changes in the current transaction.

In SQLAlchemy:

```
db.session.rollback()
```

Example:

```
try:
    db.session.add(student)
    db.session.commit()

except Exception:
    db.session.rollback()
```

The flow is:

```
Database operation
       ↓
     Error
       ↓
   rollback()
       ↓
Undo uncommitted changes
```

---

# 12. Basic Transaction Pattern

A common pattern is:

```
try:
    # Database operations

    db.session.commit()

except Exception:
    db.session.rollback()
    raise
```

For example:

```
try:
    student = Student(
        name="Rahul",
        age=20
    )

    db.session.add(student)

    db.session.commit()

except Exception:
    db.session.rollback()
    raise
```

The important structure is:

```
try
 ├── database operations
 └── commit

except
 └── rollback
```

# 13. Multiple Operations in One Transaction

Suppose you have:

```
student = Student(
    name="Rahul",
    age=20
)

course = Course(
    name="Python"
)

db.session.add(student)
db.session.add(course)

db.session.commit()
```

Both objects are committed together.

Conceptually:

```
Transaction
├── Insert Student
└── Insert Course
       ↓
    COMMIT
```

If the transaction fails before the commit:

```
ROLLBACK
```

can undo the pending changes.

# 14. Transaction Example: Bank Transfer

Consider:

```
Account A = ₹10,000
Account B = ₹5,000
```

Transfer:

```
₹1,000
```

Required operations:

```
1. A = A - 1000
2. B = B + 1000
```

Using SQLAlchemy:

```
try:
    account_a.balance -= 1000
    account_b.balance += 1000

    db.session.commit()

except Exception:
    db.session.rollback()
    raise
```

The idea is:

```
Account A
   ↓
- ₹1,000

Account B
   ↓
+ ₹1,000

       ↓

    COMMIT
```

If something fails:

```
ROLLBACK
```

# 15. Why Partial Updates Are Dangerous

Imagine there is no transaction.

You perform:

```
A -= ₹1,000
```

This succeeds.

Then:

```
B += ₹1,000
```

fails.

You now have:

```
A → ₹9,000
B → ₹5,000
```

The database is inconsistent with respect to the intended transfer.

With a transaction:

```
A -= ₹1,000  ✅
B += ₹1,000  ❌
       ↓
ROLLBACK
       ↓
A → ₹10,000
B → ₹5,000
```

# 16. Transactions with Raw SQL

Transactions also work with Raw SQL.

Example:

```
from sqlalchemy import text

try:
    db.session.execute(
        text("""
            UPDATE accounts
            SET balance = balance - :amount
            WHERE id = :id
        """),
        {
            "amount": 1000,
            "id": 1
        }
    )

    db.session.execute(
        text("""
            UPDATE accounts
            SET balance = balance + :amount
            WHERE id = :id
        """),
        {
            "amount": 1000,
            "id": 2
        }
    )

    db.session.commit()

except Exception:
    db.session.rollback()
    raise
```

Both SQL statements participate in the same transaction through the session.

A simplified transaction lifecycle is:

```
START
  ↓
Execute Operation 1
  ↓
Execute Operation 2
  ↓
Execute Operation 3
  ↓
 ┌───────────────┐
 │ Everything OK?│
 └───────┬───────┘
      Yes│No
         │
    ┌────┴────┐
    ↓         ↓
 COMMIT    ROLLBACK
    ↓         ↓
 Saved      Undone
```

# 18. `flush()` vs `commit()`

This is an important SQLAlchemy concept.

### `flush()`

Sends pending changes to the database within the current transaction.

```
db.session.flush()
```

But it does **not** permanently commit the transaction.

### `commit()`

Commits the transaction.

```
db.session.commit()
```

So:

```
flush()
  ↓
Send SQL to database
  ↓
Still inside transaction

commit()
  ↓
Finalize transaction
```

---

# 19. Why Would We Use `flush()`?

Suppose you create a record and need its generated ID before committing everything.

Example:

```
student = Student(name="Rahul")

db.session.add(student)
db.session.flush()

print(student.id)
```

After `flush()`, SQLAlchemy can send the INSERT to the database and retrieve generated values such as an auto-generated primary key.

But the transaction is still not committed.

You can then perform additional operations:

```
course = Course(
    student_id=student.id,
    name="Python"
)

db.session.add(course)

db.session.commit()
```

Conceptually:

```
Add Student
    ↓
flush()
    ↓
Student ID available
    ↓
Add Course
    ↓
commit()
```

If something fails before the commit:

```
db.session.rollback()
```

can roll back the transaction.

---

# 20. `commit()` vs `rollback()`

|Method|Purpose|
|---|---|
|`commit()`|Save transaction changes|
|`rollback()`|Undo uncommitted changes|
|`flush()`|Send pending changes to database without committing|

Remember:

```
flush ≠ commit
```

# 21. Automatic Transaction Behavior

SQLAlchemy manages transaction state for you as you work with the session.

You generally don't need to manually execute:

```
BEGIN;
```

for every normal ORM operation.

For example:

```
student = Student(name="Rahul")

db.session.add(student)

db.session.commit()
```

SQLAlchemy handles the underlying transaction mechanics.

# 22. Explicit Transaction Blocks

SQLAlchemy also provides transaction context managers.

For example:

```
with db.session.begin():
    student = Student(
        name="Rahul",
        age=20
    )

    db.session.add(student)
```

The basic idea is:

```
Enter block
    ↓
Transaction starts
    ↓
Database operations
    ↓
Block succeeds
    ↓
Commit
```

If an exception occurs:

```
Exception
   ↓
Rollback
```

This can make transaction handling cleaner.

# 23. Transaction Context Example

For multiple operations:

```
with db.session.begin():

    student = Student(
        name="Rahul",
        age=20
    )

    course = Course(
        name="Python"
    )

    db.session.add(student)
    db.session.add(course)
```

Conceptually:

```
with transaction
       ↓
Student INSERT
       ↓
Course INSERT
       ↓
Success?
  ↙          ↘
Yes          No
 ↓            ↓
Commit      Rollback
```

This style is useful when a group of operations must succeed together.

# 24. Nested Transactions

Sometimes applications need more advanced transaction control.

SQLAlchemy supports concepts such as:

```
db.session.begin_nested()
```

This can create a **SAVEPOINT** within a transaction.

Conceptually:

```
Main Transaction
│
├── Operation A
│
├── SAVEPOINT
│    ├── Operation B
│    └── Operation C
│
└── Operation D
```

A savepoint allows a portion of the work to be rolled back without necessarily discarding the entire outer transaction.

This is an advanced topic, so for now remember:

> **Nested transactions can use savepoints to provide finer-grained rollback control.**

# 25. Isolation Levels

Isolation is one of the ACID properties.

Databases provide different **isolation levels** that determine how concurrent transactions interact.

Common SQL isolation levels include:

```
READ UNCOMMITTED
READ COMMITTED
REPEATABLE READ
SERIALIZABLE
```

From weaker to stronger isolation, generally:

```
READ UNCOMMITTED
        ↓
READ COMMITTED
        ↓
REPEATABLE READ
        ↓
SERIALIZABLE
```

Higher isolation can provide stronger consistency but may reduce concurrency or increase locking.

---

# 26. Common Concurrency Problems

Isolation levels help control problems such as:

### Dirty Read

Transaction A reads data that Transaction B has changed but not committed.

```
A → reads uncommitted data from B
```

If B later rolls back, A saw data that never became permanent.

---

### Non-Repeatable Read

A transaction reads the same row twice and gets different values because another transaction modified and committed it between the reads.

```
Read → ₹100
Other transaction updates
Read → ₹150
```

---

### Phantom Read

A transaction executes the same query twice and finds a different set of rows because another transaction inserted or removed matching rows.

```
First query → 5 rows
Other transaction inserts matching row
Second query → 6 rows
```

These are advanced database concepts, but they explain why transaction isolation matters.

# 29. Common Mistakes

## Mistake 1: Forgetting `commit()`

You perform:

```
db.session.add(student)
```

but never:

```
db.session.commit()
```

The change may not become permanently saved.

---

## Mistake 2: Not rolling back after an error

Suppose:

```
try:
    db.session.add(student)
    db.session.commit()

except Exception:
    ...
```

After a database error, the session can require a rollback before it can be used normally for further work.

Use:

```
db.session.rollback()
```

---

## Mistake 3: Committing every tiny operation

Imagine:

```
operation_1
commit()

operation_2
commit()

operation_3
commit()
```

If these operations logically belong together, committing separately can allow partial success.

Better:

```
Operation 1
Operation 2
Operation 3
      ↓
One transaction
      ↓
Commit
```

when they are meant to succeed or fail together.

---

## Mistake 4: Making transactions unnecessarily large

A transaction should generally contain the database work that logically belongs together.

Avoid holding transactions open unnecessarily long because long-running transactions can increase resource usage and concurrency problems.

                 ↓

# 35. Key Takeaways

- A **transaction** groups related database operations into one logical unit.
- Transactions help prevent partial or inconsistent updates.
- **COMMIT** saves the transaction.
- **ROLLBACK** undoes uncommitted changes.
- SQLAlchemy manages transactions through `db.session`.
- Transactions work with both **ORM and Raw SQL**.
- **ACID** stands for Atomicity, Consistency, Isolation, and Durability.
- `flush()` sends pending changes to the database but does not commit them.
- `commit()` finalizes the transaction.
- `rollback()` cancels uncommitted changes.
- Isolation controls how concurrent transactions interact.
- Transactions should generally be kept focused and not unnecessarily long.
