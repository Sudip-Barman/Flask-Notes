A **database migration** is a way to manage and apply changes to a database structure over time.

For example, initially you have:

```
students
----------------
id
name
```

Later, you change your model and add:

```
students
----------------
id
name
email
```

The database needs to be updated to include the new `email` column.

A **migration records this schema change** and provides a controlled way to apply it.

### Simple definition

> **Migration = A version-controlled change to the database schema.**

---

# 2. Why Do We Need Migrations?

You might think:

> "If I change my SQLAlchemy model, can't `db.create_all()` update the database?"

No.

`db.create_all()` can create tables that don't exist, but it **does not modify existing tables**.

### Example

Initially:

```
class Student(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
```

You run:

```
db.create_all()
```

Database:

```
students
----------------
id
name
```

Now you modify the model:

```
class Student(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
    email = db.Column(db.String(120))
```

If you run:

```
db.create_all()
```

the existing table will **not automatically become**:

```
students
----------------
id
name
email
```

The `email` column will not be added.

This is where **migrations** become important.

---

# 3. What Can Migrations Change?

Migrations can manage changes such as:

- Adding a column
- Removing a column
- Renaming a column
- Changing a column type
- Adding a table
- Removing a table
- Adding constraints
- Removing constraints
- Adding indexes
- Removing indexes
- Changing relationships
- Modifying foreign keys

For example:

```
Old Database
     ↓
Add email column
     ↓
Migration
     ↓
New Database
```

---

# 4. Migration vs Normal SQL

Without migrations, you might manually execute SQL:

```
ALTER TABLE students
ADD COLUMN email VARCHAR(120);
```

This works, but there is a problem.

Imagine a project has 10 developers.

Who changed the database?

When?

What SQL was executed?

What happens when another developer gets the project?

Migrations solve these problems by keeping database changes as **versioned files**.

---

# 5. Migration Files

A migration system creates files that describe database changes.

Conceptually:

```
migrations/
│
├── migration_001.py
├── migration_002.py
├── migration_003.py
└── ...
```

Each migration represents a particular database change.

For example:

```
Migration 001
Create students table

        ↓

Migration 002
Add email column

        ↓

Migration 003
Add age column
```

So your database has a history of how its structure evolved.

---

# 6. Database Versioning

Migrations essentially give your database a **version history**.

Imagine:

```
Version 1
students
    id
    name
```

Then you add email:

```
Version 2
students
    id
    name
    email
```

Then you add age:

```
Version 3
students
    id
    name
    email
    age
```

The migration system knows:

```
1 → 2 → 3
```

This is called **database schema versioning**.

---

# 7. Upgrade

An **upgrade** applies a migration and moves the database forward.

For example:

```
Version 1
   ↓
upgrade
   ↓
Version 2
```

Suppose Version 2 adds an email column.

The upgrade effectively performs something like:

```
ALTER TABLE students
ADD COLUMN email VARCHAR(120);
```

The important point is that you normally don't have to manually write and execute this SQL when using a migration tool.

---

# 8. Downgrade

A **downgrade** reverses a migration.

For example:

```
Version 2
   ↓
downgrade
   ↓
Version 1
```

If Version 2 added:

```
email
```

then its downgrade may remove:

```
email
```

Conceptually:

```
ALTER TABLE students
DROP COLUMN email;
```

So:

```
Upgrade   → Move database forward
Downgrade → Move database backward
```

---

# 9. Migration Workflow

The typical workflow is:

```
1. Change SQLAlchemy Model
          ↓
2. Generate Migration
          ↓
3. Review Migration
          ↓
4. Apply Migration
          ↓
5. Database Updated
```

For example:

### Step 1: Existing model

```
class Student(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
```

Database:

```
students
----------------
id
name
```

### Step 2: Modify model

```
class Student(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
    email = db.Column(db.String(120))
```

### Step 3: Generate migration

The migration tool compares the model structure with the database structure and generates a migration describing the change.

Conceptually:

```
Add email column
```

### Step 4: Apply migration

The migration is executed against the database.

### Step 5: Result

```
students
----------------
id
name
email
```

Existing data can remain intact, depending on the migration and the specific schema change.

---

# 10. Migrations Preserve Existing Data

This is one of the biggest reasons migrations are useful.

Suppose:

```
students

id | name
---|-------
1  | Rahul
2  | Priya
3  | Amit
```

You add:

```
email
```

A properly designed migration can modify the table while keeping the existing rows:

```
id | name  | email
---|-------|-------
1  | Rahul | NULL
2  | Priya | NULL
3  | Amit  | NULL
```

You can then populate the new values.

Without a migration strategy, developers may resort to recreating tables or manually changing production databases, which is risky.

---

# 11. Migration History

A migration system keeps track of which migrations have already been applied.

Conceptually:

```
Migration files

001_create_students
002_add_email
003_add_age
004_add_index
```

Database has applied:

```
001 ✓
002 ✓
003 ✓
004 ✗
```

The database is therefore currently at:

```
Version 3
```

Running an upgrade applies:

```
004
```

and moves the database to:

```
Version 4
```

---

# 12. Why Migration Files Should Be in Git

Migration files are normally committed to your Git repository.

For example:

```
Project
│
├── app.py
├── models.py
├── requirements.txt
└── migrations/
    ├── 001_create_students.py
    ├── 002_add_email.py
    └── 003_add_age.py
```

Then another developer can clone the project and apply the same database changes.

This is especially important when working with:

- Teams
- Staging servers
- Production servers
- CI/CD
- Deployment environments

### Important idea

> **Code changes and database schema changes should be tracked together.**

---

# 13. Migrations and Production

Imagine your local database is:

```
Version 5
```

but production is:

```
Version 3
```

You don't want to manually remember every SQL command between versions.

Instead:

```
Production
Version 3
   ↓
Migration 004
   ↓
Migration 005
   ↓
Version 5
```

This makes deployment much more predictable.

---

# 14. Migration Does Not Mean Automatic Magic

A common misunderstanding is:

> "I changed my model, so the database will automatically change."

Not necessarily.

Changing:

```
class Student(db.Model):
    ...
```

does **not automatically modify an existing database**.

You need a migration system to detect/record the schema change and then apply it.

The next topic, **Flask-Migrate**, provides this functionality for Flask applications.

# 15. Migrations vs `db.create_all()`

|Feature|`db.create_all()`|Migrations|
|---|---|---|
|Create missing tables|✅|✅|
|Update existing tables|❌|✅|
|Add columns safely|❌|✅|
|Track schema history|❌|✅|
|Upgrade database|❌|✅|
|Downgrade database|❌|✅|
|Version control|❌|✅|
|Suitable for evolving applications|Limited|✅|

### Simple rule

```
New/simple database
       ↓
db.create_all()
```

For an application whose schema changes over time:

```
Changing database schema
       ↓
Migrations
```

# 16. Generic Example

Suppose your first model is:

```
class Product(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
```

Database:

```
products
----------------
id
name
```

Later:

```
class Product(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
    price = db.Column(db.Float)
```

Migration:

```
Add price column
```

Database becomes:

```
products
----------------
id
name
price
```

Later you add:

```
stock = db.Column(db.Integer)
```

Another migration:

```
Add stock column
```

Now:

```
products
----------------
id
name
price
stock
```

The history looks like:

```
Initial Schema
      ↓
Migration 1
Add price
      ↓
Migration 2
Add stock
```

# 17. Alembic

In the Flask-SQLAlchemy ecosystem, migrations are commonly handled through **Alembic**.

Alembic is a database migration tool designed for SQLAlchemy.

The relationship is roughly:

```
Flask
  ↓
Flask-SQLAlchemy
  ↓
SQLAlchemy
  ↓
Alembic
  ↓
MySQL
```

You normally interact with Alembic through **Flask-Migrate** in a Flask application.

We will cover Flask-Migrate separately in the next topic.

# 19. Mental Model

Think of your database like a building.

Initially:

```
🏠 Version 1
├── Room
└── Kitchen
```

Later you need another room:

```
🏠 Version 2
├── Room
├── Kitchen
└── Bedroom
```

A migration is the **construction plan** that says:

```
"Add a bedroom."
```

Another change:

```
🏠 Version 3
├── Room
├── Kitchen
├── Bedroom
└── Garage
```

Another migration:

```
"Add a garage."
```

So your database evolves:

```
V1
 ↓
V2
 ↓
V3
 ↓
V4
```

rather than being destroyed and rebuilt every time.

---

# 20. Key Takeaways

- **Migration** = controlled, versioned database schema change.
- Changing a SQLAlchemy model does not automatically update an existing database.
- `db.create_all()` creates missing tables but does not handle schema evolution.
- Migrations can add, remove, modify, and rename database structures.
- **Upgrade** moves the database forward.
- **Downgrade** reverses a migration.
- Migration files should generally be committed to Git.
- Migrations are especially important for teams and production deployments.
- **Alembic** is the migration engine commonly used with SQLAlchemy.
- **Flask-Migrate** provides a convenient Flask interface for Alembic.
