A **Model** is a Python class that represents a **database table**.

When using Flask-SQLAlchemy, instead of writing SQL like:

```
CREATE TABLE students (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(120)
);
```

you can define the table using a Python class:

```
class Student(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
    email = db.Column(db.String(120))
```

SQLAlchemy uses this class definition to understand the structure of the database table.

---

# 3.1 What is a Model?

A **model** is a Python class that describes:

- Table name
- Columns
- Data types
- Primary keys
- Constraints
- Default values
- Other database-related rules

For example:

```
class Student(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
    age = db.Column(db.Integer)
```

This represents a database table similar to:

```
students
--------------------------------
id       INTEGER       PRIMARY KEY
name     VARCHAR(100)
age      INTEGER
```

### Simple definition

> A model is a Python representation of a database table.

---

# 3.2 Why Do We Need Models?

Without an ORM, you would frequently write SQL manually:

```
INSERT INTO students (name, age)
VALUES ('Rahul', 20);
```

With a model, you can work with Python objects:

```
student = Student(
    name="Rahul",
    age=20
)

db.session.add(student)
db.session.commit()
```

SQLAlchemy converts the Python operation into the appropriate SQL.

So models give you a bridge between:

```
Python Code
     ↓
   Model
     ↓
SQLAlchemy
     ↓
   SQL
     ↓
 MySQL Table
```

---

# 3.3 `db.Model`

Every Flask-SQLAlchemy model normally inherits from:

```
db.Model
```

Example:

```
class Student(db.Model):
    ...
```

Here:

- `Student` = your Python model class
- `db.Model` = SQLAlchemy's base model class

The inheritance tells SQLAlchemy:

> "Treat this Python class as a database model."

---

# 3.4 Basic Model Syntax

The general structure is:

```
class ModelName(db.Model):
    __tablename__ = "table_name"

    column_name = db.Column(
        db.DataType,
        options
    )
```

Example:

```
class Student(db.Model):
    __tablename__ = "students"

    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100), nullable=False)
    age = db.Column(db.Integer)
```

---

# 3.5 Class → Table

This is one of the most important concepts.

```
class Student(db.Model):
```

represents a table.

For example:

```
Python                         MySQL

Student class        →        students table
```

Think of it like this:

```
class Student
      ↓
students
      ↓
+----+--------+-----+
| id | name   | age |
+----+--------+-----+
| 1  | Rahul  | 20  |
| 2  | Priya  | 21  |
+----+--------+-----+
```

# 3.6 Column

A database table contains columns.

In a model, columns are defined using:

```
db.Column()
```

Example:

```
id = db.Column(db.Integer)
name = db.Column(db.String(100))
age = db.Column(db.Integer)
```

Here:

```
Python attribute     Database column

id              →    id
name            →    name
age             →    age
```

# 3.7 Common SQLAlchemy Data Types

Flask-SQLAlchemy provides SQLAlchemy data types through `db`.

### Integer

```
id = db.Column(db.Integer)
```

Used for whole numbers:

```
1
10
100
500
```

---

### String

```
name = db.Column(db.String(100))
```

Used for short text.

The `100` represents the maximum length.

Example:

```
name = db.Column(db.String(100))
```

roughly corresponds to:

```
VARCHAR(100)
```

---

### Text

```
description = db.Column(db.Text)
```

Used for longer text.

For example:

```
description = db.Column(db.Text)
```

can store paragraphs or large amounts of text.

---

### Boolean

```
is_active = db.Column(db.Boolean)
```

Used for:

```
True
False
```

---

### Float

```
rating = db.Column(db.Float)
```

Used for decimal numbers where approximate floating-point values are acceptable.

Example:

```
4.5
8.75
99.99
```

---

### Numeric

For values where exact decimal precision matters, such as financial amounts:

```
price = db.Column(db.Numeric(10, 2))
```

This means:

```
10 total digits
2 digits after decimal
```

Example:

```
1250.50
```

For money, `Numeric` is generally preferable to `Float`.

---

### Date

```
birth_date = db.Column(db.Date)
```

Stores dates such as:

```
2026-09-11
```

---

### DateTime

```
created_at = db.Column(db.DateTime)
```

Stores both date and time:

```
2026-09-11 10:30:45
```

# 3.8 Primary Key

A primary key uniquely identifies each row.

Usually we create an `id` column:

```
id = db.Column(db.Integer, primary_key=True)
```

Example:

```
id | name
---+-------
1  | Rahul
2  | Priya
3  | Amit
```

Each student has a unique ID.

### Why `primary_key=True`?

It tells SQLAlchemy:

> This column is the primary key of the table.

For an integer primary key, the database commonly handles generating new IDs when rows are inserted.

---

# 3.9 `nullable=False`

Suppose a student's name must always exist.

```
name = db.Column(
    db.String(100),
    nullable=False
)
```

This means:

> The column cannot contain `NULL`.

Without it:

```
name = db.Column(db.String(100))
```

the database can potentially store:

```
NULL
```

With:

```
nullable=False
```

the value is required.

---

# 3.10 `unique=True`

Suppose every student's email must be different.

```
email = db.Column(
    db.String(120),
    unique=True
)
```

This creates a uniqueness constraint.

So this should not be allowed:

```
id | email
---+----------------
1  | a@example.com
2  | a@example.com
```

The database will reject the duplicate value.

---

# 3.11 `default`

You can provide a default value.

Example:

```
is_active = db.Column(
    db.Boolean,
    default=True
)
```

If you create a student without specifying `is_active`, SQLAlchemy can use:

```
True
```

Example:

```
student = Student(name="Rahul")
```

The resulting value can be:

```
is_active = True
```

---

# 3.12 `index=True`

An index can improve searching/filtering performance.

Example:

```
email = db.Column(
    db.String(120),
    index=True
)
```

This tells the database to create an index for that column.

Indexes are especially useful for columns that are frequently searched.

For example:

```
SELECT * FROM students
WHERE email = 'rahul@example.com';
```

An index can make this kind of lookup faster.

However, indexes also consume storage and can add overhead to inserts/updates, so you should not index every column.

---

# 3.13 `__tablename__`

You can explicitly specify the database table name:

```
class Student(db.Model):
    __tablename__ = "students"
```

Now the model maps to:

```
students
```

table.

### Why explicitly define it?

It makes the table name predictable and clear.

For example:

```
class Student(db.Model):
    __tablename__ = "students"
```

is easier to understand than relying entirely on automatic table-name generation.

---

# 3.14 Complete Student Model

Here is a good beginner model:

```
class Student(db.Model):
    __tablename__ = "students"

    id = db.Column(
        db.Integer,
        primary_key=True
    )

    name = db.Column(
        db.String(100),
        nullable=False
    )

    email = db.Column(
        db.String(120),
        unique=True,
        nullable=False
    )

    age = db.Column(
        db.Integer
    )

    is_active = db.Column(
        db.Boolean,
        default=True
    )
```

This describes a table approximately like:

```
students
------------------------------------------------
id          INTEGER       PRIMARY KEY
name        VARCHAR(100)  NOT NULL
email       VARCHAR(120)  UNIQUE NOT NULL
age         INTEGER
is_active   BOOLEAN       DEFAULT TRUE
```

# 3.15 Model → Object → Row

This is another important ORM concept.

Suppose we have:

```
class Student(db.Model):
    __tablename__ = "students"

    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
    age = db.Column(db.Integer)
```

We can create a Python object:

```
student = Student(
    name="Rahul",
    age=20
)
```

Here:

```
Student class
      ↓
Student object
      ↓
Database row
```

The object represents one potential row.

For example:

```
Python object

student
 ├── name = "Rahul"
 └── age = 20
```

can become:

```
students table

+----+-------+-----+
| id | name  | age |
+----+-------+-----+
| 1  | Rahul | 20  |
+----+-------+-----+
```

The `id` may be generated by the database.

# 3.16 Complete Flask Example

A simple application can look like this:

```
from flask import Flask
from flask_sqlalchemy import SQLAlchemy

app = Flask(__name__)

app.config["SQLALCHEMY_DATABASE_URI"] = (
    "mysql+pymysql://root:password@localhost/school"
)

db = SQLAlchemy(app)


class Student(db.Model):
    __tablename__ = "students"

    id = db.Column(
        db.Integer,
        primary_key=True
    )

    name = db.Column(
        db.String(100),
        nullable=False
    )

    email = db.Column(
        db.String(120),
        unique=True,
        nullable=False
    )

    age = db.Column(
        db.Integer
    )


with app.app_context():
    db.create_all()


if __name__ == "__main__":
    app.run(debug=True)
```

# 3.17 What Does `db.create_all()` Do?

This:

```
db.create_all()
```

asks SQLAlchemy to create the database tables represented by your models if they do not already exist.

For our model:

```
class Student(db.Model):
```

SQLAlchemy can create:

```
students
```

table.

Conceptually:

```
Student model
      ↓
SQLAlchemy
      ↓
CREATE TABLE students ...
      ↓
MySQL
```

### Important

`db.create_all()` **does not manage schema changes**.

For example, suppose your original model is:

```
class Student(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
```

Later you add:

```
email = db.Column(db.String(120))
```

Running:

```
db.create_all()
```

does not reliably modify the existing table to add the new column.

That's why we later learn:

```
Migrations
Flask-Migrate
```

in this module.

# 3.18 Why `app.app_context()`?

You may see:

```
with app.app_context():
    db.create_all()
```

The Flask application context gives Flask-SQLAlchemy access to the current Flask application configuration.

Think of it as:

```
Flask application
       ↓
Application context
       ↓
Flask-SQLAlchemy knows which app/database to use
       ↓
Database operation
```

You'll see application contexts again when working with databases outside normal request handling.

# 3.20 Model vs Table

These terms are related but not identical.

### Model

Python representation:

```
class Student(db.Model):
```

### Table

Actual database structure:

```
students
```

So:

```
Python side                 Database side

Student model       →       students table

id attribute        →       id column

name attribute      →       name column

Student object      →       table row
```

This mapping is the heart of ORM.

# 3.21 Important Column Options

You should remember these:

|Option|Meaning|
|---|---|
|`primary_key=True`|Makes the column a primary key|
|`nullable=False`|Value is required|
|`unique=True`|Values must be unique|
|`default=value`|Provides a default value|
|`index=True`|Creates an index|
|`db.ForeignKey(...)`|Connects a column to another table|
|`db.String(100)`|String with maximum length|
|`db.Integer`|Integer value|
|`db.Text`|Long text|
|`db.Boolean`|True/False|
|`db.Date`|Date|
|`db.DateTime`|Date + time|
|`db.Numeric(10, 2)`|Exact decimal value|

We'll study `ForeignKey` and relationships more deeply in **8.6 Relationships**.

# 3.23 Best Practices

### 1. Use clear model names

```
class Student(db.Model):
```

rather than unclear names like:

```
class S(db.Model):
```

### 2. Explicitly name important tables

```
__tablename__ = "students"
```

### 3. Use appropriate data types

Don't use:

```
age = db.Column(db.String(10))
```

when the value is actually numeric.

Prefer:

```
age = db.Column(db.Integer)
```

### 4. Use constraints

For required data:

```
nullable=False
```

For unique data:

```
unique=True
```

### 5. Don't index everything

Only add indexes where they provide a useful query-performance benefit.

### 6. Don't use `create_all()` as a migration system

For development/testing it is useful.

For changing an existing database schema, we'll later use **migrations**.
