# What is a Virtual Environment?

## Definition

A **Virtual Environment (venv)** is an isolated Python environment that contains its own:

- Python interpreter
- Installed packages
- Dependencies

It allows each project to have its own set of libraries without affecting other projects.

> **Simple Definition:**  
> A virtual environment is a separate workspace for a Python project where all its packages are stored independently.

---

# Why Do We Need a Virtual Environment?

Imagine you have two Flask projects.

```
Project A
Uses Flask 2.3

Project B
Uses Flask 3.1
```

If both use the **global Python installation**, upgrading Flask for Project B could break Project A.

A virtual environment solves this by giving each project its own isolated packages.

---

# Real-Life Analogy

Imagine you're cooking.

Without separate containers:

```
Sugar
Salt
Flour
Rice

↓

Everything mixed together ❌
```

With containers:

```
Sugar → Container 1
Salt → Container 2
Rice → Container 3
Flour → Container 4

Everything stays organized ✅
```

A virtual environment is like a dedicated container for one project.

---

# Without a Virtual Environment

```
Python

├── Flask
├── NumPy
├── Django
├── TensorFlow
├── Requests
├── SQLAlchemy
├── Pandas
└── ...
```

All projects share the same packages.

Changing one package may affect every project.

---

# With Virtual Environments

```
Computer

│
├── Project A
│      ├── venv
│      ├── Flask 3.1
│      └── Requests
│
├── Project B
│      ├── venv
│      ├── Django
│      └── Pillow
│
└── Project C
       ├── venv
       ├── FastAPI
       └── SQLAlchemy
```

Each project is completely independent.

---

# Advantages

- Isolates project dependencies.
- Prevents version conflicts.
- Keeps projects clean and reproducible.
- Makes deployment easier.
- Recommended for every Python project.

---

# Creating a Virtual Environment

Move into your project folder.

```
cd FlaskTutorial
```

Create the environment.

```
python -m venv .venv
```

Here:

- `python` runs Python.
- `-m` runs a Python module.
- `venv` is the built-in virtual environment module.
- `.venv` is the folder name (you can choose another name, but `.venv` is a common convention).

---

# Folder Structure

Before:

```
FlaskTutorial/
```

After:

```
FlaskTutorial/

│
├── .venv/
```

---

# What's Inside `.venv`?

```
.venv/

├── Include/
├── Lib/
├── Scripts/
├── pyvenv.cfg
```

### Include/

Contains header files used when compiling some Python packages.

---

### Lib/

Stores installed Python packages.

Example:

```
Lib/

site-packages/

Flask/

Jinja2/

Werkzeug/

...
```

---

### Scripts/

Contains executables such as:

```
python.exe

pip.exe

activate
```

These are the tools you'll use while the virtual environment is active.

---

### pyvenv.cfg

Stores configuration information about the virtual environment.

---

# Activating the Virtual Environment

## Windows (Command Prompt)

```
.venv\Scripts\activate
```

---

## Windows (PowerShell)

```
.venv\Scripts\Activate.ps1
```

---

## Linux / macOS

```
source .venv/bin/activate
```

---

# How Do You Know It's Active?

Your terminal prompt changes.

Before:

```
C:\Projects\FlaskTutorial>
```

After:

```
(.venv) C:\Projects\FlaskTutorial>
```

The `(.venv)` prefix indicates that commands like `python` and `pip` now use the virtual environment.

---

# Installing Packages

Once activated:

```
pip install flask
```

Flask is installed **inside the virtual environment**, not globally.

---

# Viewing Installed Packages

```
pip list
```

Example:

```
Flask
Werkzeug
Jinja2
Click
itsdangerous
blinker
```

---

# Deactivating the Virtual Environment

When you're finished working:

```
deactivate
```

The terminal prompt returns to normal.

---

# Deleting a Virtual Environment

A virtual environment is just a folder.

To remove it:

```
Delete the .venv folder
```

No uninstall command is needed.

---

# Recreating a Virtual Environment

If you have a `requirements.txt` file:

```
python -m venv .venv
```

Activate it, then run:

```
pip install -r requirements.txt
```

This reinstalls all required packages.

---

# Best Practices

### 1. Use one virtual environment per project.

✔️ Good

```
BloodBank/
    .venv/

AuLi/
    .venv/

Portfolio/
    .venv/
```

❌ Avoid sharing one virtual environment across unrelated projects.

---

### 2. Name it `.venv`

This is widely recognized by editors like VS Code and keeps project folders consistent.

---

### 3. Do **not** commit `.venv` to Git

Add it to your `.gitignore` file:

```
.venv/
```

Instead, commit `requirements.txt` so others can recreate the environment.

---

### 4. Always activate before working

This ensures `python` and `pip` point to the correct environment.

---

# Common Mistakes

❌ Installing packages before activating the virtual environment.

Result: Packages are installed globally instead.

---

❌ Forgetting to activate the virtual environment.

You may see:

```
ModuleNotFoundError: No module named 'flask'
```

because you're using a different Python installation.

---

❌ Committing `.venv` to GitHub.

This greatly increases repository size and is unnecessary.

# Frequently Used Commands

| Command                           | Purpose                        |
| --------------------------------- | ------------------------------ |
| `python -m venv .venv`            | Create a virtual environment   |
| `.venv\Scripts\activate`          | Activate (Windows CMD)         |
| `.venv\Scripts\Activate.ps1`      | Activate (PowerShell)          |
| `source .venv/bin/activate`       | Activate (Linux/macOS)         |
| `deactivate`                      | Deactivate the environment     |
| `pip list`                        | List installed packages        |
| `pip freeze > requirements.txt`   | Save dependencies              |
| `pip install -r requirements.txt` | Install dependencies from file |
