Error handling is the process of **detecting, managing, and returning appropriate responses when something goes wrong in an API**.

A good API should not simply crash or return confusing errors.

Instead:

```
Request
   ↓
Something goes wrong
   ↓
Detect error
   ↓
Handle error
   ↓
Return proper status code
   ↓
Return useful JSON
```

For REST APIs, error handling is especially important because the frontend or another client needs a predictable way to understand what happened.

---

# 1. What is an API Error?

An API error occurs when the server cannot successfully complete a request.

Examples:

```
Invalid JSON
Missing required field
Invalid ID
User not found
Wrong credentials
Insufficient permission
Database failure
Unexpected server exception
```

For example:

```
GET /api/users/9999
```

If user `9999` doesn't exist:

```
{
    "error": "User not found"
}
```

with:

```
404 Not Found
```

---

# 2. Why Error Handling Matters

Without proper error handling, an API might return:

```
Internal Server Error
```

for almost everything.

That's not very helpful.

A good API distinguishes between:

```
Client mistake
        ↓
4xx

Server problem
        ↓
5xx
```

For example:

```
Missing name
    → 400

User doesn't exist
    → 404

Not logged in
    → 401

Not allowed
    → 403

Unexpected database failure
    → 500
```

---

# 3. HTTP Error Categories

The most important categories are:

|Category|Meaning|
|---|---|
|4xx|Client-side/request problem|
|5xx|Server-side problem|

### 4xx

The request is invalid, unauthorized, forbidden, or otherwise cannot be fulfilled because of the request/client context.

Examples:

```
400 Bad Request
401 Unauthorized
403 Forbidden
404 Not Found
409 Conflict
422 Unprocessable Content
```

### 5xx

Something went wrong on the server side.

Examples:

```
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

For normal Flask API development, `400`, `401`, `403`, `404`, `409`, `422`, and `500` are particularly useful.

---

# 4. `400 Bad Request`

Use `400` when the request itself is malformed or invalid.

Example:

```
{
    "name": ""
}
```

If `name` is required:

```
if not name:
    return jsonify({
        "error": "Name is required"
    }), 400
```

Response:

```
400 Bad Request
```

---

# 5. `401 Unauthorized`

As we learned earlier, `401` is generally used when authentication is missing or invalid.

Examples:

```
No JWT
Invalid JWT
Expired JWT
Invalid credentials
```

Example:

```
return jsonify({
    "error": "Authentication required"
}), 401
```

Remember:

```
401 → Authentication problem
```

---

# 6. `403 Forbidden`

Use `403` when the user is authenticated but doesn't have permission.

Example:

```
if user.role != "admin":
    return jsonify({
        "error": "Admin access required"
    }), 403
```

Meaning:

```
User identity known
       ↓
Permission denied
       ↓
403
```

---

# 7. `404 Not Found`

Use `404` when the requested resource doesn't exist.

Example:

```
GET /api/products/1000
```

Suppose product `1000` doesn't exist.

```
product = db.session.get(Product, product_id)

if product is None:
    return jsonify({
        "error": "Product not found"
    }), 404
```

Response:

```
{
    "error": "Product not found"
}
```

---

# 8. `409 Conflict`

`409` is useful when the request conflicts with the current state of the resource.

A common example is duplicate data.

Suppose email addresses must be unique:

```
user@example.com
```

already exists.

A new registration attempts to use the same email.

```
existing_user = User.query.filter_by(
    email=email
).first()

if existing_user:
    return jsonify({
        "error": "Email already registered"
    }), 409
```

Response:

```
409 Conflict
```

Think:

```
Request is understandable
       ↓
But conflicts with existing state
       ↓
409
```

---

# 9. `422 Unprocessable Content`

`422` is commonly used when the request is structurally valid but the supplied data fails validation.

For example:

```
{
    "name": "John",
    "age": -5
}
```

The JSON is valid.

But:

```
age = -5
```

is invalid according to the application's rules.

Response:

```
422 Unprocessable Content
```

You may also see Flask applications use `400` for validation errors.

Both patterns can be valid if the API uses them consistently.

---

# 10. `500 Internal Server Error`

A `500` means an unexpected server-side error occurred.

For example:

```
result = 10 / 0
```

causes:

```
ZeroDivisionError
```

The API should not expose the Python traceback to the client in production.

Instead, the client should receive something like:

```
{
    "error": "Internal server error"
}
```

with:

```
500 Internal Server Error
```

---

# 11. Never Expose Internal Errors

Suppose this happens:

```
password = user["password"]
```

but `user` is `None`.

Python might produce a traceback.

You should **not** return this to the client:

```
AttributeError: 'NoneType' object has no attribute...
```

because internal errors can reveal implementation details.

Instead:

```
{
    "error": "Internal server error"
}
```

Log the technical details on the server.

So:

```
Client
→ Safe error message

Server logs
→ Detailed technical information
```

---

# 12. Basic `try/except`

Python's `try/except` can catch expected exceptions.

```
try:
    result = 10 / 0

except ZeroDivisionError:
    return jsonify({
        "error": "Invalid calculation"
    }), 400
```

The general pattern:

```
try:
    # Risky operation

except SomeError:
    # Handle error
```

---

# 13. Database Error Handling

Database operations can fail.

For example:

```
try:
    db.session.add(user)
    db.session.commit()

except Exception:
    db.session.rollback()

    return jsonify({
        "error": "Unable to create user"
    }), 500
```

The important part is:

```
db.session.rollback()
```

If a transaction fails, rollback prevents the failed transaction from remaining in an unusable state.

---

# 14. Why Rollback Matters

Imagine:

```
Start transaction
     ↓
INSERT user
     ↓
INSERT order
     ↓
Database error
```

If the transaction isn't handled correctly, the session may remain in a failed state.

With rollback:

```
Database error
     ↓
Rollback
     ↓
Transaction reset
     ↓
Safe error response
```

This connects directly with the **transactions** topic from Module 8.

# 15. A Better CRUD Error Pattern

Consider:

```
@app.post("/api/products")
def create_product():

    data = request.get_json()

    if not data:
        return jsonify({
            "error": "JSON body required"
        }), 400

    name = data.get("name")
    price = data.get("price")

    if not name:
        return jsonify({
            "error": "Name is required"
        }), 400

    if price is None:
        return jsonify({
            "error": "Price is required"
        }), 400

    product = Product(
        name=name,
        price=price
    )

    try:
        db.session.add(product)
        db.session.commit()

    except Exception:
        db.session.rollback()

        return jsonify({
            "error": "Unable to create product"
        }), 500

    return jsonify({
        "message": "Product created",
        "id": product.id
    }), 201
```

Notice the layers:

```
Request
 ↓
Validate input
 ↓
Create object
 ↓
Database operation
 ↓
Handle database failure
 ↓
Response
```

---

# 16. Don't Use One Giant `try/except`

Avoid doing this:

```
@app.post("/api/products")
def create_product():

    try:
        # Everything
        # validation
        # database
        # business logic
        # response

    except Exception:
        return jsonify({
            "error": "Something went wrong"
        }), 500
```

Why?

Because you might accidentally turn a client error into a server error.

For example:

```
Missing name
```

should be:

```
400
```

not:

```
500
```

It's better to deliberately handle expected errors and use a global handler for unexpected exceptions.

# 17. Flask Error Handlers

Flask allows you to define global error handlers.

For example:

```
@app.errorhandler(404)
def handle_404(error):

    return jsonify({
        "error": "Resource not found"
    }), 404
```

Now a missing route can return JSON instead of Flask's default HTML error page.

# 20. Handling 405

`405 Method Not Allowed` means the endpoint exists, but the HTTP method isn't supported.

For example:

```
Route:
POST /api/products

Client:
DELETE /api/products
```

The route may exist, but DELETE isn't allowed.

Handler:

```
@app.errorhandler(405)
def handle_405(error):

    return jsonify({
        "error": "Method not allowed"
    }), 405
```

---

# 21. Handling 500 Globally

You can define:

```
@app.errorhandler(500)
def handle_500(error):

    return jsonify({
        "error": "Internal server error"
    }), 500
```

This gives API clients a consistent JSON response.

However, in development, you still want useful debugging information in your development environment and logs. Don't hide everything from yourself while building.

# 22. Custom API Error Responses

Instead of returning different shapes everywhere:

```
{
    "error": "User not found"
}
```

```
{
    "message": "Something failed"
}
```

```
{
    "problem": "Invalid request"
}
```

it is better to establish a consistent format.

For example:

```
{
    "error": {
        "code": "USER_NOT_FOUND",
        "message": "User not found"
    }
}
```

Now clients know what structure to expect.

# 23. Error Codes

An application-specific error code can be useful.

Example:

```
{
    "error": {
        "code": "EMAIL_ALREADY_EXISTS",
        "message": "Email is already registered"
    }
}
```

Another:

```
{
    "error": {
        "code": "PRODUCT_NOT_FOUND",
        "message": "Product not found"
    }
}
```

The HTTP status tells the general category:

```
409
```

while the application error code provides more detail:

```
EMAIL_ALREADY_EXISTS
```

---

# 24. Error Response Structure

A practical structure could be:

```
{
    "success": false,
    "error": {
        "code": "PRODUCT_NOT_FOUND",
        "message": "Product not found"
    }
}
```

For a validation error:

```
{
    "success": false,
    "error": {
        "code": "VALIDATION_ERROR",
        "message": "Invalid request data",
        "fields": {
            "price": "Price must be greater than 0"
        }
    }
}
```

This becomes especially useful when a frontend needs to display field-specific errors.

---

# 25. Don't Leak Sensitive Information

Avoid returning:

```
{
    "error": "Database password incorrect: mysql://root:password@..."
}
```

or:

```
{
    "error": "SQL query failed: SELECT * FROM users..."
}
```

or:

```
{
    "error": "Traceback..."
}
```

Instead:

```
{
    "error": {
        "code": "INTERNAL_ERROR",
        "message": "Internal server error"
    }
}
```

Technical information belongs in secure server logs, not public API responses.

---

# 26. Logging Errors

Error handling and logging work together.

For example:

```
import logging

logger = logging.getLogger(__name__)
```

Then:

```
try:
    db.session.commit()

except Exception:
    db.session.rollback()

    logger.exception(
        "Failed to create product"
    )

    return jsonify({
        "error": "Internal server error"
    }), 500
```

`logger.exception()` records the exception and traceback in the server logs.

So:

```
User
 ↓
Safe JSON error

Server
 ↓
Detailed logs
 ↓
Developer investigates
```

That's the healthy separation.

# 27. Validation Errors vs Server Errors

This distinction is extremely important.

### User/request problem

```
{
    "name": ""

```

Response:

```
400 or 422
```

### Server/database problem

```

```

Response:

```
500 or another appropriate 5xx
```

Don't blame the user for your database having a bad afternoon. ☕

# 28. Error Handling in CRUD APIs

Let's map common CRUD failures.

|Operation|Possible error|Status|
|---|---|---|
|POST|Invalid input|400/422|
|POST|Duplicate resource|409|
|GET|Resource doesn't exist|404|
|PATCH|Invalid input|400/422|
|PATCH|Resource doesn't exist|404|

# 29. Example: GET Resource

```
@app.get("/api/products/<int:product_id>")
def get_product(product_id):

    product = db.session.get(
        Product,
        product_id
    )

    if product is None:
        return jsonify({
            "error": {
                "code": "PRODUCT_NOT_FOUND",
                "message": "Product not found"
            }
        }), 404

    return jsonify({
        "id": product.id,
        "name": product.name,
        "price": product.price
    })
```

Clean and predictable.

# 30. Example: PATCH Validation

```
@app.patch("/api/products/<int:product_id>")
def update_product(product_id):

    product = db.session.get(
        Product,
        product_id
    )

    if product is None:
        return jsonify({
            "error": {
                "code": "PRODUCT_NOT_FOUND",
                "message": "Product not found"
            }
        }), 404

    data = request.get_json(silent=True)

    if data is None:
        return jsonify({
            "error": {
                "code": "INVALID_JSON",
                "message": "Valid JSON body required"
            }
        }), 400

    if "price" in data:

        if not isinstance(
            data["price"],
            (int, float)
        ):
            return jsonify({
                "error": {
                    "code": "INVALID_PRICE",
                    "message": "Price must be a number"
                }
            }), 422

    # Update fields...
```

Notice how validation happens before the database update.

# 31. Handling Unexpected Exceptions

For unexpected errors, Flask can use a global handler:

```
@app.errorhandler(Exception)
def handle_exception(error):

    app.logger.exception(
        "Unexpected server error"
    )

    return jsonify({
        "error": {
            "code": "INTERNAL_ERROR",
            "message": "Internal server error"
        }
    }), 500
```

This is useful for APIs because clients consistently receive JSON.

However, be careful when designing broad exception handlers. You don't want to accidentally swallow errors that should be handled differently, especially HTTP exceptions generated intentionally by Flask.

---

# 32. `abort()`

Flask provides `abort()` for quickly triggering HTTP errors.

Example:

```
from flask import abort
```

Then:

```
@app.get("/api/products/<int:product_id>")
def get_product(product_id):

    product = db.session.get(
        Product,
        product_id
    )

    if product is None:
        abort(404)

    return jsonify({
        "id": product.id,
        "name": product.name
    })
```

Flask then generates a `404` error.

For APIs, you may prefer custom JSON error handlers so the response has a consistent structure.

# 33. Custom Error Classes

For larger applications, you can create your own application exceptions.

For example:

```
class APIError(Exception):

    def __init__(
        self,
        message,
        status_code=400,
        code="API_ERROR"
    ):
        self.message = message
        self.status_code = status_code
        self.code = code
```

Then:

```
raise APIError(
    "Product not found",
    404,
    "PRODUCT_NOT_FOUND"
)
```

A global handler can convert it into JSON.

This approach becomes useful when an application has many endpoints and complex business logic.

You don't need this for every small Flask API, but it's good to understand the pattern.

# 34. Error Handling Architecture

A well-structured API can look like this:

```
                 HTTP Request
                      ↓
                   Flask
                      ↓
                Route / View
                      ↓
                 Validation
                      ↓
               Business Logic
                      ↓
                  Database
                      ↓
                ┌─────┴─────┐
                ↓           ↓
             Success       Error
                ↓           ↓
             2xx/3xx     Error Handler
                            ↓
                         4xx/5xx
                            ↓
                       JSON Response
```

# 35. Error Handling Strategy

A good strategy is:

### Step 1: Validate request

```
Is the input valid?
```

If no:

```
400 / 422
```

### Step 2: Authenticate

```
Is the user authenticated?
```

If no:

```
401
```

### Step 3: Authorize

```
Is the user allowed?
```

If no:

```
403
```

### Step 4: Find resource

```
Does it exist?
```

If no:

```
404
```

### Step 5: Check conflicts

```
Does this violate a resource constraint?
```

If yes:

```
409
```

### Step 6: Perform operation

If an unexpected server problem occurs:

```
500
```

# 39. Common Mistakes

### ❌ Mistake 1: Returning `200` for errors

Bad:

```
{
    "success": false,
    "error": "User not found"
}
```

with:

```
200 OK
```

The HTTP status should communicate the outcome.

Use:

```
404 Not Found
```

---

### ❌ Mistake 2: Returning `500` for validation errors

Missing required input is normally a client/request problem.

Use:

```
400 / 422
```

not:

```
500
```

---

### ❌ Mistake 3: Exposing tracebacks

Never expose internal Python tracebacks in production API responses.

---

### ❌ Mistake 4: Forgetting database rollback

After a failed transaction:

```
db.session.rollback()
```

when appropriate.

---

### ❌ Mistake 5: Inconsistent JSON

Don't make every endpoint return a completely different error format.

---

### ❌ Mistake 6: Catching every exception and hiding it

Always log unexpected errors.

---

### ❌ Mistake 7: Confusing 401 and 403

```
401 → Authentication
403 → Authorization
```

# 40. Final Mental Model

Think of API error handling as a traffic-control system:

```
                 REQUEST
                    ↓
              ┌───────────┐
              │ Validate  │
              └─────┬─────┘
                    ↓
              ┌───────────┐
              │   Auth    │
              └─────┬─────┘
                    ↓
              ┌───────────┐
              │Permission │
              └─────┬─────┘
                    ↓
              ┌───────────┐
              │ Resource  │
              └─────┬─────┘
                    ↓
              ┌───────────┐
              │  Logic    │
              └─────┬─────┘
                    ↓
              ┌───────────┐
              │ Database  │
              └─────┬─────┘
                    ↓
                 RESPONSE
```

At every checkpoint:

```
Invalid input      → 400 / 422
Not authenticated  → 401
Not authorized     → 403
Not found          → 404
Conflict           → 409
Unexpected failure → 500
```

### Golden rule

> **An API error should tell the client what kind of problem occurred without exposing sensitive internal implementation details.**
