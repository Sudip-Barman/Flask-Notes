
Input validation is one of the most important parts of a REST API.

A client can send **anything** to your API. Your backend must decide whether that data is acceptable before using it.

> **Golden Rule:** Never trust data coming from the client.

---

# 1. What Is Input Validation?

**Input validation** means checking whether incoming data:

- Exists when required
- Has the correct data type
- Has the correct format
- Has an acceptable length
- Is within an allowed range
- Contains allowed values
- Follows business rules

For example, suppose an API creates a product:

```
{
    "name": "Laptop",
    "price": 50000,
    "quantity": 5
}
```

The server should validate:

```
name     → required string
price    → number greater than 0
quantity → integer greater than or equal to 0
```

If the client sends:

```
{
    "name": "",
    "price": -5000,
    "quantity": "five"
}
```

the API should reject the request.

---

# 2. Why Is Input Validation Important?

Without validation, bad data can enter your application.

```
Client
   ↓
Bad / unexpected data
   ↓
API
   ↓
Database
```

This can cause:

- Database errors
- Incorrect calculations
- Invalid records
- Application crashes
- Security problems
- Unexpected application behavior

With validation:

```
Client
   ↓
Input
   ↓
Validation
   ↓
Valid?
 ┌───────┴───────┐
No              Yes
 ↓                ↓
Error          Business Logic
                  ↓
               Database
```

---

# 3. Never Trust Client Input

The frontend may have validation:

```
if (price <= 0) {
    alert("Invalid price");
}
```

But this is **not enough**.

A user can bypass the frontend and directly send:

```
POST /api/products
```

with:

```
{
    "name": "Laptop",
    "price": -100
}
```

Therefore:

> **Frontend validation improves user experience. Backend validation provides actual protection.**

---

# 4. Types of Input Validation

There are several common validation categories.

|Validation|Example|
|---|---|
|Required|Name must exist|
|Type|Age must be an integer|
|Length|Name must be 2-100 characters|
|Format|Email must have valid format|
|Range|Price must be greater than 0|
|Allowed values|Status must be `active` or `inactive`|
|Structure|JSON must contain expected fields|
|Business rule|End date cannot be before start date|

---

# 5. Required Field Validation

Suppose an API expects:

```
{
    "name": "John",
    "email": "john@example.com"
}
```

We can check whether required fields exist.

```
data = request.get_json(silent=True)

if not data:
    return jsonify({
        "error": "JSON body is required"
    }), 400

if "name" not in data:
    return jsonify({
        "error": "Name is required"
    }), 400

if "email" not in data:
    return jsonify({
        "error": "Email is required"
    }), 400
```

---

# 6. Checking Empty Values

Checking whether a key exists is not always enough.

This request contains the key:

```
{
    "name": ""
}
```

But the value is empty.

A better validation:

```
name = data.get("name")

if not name:
    return jsonify({
        "error": "Name is required"
    }), 400
```

For strings, you may want:

```
name = data.get("name")

if not isinstance(name, str) or not name.strip():
    return jsonify({
        "error": "Name must be a non-empty string"
    }), 400
```

---

# 7. Type Validation

Suppose `age` must be an integer.

Valid:

```
{
    "age": 20
}
```

Invalid:

```
{
    "age": "twenty"
}
```

Validation:

```
age = data.get("age")

if not isinstance(age, int):
    return jsonify({
        "error": "Age must be an integer"
    }), 400
```

You can also check the range:

```
if age < 0:
    return jsonify({
        "error": "Age cannot be negative"
    }), 400
```

---

# 8. Boolean Validation

Be careful with boolean values.

Valid:

```
{
    "active": true
}
```

Invalid:

```
{
    "active": "true"
}
```

Validation:

```
active = data.get("active")

if not isinstance(active, bool):
    return jsonify({
        "error": "Active must be a boolean"
    }), 400
```

---

# 9. Number Validation

Suppose a product price must be positive.

```
price = data.get("price")

if not isinstance(price, (int, float)):
    return jsonify({
        "error": "Price must be a number"
    }), 400

if price <= 0:
    return jsonify({
        "error": "Price must be greater than 0"
    }), 400
```

This gives us two levels of validation:

```
Is it a number?
      ↓
Is the number acceptable?
```

---

# 10. String Length Validation

Suppose a username must contain between 3 and 50 characters.

```
username = data.get("username")

if not isinstance(username, str):
    return jsonify({
        "error": "Username must be a string"
    }), 400

username = username.strip()

if len(username) < 3:
    return jsonify({
        "error": "Username must contain at least 3 characters"
    }), 400

if len(username) > 50:
    return jsonify({
        "error": "Username cannot exceed 50 characters"
    }), 400
```

Why limit length?

Because your application should not blindly accept enormous strings.

---

# 11. Email Validation

A basic email validation can use a regular expression.

```
import re

email = data.get("email")

pattern = r"^[^@\s]+@[^@\s]+\.[^@\s]+$"

if not isinstance(email, str) or not re.match(pattern, email):
    return jsonify({
        "error": "Invalid email address"
    }), 400
```

Example:

```
john@example.com     → valid
john@example         → invalid
john                 → invalid
```

However, email validation can become surprisingly complicated.

For production applications, a dedicated validation library is often preferable.

---

# 12. Allowed Values

Suppose a user's status can only be:

```
active
inactive
pending
```

Validate it:

```
status = data.get("status")

allowed_statuses = {
    "active",
    "inactive",
    "pending"
}

if status not in allowed_statuses:
    return jsonify({
        "error": "Invalid status"
    }), 400
```

This prevents values such as:

```
deleted
random
hello
123
```

from entering the system when they are not supported.

---

# 13. JSON Structure Validation

Suppose your endpoint expects:

```
{
    "name": "Laptop",
    "price": 50000
}
```

First make sure the body is an object/dictionary.

```
data = request.get_json(silent=True)

if not isinstance(data, dict):
    return jsonify({
        "error": "Request body must be a JSON object"
    }), 400
```

Then validate individual fields.

```
name = data.get("name")
price = data.get("price")
```

---

# 14. `request.get_json()` vs `silent=True`

Normally:

```
data = request.get_json()
```

If the request contains invalid JSON, Flask can raise an error.

For APIs, you may prefer:

```
data = request.get_json(silent=True)
```

With `silent=True`, Flask returns `None` instead of raising an exception for JSON parsing problems.

Example:

```
data = request.get_json(silent=True)

if data is None:
    return jsonify({
        "error": "Invalid JSON"
    }), 400
```

---

# 15. Complete Validation Example

Let's create a product API.

```
from flask import Flask, request, jsonify

app = Flask(__name__)


@app.post("/api/products")
def create_product():

    data = request.get_json(silent=True)

    # JSON validation
    if not isinstance(data, dict):
        return jsonify({
            "error": "Request body must be a JSON object"
        }), 400

    # Name validation
    name = data.get("name")

    if not isinstance(name, str) or not name.strip():
        return jsonify({
            "error": "Name is required"
        }), 400

    name = name.strip()

    if len(name) > 100:
        return jsonify({
            "error": "Name cannot exceed 100 characters"
        }), 400

    # Price validation
    price = data.get("price")

    if not isinstance(price, (int, float)):
        return jsonify({
            "error": "Price must be a number"
        }), 400

    if price <= 0:
        return jsonify({
            "error": "Price must be greater than 0"
        }), 400

    # If everything is valid
    return jsonify({
        "message": "Product data is valid",
        "product": {
            "name": name,
            "price": price
        }
    }), 201
```

The flow is:

```
JSON
 ↓
Is it an object?
 ↓
Is name present?
 ↓
Is name a string?
 ↓
Is name length valid?
 ↓
Is price a number?
 ↓
Is price > 0?
 ↓
Business Logic
```

# 16. Validation Error Response

A good API should give the client useful information.

Instead of:

```
{
    "error": "Invalid input"
}
```

you can return field-specific errors:

```
{
    "success": false,
    "errors": {
        "name": "Name is required",
        "price": "Price must be greater than 0"
    }
}
```

This is especially useful for frontend applications.

---

# 17. Multiple Validation Errors

Instead of stopping at the first error, you can collect all validation errors.

```
data = request.get_json(silent=True)

errors = {}

if not isinstance(data, dict):
    return jsonify({
        "success": False,
        "errors": {
            "body": "Request body must be a JSON object"
        }
    }), 400

name = data.get("name")
price = data.get("price")

if not isinstance(name, str) or not name.strip():
    errors["name"] = "Name is required"

if not isinstance(price, (int, float)):
    errors["price"] = "Price must be a number"
elif price <= 0:
    errors["price"] = "Price must be greater than 0"

if errors:
    return jsonify({
        "success": False,
        "errors": errors
    }), 400
```

Response:

```
{
    "success": false,
    "errors": {
        "name": "Name is required",
        "price": "Price must be greater than 0"
    }
}
```

This saves the client from making multiple requests just to discover multiple errors.

# 18. Validation vs Business Rules

These concepts are related but not identical.

### Structural validation

Checks whether the data has an acceptable structure.

```
price must be a number
name must be a string
age must be an integer
```

### Business validation

Checks whether the data makes sense according to application rules.

```
Start date cannot be after end date.

A product cannot be sold if it is inactive.

A user cannot transfer more money than their balance.

An order cannot be cancelled after shipment.
```

Think:

```
Input Validation
       ↓
"Is this data shaped correctly?"
       ↓
Business Rules
       ↓
"Does this operation make sense?"
```

# 19. Validation and Database Constraints

Database constraints are another layer of protection.

For example:

```
email = db.Column(
    db.String(120),
    unique=True,
    nullable=False
)
```

This helps ensure:

```
email cannot be NULL
email must be unique
```

But database constraints should **not** replace API validation.

A good architecture is:

```
Client
   ↓
API Validation
   ↓
Business Rules
   ↓
SQLAlchemy
   ↓
Database Constraints
   ↓
Database
```

Each layer catches different problems.

# 20. PATCH Validation

PATCH introduces an important difference.

Suppose the product currently is:

```
{
    "name": "Laptop",
    "price": 50000
}
```

The client sends:

```
{
    "price": 55000
}
```

That's valid because only `price` is being updated.

Therefore, don't require every field for PATCH.

```
data = request.get_json(silent=True)

if "name" in data:
    if not isinstance(data["name"], str):
        return jsonify({
            "error": "Name must be a string"
        }), 400

if "price" in data:
    if not isinstance(data["price"], (int, float)):
        return jsonify({
            "error": "Price must be a number"
        }), 400
```

The important distinction:

```
POST
 ↓
Required fields usually need to be present

PATCH
 ↓
Only supplied fields need validation
```

---

# 21. Unexpected Fields

Suppose your API accepts:

```
{
    "name": "Laptop",
    "price": 50000
}
```

But the client sends:

```
{
    "name": "Laptop",
    "price": 50000,
    "is_admin": true
}
```

Should the API accept `is_admin`?

Usually, you should define what fields are allowed.

```
allowed_fields = {
    "name",
    "price"
}

unexpected_fields = set(data.keys()) - allowed_fields

if unexpected_fields:
    return jsonify({
        "error": "Unexpected fields",
        "fields": list(unexpected_fields)
    }), 400
```

This is especially important for sensitive fields.

Never allow a client to simply send:

```
{
    "role": "admin"
}
```

and automatically change their role.

---

# 22. Validation vs Sanitization

These are different concepts.

### Validation

Asks:

> "Is this input acceptable?"

Example:

```
if price <= 0:
    reject()
```

### Sanitization

Transforms or cleans input.

Example:

```
name = name.strip()
```

So:

```
Validation → Accept or reject
Sanitization → Clean or transform
```

Do not assume sanitizing input makes it safe for every output context.

For example, HTML escaping should happen according to where the data is being displayed.

---

# 23. Input Validation Is Not SQL Injection Protection

Never build SQL using string concatenation:

```
query = f"SELECT * FROM users WHERE email = '{email}'"
```

Instead, use parameterized queries or SQLAlchemy.

Validation is useful, but it is **not a replacement for safe database queries**.

```
Validation
     +
Parameterized SQL / ORM
     +
Authentication
     +
Authorization
     +
Database constraints
```

Security usually comes from multiple layers.

# 24. Schema Validation

As applications grow, manually writing:

```
if ...
if ...
if ...
if ...
```

for every endpoint becomes repetitive.

Schema validation libraries can define the expected structure in one place.

Popular Python choices include:

- **Marshmallow**
- **Pydantic**
- **Flask-Smorest** with schema-based API development

Conceptually:

```
Request JSON
     ↓
Schema
     ↓
Validation
     ↓
Validated Data
     ↓
Route Logic
```

For a small Flask application, manual validation is perfectly useful for learning and simple APIs.

For larger applications, schema-based validation can make the code more organized and reusable.

# 25. Validation Helper Functions

You can also move repeated validation into helper functions.

Example:

```
def validate_product(data):

    errors = {}

    name = data.get("name")
    price = data.get("price")

    if not isinstance(name, str) or not name.strip():
        errors["name"] = "Name is required"

    if not isinstance(price, (int, float)):
        errors["price"] = "Price must be a number"
    elif price <= 0:
        errors["price"] = "Price must be greater than 0"

    return errors
```

Then:

```
@app.post("/api/products")
def create_product():

    data = request.get_json(silent=True)

    if not isinstance(data, dict):
        return jsonify({
            "error": "Invalid JSON body"
        }), 400

    errors = validate_product(data)

    if errors:
        return jsonify({
            "success": False,
            "errors": errors
        }), 400

    # Continue with database operation
```

This keeps routes cleaner.

# 26. Validation Flow in a Real API

A typical API request can follow this pipeline:

```
                 HTTP Request
                      ↓
                Parse Request
                      ↓
              JSON / Form Data
                      ↓
               Basic Validation
                      ↓
          ┌───────────┴───────────┐
          ↓                       ↓
       Invalid                  Valid
          ↓                       ↓
      400 / 422             Authentication
                                  ↓
                             Authorization
                                  ↓
                           Business Rules
                                  ↓
                              Database
                                  ↓
                           JSON Response
```

# 27. 400 vs 422 for Validation

Both are commonly encountered.

### 400 Bad Request

Often used for malformed or invalid request data.

```
{
    "error": "Invalid JSON"
}
```

### 422 Unprocessable Content

Often used when the request structure is understandable but the values fail validation.

For example:

```
{
    "age": -10
}
```

The JSON is valid, but the value is unacceptable.

A project can choose a consistent convention.

For a beginner Flask API, using **400 consistently for basic validation errors** is perfectly reasonable.

The most important thing is consistency.

# 28. Security Considerations

Good input validation should also consider abuse.

### Limit string lengths

```
if len(name) > 100:
    ...
```

### Limit numeric ranges

```
if quantity > 100000:
    ...
```

### Validate file uploads

Check:

- File type
- File size
- Filename
- Content where appropriate

### Don't trust IDs

If a client sends:

```
{
    "user_id": 10
}
```

don't automatically assume they are allowed to modify user 10.

Authorization must still be checked.

### Don't trust roles

Never rely on:

```
{
    "role": "admin"
}
```

from the client to grant privileges.

### Don't accept unlimited payloads

Very large requests can consume memory and processing resources.

# 29. Common Input Validation Mistakes

### ❌ Mistake 1: Only validating frontend

```
Frontend validation
      ↓
Assume data is safe
```

Wrong.

Backend must validate again.

---

### ❌ Mistake 2: Checking only whether a key exists

```
if "price" in data:
```

This does not guarantee:

```
price is a number
price > 0
price is within acceptable range
```

---

### ❌ Mistake 3: Trusting client-supplied roles

```
role = data.get("role")
```

Never use this to grant privileges.

---

### ❌ Mistake 4: No length limits

Allowing unlimited strings can create storage and resource problems.

---

### ❌ Mistake 5: Returning unclear errors

Avoid:

```
{
    "error": "Something went wrong"
}
```

Prefer:

```
{
    "success": false,
    "errors": {
        "price": "Price must be greater than 0"
    }
}
```

---

### ❌ Mistake 6: Treating validation as authorization

Validation asks:

> Is this data acceptable?

Authorization asks:

> Is this user allowed to perform this action?

They are different security layers.

# 30. Best-Practice Validation Checklist

Before processing API input, consider:

```
□ Is the request body present?
□ Is the JSON valid?
□ Is the JSON structure correct?
□ Are required fields present?
□ Are data types correct?
□ Are strings within length limits?
□ Are numbers within acceptable ranges?
□ Are enum/status values allowed?
□ Are formats valid?
□ Are cross-field rules satisfied?
□ Are unexpected fields handled?
□ Is authentication checked?
□ Is authorization checked?
□ Are database constraints also present?
□ Are errors returned consistently?
```

## Quick Revision

|Concept|Meaning|
|---|---|
|Input validation|Checking whether client data is acceptable|
|Required validation|Checking mandatory fields|
|Type validation|Checking string/int/float/bool etc.|
|Format validation|Checking email, dates, patterns etc.|
|Range validation|Checking numeric limits|
|Length validation|Checking string/list limits|
|Allowed values|Restricting values to predefined choices|
|Business validation|Checking application-specific rules|
|Sanitization|Cleaning or transforming input|
|Schema validation|Validating data against a defined schema|
|Backend validation|Mandatory even when frontend validates|
|400|Common choice for invalid request data|
|422|Often used for semantic validation failures|

### One sentence to remember:

> **Input validation is the API's gatekeeper: check the shape, type, format, limits, and rules of incoming data before allowing it to reach your application logic or database.**
