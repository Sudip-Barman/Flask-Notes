**JWT authentication** is one of the most common ways to authenticate users in modern REST APIs.

JWT stands for:

> **JSON Web Token**

Instead of maintaining a traditional server-side login session, the server generates a token after successful login. The client then sends that token with future API requests.

The core idea is:

```
Login
  ↓
Verify credentials
  ↓
Generate JWT
  ↓
Client receives JWT
  ↓
Client sends JWT with requests
  ↓
Server verifies JWT
  ↓
Identify user
  ↓
Allow protected API
```

---

# 1. What is JWT?

A JWT is a compact, URL-safe token containing information called **claims**, together with a cryptographic signature.

A JWT usually looks like:

```
xxxxx.yyyyy.zzzzz
```

For example:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.
eyJzdWIiOjEwLCJleHAiOjE3...
.
abc123...
```

The three sections are separated by dots:

```
HEADER.PAYLOAD.SIGNATURE
```

So:

```
JWT
├── Header
├── Payload
└── Signature
```

---

# 2. Why Do We Need JWT?

Imagine a user logs into an API:

```
POST /api/login
```

with:

```
{
    "email": "user@example.com",
    "password": "password123"
}
```

The server verifies the credentials.

Now the server needs some way to recognize the user in future requests.

Without authentication:

```
GET /api/profile
```

The server doesn't know who is requesting the profile.

JWT solves this by giving the client a token:

```
Login
  ↓
Valid credentials
  ↓
JWT generated
  ↓
Client receives JWT
```

Future request:

```
GET /api/profile
Authorization: Bearer <JWT>
```

The server verifies the token and identifies the user.

The complete flow:

```
                  CLIENT

                            ↓

                            │
                            ↓

```

# 4. JWT Structure

A JWT has three parts:

```
HEADER.PAYLOAD.SIGNATURE
```

For example:

```
abc123.def456.xyz789
```

These parts have different purposes.

|Part|Purpose|
|---|---|
|Header|Describes the token|
|Payload|Contains claims/data|
|Signature|Verifies token integrity|

---

# 5. JWT Header

The header generally contains information such as the signing algorithm and token type.

Example decoded header:

```
{
    "alg": "HS256",
    "typ": "JWT"
}
```

### `alg`

Specifies the cryptographic algorithm.

For example:

```
HS256
```

### `typ`

Usually:

```
JWT
```

So conceptually:

```
Header
   ↓
How is this token structured/signed?
```

---

# 6. JWT Payload

The payload contains **claims**.

Example:

```
{
    "sub": "10",
    "name": "Example User",
    "role": "staff"
}
```

Here:

```
sub  → Subject/user identifier
name → User name
role → User role
```

The payload is useful because the server can obtain information about the authenticated identity from the token.

---

# 7. Important JWT Claims

JWT defines several registered claim names.

Some commonly encountered claims are:

|Claim|Meaning|
|---|---|
|`sub`|Subject|
|`iss`|Issuer|
|`aud`|Audience|
|`exp`|Expiration time|
|`iat`|Issued-at time|
|`nbf`|Not-before time|
|`jti`|JWT ID|

Example:

```
{
    "sub": "10",
    "iss": "my-api",
    "iat": 1789200000,
    "exp": 1789203600
}
```

You don't need to memorize all of them immediately.

The most important ones to recognize are:

```
sub → Who?
iat → When issued?
exp → When does it expire?
```

---

# 8. JWT Signature

The signature is what allows the server to detect whether the token has been modified.

Conceptually:

```
Header
   +
Payload
   ↓
Signing process
   ↓
Secret/private key
   ↓
Signature
```

The final JWT becomes:

```
HEADER.PAYLOAD.SIGNATURE
```

When the client sends the token back, the server verifies the signature.

```
JWT
 ↓
Verify signature
 ↓
Valid?
 ┌───┴───┐
No      Yes
 ↓        ↓
Reject   Continue
```

---

# 9. Very Important: JWT Payload Is Not Secret

A common beginner mistake is thinking:

> "The JWT is encrypted, so nobody can read it."

Usually, that is **not true**.

Standard JWTs are commonly **signed, not encrypted**.

The payload can generally be decoded and read by someone who possesses the token.

For example:

```
{
    "user_id": 10,
    "role": "staff"
}
```

should not contain sensitive secrets such as:

```
Password
Credit card number
Private API keys
```

The signature protects **integrity**, not confidentiality.

### Remember:

```
Signed ≠ Encrypted
```

---

# 10. JWT Signing

There are two broad families of JWT signing approaches.

## Symmetric signing

The same secret is used to sign and verify.

Example:

```
HS256
```

Conceptually:

```
Secret
  ↓
Sign JWT

Same Secret
  ↓
Verify JWT
```

---

## Asymmetric signing

A private key signs the token, while a public key verifies it.

Examples include algorithms such as:

```
RS256
ES256
```

Conceptually:

```
Private Key
    ↓
Sign JWT
    ↓
JWT
    ↓
Public Key
    ↓
Verify JWT
```

For beginner Flask applications, you will often encounter symmetric signing first.

---

# 11. JWT Secret Key

When using a symmetric algorithm, the server needs a secret.

Conceptually:

```
JWT_SECRET = "very-secret-value"
```

However, don't hard-code real production secrets like this.

Instead, use an environment variable:

```
import os

JWT_SECRET = os.environ["JWT_SECRET"]
```

For example:

```
Environment
    ↓
JWT_SECRET
    ↓
Flask
    ↓
JWT signing/verification
```

The secret must remain private.

# 12. Installing JWT Support in Flask

A commonly used Flask extension is **Flask-JWT-Extended**.

Install it:

```
pip install Flask-JWT-Extended
```

Then import it:

```
from flask_jwt_extended import JWTManager
```

Create the Flask application:

```
from flask import Flask

app = Flask(__name__)

app.config["JWT_SECRET_KEY"] = "change-this-secret"

jwt = JWTManager(app)
```

For production, use a strong secret stored outside the source code.

# 13. Creating a JWT

With Flask-JWT-Extended:

```
from flask_jwt_extended import create_access_token
```

Then:

```
access_token = create_access_token(identity=user.id)
```

The token represents the authenticated identity.

For example:

```
@app.post("/api/login")
def login():

    # Normally credentials are verified here

    user_id = 10

    access_token = create_access_token(
        identity=user_id
    )

    return {
        "access_token": access_token
    }
```

Response:

```
{
    "access_token": "eyJhbGciOiJIUzI1NiIs..."
}
```

---

# 14. Client Sends the JWT

After login, the client receives:

```
access_token
```

For a protected API request, it sends:

```
GET /api/profile
Authorization: Bearer <access_token>
```

The important structure is:

```
Authorization: Bearer TOKEN
```

Not:

```
Authorization: TOKEN
```

The `Bearer` scheme tells the server that the credential is being presented as a bearer token.

# 15. Protecting a Flask Route

Import:

```
from flask_jwt_extended import jwt_required
```

Then:

```
@app.get("/api/profile")
@jwt_required()
def profile():

    return {
        "message": "Protected profile"
    }
```

Now the endpoint requires a valid JWT.

Without a valid token:

```
GET /api/profile
        ↓
JWT check
        ↓
No valid JWT
        ↓
Request rejected
```

---

# 16. Getting the Current User

To retrieve the identity stored in the JWT:

```
from flask_jwt_extended import get_jwt_identity
```

Then:

```
@app.get("/api/profile")
@jwt_required()
def profile():

    user_id = get_jwt_identity()

    return {
        "user_id": user_id
    }
```

If the token was created with:

```
create_access_token(identity=10)
```

then:

```
get_jwt_identity()
```

returns the identity:

```
10
```

# 17. JWT Login + Protected API Example

Here is a simple complete example:

```
from flask import Flask, request, jsonify
from flask_jwt_extended import (
    JWTManager,
    create_access_token,
    jwt_required,
    get_jwt_identity
)

app = Flask(__name__)

app.config["JWT_SECRET_KEY"] = "change-this-secret"

jwt = JWTManager(app)


@app.post("/api/login")
def login():

    data = request.get_json()

    email = data.get("email")
    password = data.get("password")

    # Normally verify against the database
    if email != "user@example.com" or password != "password123":
        return jsonify({
            "error": "Invalid credentials"
        }), 401

    user_id = 10

    access_token = create_access_token(
        identity=user_id
    )

    return jsonify({
        "access_token": access_token
    })


@app.get("/api/profile")
@jwt_required()
def profile():

    user_id = get_jwt_identity()

    return jsonify({
        "user_id": user_id,
        "message": "Authenticated successfully"
    })


if __name__ == "__main__":
    app.run(debug=True)
```

In a real application, the login process should check the database.

For example:

```
@app.post("/api/login")
def login():

    data = request.get_json()

    email = data.get("email")
    password = data.get("password")

    user = User.query.filter_by(email=email).first()

    if user is None:
        return jsonify({
            "error": "Invalid credentials"
        }), 401

    if not check_password_hash(
        user.password_hash,
        password
    ):
        return jsonify({
            "error": "Invalid credentials"
        }), 401

    access_token = create_access_token(
        identity=user.id
    )

    return jsonify({
        "access_token": access_token
    })
```

This connects the concepts from our earlier modules:

```
User
 ↓
Password Hashing
 ↓
Login
 ↓
JWT
 ↓
Protected API
```

# 20. JWT Should Usually Identify a User

A good pattern is:

```
create_access_token(identity=user.id)
```

Then:

```
user_id = get_jwt_identity()
```

Then query the database:

```
user = db.session.get(User, user_id)
```

This gives you:

```
JWT
 ↓
User ID
 ↓
Database
 ↓
Current User
```

This can be safer and more flexible than putting a large amount of user data inside the JWT.

# 21. Additional JWT Claims

Sometimes you need additional information in the token.

For example:

```
access_token = create_access_token(
    identity=user.id,
    additional_claims={
        "role": user.role
    }
)
```

The token might conceptually contain:

```
{
    "sub": "10",
    "role": "manager"
}
```

You can later read claims using JWT utilities.

However, be careful with authorization decisions based on claims that can become stale.

For example:

```
User role in database:
manager

JWT created:
manager

Later:
Admin changes user → staff

Old JWT:
still says manager
```

This is one reason token lifetime and authorization design matter.

---

# 22. Access Token Expiration

JWTs can have expiration times.

Example:

```
from datetime import timedelta

app.config["JWT_ACCESS_TOKEN_EXPIRES"] = timedelta(
    minutes=30
)
```

Now an access token expires after the configured period.

Conceptually:

```
JWT created
    ↓
30 minutes
    ↓
Expired
    ↓
Rejected
```

This reduces the useful lifetime of a stolen token.

---

# 23. Expired JWT

Suppose:

```
Token issued:
10:00 AM

Token expires:
10:30 AM
```

At:

```
10:45 AM
```

the client sends the token.

The server detects:

```
Token expired
```

and rejects the request.

The client may need to authenticate again or use a refresh-token mechanism, depending on the application's design.

---

# 24. Access Token vs Refresh Token

Modern authentication systems often use two token types.

### Access token

Used for API requests.

```
Shorter lifetime
```

### Refresh token

Used to obtain a new access token.

```
Longer lifetime
```

Conceptually:

```
Login
  ↓
Access Token + Refresh Token
  ↓
Access Token
  ↓
API requests
  ↓
Expires
  ↓
Refresh Token
  ↓
New Access Token
```

Don't confuse these with each other.

For the basic JWT course, focus first on **access tokens**.

# 25. JWT Is Stateless

One important advantage of JWT authentication is that the server can often verify a token without maintaining a traditional server-side login session for every client.

Conceptually:

```
Traditional session

Client
 ↓
Session ID
 ↓
Server
 ↓
Session storage
```

JWT:

```
Client
 ↓
JWT
 ↓
Server
 ↓
Verify signature
 ↓
Read claims
```

This is why JWT is often described as **stateless authentication**.

However, real systems can still maintain server-side state for things such as refresh tokens, revocation, sessions, or security controls.

So don't interpret "stateless" as "the server never stores anything related to authentication."

# 27. JWT Security

JWT is not automatically secure just because it is JWT.

You still need good security practices.

### Use HTTPS

```
HTTP ❌
HTTPS ✅
```

### Protect the signing secret

Never expose:

```
JWT_SECRET
```

to the frontend.

### Don't put sensitive information in the payload

Remember:

```
JWT payload ≠ encrypted storage
```

### Use expiration

Don't create tokens that remain valid forever unless you have a strong reason.

### Don't log tokens

Avoid:

```
print(access_token)
```

in production logs.

### Validate tokens on the backend

Frontend checks are not security controls.

---

# 28. Where Should the JWT Be Stored?

This is an important web security topic.

A browser application can store tokens in different places, but each choice has security tradeoffs.

Common options include:

```
localStorage
sessionStorage
HttpOnly cookie
```

For browser applications, storing sensitive authentication tokens in JavaScript-accessible storage can increase exposure if the application has an XSS vulnerability.

An `HttpOnly` cookie can prevent JavaScript from directly reading the cookie, but then you also need to consider CSRF protections and cookie configuration.

So there isn't a universal:

> "Always store JWT in X."

The architecture and threat model matter.

# 30. JWT Authentication Mental Model

Think of the JWT as a **signed identity ticket**.

```
User
 ↓
Login
 ↓
Server verifies identity
 ↓
Server issues signed ticket
 ↓
Client carries ticket
 ↓
Client presents ticket
 ↓
Server verifies ticket
 ↓
Server knows the claimed identity
 ↓
Protected API continues
```

The ticket isn't a secret diary. Anyone holding it may be able to read its payload, so don't put confidential information inside it.

# 31. Common JWT Mistakes

### ❌ Mistake 1: Thinking JWT is encryption

JWT is commonly signed, not encrypted.

### ❌ Mistake 2: Putting passwords in JWT

Never.

### ❌ Mistake 3: Using a weak secret

Don't use:

```
JWT_SECRET_KEY = "12345"
```

Use a strong randomly generated secret.

### ❌ Mistake 4: Never expiring tokens

Long-lived tokens increase risk if stolen.

### ❌ Mistake 5: Trusting the frontend

A frontend saying:

```
"I am admin"
```

means nothing by itself.

### ❌ Mistake 6: Forgetting `Bearer`

Correct:

```
Authorization: Bearer <token>
```

### ❌ Mistake 7: Putting too much information into JWT

Keep claims purposeful and minimal.

### ❌ Mistake 8: Hard-coding production secrets

Use environment/configuration management.

# 32. JWT and Authorization

Authentication answers:

```
Who is this?
```

JWT can establish that identity.

Authorization then answers:

```
What can this user do?
```

For example:

```
JWT
 ↓
user_id = 10
 ↓
Database
 ↓
User role = manager
 ↓
Authorization check
 ↓
Can access reports?
 ↓
Yes
```

So JWT authentication and authorization are related but not identical.

We'll explore protected APIs and authorization more deeply in **10.9**.
