
In a REST API, **routes and endpoints define how clients interact with resources**.

If JSON is the language of your API, then **endpoints are the addresses** where that communication happens.

For example:

```
GET /api/users
```

means:

> "Give me the users."

And:

```
POST /api/users
```

means:

> "Create a new user."

The URL identifies **what resource** you are working with, while the HTTP method identifies **what you want to do**.

---

# 1. What is an API Route?

A **route** is a rule in your Flask application that tells Flask:

> "When a request comes to this URL using this HTTP method, execute this function."

Example:

```
@app.get("/api/users")
def get_users():
    return {
        "message": "Getting users"
    }
```

Here:

```
/api/users
```

is the route path.

And:

```
get_users()
```

is the function that handles the request.

---

# 2. What is an Endpoint?

An **endpoint** is a specific API location that a client can interact with.

For example:

```
GET /api/users
```

is an endpoint.

Another:

```
GET /api/users/10
```

is another endpoint.

Another:

```
POST /api/users
```

is also an endpoint.

A useful way to think about it:

```
Route
 ↓
URL + HTTP method
 ↓
Endpoint
 ↓
Server-side operation
```

---

# 3. Route vs Endpoint

These terms are often used interchangeably, but there is a useful distinction.

### Route

The route is the application's definition:

```
@app.get("/api/users")
def get_users():
    ...
```

### Endpoint

The endpoint is the callable API interface:

```
GET /api/users
```

In everyday Flask/API discussions, developers often simply call both a **route** or **endpoint**.

---

# 4. Basic Flask API Route

```
from flask import Flask, jsonify

app = Flask(__name__)

@app.get("/api/users")
def get_users():
    return jsonify({
        "message": "Users retrieved"
    })
```

Now a client can make:

```
GET /api/users
```

and receive:

```
{
    "message": "Users retrieved"
}
```

# 5. API URL Structure

A typical REST API URL looks like:

```
https://example.com/api/users/10
```

Break it down:

```
https://
    ↓
Protocol

example.com
    ↓
Domain

/api
    ↓
API namespace

/users
    ↓
Resource

/10
    ↓
Specific resource ID
```

So:

```
https://example.com/api/users/10
```

means:

> User resource with ID 10.

---

# 6. Use `/api` as an API Namespace

It is common to separate API routes from normal web pages.

For example:

```
/
/about
/contact
```

could be HTML pages.

While:

```
/api/users
/api/products
/api/orders
```

are API endpoints.

This makes the application's structure easier to understand.

---

# 7. Resource-Based URLs

REST APIs should generally use **resources**, not actions, in URLs.

### Good

```
/api/users
/api/products
/api/orders
```

### Less RESTful

```
/api/getUsers
/api/createUser
/api/deleteUser
```

Why?

Because the HTTP method already describes the action.

For example:

```
GET /api/users
```

means:

```
GET
 ↓
Read
 ↓
users
```

And:

```
POST /api/users
```

means:

```
POST
 ↓
Create
 ↓
users
```

The URL identifies the **thing**, while HTTP identifies the **operation**.

# 8. CRUD Endpoint Design

For a `users` resource:

|Operation|HTTP Method|Endpoint|
|---|---|---|
|Get all users|GET|`/api/users`|
|Get one user|GET|`/api/users/10`|
|Create user|POST|`/api/users`|
|Replace user|PUT|`/api/users/10`|
|Update user|PATCH|`/api/users/10`|
|Delete user|DELETE|`/api/users/10`|

Notice something important:

The same resource URL can support different operations.

```
/api/users
```

can handle:

```
GET
POST
```

while:

```
/api/users/10
```

can handle:

```
GET
PUT
PATCH
DELETE
```

# 9. Collection vs Individual Resource

This is one of the most important concepts in endpoint design.

## Collection

```
/api/users
```

represents the collection of users.

Example:

```
GET /api/users
```

Response:

```
[
    {
        "id": 1,
        "name": "Rahul"
    },
    {
        "id": 2,
        "name": "Priya"
    }
]
```

## Individual resource

```
/api/users/10
```

represents one particular user.

Example:

```
GET /api/users/10
```

Response:

```
{
    "id": 10,
    "name": "Rahul"
}
```

### Mental model

```
/api/users
    │
    ├── User 1
    ├── User 2
    ├── User 3
    └── User 10
             ↑
       /api/users/10
```

# 10. Flask Dynamic Routes

Flask allows dynamic URL parameters.

```
@app.get("/api/users/<int:user_id>")
def get_user(user_id):
    return jsonify({
        "id": user_id
    })
```

Request:

```
GET /api/users/10
```

Flask receives:

```
user_id = 10
```

Response:

```
{
    "id": 10
}
```

---

# 11. Why `<int:user_id>`?

The syntax:

```
<int:user_id>
```

means:

> Capture this part of the URL and convert it to an integer.

Example:

```
/api/users/25
```

becomes:

```
user_id = 25
```

Other converters include:

```
<string:name>
<int:id>
<float:price>
<path:path>
<uuid:user_id>
```

For example:

```
@app.get("/api/products/<int:product_id>")
def get_product(product_id):
    ...
```

---

# 12. String Route Parameter

You can also capture text.

```
@app.get("/api/users/<username>")
def get_user(username):
    return jsonify({
        "username": username
    })
```

Request:

```
/api/users/rahul
```

gives:

```
username = "rahul"
```

---

# 13. Nested Resources

Sometimes resources have a relationship.

For example:

```
users
orders
```

An order may belong to a user.

You could represent:

```
/api/users/10/orders
```

Meaning:

> Orders belonging to user 10.

Example:

```
@app.get("/api/users/<int:user_id>/orders")
def get_user_orders(user_id):
    return jsonify({
        "user_id": user_id,
        "orders": []
    })
```

Request:

```
GET /api/users/10/orders
```

---

# 14. Don't Over-Nest URLs

Nested resources are useful, but excessive nesting can make APIs difficult to use.

For example:

```
/api/users/10/orders/25/items/5
```

can become difficult to understand.

Sometimes a flatter endpoint is better:

```
/api/order-items/5
```

or:

```
/api/orders/25/items
```

### Practical guideline

Keep nesting reasonably shallow.

Usually:

```
/api/users/10/orders
```

is understandable.

But very deep nesting should be questioned.

---

# 15. Singular vs Plural Resource Names

For collections, plural nouns are generally preferred.

Use:

```
/api/users
/api/products
/api/orders
/api/students
```

rather than:

```
/api/user
/api/product
/api/order
```

Then an individual resource is:

```
/api/users/10
```

This creates a predictable pattern.

```
Collection:
 /api/users

Individual:
 /api/users/10
```

---

# 16. Use Nouns, Not Verbs

### Better

```
GET /api/users
POST /api/users
DELETE /api/users/10
```

### Avoid

```
GET /api/getUsers
POST /api/createUser
POST /api/deleteUser
```

The HTTP method already tells us the operation.

Think:

```
URL       → What?
METHOD    → What action?
```

---

# 17. HTTP Method + Resource

This is the core of REST endpoint design:

```
             Resource
                ↓
        /api/products/10
                ↑
              URL

        HTTP Method
                ↓
              PATCH
                ↓
        Update product
```

Change the method:

```
GET /api/products/10
```

Now you're reading it.

Change it to:

```
DELETE /api/products/10
```

Now you're deleting it.

The resource stays the same.

# 18. Query Parameters

Query parameters are useful for **filtering, searching, sorting, and pagination**.

Example:

```
/api/products?category=books
```

Here:

```
category=books
```

is a query parameter.

Another:

```
/api/products?page=2&limit=20
```

There are two parameters:

```
page=2
limit=20
```

---

# 19. Query Parameters vs Path Parameters

This distinction is very important.

### Path parameter

```
/api/users/10
```

`10` identifies a specific resource.

```
@app.get("/api/users/<int:user_id>")
def get_user(user_id):
    ...
```

### Query parameter

```
/api/users?role=admin
```

`role=admin` filters or modifies how the collection is retrieved.

Flask:

```
from flask import request

@app.get("/api/users")
def get_users():
    role = request.args.get("role")

    return jsonify({
        "role": role
    })
```

---

# 20. When Should You Use Path Parameters?

Use path parameters when identifying a specific resource.

Example:

```
/api/users/10
/api/products/25
/api/orders/500
```

The ID is part of the resource identity.

```
/users/10
       ↑
   Resource ID
```

---

# 21. When Should You Use Query Parameters?

Use query parameters when modifying the **retrieval criteria**.

Examples:

```
/api/users?role=admin
```

```
/api/products?category=books
```

```
/api/products?sort=price
```

```
/api/users?page=2&limit=20
```

These don't identify one specific resource.

---

# 22. Multiple Query Parameters

Example:

```
/api/products?category=books&min_price=100&max_price=500
```

Flask:

```
@app.get("/api/products")
def get_products():
    category = request.args.get("category")
    min_price = request.args.get("min_price")
    max_price = request.args.get("max_price")

    return jsonify({
        "category": category,
        "min_price": min_price,
        "max_price": max_price
    })
```

---

# 23. Optional Query Parameters

Query parameters are usually optional.

For example:

```
/api/products
```

could return all products.

While:

```
/api/products?category=books
```

could return only books.

Flask:

```
@app.get("/api/products")
def get_products():
    category = request.args.get("category")

    if category:
        # Filter products
        pass

    return jsonify([])
```

This gives one endpoint multiple useful retrieval options.

---

# 24. API Versioning

As an API grows, its structure may change.

Versioning helps maintain compatibility.

Common approaches include:

```
/api/v1/users
/api/v2/users
```

Example:

```
@app.get("/api/v1/users")
def get_users_v1():
    ...
```

Later:

```
@app.get("/api/v2/users")
def get_users_v2():
    ...
```

### Why version APIs?

Suppose an existing frontend expects:

```
{
    "name": "Rahul"
}
```

But your new API changes it to:

```
{
    "full_name": "Rahul"
}
```

Existing clients could break.

Versioning gives clients time to migrate.

---

# 25. API Versioning Is a Design Decision

You don't necessarily need:

```
v1
v2
v3
```

from day one.

For small projects, simple:

```
/api/users
```

may be perfectly reasonable.

Versioning becomes particularly useful when:

- APIs are public
- Multiple clients consume the API
- Breaking changes are expected
- Older clients need continued support

# 26. Flask Route Organization

A small project might have:

```
@app.get("/api/users")
def get_users():
    ...


@app.post("/api/users")
def create_user():
    ...


@app.get("/api/users/<int:user_id>")
def get_user(user_id):
    ...


@app.patch("/api/users/<int:user_id>")
def update_user(user_id):
    ...


@app.delete("/api/users/<int:user_id>")
def delete_user(user_id):
    ...
```

This works.

But as the project grows, putting every route inside one file becomes messy.

A better structure is to separate API routes into modules.

For example:

```
project/
│
├── app.py
│
├── routes/
│   ├── users.py
│   ├── products.py
│   └── orders.py
│
├── models/
│   ├── user.py
│   ├── product.py
│   └── order.py
│
└── services/
```

Later, Flask **Blueprints** can help organize these routes.

---

# 27. Flask Blueprints for API Routes

A Blueprint lets you group related routes.

Example:

```
from flask import Blueprint, jsonify

users_bp = Blueprint("users", __name__)

@users_bp.get("/users")
def get_users():
    return jsonify([])
```

Then register it:

```
from flask import Flask
from routes.users import users_bp

app = Flask(__name__)

app.register_blueprint(
    users_bp,
    url_prefix="/api"
)
```

The final endpoint becomes:

```
GET /api/users
```

This is useful for larger Flask applications.

---

# 28. Route Naming in Flask

Flask also gives routes endpoint names internally.

Example:

```
@app.get("/api/users")
def get_users():
    ...
```

The function name:

```
get_users
```

becomes the Flask endpoint name by default.

You can use:

```
url_for("get_users")
```

to generate its URL.

This is especially useful when building larger Flask applications.

# 31. Avoid Action-Based URLs

Suppose you want to deactivate a user.

You might see:

```
POST /api/users/10/deactivate
```

This can be reasonable for a domain-specific action, but don't turn every operation into an action endpoint.

For ordinary CRUD:

```
PATCH /api/users/10
```

with:

```
{
    "is_active": false
}
```

is often cleaner.

### Important nuance

Not every operation maps neatly to CRUD.

For genuine domain actions, action-style endpoints can be appropriate.

For example:

```
POST /api/orders/101/cancel
```

can make sense when "cancel" is a business operation rather than simply changing one field.

# 32. Endpoint Naming Consistency

Choose a naming convention and keep it consistent.

For example:

```
/api/users
/api/products
/api/orders
```

Don't mix:

```
/api/users
/api/product
/api/customerOrders
/api/GetStudents
```

A clean API feels predictable.

If one endpoint follows a pattern, developers should be able to predict the others.

You may encounter:

```
/api/users
```

and:

```
/api/users/
```

Both styles exist.

The important thing is **consistency**.

For example, choose:

```
/api/users
/api/products
```

# 34. URL Naming Style

REST APIs commonly use lowercase resource names:

```
/api/users
/api/products
/api/order-items
```

Avoid inconsistent styles such as:

```
/api/UserList
/api/GetProducts
/api/productData
```

For multi-word resources, kebab-case is commonly readable:

```
/api/order-items
```

A clean API might look like:

```
/api
│
├── /users
│   ├── GET

│   └── /<id>
│       ├── GET

│       ├── PATCH

├── /products
│   ├── GET

│       ├── GET

    ├── GET
    ├── POST

        ├── PATCH
        └── DELETE
```

This structure scales nicely.

# 36. Complete Flask Example

```
from flask import Flask, request, jsonify

app = Flask(__name__)


# Get all users
@app.get("/api/users")
def get_users():
    return jsonify([
        {
            "id": 1,
            "name": "Rahul"
        },
        {
            "id": 2,
            "name": "Priya"
        }
    ])


# Create a user
@app.post("/api/users")
def create_user():
    data = request.get_json()

    return jsonify({
        "message": "User created",
        "data": data
    }), 201


# Get one user
@app.get("/api/users/<int:user_id>")
def get_user(user_id):
    return jsonify({
        "id": user_id,
        "name": "Rahul"
    })


# Update part of a user
@app.patch("/api/users/<int:user_id>")
def update_user(user_id):
    data = request.get_json()

    return jsonify({
        "message": "User updated",
        "id": user_id,
        "data": data
    })


# Delete a user
@app.delete("/api/users/<int:user_id>")
def delete_user(user_id):
    return jsonify({
        "message": "User deleted",
        "id": user_id
    })


if __name__ == "__main__":
    app.run(debug=True)
```

# 37. What Happens During a Request?

Suppose the client sends:

```
PATCH /api/users/10
```

with:

```
{
    "name": "Amit"
}
```

Flask matches:

```
@app.patch("/api/users/<int:user_id>")
```

Then:

```
URL
 ↓
/api/users/10
 ↓
Route matching
 ↓
user_id = 10
 ↓
update_user(10)
 ↓
request.get_json()
 ↓
{"name": "Amit"}
 ↓
Business logic
 ↓
Database
 ↓
JSON response
```

This is the complete endpoint lifecycle.

# 38. REST Endpoint Design Checklist

When creating an endpoint, ask:

### 1. What is the resource?

```
users
products
orders
students
```

### 2. Is it a collection or individual resource?

```
/api/users
/api/users/10
```

### 3. Which HTTP method?

```
GET
POST
PUT
PATCH
DELETE
```

### 4. Does the resource need an ID?

```
/api/users/10
```

### 5. Should filtering use query parameters?

```
/api/users?role=admin
```

### 6. Is the URL predictable?

If I know `/api/users`, can I guess `/api/products`?

### 7. Is the naming consistent?

Use the same conventions throughout the API.

# 39. Common API Route Mistakes

### ❌ Mistake 1: Using verbs everywhere

```
/api/getUsers
/api/createUser
/api/deleteUser
```

Prefer:

```
GET /api/users
POST /api/users
DELETE /api/users/10
```

---

### ❌ Mistake 2: POST for everything

```
POST /api/getUsers
POST /api/deleteUser
POST /api/updateUser
```

Prefer the appropriate HTTP method.

---

### ❌ Mistake 3: Putting filters into the path unnecessarily

Instead of:

```
/api/users/role/admin
```

a collection filter can often be:

```
/api/users?role=admin
```

---

### ❌ Mistake 4: Excessive nesting

Avoid unnecessarily complicated paths such as:

```
/api/users/10/orders/20/items/5/reviews
```

when a flatter resource structure would work.

---

### ❌ Mistake 5: Inconsistent naming

```
/api/users
/api/Product
/api/get_orders
/api/customerData
```

Choose one clear convention.

# 40. Path Parameters vs Query Parameters

Keep this table handy:

|Feature|Path Parameter|Query Parameter|
|---|---|---|
|Example|`/users/10`|`/users?role=admin`|
|Purpose|Identify resource|Filter/modify retrieval|
|Required?|Often|Usually optional|
|Flask access|Route variable|`request.args`|
|Example|`user_id=10`|`role=admin`|

### Easy rule

> **Path = which resource?**

> **Query = which subset/how should I retrieve it?**

# 41. REST Endpoint Mental Model 🧠

Think of an API as a **city map**:

```
                    API
                     │
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      users       products      orders
        │            │            │
        ↓            ↓            ↓
     /users       /products     /orders
        │
        ↓
      /10
        │
        ↓
   Specific User
```

Then HTTP methods tell you what you're doing at that address:

```
GET       → Look
POST      → Create
PUT       → Replace
PATCH     → Modify
DELETE    → Remove
```

And query parameters refine the request:

```
/api/products?category=books&page=2
```

So the formula is:

```
Endpoint Design
=
Resource
+
HTTP Method
+
Path Parameters
+
Query Parameters
```
