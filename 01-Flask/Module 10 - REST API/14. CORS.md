**CORS** is one of the most important concepts when connecting a frontend application such as React with a Flask REST API.

You may have a situation like this:

```
React Frontend
http://localhost:5173
        ↓
        API Request
        ↓
Flask Backend
http://localhost:5000
```

The browser may block the request because these are **different origins**.

That is where CORS comes in.

> **Golden Rule:** CORS controls which browser origins are allowed to make cross-origin requests to your API.

---

# 1. What Is CORS?

**CORS** stands for:

> **Cross-Origin Resource Sharing**

It is a browser security mechanism that controls whether a webpage can request resources from a different origin.

For example:

```
Frontend:
http://localhost:5173

Backend:
http://localhost:5000
```

These are different origins because their ports are different.

Without appropriate CORS configuration, the browser may block the frontend from accessing the API response.

---

# 2. Why Does CORS Exist?

Imagine a user logs into:

```
https://bank.example
```

and the browser stores their authentication information.

Now imagine a malicious website:

```
https://evil.example
```

trying to make requests to:

```
https://bank.example/api/account
```

The browser needs a security mechanism to prevent arbitrary websites from freely reading responses from other websites.

CORS is part of that browser security model.

Think of it as a **bouncer at the API door**:

```
Browser
   ↓
"I came from http://localhost:5173"
   ↓
API
   ↓
"Is that origin allowed?"
   ↓
YES → Browser can expose response
NO  → Browser blocks access
```

---

# 3. What Is an Origin?

This is extremely important.

An origin consists of:

```
Scheme + Host + Port
```

For example:

```
http://localhost:5000
```

contains:

```
Scheme → http
Host   → localhost
Port   → 5000
```

Another:

```
https://example.com
```

contains:

```
Scheme → https
Host   → example.com
Port   → 443
```

---

# 4. When Are Two URLs Different Origins?

Consider:

```
http://localhost:5000
http://localhost:5001
```

Different ports:

```
5000 ≠ 5001
```

Therefore:

```
Different origin
```

---

Consider:

```
http://localhost:5000
https://localhost:5000
```

Different schemes:

```
http ≠ https
```

Therefore:

```
Different origin
```

---

Consider:

```
https://example.com
https://api.example.com
```

Different hosts:

```
example.com ≠ api.example.com
```

Therefore:

```
Different origin
```

---

# 5. Same-Origin Example

These are the same origin:

```
https://example.com/products
https://example.com/users
https://example.com/api/products
```

They all use:

```
https
example.com
same port
```

The **path does not define the origin**.

So:

```
https://example.com/products
https://example.com/api/products
```

have the same origin.

---

# 6. Different Origin Example

These are different:

```
http://localhost:5173
http://localhost:5000
```

Even though:

```
localhost
```

is the same, the ports differ.

This is one of the most common situations when developing:

```
React
   ↓
localhost:5173

Flask
   ↓
localhost:5000
```

---

# 7. What Does CORS Actually Do?

Suppose React sends:

```
GET /api/products
Origin: http://localhost:5173
```

The Flask server can respond with:

```
Access-Control-Allow-Origin: http://localhost:5173
```

The browser sees:

```
Requested origin:
http://localhost:5173

Allowed origin:
http://localhost:5173

        ↓

       MATCH
        ↓

Allow frontend to access response
```

If the server doesn't allow that origin, the browser prevents JavaScript from accessing the cross-origin response.

---

# 8. CORS Is Mainly a Browser Concern

This is an important distinction.

CORS is enforced by **web browsers**.

For example:

```
React
 ↓
Browser
 ↓
Flask API
```

The browser applies the CORS rules.

But if you use something like:

```
Python requests
```

directly from a server, CORS doesn't work in the same browser-enforced way.

For example:

```
import requests

response = requests.get(
    "http://localhost:5000/api/products"
)
```

Python isn't a browser, so the browser's CORS enforcement doesn't apply.

Therefore:

> **CORS is not an authentication or authorization mechanism.**

---

# 9. CORS vs Authentication

These are completely different concepts.

### CORS

Controls:

```
Which browser origins may access the response?
```

### Authentication

Controls:

```
Who is the user?
```

### Authorization

Controls:

```
What is the user allowed to do?
```

So:

```
CORS
 ↓
Browser origin policy

Authentication
 ↓
Identity

Authorization
 ↓
Permissions
```

CORS does **not** replace JWT, sessions, roles, or permissions.

---

# 10. Installing Flask-CORS

The easiest way to configure CORS in Flask is the `Flask-CORS` extension.

Install:

```
pip install Flask-CORS
```

Then:

```
from flask import Flask
from flask_cors import CORS

app = Flask(__name__)

CORS(app)
```

Now Flask allows cross-origin requests according to Flask-CORS's configuration.

---

# 11. Allow a Specific Origin

Instead of allowing every origin, you can specify one.

```
from flask_cors import CORS

CORS(
    app,
    origins=["http://localhost:5173"]
)
```

Now:

```
http://localhost:5173
```

is allowed.

This is generally better than opening your API to every browser origin.

---

# 12. Allow Multiple Origins

You may have:

```
Development frontend:
http://localhost:5173

Production frontend:
https://frontend.example.com
```

You can configure:

```
CORS(
    app,
    origins=[
        "http://localhost:5173",
        "https://frontend.example.com"
    ]
)
```

Now both are allowed.

---

# 13. Allow CORS Only for API Routes

Suppose your Flask application contains:

```
/
 /login
 /dashboard
 /api/products
 /api/users
```

You may only want CORS on API routes.

For example:

```
CORS(
    app,
    resources={
        r"/api/*": {
            "origins": "http://localhost:5173"
        }
    }
)
```

Conceptually:

```
/api/products → CORS enabled
/api/users    → CORS enabled

/             → not necessarily configured for CORS
```

This can be cleaner for applications containing both web pages and APIs.

---

# 14. The `Origin` Header

Browsers can send:

```
Origin: http://localhost:5173
```

This tells the server:

> "This request originated from this web origin."

The server can respond:

```
Access-Control-Allow-Origin: http://localhost:5173
```

The browser checks the response.

Conceptually:

```
Browser
   │
   │ Origin: http://localhost:5173
   ↓
Flask
   │
   │ Access-Control-Allow-Origin:
   │ http://localhost:5173
   ↓
Browser
   │
   ↓
Allow / Block
```

---

# 15. `Access-Control-Allow-Origin`

This is one of the most important CORS response headers.

Example:

```
Access-Control-Allow-Origin: http://localhost:5173
```

It tells the browser that the specified origin is allowed to access the response.

---

# 16. Wildcard `*`

You may see:

```
Access-Control-Allow-Origin: *
```

This means the server allows cross-origin access broadly.

In Flask:

```
CORS(app, resources={
    r"/api/*": {
        "origins": "*"
    }
})
```

This can be useful for genuinely public APIs.

But don't automatically use:

```
CORS(app)
```

or:

```
origins="*"
```

for every production application.

For private APIs, explicitly define allowed origins when practical.

---

# 17. CORS Request Types

CORS requests can broadly involve:

### Simple requests

Some requests can be sent without a separate preflight request.

For example:

```
GET /api/products
Origin: http://localhost:5173
```

---

### Preflighted requests

Some cross-origin requests require the browser to ask permission first.

The browser sends:

```
OPTIONS /api/products
```

This is called a:

> **Preflight request**

---

# 18. What Is a Preflight Request?

Suppose React wants to send:

```
PATCH /api/products/10
```

with:

```
Content-Type: application/json
Authorization: Bearer <token>
```

The browser may first send:

```
OPTIONS /api/products/10
```

with headers describing the intended request.

Conceptually:

```
Browser
   ↓
"Can I send this PATCH request?"
   ↓
OPTIONS
   ↓
Flask
   ↓
"Yes, this origin/method/header is allowed."
   ↓
Browser
   ↓
PATCH
   ↓
Flask
```

---

# 19. Why Does the Browser Do This?

The browser wants to determine whether the server permits the intended cross-origin operation before sending certain potentially impactful requests.

This helps prevent websites from freely performing cross-origin operations that the target server has not opted into.

---

# 20. `OPTIONS` Method

The preflight commonly uses:

```
OPTIONS
```

It can ask about:

- Allowed origin
- Allowed HTTP methods
- Allowed headers

For example:

```
Access-Control-Request-Method: PATCH
Access-Control-Request-Headers: Content-Type, Authorization
```

The server can respond with:

```
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
```

Then the browser can send the actual request if the CORS policy permits it.

---

# 21. Allowing HTTP Methods

You can configure:

```
CORS(
    app,
    resources={
        r"/api/*": {
            "origins": "http://localhost:5173",
            "methods": [
                "GET",
                "POST",
                "PUT",
                "PATCH",
                "DELETE"
            ]
        }
    }
)
```

This tells Flask-CORS which methods should be allowed for cross-origin API requests.

---

# 22. Allowing Headers

Suppose your frontend sends:

```
Content-Type: application/json
Authorization: Bearer token
```

You may configure:

```
CORS(
    app,
    resources={
        r"/api/*": {
            "origins": "http://localhost:5173",
            "allow_headers": [
                "Content-Type",
                "Authorization"
            ]
        }
    }
)
```

The browser can then complete the CORS exchange when those headers are allowed.

---

# 23. Credentials and CORS

This is an important advanced concept.

Suppose your API uses cookies or session authentication.

The frontend may need to send credentials.

For example, JavaScript:

```
fetch("http://localhost:5000/api/profile", {
    credentials: "include"
});
```

The server can configure credential support:

```
CORS(
    app,
    supports_credentials=True,
    origins=["http://localhost:5173"]
)
```

Now the browser can participate in credentialed cross-origin requests when the rest of the cookie/CORS policy is correctly configured.

---

# 24. Important Wildcard + Credentials Rule

You generally cannot use:

```
Access-Control-Allow-Origin: *
```

together with credentialed cross-origin requests.

So this is problematic:

```
CORS(
    app,
    origins="*",
    supports_credentials=True
)
```

Instead, specify the actual allowed origins:

```
CORS(
    app,
    origins=["http://localhost:5173"],
    supports_credentials=True
)
```

This is one reason explicit origins are important for private applications.

---

# 25. CORS With JWT

Suppose your API uses JWT authentication.

React sends:

```
Authorization: Bearer eyJ...
```

CORS needs to allow the browser to send the `Authorization` header when the request requires preflight.

Example:

```
CORS(
    app,
    resources={
        r"/api/*": {
            "origins": "http://localhost:5173",
            "allow_headers": ["Content-Type", "Authorization"]
        }
    }
)
```

The overall flow becomes:

```
React
 ↓
Browser
 ↓
CORS check
 ↓
JWT request
 ↓
Flask
 ↓
Verify JWT
 ↓
Authorization
 ↓
Database
 ↓
JSON response
```

Notice:

```
CORS ≠ JWT
```

CORS controls browser access.

JWT authenticates the API request.

---

# 26. CORS With Flask Sessions

If you use Flask sessions with cookies across origins, CORS and cookie settings need to work together.

Example:

```
CORS(
    app,
    origins=["http://localhost:5173"],
    supports_credentials=True
)
```

You may also need appropriate cookie configuration, such as:

```
app.config["SESSION_COOKIE_HTTPONLY"] = True
app.config["SESSION_COOKIE_SECURE"] = True
```

Cookie `SameSite` behavior also matters for cross-site scenarios.

The exact cookie configuration depends on whether the frontend and backend are same-site, cross-site, using HTTPS, and how authentication is designed.

---

# 27. CORS Does Not Protect Your API From Direct Requests

This is a very important security point.

Suppose your API has:

```
DELETE /api/products/10
```

CORS does **not** mean that only your frontend can call it.

A person can use:

```
curl
Postman
Python requests
another backend
```

to send requests directly.

Therefore:

```
CORS
  ↓
Browser access control

Authentication
  ↓
Identity verification

Authorization
  ↓
Permission verification
```

Your API still needs authentication and authorization.

---

# 28. Example: Flask + React

Suppose:

```
React:
http://localhost:5173

Flask:
http://localhost:5000
```

Flask:

```
from flask import Flask, jsonify
from flask_cors import CORS

app = Flask(__name__)

CORS(
    app,
    resources={
        r"/api/*": {
            "origins": "http://localhost:5173"
        }
    }
)


@app.get("/api/products")
def get_products():

    return jsonify({
        "success": True,
        "data": [
            {
                "id": 1,
                "name": "Laptop"
            },
            {
                "id": 2,
                "name": "Keyboard"
            }
        ]
    })
```

React:

```
fetch("http://localhost:5000/api/products")
    .then(response => response.json())
    .then(data => {
        console.log(data);
    });
```

The browser sees:

```
Frontend origin
http://localhost:5173

Allowed by Flask
http://localhost:5173

        ↓

CORS passes
        ↓

React receives JSON
```

# 29. Common CORS Error

You may see a browser console error similar to:

```
Access to fetch at 'http://localhost:5000/api/products'
from origin 'http://localhost:5173'
has been blocked by CORS policy.
```

This means the browser's CORS checks were not satisfied.

Possible causes include:

```
Wrong allowed origin
Missing CORS headers
Preflight failure
Method not allowed
Custom header not allowed
Credential configuration problem
```

---

# 30. How to Debug CORS

When you see a CORS error, check these things.

### Step 1: Check frontend origin

For example:

```
http://localhost:5173
```

Make sure you haven't configured:

```
http://localhost:3000
```

by mistake.

---

### Step 2: Check backend URL

Make sure React is actually calling:

```
http://localhost:5000
```

and not another port.

---

### Step 3: Check HTTP method

If you're sending:

```
PATCH
```

make sure your CORS configuration permits it.

---

### Step 4: Check headers

If sending:

```
Authorization
Content-Type
```

make sure the server's CORS configuration handles them appropriately.

---

### Step 5: Check preflight

Open browser DevTools:

```
Network
   ↓
OPTIONS request
```

Look at:

```
Status code
Response headers
Request headers
```

If the OPTIONS request fails, the actual request may never happen.

---

# 31. CORS and `Content-Type: application/json`

A frontend commonly sends:

```
fetch("http://localhost:5000/api/products", {
    method: "POST",
    headers: {
        "Content-Type": "application/json"
    },
    body: JSON.stringify({
        name: "Laptop",
        price: 50000
    })
});
```

Because of the request characteristics, the browser may perform a preflight.

The server must be configured so that the CORS policy permits the origin, method, and relevant headers.

This is why you may see:

```
OPTIONS
```

before:

```
POST
```

in DevTools.

# 33. Development vs Production

During development, you might have:

```
http://localhost:5173
```

But after deployment:

```
https://frontend.example.com
```

Your production CORS configuration should use the real production origin.

For example:

```
CORS(
    app,
    resources={
        r"/api/*": {
            "origins": [
                "https://frontend.example.com"
            ]
        }
    }
)
```

Don't accidentally leave development origins as your only production configuration.

---

# 34. Environment-Based CORS

A better approach is often to configure origins through environment variables.

For example:

```
import os

allowed_origins = os.getenv(
    "FRONTEND_ORIGIN",
    "http://localhost:5173"
)

CORS(
    app,
    resources={
        r"/api/*": {
            "origins": allowed_origins
        }
    }
)
```

Development:

```
FRONTEND_ORIGIN=http://localhost:5173
```

Production:

```
FRONTEND_ORIGIN=https://frontend.example.com
```

This prevents hardcoding deployment-specific configuration into your application code.

# 35. CORS and Reverse Proxies

In production, your Flask API might sit behind:

```
Browser
   ↓
CDN / Reverse Proxy
   ↓
Nginx
   ↓
Flask
```

CORS headers may be handled by:

- Flask
- Nginx
- API gateway
- Cloud infrastructure

Be careful not to configure conflicting CORS policies in multiple layers.

You generally want one clear policy.

# 36. Common Mistakes

### ❌ Mistake 1: Using `*` everywhere

```
CORS(app)
```

or:

```
origins="*"
```

may be too permissive for a private application.

Prefer specific origins where appropriate.

---

### ❌ Mistake 2: Thinking CORS is authentication

Wrong:

```
CORS = security/authentication
```

Correct:

```
CORS = browser cross-origin access control
```

---

### ❌ Mistake 3: Forgetting the port

These are different origins:

```
http://localhost:3000
http://localhost:5173
```

---

### ❌ Mistake 4: Forgetting HTTPS

These are also different:

```
http://example.com
https://example.com
```

---

### ❌ Mistake 5: Ignoring OPTIONS

If your browser sends:

```
OPTIONS
```

don't automatically think something is broken.

It may be a legitimate CORS preflight request.

---

### ❌ Mistake 6: Allowing an origin from user input

Don't blindly reflect arbitrary origins.

Bad conceptual approach:

```
origin = request.headers.get("Origin")

# blindly allow it
```

Allowed origins should come from trusted configuration.

---

### ❌ Mistake 7: Fixing CORS when the actual problem is authentication

For example:

```
401 Unauthorized
```

is not automatically a CORS problem.

Check the actual network response and browser console carefully.

---

# 38. CORS + Authentication + Authorization

These three concepts are easy to confuse.

```
                   API REQUEST
                        ↓
              ┌──────────────────┐
              │      CORS        │
              │ Browser policy   │
              └────────┬─────────┘
                       ↓
              ┌──────────────────┐
              │ Authentication   │
              │ Who are you?     │
              └────────┬─────────┘
                       ↓
              ┌──────────────────┐
              │ Authorization    │
              │ What can you do? │
              └────────┬─────────┘
                       ↓
                 Business Logic
                       ↓
                    Database
```

Each solves a different problem.

# 39. Practical Flask Configuration

For a typical React + Flask API during development:

```
from flask import Flask
from flask_cors import CORS

app = Flask(__name__)

CORS(
    app,
    resources={
        r"/api/*": {
            "origins": [
                "http://localhost:5173"
            ],
            "methods": [
                "GET",
                "POST",
                "PUT",
                "PATCH",
                "DELETE"
            ],
            "allow_headers": [
                "Content-Type",
                "Authorization"
            ]
        }
    }
)
```

This says:

```
API routes:
    /api/*

Allowed frontend:
    http://localhost:5173

Allowed methods:
    GET
    POST
    PUT
    PATCH
    DELETE

Allowed headers:
    Content-Type
    Authorization
```

For a JWT-based API, this is a useful development configuration.

# 40. CORS Checklist

Before deploying a frontend + Flask API, check:

```
□ What is the frontend origin?
□ What is the backend origin?
□ Are they different origins?
□ Is the frontend origin explicitly allowed?
□ Are required HTTP methods allowed?
□ Are required headers allowed?
□ Does preflight OPTIONS work?
□ Are credentials required?
□ If credentials are used, is the origin explicit?
□ Are cookies configured correctly?
□ Is HTTPS used in production?
□ Are development origins removed/restricted in production?
□ Is CORS being confused with authentication?
□ Is the API still protected by authentication/authorization?
```

# 42. The Most Important Things to Remember

### 1. Origin includes the port

```
http://localhost:3000
            ≠
http://localhost:5173
```

### 2. CORS is mainly enforced by browsers

```
Browser → CORS rules apply
Python requests → browser CORS enforcement doesn't apply
```

### 3. CORS isn't authentication

```
CORS → Can this browser origin access the response?
JWT/session → Who is making the request?
Authorization → What can they do?
```

### 4. Preflight is normal

```
OPTIONS
   ↓
Permission check
   ↓
Actual request
```

### 5. Don't blindly allow every origin

For private APIs, prefer explicitly configured trusted origins.
