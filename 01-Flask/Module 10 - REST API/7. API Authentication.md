API authentication is the process of **verifying who is making an API request**.

When an API contains private data or actions, the server needs to answer:

> **“Who is this client/user, and are they allowed to access this API?”**

This topic is especially important because the next topic, **10.8 JWT Authentication**, will build directly on these concepts.

---

# 1. What is API Authentication?

**API Authentication** means verifying the identity of the client or user sending an API request.

For example, suppose we have:

```
GET /api/profile
```

A public API might allow anyone to access it.

But a private profile API should require authentication:

```
Client
   ↓
GET /api/profile
   +
Authentication credentials
   ↓
Flask
   ↓
Verify identity
   ↓
Return profile
```

Without valid authentication:

```
401 Unauthorized
```

---

# 2. Authentication vs Authorization

These two concepts are closely related but different.

|Concept|Question|
|---|---|
|Authentication|Who are you?|
|Authorization|What are you allowed to do?|

Example:

```
User logs in
    ↓
Authentication
    ↓
User = Sudip
    ↓
Authorization
    ↓
Role = Manager
    ↓
Can access reports
    ↓
Cannot delete system users
```

### Simple memory trick

```
Authentication → Identity
Authorization  → Permission
```

---

# 3. Why Does an API Need Authentication?

Consider an API:

```
GET /api/users
```

Without authentication, anyone could potentially request user information.

For example:

```
Browser
   ↓
GET /api/users
   ↓
Server
   ↓
All users returned
```

That can expose private information.

With authentication:

```
Browser
   ↓
GET /api/users
   +
Valid credentials
   ↓
Server
   ↓
Verify user
   ↓
Return data
```

Authentication protects APIs from unauthorized access.

---

# 4. Public vs Protected API

APIs can generally be divided into two categories.

## Public API

Does not require authentication.

```
GET /api/products
```

Example:

```
@app.get("/api/products")
def get_products():
    return {
        "products": [
            {"id": 1, "name": "Laptop"},
            {"id": 2, "name": "Mouse"}
        ]
    }
```

Anyone can request it.

---

## Protected API

Requires authentication.

```
GET /api/profile
Authorization: ...
```

The server checks the authentication information before returning the data.

```
Request
   ↓
Authentication check
   ↓
Valid?
 ┌───┴───┐
Yes      No
 ↓        ↓
Data     401
```

# 5. Common API Authentication Methods

There are several ways APIs can authenticate clients.

|Method|Common use|
|---|---|
|Session / Cookie Authentication|Traditional web applications|
|API Keys|Application-to-application APIs|
|Basic Authentication|Simple internal/limited APIs|
|Bearer Tokens|Token-based APIs|
|JWT|Modern token-based APIs|
|OAuth 2.0|Delegated access and third-party authentication|

For Flask development, the most important ones to understand are:

```
Session Authentication
        ↓
Token Authentication
        ↓
JWT Authentication
```

# 6. Session-Based API Authentication

Flask already provides session support.

A user logs in:

```
POST /api/login
```

The server verifies the credentials and creates a session.

```
session["user_id"] = user.id
```

Later, the client requests:

```
GET /api/profile
```

The browser sends the session cookie.

Flask can then identify the user.

---

# 7. Simple Session Authentication Example

First:

```
from flask import Flask, session, jsonify

app = Flask(__name__)

app.config["SECRET_KEY"] = "change-this-secret-key"
```

Login:

```
@app.post("/api/login")
def login():
    # Normally credentials would be verified here

    user_id = 10

    session["user_id"] = user_id

    return jsonify({
        "message": "Login successful"
    })
```

Protected API:

```
@app.get("/api/profile")
def profile():

    user_id = session.get("user_id")

    if user_id is None:
        return jsonify({
            "error": "Authentication required"
        }), 401

    return jsonify({
        "user_id": user_id,
        "name": "Example User"
    })
```

---

# 8. How This Works

The login process:

```
POST /api/login
       ↓
Check email/password
       ↓
Credentials valid?
       ↓
Create session
       ↓
session["user_id"] = 10
       ↓
Login successful
```

Later:

```
GET /api/profile
       ↓
Read session
       ↓
user_id = 10
       ↓
Find user
       ↓
Return profile
```

If there is no session:

```
GET /api/profile
       ↓
No user_id
       ↓
401 Unauthorized
```

---

# 9. Session Authentication for Browser Applications

Session authentication is very useful when your API and frontend are closely connected.

Example:

```
Browser
   ↓
Flask application
   ↓
Session Cookie
```

The browser automatically sends the cookie with requests when appropriate.

This makes sessions convenient for traditional web applications.

---

# 10. Token-Based Authentication

Another approach is **token authentication**.

Instead of relying primarily on a session cookie, the server gives the client a token after successful login.

Example:

```
POST /api/login
       ↓
Email + Password
       ↓
Flask verifies credentials
       ↓
Generate token
       ↓
Return token
```

Response:

```
{
    "message": "Login successful",
    "access_token": "abc123..."
}
```

The client can then use that token for protected requests.

---

# 11. Sending a Token with an API Request

A common approach is the `Authorization` header.

```
GET /api/profile
Authorization: Bearer abc123...
```

The structure is:

```
Authorization:
    Bearer <token>
```

For example:

```
Authorization: Bearer eyJhbGciOi...
```

The server extracts the token:

```
Request
   ↓
Authorization header
   ↓
Bearer token
   ↓
Verify token
   ↓
Identify user
   ↓
Allow request
```

This is the foundation for JWT authentication.

---

# 12. Why Use Tokens?

Tokens are particularly useful when different clients communicate with the same API.

For example:

```
             ┌── Web App
             │
             ├── Android App
             │
             ├── iOS App
             │
             └── Other Client
                    ↓
                Flask API
```

Each client can authenticate using a token.

This is one reason token-based authentication is common in modern APIs.

---

# 13. Session vs Token Authentication

|Feature|Session|Token|
|---|---|---|
|Authentication state|Server/session mechanism|Token|
|Commonly sent|Cookie|Authorization header|
|Browser support|Excellent|Excellent|
|Mobile/API clients|Possible|Very common|
|Server-side session storage|Often involved|Not necessarily|
|JWT compatible|Not required|Yes|
|Useful for separate frontend/API|Possible|Very common|

Neither approach is universally "better".

The correct choice depends on the application architecture.

# 14. API Keys

Another authentication mechanism is an **API key**.

Example:

```
GET /api/products
X-API-Key: abc123xyz
```

The server checks:

```
API key
   ↓
Is it valid?
   ↓
Yes → Allow
No  → Reject
```

API keys are commonly used to identify an **application or client**, rather than a logged-in end user.

For example:

```
Weather Application
       ↓
API Key
       ↓
Weather API
```

API keys are common in service-to-service APIs.

---

# 15. API Key vs User Authentication

Suppose an application has:

```
User A
User B
User C
```

A single API key might identify the application:

```
My Application
       ↓
API Key
       ↓
External API
```

But user authentication identifies individual users:

```
User A → Token A
User B → Token B
User C → Token C
```

Therefore:

```
API Key
→ Usually identifies an application/client

User Token
→ Usually identifies an authenticated user
```

---

# 16. Basic Authentication

HTTP Basic Authentication sends credentials through the `Authorization` header.

Conceptually:

```
Authorization: Basic <encoded-credentials>
```

The credentials represent:

```
username + password
```

Basic Authentication should only be used with **HTTPS**, because encoding is not encryption.

It is generally less suitable for modern user-facing applications than stronger token/session approaches.

---

# 17. OAuth 2.0

OAuth 2.0 is an authorization framework used when one application needs delegated access to another service.

A common example:

```
Your Application
       ↓
Google/Microsoft/etc.
       ↓
User grants permission
       ↓
Application receives authorization
```

OAuth 2.0 is broader than simply "logging in".

For this Flask course, remember the basic distinction:

```
Session
→ Browser session

API Key
→ Identify application/client

JWT
→ Token-based authentication

OAuth 2.0
→ Delegated authorization
```

You don't need to master OAuth 2.0 before learning JWT.

---

# 18. Protecting an API Endpoint

A protected API generally follows this structure:

```
@app.get("/api/profile")
def profile():

    # Authentication check
    if not authenticated():
        return jsonify({
            "error": "Authentication required"
        }), 401

    # Protected logic
    return jsonify({
        "name": "Example User"
    })
```

The important idea is:

```
Request
   ↓
Authentication
   ↓
Valid?
   ↓
Authorization
   ↓
Business logic
   ↓
Response
```

Don't put the business logic first and authentication afterward. By then, the castle gate is guarding the garden shed. 🏰

---

# 19. 401 Unauthorized

`401` means the request does not have valid authentication.

Examples:

```
No token
Invalid token
Expired token
Invalid credentials
Missing authentication
```

Response:

```
{
    "error": "Authentication required"
}
```

Status:

```
401 Unauthorized
```

---

# 20. 403 Forbidden

`403` is different.

The user is authenticated, but they don't have permission.

Example:

```
User
 ↓
Authenticated
 ↓
Role = staff
 ↓
Requests admin-only API
 ↓
403 Forbidden
```

Example:

```
{
    "error": "You do not have permission to perform this action"
}
```

### Remember

```
401 → Who are you?
      Authentication problem

403 → I know who you are,
      but you cannot do this.
```

# 22. Authentication Should Happen Before Authorization

A good mental model is:

```
                 Request
                    ↓
            Authentication
                    ↓
             Who is this?
                    ↓
              User found
                    ↓
            Authorization
                    ↓
          What can they do?
                    ↓
             API operation
                    ↓
               Response
```

For example:

```
GET /api/users/10
        ↓
Is the requester authenticated?
        ↓
Yes
        ↓
Is the requester allowed to read this user?
        ↓
Yes
        ↓
Return user
```

# 23. Never Trust the Client

One of the most important API security rules:

> **Never trust information supplied by the client.**

For example, don't do this:

```
{
    "user_id": 10,
    "role": "admin"
}
```

and simply assume:

```
role = data["role"]
```

A malicious client could send:

```
{
    "user_id": 10,
    "role": "admin"
}
```

even if they aren't an administrator.

The server must determine identity and permissions from trusted authentication information.

```
Client
  ↓
"I am admin"
  ↓
❌ Don't trust blindly

Authentication system
  ↓
Actual authenticated identity
  ↓
Server checks role
  ↓
Permission decision
```

---

# 24. Never Put Passwords in URLs

Bad:

```
/api/login?email=user@example.com&password=123456
```

URLs can appear in logs, browser history, monitoring systems, and other places.

Instead, send credentials in an appropriate request body:

```
POST /api/login
Content-Type: application/json
```

```
{
    "email": "user@example.com",
    "password": "123456"
}
```

And always use **HTTPS** in production.

---

# 25. Authentication Security Rules

Keep these rules in your mental toolbox:

### 1. Use HTTPS

Never send credentials or authentication tokens over plain HTTP in production.

### 2. Never store plaintext passwords

Use password hashing.

```
generate_password_hash(password)
```

### 3. Don't log passwords

Avoid:

```
print(password)
```

and don't include passwords in application logs.

### 4. Protect tokens

Treat tokens like sensitive credentials.

### 5. Use expiration where appropriate

Tokens should generally have controlled lifetimes.

### 6. Validate authentication on the server

Never rely only on frontend checks.

### 7. Return correct status codes

```
401 → Authentication problem
403 → Authorization problem
```

# 26. Authentication Middleware / Decorators

When many APIs require authentication, we don't want to repeat this:

```
user_id = ...
if user_id is None:
    ...
```

on every route.

Instead, we can create a decorator.

Conceptually:

```
@app.get("/api/profile")
@login_required
def profile():
    ...
```

The decorator handles authentication before the route executes.

Flow:

```
Request
   ↓
@login_required
   ↓
Authentication check
   ↓
Valid?
 ┌───┴───┐
No      Yes
 ↓        ↓
401     Route
```

This becomes particularly useful when implementing JWT authentication.

---

# 27. A Simple Authentication Decorator

Using Flask sessions:

```
from functools import wraps
from flask import session, jsonify

def login_required(view):

    @wraps(view)
    def wrapped_view(*args, **kwargs):

        user_id = session.get("user_id")

        if user_id is None:
            return jsonify({
                "error": "Authentication required"
            }), 401

        return view(*args, **kwargs)

    return wrapped_view
```

Use it:

```
@app.get("/api/profile")
@login_required
def profile():

    return jsonify({
        "message": "Welcome to your profile"
    })
```

Now the authentication logic is reusable.

---

# 28. Authentication Decorator Flow

```
GET /api/profile
       ↓
@login_required
       ↓
Check authentication
       ↓
 ┌─────┴─────┐
 ↓           ↓
Invalid     Valid
 ↓           ↓
401       profile()
             ↓
          Response
```

Later, the same idea can be used with JWT:

```
@jwt_required()
def profile():
    ...
```

The exact implementation depends on the JWT library being used.

# 29. Session Authentication vs JWT

This distinction is especially important for your next topic.

### Session

```
Login
 ↓
Server creates session
 ↓
Client receives cookie
 ↓
Client sends cookie
 ↓
Server checks session
```

### JWT

```
Login
 ↓
Server generates JWT
 ↓
Client receives token
 ↓
Client sends Bearer token
 ↓
Server verifies JWT
```

So:

```
Session
→ Cookie + session

JWT
→ Token + Authorization header
```

# 30. What is JWT?

You only need a preview for now.

**JWT** stands for:

> **JSON Web Token**

It is a compact token format commonly used for authentication and authorization between clients and APIs.

Example:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

A client might send:

```
Authorization: Bearer eyJhbGciOi...
```

The Flask server verifies the token and obtains trusted claims from it.

We'll study exactly how this works in **10.8 JWT Authentication**.

# 33. Important Headers

### Content-Type

Tells the server what format the request body uses.

```
Content-Type: application/json
```

### Authorization

Used for authentication credentials such as bearer tokens.

```
Authorization: Bearer <token>
```

These two headers have different jobs:

```
Content-Type
→ What is the request body?

Authorization
→ Who is making the request?
```

# 34. Common Mistakes

### ❌ Mistake 1: Confusing authentication and authorization

```
Authentication ≠ Authorization
```

### ❌ Mistake 2: Protecting only the frontend

Hiding an admin button isn't security.

```
Frontend restriction
      ↓
Not enough
```

The backend API must enforce access.

### ❌ Mistake 3: Returning 403 for unauthenticated users

Usually:

```
Not authenticated → 401
Authenticated but forbidden → 403
```

### ❌ Mistake 4: Sending passwords in URLs

Avoid it.

### ❌ Mistake 5: Storing plaintext passwords

Never do this.

### ❌ Mistake 6: Trusting client-provided roles

Never trust:

```
{
    "role": "admin"
}
```

just because the client says so.

### ❌ Mistake 7: Forgetting HTTPS

Authentication credentials and tokens must be protected in transit.
