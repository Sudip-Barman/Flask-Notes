REST API is one of the most important concepts when building a backend that communicates with a frontend, mobile application, or another service.

Since you already learned **Flask, MySQL, SQLAlchemy, authentication, roles, and permissions**, this topic connects those concepts together.

---

## 1. What is an API?

**API** stands for **Application Programming Interface**.

An API allows two software systems to communicate with each other.

For example:

```
React Frontend
      ↓
     API
      ↓
Flask Backend
      ↓
   Database
```

The frontend doesn't need to directly access the database.

Instead, it asks the Flask backend for data.

Example:

```
Frontend:
"Give me all products"

        ↓

GET /api/products

        ↓

Flask:
"Let me get the products from the database."

        ↓

Database

        ↓

Flask returns JSON

        ↓

Frontend receives data
```

---

# 2. What is a REST API?

**REST** stands for:

> **Representational State Transfer**

A **REST API** is an API designed around REST principles and HTTP.

In a REST API, things are treated as **resources**.

Examples of resources:

```
Users
Products
Orders
Students
Courses
Books
```

Each resource gets a URL.

For example:

```
/api/users
/api/products
/api/orders
/api/students
```

---

# 3. What is a Resource?

A **resource** is a piece of data or an object that the API manages.

Suppose we have a product:

```
{
    "id": 10,
    "name": "Laptop",
    "price": 55000
}
```

The product is a resource.

Its endpoint could be:

```
/api/products/10
```

Here:

```
/api/products → Collection of products

/api/products/10 → One specific product
```

This is a very important REST concept.

---

# 4. Client and Server

REST normally follows a **client-server architecture**.

### Client

The client is the application making the request.

Examples:

```
React
Android App
iOS App
Web Browser
Postman
Another Backend
```

### Server

The server receives the request and processes it.

In your case:

```
Flask
```

So:

```
Client
  ↓
HTTP Request
  ↓
Flask Server
  ↓
Database
  ↓
Flask Server
  ↓
HTTP Response
  ↓
Client
```

---

# 5. REST API Request-Response Cycle

Every API interaction generally follows:

```
Client
   ↓
HTTP Request
   ↓
Flask Route
   ↓
Business Logic
   ↓
Database
   ↓
Flask
   ↓
HTTP Response
   ↓
Client
```

For example:

```
GET /api/products
```

Flask receives it:

```
@app.route("/api/products")
def products():
    ...
```

Flask gets data from the database and returns:

```
[
    {
        "id": 1,
        "name": "Laptop"
    },
    {
        "id": 2,
        "name": "Phone"
    }
]
```

# 6. REST Uses HTTP

REST APIs commonly use HTTP because HTTP already provides methods for interacting with resources.

The most important methods are:

|Method|Purpose|
|---|---|
|`GET`|Read data|
|`POST`|Create data|
|`PUT`|Replace/update data|
|`PATCH`|Partially update data|
|`DELETE`|Delete data|

Example:

```
GET     /api/products
POST    /api/products
GET     /api/products/10
PUT     /api/products/10
PATCH   /api/products/10
DELETE  /api/products/10
```

We'll study these methods separately in the next topic.

---

# 7. REST Endpoint

An **endpoint** is a specific URL through which an API provides access to a resource or operation.

Example:

```
/api/products
```

This could represent the products collection.

Another:

```
/api/products/10
```

represents product `10`.

Think:

```
/api/products
      ↓
All products

/api/products/10
      ↓
Product with ID 10
```

---

# 8. Collection vs Individual Resource

This is an important REST pattern.

### Collection

```
/api/users
```

Represents the collection of users.

### Individual resource

```
/api/users/15
```

Represents one user.

Therefore:

```
/api/users
      ↓
Collection

/api/users/15
      ↓
Individual resource
```

---

# 9. REST URLs Should Represent Resources

A common beginner mistake is putting actions directly into URLs.

For example:

```
/api/getUsers
/api/createUser
/api/deleteUser
```

A more RESTful design is:

```
/api/users
```

Then the HTTP method tells the server what action is being requested.

```
GET    /api/users
       ↓
Get users

POST   /api/users
       ↓
Create user

DELETE /api/users/10
       ↓
Delete user 10
```

The URL represents **what**, while the HTTP method helps describe **what to do with it**.

# 11. REST is Stateless

One of the important REST principles is **statelessness**.

It means:

> Each request should contain the information necessary for the server to process that request.

The server should not depend on hidden request history to understand the current request.

For example, with JWT authentication:

```
Request 1
Authorization: Bearer TOKEN
```

Then:

```
Request 2
Authorization: Bearer TOKEN
```

Each request contains the authentication information needed by the API.

---

# 12. Stateless vs Stateful

### Stateful idea

The server remembers previous interaction state.

```
Request 1
   ↓
Server remembers user

Request 2
   ↓
Server uses remembered state
```

### Stateless REST idea

Each request carries the necessary context.

```
Request 1
   ↓
Contains required information

Request 2
   ↓
Contains required information
```

JWT-based APIs commonly follow this stateless approach.

# 13. REST API and JSON

REST APIs commonly use **JSON** to exchange data.

Example request:

```
{
    "name": "Rahul",
    "email": "rahul@example.com"
}
```

Example response:

```
{
    "id": 10,
    "name": "Rahul",
    "email": "rahul@example.com"
}
```

JSON is popular because it is:

- Easy to read
- Easy to generate
- Easy to parse
- Supported by JavaScript
- Supported by Python
- Suitable for web and mobile applications

We'll study JSON in detail in **10.3**.

# 14. Flask REST API Example

A very simple Flask API:

```
from flask import Flask, jsonify

app = Flask(__name__)


@app.route("/api/hello")
def hello():

    return jsonify({
        "message": "Hello from Flask API"
    })
```

Run the Flask application.

Then request:

```
/api/hello
```

Response:

```
{
    "message": "Hello from Flask API"
}
```

That's already an API endpoint.

# 15. Flask API with Data

Suppose we have:

```
products = [
    {
        "id": 1,
        "name": "Laptop",
        "price": 55000
    },
    {
        "id": 2,
        "name": "Phone",
        "price": 25000
    }
]
```

We can create:

```
@app.route("/api/products")
def get_products():

    return jsonify(products)
```

Request:

```
GET /api/products
```

Response:

```
[
    {
        "id": 1,
        "name": "Laptop",
        "price": 55000
    },
    {
        "id": 2,
        "name": "Phone",
        "price": 25000
    }
]
```

Later, instead of a Python list, we'll retrieve the data using SQLAlchemy.

# 16. Traditional Flask Route vs REST API

A normal Flask application might have:

```
@app.route("/products")
def products():
    return render_template(
        "products.html",
        products=products
    )
```

The server returns an HTML page.

```
Browser
  ↓
Flask
  ↓
HTML
  ↓
Browser displays page
```

A REST API instead returns data:

```
@app.route("/api/products")
def products_api():
    return jsonify(products)
```

Architecture:

```
React / Mobile App
        ↓
   /api/products
        ↓
      Flask
        ↓
       JSON
        ↓
React / Mobile App
```

This separation is extremely useful.

```
        Flask REST API
              │
              ↓

              │
              ↓

```


Flask:


React receives JSON and displays it.

This is how frontend and backend are commonly separated.

# 19. REST API vs Database

An API is **not the database**.

These are different layers:

```
Frontend
   ↓
REST API
   ↓
Business Logic
   ↓
ORM
   ↓
Database
```

For example:

```
React
 ↓
GET /api/products
 ↓
Flask
 ↓
SQLAlchemy
 ↓
MySQL
```

The frontend communicates with Flask, not directly with MySQL.

This provides:

- Security
- Validation
- Authentication
- Authorization
- Business logic
- Database abstraction

# 21. Important REST Principles

You don't need to memorize every academic detail, but understand these major ideas.

### 1. Client-server

Client and server have separate responsibilities.

### 2. Stateless

Each request contains the information needed to process it.

### 3. Resource-based

URLs represent resources.

```
/api/users
/api/products
/api/orders
```

### 4. Uniform interface

Use consistent conventions for URLs, HTTP methods, requests, and responses.

### 5. Representations

Resources can be represented using formats such as JSON.

### 6. Cacheability

Some responses can be cached when appropriate.

These principles help create APIs that are predictable and scalable.

# 23. Complete Example

Let's combine the fundamental ideas.

### Endpoint

```
/api/books
```

### Get all books

```
GET /api/books
```

### Get one book

```
GET /api/books/5
```

### Create a book

```
POST /api/books
```

Request:

```
{
    "title": "Python Basics",
    "author": "Rahul"
}
```

### Update a book

```
PATCH /api/books/5
```

### Delete a book

```
DELETE /api/books/5
```

Notice the pattern:

```
Resource:
    /api/books

Collection:
    /api/books

Individual resource:
    /api/books/5

Operations:
    GET
    POST
    PATCH
    DELETE
```

This pattern is the foundation of CRUD REST APIs.

# 24. Common Beginner Mistakes

### ❌ Mistake 1: Thinking REST is a programming language

REST is an **architectural style**.

---

### ❌ Mistake 2: Thinking API means database

An API is a communication interface.

```
API ≠ Database
```

---

### ❌ Mistake 3: Using action-based URLs everywhere

Instead of:

```
/api/getUsers
/api/deleteUser
```

prefer:

```
GET /api/users
DELETE /api/users/10
```

---

### ❌ Mistake 4: Returning HTML from an API

A REST API normally returns structured data such as JSON.

---

### ❌ Mistake 5: Letting frontend access database directly

Avoid:

```
React → MySQL
```

Prefer:

```
React → Flask API → MySQL
```
