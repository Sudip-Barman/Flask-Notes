
In **10.8 JWT Authentication**, we learned how an API identifies a user using a JWT.

Now we take the next step:

> **After identifying the user, what is that user allowed to do?**

That is **authorization**.

The core relationship is:

```
Authentication
      ↓
Who are you?
      ↓
Authorization
      ↓
What are you allowed to do?
      ↓
Allow / Deny
```

---

# 1. What is Authorization?

**Authorization** is the process of deciding whether an authenticated user has permission to perform a particular action or access a particular resource.

For example:

```
User logs in
    ↓
Authentication
    ↓
User = 25
    ↓
Authorization
    ↓
Role = staff
    ↓
Can view products?
    ↓
Yes
```

But:

```
Can delete users?
    ↓
No
    ↓
403 Forbidden
```

---

# 2. Authentication vs Authorization

This distinction is extremely important.

|Authentication|Authorization|
|---|---|
|Verifies identity|Verifies permissions|
|"Who are you?"|"What can you do?"|
|Happens first|Happens after authentication|
|Login/password/JWT|Roles/permissions/policies|
|Example: User ID = 25|Example: Can delete products?|

### Easy memory trick

```
Authentication → Identity
Authorization  → Access
```

---

# 3. What is a Protected API?

A **protected API** is an endpoint that cannot be used freely by everyone.

For example:

```
GET /api/profile
```

might require authentication.

And:

```
DELETE /api/users/25
```

might require both:

```
Authentication
      +
Admin permission
```

So there can be different levels of protection.

```
Public API
    ↓
Authentication required
    ↓
Specific role required
    ↓
Specific permission required
```

---

# 4. Public vs Protected APIs

### Public

```
GET /api/products
```

Anyone can access it.

### Authenticated

```
GET /api/profile
```

Requires a valid JWT.

### Role-protected

```
GET /api/admin/users
```

Requires an administrator role.

### Permission-protected

```
DELETE /api/products/10
```

Requires a specific permission such as:

```
products.delete
```

# 5. Authorization Flow

A protected API generally follows this sequence:

```
Client
  ↓
API Request
  ↓
Is user authenticated?
  ↓
 ┌───────┴───────┐
No              Yes
 ↓                ↓
401          Check permission
                   ↓
              Allowed?
              /      \
            No        Yes
            ↓          ↓
           403      API Logic
                       ↓
                    Database
                       ↓
                  JSON Response
```

This gives us two important failure points:

```
401 → Authentication failed
403 → Authorization failed
```

---

# 6. JWT Authentication Alone Is Not Authorization

Suppose a user has a valid JWT.

```
JWT
 ↓
Valid
 ↓
User = 25
```

That only tells us:

> "We know who this user is."

It does **not** automatically mean:

> "This user can do everything."

For example:

```
User 25
Role = staff
```

might be allowed to:

```
View products
View orders
Update orders
```

but not:

```
Delete users
Change system settings
```

So:

```
Valid JWT ≠ Full access
```

# 7. Roles

A **role** is a broad category assigned to a user.

Examples:

```
admin
manager
staff
customer
```

Example database model:

```
class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)

    name = db.Column(
        db.String(100),
        nullable=False
    )

    email = db.Column(
        db.String(120),
        unique=True,
        nullable=False
    )

    password_hash = db.Column(
        db.String(255),
        nullable=False
    )

    role = db.Column(
        db.String(50),
        nullable=False,
        default="customer"
    )
```

Now each user can have a role.

```
User 1 → admin
User 2 → manager
User 3 → staff
User 4 → customer
```

---

# 8. Role-Based Authorization

A simple approach is to check the user's role.

Example:

```
if user.role != "admin":
    return jsonify({
        "error": "Forbidden"
    }), 403
```

For example:

```
@app.get("/api/admin/users")
@jwt_required()
def admin_users():

    user_id = get_jwt_identity()

    user = db.session.get(User, user_id)

    if user is None:
        return jsonify({
            "error": "User not found"
        }), 401

    if user.role != "admin":
        return jsonify({
            "error": "Admin access required"
        }), 403

    return jsonify({
        "message": "Admin user list"
    })
```

The flow is:

```
JWT
 ↓
User ID
 ↓
Database
 ↓
User role
 ↓
role == admin?
 ↓
Allow / 403
```

---

# 9. Why Check the Database?

You might wonder:

> "Why not just put the role in the JWT?"

You can include claims such as:

```
{
    "sub": "25",
    "role": "manager"
}
```

But consider this:

```
10:00 AM
User role = manager
JWT created
```

Later:

```
10:30 AM
Admin changes role
manager → staff
```

The old JWT might still contain:

```
role = manager
```

until it expires.

Therefore, for sensitive authorization decisions, checking current server-side state can be important.

A common pattern is:

```
JWT
 ↓
User ID
 ↓
Database
 ↓
Current role/permissions
 ↓
Authorization
```

# 10. Creating a Role Decorator

If every admin endpoint contains:

```
if user.role != "admin":
```

our code becomes repetitive.

A decorator can solve this.

```
from functools import wraps
from flask import jsonify
from flask_jwt_extended import (
    jwt_required,
    get_jwt_identity
)

def admin_required(view):

    @wraps(view)
    @jwt_required()
    def wrapped_view(*args, **kwargs):

        user_id = get_jwt_identity()

        user = db.session.get(User, user_id)

        if user is None:
            return jsonify({
                "error": "User not found"
            }), 401

        if user.role != "admin":
            return jsonify({
                "error": "Admin access required"
            }), 403

        return view(*args, **kwargs)

    return wrapped_view
```

Now:

```
@app.get("/api/admin/users")
@admin_required
def admin_users():

    return jsonify({
        "message": "Admin users"
    })
```

Much cleaner.

---

# 11. Multiple Roles

Sometimes an API should allow more than one role.

For example:

```
admin
manager
```

can both view reports.

We can create a reusable decorator:

```
def roles_required(*allowed_roles):

    def decorator(view):

        @wraps(view)
        @jwt_required()
        def wrapped_view(*args, **kwargs):

            user_id = get_jwt_identity()

            user = db.session.get(User, user_id)

            if user is None:
                return jsonify({
                    "error": "User not found"
                }), 401

            if user.role not in allowed_roles:
                return jsonify({
                    "error": "Forbidden"
                }), 403

            return view(*args, **kwargs)

        return wrapped_view

    return decorator
```

Use it:

```
@app.get("/api/reports")
@roles_required("admin", "manager")
def reports():

    return jsonify({
        "message": "Reports"
    })
```

Now:

```
admin   → ✅
manager → ✅
staff   → ❌
customer → ❌
```

# 12. Permissions

Roles are useful, but sometimes they are too broad.

Imagine:

```
manager
```

can do:

```
users.read
users.update
reports.read
```

but cannot:

```
users.delete
```

This is where **permissions** become useful.

A permission represents a specific action.

Examples:

```
users.create
users.read
users.update
users.delete

products.create
products.read
products.update
products.delete

reports.read
reports.export
```

---

# 13. Role vs Permission

Think of it like this:

```
Role
 ↓
Collection of permissions
 ↓
Specific actions
```

For example:

```
Manager
│
├── users.read
├── users.update
├── reports.read
└── reports.export
```

Staff:

```
Staff
│
├── users.read
└── reports.read
```

Customer:

```
Customer
│
└── products.read
```

---

# 14. Permission Mapping

A simple implementation can use a Python dictionary.

```
ROLE_PERMISSIONS = {

    "admin": {
        "users.create",
        "users.read",
        "users.update",
        "users.delete",
        "reports.read",
        "reports.export"
    },

    "manager": {
        "users.read",
        "users.update",
        "reports.read",
        "reports.export"
    },

    "staff": {
        "users.read",
        "reports.read"
    },

    "customer": {
        "products.read"
    }
}
```

Now create a helper:

```
def has_permission(user, permission):

    permissions = ROLE_PERMISSIONS.get(
        user.role,
        set()
    )

    return permission in permissions
```

---

# 15. Permission-Based API

Now we can check:

```
if not has_permission(
    user,
    "users.delete"
):
    return jsonify({
        "error": "Permission denied"
    }), 403
```

Complete example:

```
@app.delete("/api/users/<int:user_id>")
@jwt_required()
def delete_user(user_id):

    current_user_id = get_jwt_identity()

    current_user = db.session.get(
        User,
        current_user_id
    )

    if current_user is None:
        return jsonify({
            "error": "User not found"
        }), 401

    if not has_permission(
        current_user,
        "users.delete"
    ):
        return jsonify({
            "error": "Permission denied"
        }), 403

    user = db.session.get(User, user_id)

    if user is None:
        return jsonify({
            "error": "User not found"
        }), 404

    db.session.delete(user)
    db.session.commit()

    return jsonify({
        "message": "User deleted"
    })
```

Now the API is protected by a **specific permission**, not simply an admin label.

---

# 16. Permission Decorator

We can make this reusable too.

```
def permission_required(permission):

    def decorator(view):

        @wraps(view)
        @jwt_required()
        def wrapped_view(*args, **kwargs):

            user_id = get_jwt_identity()

            user = db.session.get(User, user_id)

            if user is None:
                return jsonify({
                    "error": "User not found"
                }), 401

            if not has_permission(
                user,
                permission
            ):
                return jsonify({
                    "error": "Permission denied"
                }), 403

            return view(*args, **kwargs)

        return wrapped_view

    return decorator
```

Now our route becomes:

```
@app.delete("/api/users/<int:user_id>")
@permission_required("users.delete")
def delete_user(user_id):

    # Delete logic

    return jsonify({
        "message": "User deleted"
    })
```

This is much easier to maintain.

# 18. Resource-Level Authorization

There is another important concept.

Suppose User 10 requests:

```
GET /api/orders/100
```

The user may be authenticated.

But does User 10 actually own Order 100?

That's a different authorization question.

For example:

```
if order.user_id != current_user.id:
    return jsonify({
        "error": "Forbidden"
    }), 403
```

Now authorization depends on the specific resource.

```
User
 ↓
Authenticated?
 ↓
Yes
 ↓
Owns this order?
 ↓
Yes → Allow
No  → 403
```

This is sometimes called **object-level authorization** or **resource-level authorization**.

---

# 19. Why Resource-Level Authorization Matters

Imagine:

```
/api/orders/10
/api/orders/11
/api/orders/12
```

A user may legitimately access:

```
Order 10
```

but not:

```
Order 11
Order 12
```

Simply checking:

```
@jwt_required()
```

isn't enough.

The API must also check:

```
Does this authenticated user have access to this particular order?
```

This is a very important real-world security concept.

Suppose we have:

```
Products API
```

We could design permissions like this:

|Endpoint|Permission|
|---|---|
|`GET /api/products`|`products.read`|
|`GET /api/products/10`|`products.read`|
|`POST /api/products`|`products.create`|
|`PATCH /api/products/10`|`products.update`|
|`DELETE /api/products/10`|`products.delete`|

This creates a clean relationship:

```
HTTP Request
     ↓
Authentication
     ↓
Current User
     ↓
Permission Check
     ↓
CRUD Operation
```

# 21. Frontend Authorization vs Backend Authorization

This is one of the most important rules in full-stack development.

Suppose the frontend hides the delete button:

```
Delete button
    ↓
Hidden for staff
```

That's good for user experience.

But it is **not security**.

A user could manually send:

```
DELETE /api/users/10
```

directly to the backend.

Therefore:

```
Frontend authorization
→ UI convenience

Backend authorization
→ Actual security
```

The backend must always enforce permissions.

---

# 22. Example: Frontend + Backend

Frontend:

```
if (user.role === "admin") {
    showDeleteButton();
}
```

This improves the interface.

But backend:

```
@app.delete("/api/users/<int:user_id>")
@permission_required("users.delete")
def delete_user(user_id):
    ...
```

is what actually protects the resource.

Think:

```
Frontend
→ "Should I show the button?"

Backend
→ "Should I allow the action?"
```

# 23. 401 vs 403

Let's make this crystal clear.

### 401

User isn't successfully authenticated.

```
No JWT
Invalid JWT
Expired JWT
Invalid authentication
```

Response:

```
401 Unauthorized
```

---

### 403

User is authenticated but isn't allowed to perform the action.

```
Valid JWT
+
Insufficient permission
```

Response:

```
403 Forbidden
```

### Memory trick

```
401 → "I don't know you."
403 → "I know you, but no."
```

# 25. Role-Based Access Control

This design is commonly called **RBAC**:

> **Role-Based Access Control**

The relationship is:

```
User
 ↓
Role
 ↓
Permissions
 ↓
Resources/Actions
```

Example:

```
User: John
   ↓
Role: Manager
   ↓
Permissions:
   ├── users.read
   ├── users.update
   ├── reports.read
   └── reports.export
```

# 26. Database-Based Authorization

For small applications, this can be enough:

```
ROLE_PERMISSIONS = {
    "admin": {...},
    "manager": {...},
    "staff": {...}

```

For larger systems, permissions are often stored in the database.

A common design:

```
users
roles
permissions
user_roles
role_permissions
```

Relationship:

```
Users
  ↓
User Roles
  ↓
Roles
  ↓
Role Permissions
  ↓
Permissions
```

Example:

```
User
  ↓
Manager
  ↓
users.read
users.update

```

This makes permissions easier to manage dynamically.

# 27. Least Privilege

A very important security principle is:

> **Give users only the permissions they need.**

For example, if a staff member only needs to read users:

```
users.read
```

don't give them:

```
users.delete
users.update
users.create
```

So:

```
Minimum required access
        ↓
Less damage if account is compromised
```

This is called the **principle of least privilege**.

---

# 28. Don't Trust Client-Supplied Permissions

Never do this:

```
{
    "role": "admin",
    "permission": "users.delete"
}
```

and assume it is true.

The client can modify the request.

Instead:

```
JWT
 ↓
Authenticated identity
 ↓
Server/database
 ↓
Actual role
 ↓
Actual permissions
 ↓
Authorization decision
```

The server is the authority.

---

# 29. Protect Every Sensitive Endpoint

Don't protect only:

```
GET /api/admin
```

while leaving:

```
DELETE /api/users/10
POST /api/users
PATCH /api/users/10
```

unprotected.

Each sensitive endpoint needs appropriate authorization.

A useful review question is:

> **"What happens if someone calls this endpoint directly without using my frontend?"**

If the answer is:

> "The backend still rejects unauthorized users."

then you're thinking in the right direction.

# 31. Practical Flask Pattern

A clean protected API often follows this structure:

```
@app.patch("/api/products/<int:product_id>")
@permission_required("products.update")
def update_product(product_id):

    # 1. Find product
    product = db.session.get(
        Product,
        product_id
    )

    # 2. Check resource
    if product is None:
        return jsonify({
            "error": "Product not found"
        }), 404

    # 3. Read request data
    data = request.get_json()

    # 4. Validate input
    # ...

    # 5. Update product
    # ...

    # 6. Commit
    db.session.commit()

    # 7. Return response
    return jsonify({
        "message": "Product updated"
    })
```

The decorator handles:

```
JWT
 ↓
Authentication
 ↓
Authorization
```

The route handles:

```
Resource
 ↓
Validation
 ↓
Business logic
 ↓
Database
 ↓
Response
```

This separation keeps the code cleaner.

# 32. Common Mistakes

### ❌ Mistake 1: JWT means full authorization

No.

```
JWT → Authentication
```

You still need authorization.

---

### ❌ Mistake 2: Frontend-only authorization

Hiding buttons isn't security.

---

### ❌ Mistake 3: Trusting `role` from request JSON

Never trust client-provided roles.

---

### ❌ Mistake 4: Using 401 for every denial

Remember:

```
Authentication failure → 401
Authorization failure → 403
```

---

### ❌ Mistake 5: Forgetting resource ownership

Being logged in doesn't automatically mean the user can access every resource.

---

### ❌ Mistake 6: Giving everyone admin permissions

Use least privilege.

---

### ❌ Mistake 7: Repeating authorization code everywhere

Use decorators/helpers when the same authorization logic is repeated.
