When an API has only a few records, returning everything is simple:

```
GET /api/products
```

But imagine the database contains **100,000 products**.

Returning all 100,000 records in one response is inefficient.

This is where **pagination** and **filtering** become important.

---

# 1. What Is Pagination?

**Pagination** means dividing a large collection of data into smaller groups called **pages**.

For example, instead of:

```
100,000 products
       ↓
One huge response
```

we can return:

```
Page 1 → Products 1-20
Page 2 → Products 21-40
Page 3 → Products 41-60
...
```

A client can request:

```
GET /api/products?page=1&per_page=20
```

---

# 2. Why Do We Need Pagination?

Without pagination:

```
Database
   ↓
100,000 records
   ↓
Flask
   ↓
Huge JSON response
   ↓
Client
```

Problems can include:

- Large response size
- Higher memory usage
- Slower API responses
- More database work
- Slower frontend rendering
- Poor mobile performance
- Unnecessary network traffic

With pagination:

```
Database
   ↓
Requested 20 records
   ↓
Flask
   ↓
Small JSON response
   ↓
Client
```

Pagination is therefore both a **performance** and **usability** technique.

---

# 3. Basic Pagination Parameters

The most common parameters are:

```
page
per_page
```

Example:

```
GET /api/products?page=2&per_page=10
```

Meaning:

```
page = 2
per_page = 10
```

So the client is requesting the second group of 10 products.

---

# 4. Pagination With `request.args`

Flask can read query parameters using:

```
request.args.get()
```

Example:

```
page = request.args.get("page", 1, type=int)
per_page = request.args.get("per_page", 10, type=int)
```

If the client sends:

```
GET /api/products?page=3&per_page=20
```

then:

```
page
# 3

per_page
# 20
```

If nothing is supplied:

```
page
# 1

per_page
# 10
```

---

# 5. Why Set Defaults?

Suppose the client simply requests:

```
GET /api/products
```

We still want a sensible result.

So:

```
page = request.args.get("page", 1, type=int)
per_page = request.args.get("per_page", 10, type=int)
```

means:

```
No page       → page 1
No per_page   → 10 records
```

---

# 6. Validate Pagination Parameters

The client can send bad values:

```
GET /api/products?page=-5&per_page=100000
```

Never blindly trust them.

For example:

```
page = request.args.get("page", 1, type=int)
per_page = request.args.get("per_page", 10, type=int)

if page < 1:
    return jsonify({
        "error": "Page must be at least 1"
    }), 400

if per_page < 1:
    return jsonify({
        "error": "per_page must be at least 1"
    }), 400

if per_page > 100:
    return jsonify({
        "error": "per_page cannot exceed 100"
    }), 400
```

The maximum is important.

Otherwise someone could request:

```
?per_page=10000000
```

and force the server to process a massive amount of data.

---

# 7. Pagination With SQLAlchemy

SQLAlchemy provides:

```
.limit()
.offset()
```

For example:

```
products = (
    Product.query
    .limit(10)
    .offset(20)
    .all()
)
```

This means:

```
Skip 20 records
Take 10 records
```

---

# 8. Calculating the Offset

The general formula is:

```
offset = (page - 1) × per_page
```

For example:

```
page = 1
per_page = 10

offset = (1 - 1) × 10
       = 0
```

Page 2:

```
offset = (2 - 1) × 10
       = 10
```

Page 3:

```
offset = (3 - 1) × 10
       = 20
```

So:

```
Page 1 → offset 0
Page 2 → offset 10
Page 3 → offset 20
Page 4 → offset 30
```

---

# 9. Basic Paginated API

Example:

```
@app.get("/api/products")
def get_products():

    page = request.args.get("page", 1, type=int)
    per_page = request.args.get("per_page", 10, type=int)

    if page < 1:
        return jsonify({
            "error": "Page must be at least 1"
        }), 400

    if per_page < 1 or per_page > 100:
        return jsonify({
            "error": "per_page must be between 1 and 100"
        }), 400

    offset = (page - 1) * per_page

    products = (
        Product.query
        .order_by(Product.id)
        .limit(per_page)
        .offset(offset)
        .all()
    )

    return jsonify([
        {
            "id": product.id,
            "name": product.name,
            "price": product.price
        }
        for product in products
    ])
```

Now:

```
GET /api/products?page=2&per_page=10
```

returns the second page.

---

# 10. Why `ORDER BY` Matters

You will often see:

```
.order_by(Product.id)
```

before pagination.

This is important because pagination should have a **stable ordering**.

Without predictable ordering, records can potentially appear in different pages between requests, especially as the underlying data changes.

A common approach:

```
.order_by(Product.id.asc())
```

or:

```
.order_by(Product.created_at.desc())
```

The exact ordering depends on the API.

---

# 11. Pagination Metadata

Returning only the records isn't very useful for a frontend.

Suppose the response is:

```
[
    {
        "id": 1,
        "name": "Laptop"
    },
    {
        "id": 2,
        "name": "Keyboard"
    }
]
```

The frontend doesn't know:

- How many total products exist
- How many pages exist
- Whether there is a next page
- Whether there is a previous page

A better response includes metadata.

---

# 12. Good Pagination Response

Example:

```
{
    "data": [
        {
            "id": 1,
            "name": "Laptop",
            "price": 50000
        },
        {
            "id": 2,
            "name": "Keyboard",
            "price": 1500
        }
    ],
    "pagination": {
        "page": 1,
        "per_page": 10,
        "total": 125,
        "pages": 13,
        "has_next": true,
        "has_previous": false
    }
}
```

Now the frontend has everything needed to build pagination controls.

# 13. Calculating Total Pages

Suppose:

```
total = 125
per_page = 10
```

Then:

```
125 ÷ 10 = 12.5
```

We need to round upward:

```
pages = 13
```

In Python:

```
import math

pages = math.ceil(total / per_page)
```

---

# 14. SQLAlchemy Count

To know the total number of records:

```
total = Product.query.count()
```

Then:

```
pages = math.ceil(total / per_page)
```

Complete example:

```
import math

@app.get("/api/products")
def get_products():

    page = request.args.get("page", 1, type=int)
    per_page = request.args.get("per_page", 10, type=int)

    if page < 1:
        return jsonify({
            "error": "Page must be at least 1"
        }), 400

    if per_page < 1 or per_page > 100:
        return jsonify({
            "error": "per_page must be between 1 and 100"
        }), 400

    total = Product.query.count()

    pages = math.ceil(total / per_page)

    offset = (page - 1) * per_page

    products = (
        Product.query
        .order_by(Product.id)
        .limit(per_page)
        .offset(offset)
        .all()
    )

    return jsonify({
        "data": [
            {
                "id": product.id,
                "name": product.name,
                "price": product.price
            }
            for product in products
        ],
        "pagination": {
            "page": page,
            "per_page": per_page,
            "total": total,
            "pages": pages,
            "has_next": page < pages,
            "has_previous": page > 1
        }
    })
```

# 15. What If the Page Doesn't Exist?

Suppose there are only:

```
25 products
```

with:

```
per_page = 10
```

Then:

```
pages = 3
```

A client requests:

```
GET /api/products?page=100
```

There are two common approaches.

### Option 1: Return an empty list

```
{
    "data": [],
    "pagination": {
        "page": 100,
        "pages": 3
    }
}
```

### Option 2: Return an error

```
{
    "error": "Page does not exist"
}
```

Both approaches can be valid. Choose a consistent API convention.

For many APIs, returning an empty `data` array is convenient.

# 16. What Is Filtering?

**Filtering** means returning only records that match specific conditions.

Suppose we have:

```
1000 products
```

The client might only want products costing more than ₹10,000.

Instead of:

```
GET /api/products
```

we can use:

```
GET /api/products?min_price=10000
```

The API filters the database results.

---

# 17. Filtering With Query Parameters

Example:

```
min_price = request.args.get("min_price", type=float)

query = Product.query

if min_price is not None:
    query = query.filter(Product.price >= min_price)

products = query.all()
```

The important pattern is:

```
Start query
    ↓
Check filter
    ↓
Apply filter if provided
    ↓
Execute query
```

---

# 18. Exact Filtering

Suppose we want to filter by status.

Request:

```
GET /api/products?status=active
```

Code:

```
status = request.args.get("status")

query = Product.query

if status:
    query = query.filter(Product.status == status)

products = query.all()
```

---

# 19. Multiple Filters

We can combine filters.

Example:

```
GET /api/products?status=active&min_price=1000
```

Code:

```
status = request.args.get("status")
min_price = request.args.get("min_price", type=float)

query = Product.query

if status:
    query = query.filter(Product.status == status)

if min_price is not None:
    query = query.filter(Product.price >= min_price)

products = query.all()
```

This produces conceptually:

```
WHERE status = 'active'
AND price >= 1000
```

---

# 20. Maximum Price

We can support:

```
GET /api/products?max_price=50000
```

```
max_price = request.args.get("max_price", type=float)

if max_price is not None:
    query = query.filter(Product.price <= max_price)
```

Now we can have:

```
GET /api/products?min_price=10000&max_price=50000
```

Meaning:

```
price >= 10000
AND
price <= 50000
```

---

# 21. Search vs Filtering

These concepts are related but different.

### Filtering

Usually matches a specific condition.

```
GET /api/products?status=active
```

### Searching

Usually looks for a value across text.

```
GET /api/products?search=laptop
```

For example:

```
search = request.args.get("search")

if search:
    query = query.filter(
        Product.name.ilike(f"%{search}%")
    )
```

This could match:

```
Laptop
Gaming Laptop
Laptop Stand
Laptop Bag
```

---

# 22. Filtering With Pagination

In real APIs, filtering and pagination are commonly used together.

Example:

```
GET /api/products?status=active&min_price=1000&page=2&per_page=20
```

The processing order should conceptually be:

```
Request
  ↓
Read query parameters
  ↓
Build filters
  ↓
Count filtered records
  ↓
Apply ordering
  ↓
Apply pagination
  ↓
Execute query
  ↓
JSON response
```

This is important.

You generally want to paginate the **filtered result set**, not paginate everything first and filter afterward.

---

# 23. Complete Filtering + Pagination Example

```
import math

@app.get("/api/products")
def get_products():

    page = request.args.get("page", 1, type=int)
    per_page = request.args.get("per_page", 10, type=int)

    status = request.args.get("status")
    min_price = request.args.get("min_price", type=float)
    max_price = request.args.get("max_price", type=float)

    # Validate pagination
    if page < 1:
        return jsonify({
            "error": "Page must be at least 1"
        }), 400

    if per_page < 1 or per_page > 100:
        return jsonify({
            "error": "per_page must be between 1 and 100"
        }), 400

    # Validate price range
    if min_price is not None and min_price < 0:
        return jsonify({
            "error": "min_price cannot be negative"
        }), 400

    if max_price is not None and max_price < 0:
        return jsonify({
            "error": "max_price cannot be negative"
        }), 400

    if (
        min_price is not None
        and max_price is not None
        and min_price > max_price
    ):
        return jsonify({
            "error": "min_price cannot be greater than max_price"
        }), 400

    # Build query
    query = Product.query

    if status:
        query = query.filter(Product.status == status)

    if min_price is not None:
        query = query.filter(Product.price >= min_price)

    if max_price is not None:
        query = query.filter(Product.price <= max_price)

    # Count filtered records
    total = query.count()

    pages = math.ceil(total / per_page)

    # Pagination
    offset = (page - 1) * per_page

    products = (
        query
        .order_by(Product.id)
        .limit(per_page)
        .offset(offset)
        .all()
    )

    return jsonify({
        "data": [
            {
                "id": product.id,
                "name": product.name,
                "price": product.price,
                "status": product.status
            }
            for product in products
        ],
        "pagination": {
            "page": page,
            "per_page": per_page,
            "total": total,
            "pages": pages,
            "has_next": page < pages,
            "has_previous": page > 1
        }
    })
```

# 24. Sorting

Pagination and filtering often work together with **sorting**.

For example:

```
GET /api/products?sort=price&order=desc
```

Meaning:

```
Sort by price
Highest → lowest
```

Example:

```
sort = request.args.get("sort", "id")
order = request.args.get("order", "asc")
```

You should **not** blindly pass user input into SQL.

Instead, use an allowlist:

```
allowed_sort_fields = {
    "id": Product.id,
    "name": Product.name,
    "price": Product.price
}

sort_column = allowed_sort_fields.get(sort)

if sort_column is None:
    return jsonify({
        "error": "Invalid sort field"
    }), 400
```

Then:

```
if order == "desc":
    query = query.order_by(sort_column.desc())
else:
    query = query.order_by(sort_column.asc())
```

This is much safer than dynamically constructing raw SQL.

# 26. Pagination Styles

There are several pagination strategies.

## Offset Pagination

The approach we've used:

```
page
per_page
offset
limit
```

Example:

```
?page=5&per_page=20
```

### Advantages

- Simple
- Easy to understand
- Easy for page-number UI
- Works well for many normal applications

### Disadvantages

For very large datasets, large offsets can become expensive.

---

# 27. Cursor Pagination

Another approach is **cursor-based pagination**.

Instead of:

```
?page=5
```

the API might return a cursor:

```
{
    "data": [...],
    "next_cursor": "abc123"
}
```

The client then requests:

```
GET /api/products?cursor=abc123
```

Conceptually:

```
Page 1
   ↓
Cursor A
   ↓
Page 2
   ↓
Cursor B
   ↓
Page 3
```

Cursor pagination is useful for large or frequently changing datasets.

For beginner Flask applications, **offset pagination is easier to learn first**.

---

# 28. Offset vs Cursor

|Feature|Offset|Cursor|
|---|---|---|
|Easy to implement|✅|More complex|
|Page numbers|✅|Usually not ideal|
|Large datasets|Can become expensive|Often better|
|Simple frontend|✅|Depends|
|Frequently changing data|Can shift results|Often more stable|
|Beginner friendly|✅|❌|

You don't need cursor pagination for every API.

Choose based on the application's requirements.

### Greater than or equal

```
Product.price >= 1000
```

# 30. Multiple Conditions

You can use:

```
from sqlalchemy import and_

query = query.filter(
    and_(
        Product.price >= 1000,
        Product.price <= 50000
    )
)
```

Or commonly:

```
query = query.filter(
    Product.price >= 1000,
    Product.price <= 50000
)
```

Multiple arguments to `filter()` are combined using logical AND.

# 31. Pagination, Filtering and Database Performance

Pagination does **not** automatically make every query fast.

Suppose:

```
10 million products
```

and you're filtering by:

```
status
price
created_at
```

Indexes can become very important.

For example:

```
status = db.Column(
    db.String(20),
    index=True
)
```

Or using appropriate database indexes for commonly queried columns.

Remember:

```
Pagination
   ↓
Limits returned records

Indexes
   ↓
Help database find records efficiently
```

They solve different problems.

---

# 32. Don't Fetch Everything First

Avoid:

```
products = Product.query.all()

# Then filter in Python
filtered = [
    product
    for product in products
    if product.price > 1000
]
```

This loads all records into application memory.

Prefer:

```
products = Product.query.filter(
    Product.price > 1000
).all()
```

Now the database performs the filtering.

Better:

```
Database
   ↓
Filter
   ↓
Sort
   ↓
Limit
   ↓
Return required records
```

instead of:

```
Database
   ↓
Return everything
   ↓
Flask
   ↓
Filter in Python
```

# 35. Common Mistakes

### ❌ Returning every database record

```
Product.query.all()
```

for a huge collection can become problematic.

---

### ❌ Filtering in Python

```
Product.query.all()
```

then filtering the result in Python.

Let the database do the filtering.

---

### ❌ No maximum `per_page`

Don't allow:

```
?per_page=1000000
```

---

### ❌ No stable ordering

Pagination without predictable ordering can produce inconsistent results.

Use something like:

```
.order_by(Product.id)
```

---

### ❌ Trusting sort parameters

Don't blindly turn user input into SQL.

Use an allowlist:

```
allowed_sort_fields = {
    "name": Product.name,
    "price": Product.price
}
```

---

### ❌ Forgetting filters when counting

If your query has:

```
status = "active"
```

then the total should represent **filtered records**, not all records.

Correct:

```
query = Product.query.filter(
    Product.status == "active"
)

total = query.count()
```

# 39. Final API Example

A realistic request might look like:

```
GET /api/products?search=laptop&status=active&min_price=10000&page=2&per_page=20&sort=price&order=desc
```

The server interprets it as:

```
Search:
    laptop

Filter:
    status = active
    price >= 10000

Sort:
    price descending

Pagination:
    page = 2
    per_page = 20
```

Then:

```
Request
   ↓
Validate parameters
   ↓
Build SQLAlchemy query
   ↓
Apply search/filter
   ↓
Count matching records
   ↓
Apply sorting
   ↓
Apply limit + offset
   ↓
Execute database query
   ↓
Return data + pagination metadata
```

That is the basic architecture behind many real-world list APIs.
