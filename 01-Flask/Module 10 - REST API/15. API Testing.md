## 1. What is API Testing?

**API Testing** is the process of testing an API to make sure that its endpoints work correctly, return the correct status codes, send the expected JSON responses, handle invalid input properly, and enforce authentication and authorization.

In a Flask REST API, we can test things like:

- Does `GET /api/products` return products?
- Does `POST /api/products` create a product?
- Does invalid data return `400` or `422`?
- Does a missing product return `404`?
- Does an unauthenticated request return `401`?
- Does a user without permission receive `403`?
- Does the API return the correct JSON structure?
- Does the database actually change as expected?

### Simple mental model

```
Client
   ↓
API Request
   ↓
Flask Route
   ↓
Validation
   ↓
Authentication
   ↓
Business Logic
   ↓
Database
   ↓
API Response
   ↓
TEST
```

The test checks whether each important part behaves as expected.

---

# 2. Why API Testing is Important

An API can appear to work correctly from the frontend while still containing bugs.

For example:

```
Frontend
   ↓
POST /api/products
   ↓
API accidentally returns 200
   ↓
Product was NOT saved
```

The frontend might not immediately make the problem obvious.

API testing catches these problems directly.

### Benefits

|Benefit|Explanation|
|---|---|
|Finds bugs|Detects incorrect API behavior|
|Prevents regressions|Existing functionality stays working|
|Checks security|Tests authentication and authorization|
|Validates responses|Ensures correct JSON/status codes|
|Tests edge cases|Handles invalid or unusual input|
|Faster debugging|Problems can be isolated from frontend|
|Safe refactoring|Code can be changed with confidence|

### 3. Status code

Example:

```

201
400
401
403
404
409

```

### 4. Response body

Example:

```

```

### 8. Validation

What happens when required data is missing?

### 9. Database behavior

Was the record actually created, updated, or deleted?

There are several levels of testing.

## Unit Testing

Tests a small piece of code independently.

Example:

```
def calculate_total(price, quantity):
    return price * quantity
```

Test:

```
calculate_total(100, 3)
↓
300
```

## Integration Testing

Tests multiple components working together.

Example:

```
Flask
 ↓
SQLAlchemy
 ↓
Database
```

A test might create a product through the API and verify that it was saved in the database.

---

## API Testing

Tests the API from the HTTP layer.

```
HTTP Request
     ↓
Flask
     ↓
Database
     ↓
HTTP Response
```

This is the main focus of this topic.

---

## End-to-End Testing

Tests a complete user workflow.

For example:

```

 ↓

 ↓

 ↓

# 6. Testing Flask APIs with the Test Client

Flask provides a built-in **test client**.

It allows us to send HTTP requests to our Flask application without starting a real web server.

Example:

```
with app.test_client() as client:
    response = client.get("/api/products")
```

Think of it as a tiny fake client living inside your test.

```
Test Code
   ↓
Flask Test Client
   ↓
Flask Application
   ↓
API Route
```

# 7. Basic Flask Test

Suppose we have:

```
@app.get("/api/hello")
def hello():
    return jsonify({
        "message": "Hello"
    })
```

We can test it:

```
def test_hello():
    with app.test_client() as client:
        response = client.get("/api/hello")

        assert response.status_code == 200

        data = response.get_json()

        assert data["message"] == "Hello"
```

Let's break it down.

### Send request

```
response = client.get("/api/hello")
```

### Check status

```
assert response.status_code == 200
```

### Read JSON

```
data = response.get_json()
```

### Check response data

```
assert data["message"] == "Hello"
```

---

# 8. What is `assert`?

`assert` checks whether something is true.

Example:

```
assert 10 > 5
```

This passes.

```
assert 10 < 5
```

This fails.

In API testing:

```
assert response.status_code == 200
```

means:

> The test should pass only if the API returned HTTP 200.

# 16. Testing 404 Not Found

A good API test should also test failure cases.

Suppose product `999` does not exist:

```
def test_product_not_found():
    with app.test_client() as client:
        response = client.get("/api/products/999")

        assert response.status_code == 404

        data = response.get_json()

        assert data["success"] is False
```

We are testing the **expected failure**, not just successful requests.

This is extremely important.

# 22. Testing Authorization

Authentication alone isn't enough.

Suppose:

```
DELETE /api/users/10
```

requires an admin.

A normal authenticated user should receive:

```
403 Forbidden
```

Test:

```
def test_normal_user_cannot_delete_user():
    with app.test_client() as client:
        response = client.delete(
            "/api/users/10",
            headers={
                "Authorization": f"Bearer {user_token}"
            }
        )

        assert response.status_code == 403
```

This checks authorization.

# 27. Arrange, Act, Assert

A very useful testing pattern is:

```
Arrange
   ↓
Act
   ↓
Assert
```

## Arrange

Prepare the test.

```
product_id = 1
```

## Act

Perform the API request.

```
response = client.get(f"/api/products/{product_id}")
```

## Assert

Check the result.

```
assert response.status_code == 200
```

Complete example:

```
def test_get_product():
    # Arrange
    product_id = 1

    # Act
    with app.test_client() as client:
        response = client.get(
            f"/api/products/{product_id}"
        )

    # Assert
    assert response.status_code == 200
```

This makes tests easier to understand.

# 30. Test Database Isolation

When API tests use a database, tests should ideally not damage your real development or production data.

Use a dedicated test database.

```
Development DB
      ↓
Application development

Test DB
      ↓
Automated tests

Production DB
      ↓
Real application
```

Never casually run automated destructive tests against production.

# 31. Fixtures

Pytest provides **fixtures** for reusable test setup.

Example:

```
import pytest


@pytest.fixture
def client():
    app.config["TESTING"] = True

    with app.test_client() as client:
        yield client
```

Now tests can use:

```
def test_products(client):
    response = client.get("/api/products")

    assert response.status_code == 200
```

Instead of repeatedly writing:

```
with app.test_client() as client:
```

---

# 32. Why Fixtures Are Useful

Suppose 30 tests need a test client.

Without a fixture:

```
with app.test_client() as client:
    ...
```

would be repeated everywhere.

With a fixture:

```
def test_one(client):
    ...


def test_two(client):
    ...


def test_three(client):
    ...
```

The setup is centralized.

Fixtures can also prepare:

- Database
- Test users
- JWT tokens
- Sample products
- Authentication
- Temporary files

---

# 33. Testing JWT-Protected APIs with Fixtures

A fixture can create a token once for tests that need authentication.

Conceptually:

```
@pytest.fixture
def auth_headers():
    token = create_test_token()

    return {
        "Authorization": f"Bearer {token}"
    }
```

Then:

```
def test_profile(client, auth_headers):
    response = client.get(
        "/api/profile",
        headers=auth_headers
    )

    assert response.status_code == 200
```

This keeps authentication setup out of every individual test.

# 38. What Makes a Good API Test?

A good API test should be:

### Independent

One test should not unexpectedly depend on another.

### Repeatable

Running it multiple times should give the same expected result.

### Fast

Tests should run quickly.

### Clear

The test name should explain what is being tested.

Bad:

```
def test_api():
```

Better:

```
def test_create_product_with_valid_data():
```

Even better:

```
def test_create_product_returns_201_for_valid_data():
```

### Focused

One test should ideally verify one behavior.

# 39. Common API Testing Mistakes

### ❌ Testing only successful requests

```
200
201
```

are not enough.

Also test:

```
400
401
403
404
409
422
```

---

### ❌ Testing only status codes

This:

```
assert response.status_code == 200
```

is useful, but incomplete.

Also inspect:

```
data = response.get_json()

assert data["success"] is True
assert "data" in data
```

---

### ❌ Using production database

Don't run destructive automated tests against real user data.

---

### ❌ Depending on test order

Avoid:

```
Test A must run before Test B
```

Tests should ideally be independent.

---

### ❌ Hardcoding unstable data

If IDs change between test runs, tests can become unreliable.

Use controlled test data.

---

### ❌ Ignoring authentication

Protected endpoints must be tested with:

```
No token
Invalid token
Valid token
Insufficient permission
```

---

### ❌ Testing only the frontend

Frontend testing cannot replace API testing.

```
Frontend
   ↓
API
   ↓
Database
```

Each layer can contain different bugs.

# 42. Running Tests

pytest
```

More detailed output:

```
pytest -v
```

```
pytest tests/test_products.py
```

pytest tests/test_products.py::test_get_products

```

```

# 43. API Testing vs Manual Testing

|Manual Testing|Automated Testing|
|---|---|
|Human sends requests|Code sends requests|
|Postman/cURL|pytest|
|Good for exploration|Good for repetition|
|Easy to start|Requires setup|
|Can be slow for many cases|Fast for many tests|
|Results may depend on person|Consistent|
|Useful during development|Excellent for CI/CD|

Both are useful.

A practical workflow is:

```
Postman
   ↓
Explore API
   ↓
Confirm behavior
   ↓
Write pytest tests
   ↓
Automate regression testing
```

# 44. API Testing in CI/CD

Once tests are automated, they can run whenever code changes.

For example:

```

        ↓
GitHub
        ↓
CI pipeline
        ↓
Install dependencies
        ↓

        ↓

      /   \

This prevents broken API code from silently moving forward.

# 45. Important Testing Checklist

Before considering an API endpoint complete, ask:

```
□ Does the endpoint work?
□ Is the HTTP method correct?
□ Is the status code correct?
□ Is the JSON structure correct?
□ Are required fields validated?
□ Are invalid values rejected?
□ Is 404 handled?
□ Are duplicate/conflict cases handled?
□ Is authentication tested?
□ Is authorization tested?
□ Are headers correct?
□ Is database behavior correct?
□ Is the test independent?
□ Is the test repeatable?
```

```

        ┌────────────┼────────────┐
        ↓            ↓            ↓
     Request       Security     Response
        │            │            │
