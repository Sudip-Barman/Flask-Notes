**Database design** is the process of deciding **how data should be organized, stored, and related** before creating the actual database.

A good database design makes an application:

- Easier to maintain
- Less repetitive
- More reliable
- Easier to query
- Easier to scale

Think of it as creating the **blueprint** before constructing the database. 🧱

---

# 1. Why Do We Need Database Design?

Suppose we want to build a college management system.

A beginner might create one huge table:

```
students

┌────┬─────────┬──────────┬──────────┬────────────┬───────────┐
│ id │ name    │ course   │ teacher  │ department │ marks     │
└────┴─────────┴──────────┴──────────┴────────────┴───────────┘
```

This seems simple initially, but problems appear quickly.

For example, if 500 students belong to the same course:

```
Python
Python
Python
Python
Python
...
```

The same information is repeatedly stored.

A better design separates the information:

```
students
courses
teachers
departments
results
```

and creates relationships between them.

---

# 2. Main Goal of Database Design

The basic goal is:

> **Store each piece of information in the appropriate place and connect related information properly.**

For example:

```
students
   │
   │ belongs to
   ▼
courses
   │
   │ belongs to
   ▼
departments
```

Instead of repeating the same information everywhere.

---

# 3. Step 1: Identify the Requirements

Before creating tables, first understand what the application needs.

Suppose we're building a simple **Library Management System**.

We need to store:

```
Students
Books
Authors
Borrowing information
```

We ask:

```
Who uses the system?
What information needs to be stored?
What actions can users perform?
What things are related?
```

---

# 4. Step 2: Identify Entities

An **entity** is something about which we need to store information.

For our library:

```
Student
Book
Author
Borrow
```

These could become tables:

```
students
books
authors
borrowings
```

So:

```
Entity          Table
------------------------
Student    →    students
Book       →    books
Author     →    authors
Borrowing  →    borrowings
```

---

# 5. Step 3: Identify Attributes

Now determine what information we need about each entity.

### Student

```
id
name
email
```

### Book

```
id
title
isbn
```

### Author

```
id
name
```

### Borrowing

```
id
student_id
book_id
borrowed_at
returned_at
```

Now we have a rough structure:

```
students
├── id
├── name
└── email

books
├── id
├── title
└── isbn

authors
├── id
└── name

borrowings
├── id
├── student_id
├── book_id
├── borrowed_at
└── returned_at
```

---

# 6. Step 4: Choose Primary Keys

Each important table normally needs a column that uniquely identifies each record.

For example:

```
students
────────────
id ← Primary Key
name
email
```

```
books
────────────
id ← Primary Key
title
isbn
```

```
authors
────────────
id ← Primary Key
name
```

We'll study primary keys in detail later.

For now, remember:

> **Primary key = unique identity of a row.**

---

# 7. Step 5: Identify Relationships

Now ask:

> How are these entities connected?

For example:

```
Student borrows Book
```

Therefore:

```
students
     │
     │ borrows
     ▼
   books
```

We need a way to represent that relationship.

That's where foreign keys come in.

```
borrowings
──────────────
id
student_id
book_id
```

Here:

```
student_id → students.id
book_id    → books.id
```

────────────

# 9. Avoid Repeating Data

Consider this bad design:

```
borrowings

student_name | student_email | book_title | author_name
---------------------------------------------------------
Alice        | a@example.com | Python     | John
Alice        | a@example.com | SQL        | David
Alice        | a@example.com | Flask      | John
Bob          | b@example.com | Python     | John
```

Notice:

```
Alice
a@example.com
Python
John
```

may appear repeatedly.

This creates unnecessary duplication.

Instead:

```
students
────────────
1 | Alice | a@example.com
2 | Bob   | b@example.com
```

```
books
────────────
1 | Python | 1
2 | SQL    | 2
3 | Flask  | 1
```

```
authors
────────────
1 | John
2 | David
```

and:

```
borrowings
────────────────────
student_id | book_id
1          | 1
1          | 2
1          | 3
2          | 1
```

Now information is stored in more appropriate places.

---

# 10. Normalization

The process of organizing data to reduce unnecessary duplication and improve consistency is called **normalization**.

You don't need to memorize all the formal rules yet.

The basic idea is:

> **Don't unnecessarily store the same information repeatedly.**

For example, instead of:

```
Order 1 → Alice → Kolkata
Order 2 → Alice → Kolkata
Order 3 → Alice → Kolkata
```

we might have:

```
users
──────────────
id | name  | city
1  | Alice | Kolkata
```

and:

```
orders
────────────
id | user_id
1  | 1
2  | 1
3  | 1
```

The orders reference the user.

This reduces repetition.

---

# 11. Why Duplication Is a Problem

Suppose Alice's city is stored in 100 different rows:

```
Alice | Kolkata
Alice | Kolkata
Alice | Kolkata
...
```

Then Alice moves.

You need to change:

```
Kolkata → Delhi
```

in potentially 100 places.

If you accidentally change only 99 of them, your database becomes inconsistent.

With a better design:

```
users
──────────────
id | name  | city
1  | Alice | Kolkata
```

only one value needs to change.

---

# 12. But Don't Split Everything

Normalization doesn't mean:

> "Create a separate table for every column."

For example, this would be silly:

```
students
student_names
student_emails
student_ages
```

You normally keep related attributes together:

```
students
────────────
id
name
email
age
```

The goal is **logical organization**, not maximum number of tables.

---

# 13. Choosing Table Boundaries

A useful question is:

> Does this information represent a different entity?

For example:

```
User
Product
Order
```

are clearly different entities.

Therefore:

```
users
products
orders
```

makes sense.

But:

```
User
 ├── name
 ├── email
 └── age
```

doesn't normally require three tables.

These are attributes of the same entity.

---

# 14. One-to-One Relationship

Sometimes one record relates to exactly one record.

Example:

```
person
   │
   │ 1
   ▼
passport
```

One person has one passport, and one passport belongs to one person.

This is called:

> **One-to-One (1:1)**

---

# 15. One-to-Many Relationship

This is extremely common.

Example:

```
User
 │
 │ 1
 │
 │
 │ N
 ▼
Orders
```

One user can have many orders.

But each order belongs to one user.

That's:

> **One-to-Many (1:N)**

Example:

```
Alice
 │
 ├── Order 1
 ├── Order 2
 └── Order 3
```

---

# 16. Many-to-Many Relationship

Suppose students can enroll in many courses:

```
Student ←→ Course
```

One student:

```
Alice
 ├── Python
 ├── Java
 └── Database
```

One course can have many students:

```
Python
 ├── Alice
 ├── Bob
 └── John
```

This is:

> **Many-to-Many (M:N)**

You normally handle this with an intermediate/junction table:

```
students
courses
student_courses
```

For example:

```
student_courses

student_id | course_id
-----------+----------
1          | 1
1          | 2
2          | 1
3          | 1
```

We'll study relationships more deeply later.

---

# 17. Database Design Process

A good general workflow is:

```
Requirements
     ↓
Identify Entities
     ↓
Identify Attributes
     ↓
Choose Primary Keys
     ↓
Identify Relationships
     ↓
Reduce Unnecessary Duplication
     ↓
Create ER Diagram
     ↓
Create Tables
     ↓
Add Constraints & Indexes
     ↓
Test the Design
```

This workflow is worth remembering.

# 18. Example: Blog Database

Let's design a simple blog.

### Requirements

Users can:

```
Register
Create posts
Comment on posts
```

### Entities

```
User
Post
Comment
```

### Tables

```
users
posts
comments
```

### Attributes

```
users
────────────
id
name
email

posts
────────────
id
user_id
title
content

comments
────────────
id
post_id
user_id
content
```

### Relationships

```
users
  │
  │ 1
  ▼
posts
  │
  │ 1
  ▼
comments
```

And comments also belong to users:

```
users
  │
  │ 1
  ▼
comments
```

So the overall design becomes:

```
              users
             /     \
            /       \
           ▼         ▼
        posts     comments
           │         ▲
           └─────────┘
```

This is a database **design**, before we've even written the SQL to create it.

# 19. Database Design vs Database Implementation

These are different.

### Design

Deciding:

```
What tables?
What columns?
What relationships?
What keys?
What constraints?
```

### Implementation

Actually creating them:

```
CREATE DATABASE ...
CREATE TABLE ...
ALTER TABLE ...
```

So:

```
Database Design
      ↓
Blueprint
      ↓
SQL
      ↓
Actual Database
```
