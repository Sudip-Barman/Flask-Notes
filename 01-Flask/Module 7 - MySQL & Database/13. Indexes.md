An **Index** is a database structure that helps MySQL **find data faster**.

The easiest way to understand an index is to think about a **book**.

---

## 1. What Is an Index?

Imagine you have a 1,000-page book and want to find:

> "What is a database?"

Without an index, you might have to start from page 1 and check every page.

With an index at the back of the book:

```
Database ........ Page 237
Database Design .. Page 451
Database Model ... Page 620
```

You can jump directly to the relevant page.

A database index works with the same basic idea:

```
Without Index
─────────────
Search → Check many rows → Find result

With Index
──────────
Search → Index → Locate matching rows → Find result
```

So:

> **An index improves the speed of searching and retrieving data.**

---

# 2. Example Without an Index

Suppose we have:

```
users

id | name    | email
---+---------+-------------------
1  | Alice   | alice@gmail.com
2  | Bob     | bob@gmail.com
3  | Charlie | charlie@gmail.com
4  | David   | david@gmail.com
...
```

Now we execute:

```
SELECT *
FROM users
WHERE email = 'charlie@gmail.com';
```

If `email` isn't indexed, MySQL may need to examine many rows to find the matching one.

For a tiny table, this doesn't matter much.

But imagine:

```
10 rows
100 rows
10,000 rows
1,000,000 rows
100,000,000 rows
```

Searching through huge amounts of data can become expensive.

An index can make these lookups much faster.

---

# 3. Creating an Index

You can create an index using:

```
CREATE INDEX index_name
ON table_name (column_name);
```

Example:

```
CREATE INDEX idx_email
ON users (email);
```

Now `email` has an index:

```
users
│
├── id
├── name
└── email ← INDEX
```

---

# 4. Searching Using an Indexed Column

Now when we run:

```
SELECT *
FROM users
WHERE email = 'charlie@gmail.com';
```

MySQL can use the index to efficiently locate matching rows.

You don't manually tell MySQL:

```
"Use idx_email!"
```

MySQL's query optimizer decides whether using the index is beneficial.

---

# 5. Indexes Are Not Only for SELECT

Indexes can help operations such as:

```
SELECT
UPDATE
DELETE
JOIN
ORDER BY
```

when the indexed columns are involved in useful query conditions.

For example:

```
SELECT *
FROM users
WHERE email = 'alice@gmail.com';
```

or:

```
SELECT *
FROM orders
WHERE user_id = 10;
```

An index on `orders.user_id` can be very useful.

---

# 6. Primary Keys Automatically Have an Index

This is important.

When you define:

```
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100)
);
```

the primary key is indexed automatically by MySQL.

So you normally don't need to do:

```
CREATE INDEX idx_id
ON users(id);
```

The primary key already has its required index.

Think:

```
PRIMARY KEY
      ↓
  Automatically
     indexed
```

---

# 7. UNIQUE Also Creates an Index

Suppose:

```
CREATE TABLE users (
    id INT PRIMARY KEY,
    email VARCHAR(255) UNIQUE
);
```

The `UNIQUE` constraint requires MySQL to maintain uniqueness, and MySQL creates a unique index for it.

So:

```
id
↓
Primary Key
↓
Indexed

email
↓
UNIQUE
↓
Unique Index
```

---

# 8. Why Not Index Every Column?

This is a very important question.

You might think:

> "If indexes make searching faster, let's index every column!"

❌ Usually not a good idea.

Indexes have costs.

When you insert or modify data, MySQL may also need to update the relevant indexes.

For example:

```
Without indexes:

INSERT
  ↓
Store row
```

With several indexes:

```
INSERT
  ↓
Store row
  ↓
Update index 1
  ↓
Update index 2
  ↓
Update index 3
  ↓
...
```

So indexes can:

- improve reads
- consume additional storage
- make writes more expensive

Therefore:

> **Create indexes where they are useful, not everywhere.**

---

# 9. Index and Storage

An index requires additional storage.

Imagine:

```
Table
────────────
1 GB
```

Adding several indexes could require additional space.

So database design involves a trade-off:

```
More indexes
     ↓
Faster certain queries
     ↓
More storage
     +
Potentially slower INSERT/UPDATE/DELETE
```

---

# 10. Single-Column Index

The simplest index is an index on one column.

```
CREATE INDEX idx_name
ON users (name);
```

Now:

```
name
 ↓
INDEX
```

It can help queries such as:

```
SELECT *
FROM users
WHERE name = 'Alice';
```

---

# 11. Composite Index

A **composite index** contains multiple columns.

Example:

```
CREATE INDEX idx_name_age
ON users (name, age);
```

This index contains:

```
name + age
```

It can be useful for queries involving both columns.

For example:

```
SELECT *
FROM users
WHERE name = 'Alice'
AND age = 20;
```

---

# 12. Column Order Matters

This is one of the most important things about composite indexes.

Suppose:

```
CREATE INDEX idx_name_age
ON users (name, age);
```

The order is:

```
name
 ↓
age
```

Think of it like a phone directory sorted first by:

```
Last Name
```

and then within each last name:

```
First Name
```

So the index is primarily organized around `name`.

Therefore, an index on:

```
(name, age)
```

is generally most useful when queries use `name` as the leading column.

For example:

```
WHERE name = 'Alice'
```

or:

```
WHERE name = 'Alice' AND age = 20
```

But an index beginning with `name` is not generally equivalent to having a separate index beginning with `age`.

This is called the **leftmost-prefix principle**.

---

# 13. Composite Index Example

Suppose:

```
CREATE INDEX idx_city_age
ON students (city, age);
```

Queries involving:

```
city
```

can benefit.

Queries involving:

```
city + age
```

can also benefit.

But a query using only:

```
age
```

may not be able to use this index effectively.

So:

```
(city, age)
```

is different from:

```
(age, city)
```

The order matters.

---

# 14. UNIQUE INDEX

A unique index doesn't allow duplicate values.

Example:

```
CREATE UNIQUE INDEX idx_email
ON users (email);
```

Then:

```
alice@example.com
bob@example.com
charlie@example.com
```

is valid.

But:

```
alice@example.com
alice@example.com
```

is not allowed.

This is similar to using:

```
email VARCHAR(255) UNIQUE
```

---

# 15. FULLTEXT Index

MySQL also supports `FULLTEXT` indexes for text-search use cases.

For example:

```
CREATE FULLTEXT INDEX idx_content
ON articles (content);
```

This is designed for searching words and phrases within larger text fields.

For example, searching an article collection for a word such as:

```
database
```

is a different problem from simply checking:

```
WHERE title = 'Database'
```

`FULLTEXT` is specialized for textual searching.

You don't need to memorize its details yet.

---

# 16. What Is the Difference Between Index and Primary Key?

This is a common confusion.

### Primary Key

A primary key is mainly about **identifying a row**.

```
id → PRIMARY KEY
```

### Index

An index is mainly about **improving data access/search performance**.

```
email → INDEX
```

So:

```
PRIMARY KEY
     ↓
Identity + uniqueness
     +
Indexing

INDEX
     ↓
Faster access
```

A primary key is automatically indexed, but not every index is a primary key.

---

# 17. What Is the Difference Between Index and Foreign Key?

Another important distinction.

### Foreign Key

Defines a **relationship** between tables.

```
orders.user_id
       ↓
users.id
```

### Index

Helps MySQL **find data efficiently**.

```
orders.user_id
       ↓
INDEX
```

A foreign key and an index serve different purposes.

However, indexing foreign-key columns is often useful because those columns are frequently involved in joins and lookups.

---

# 18. Example With Users and Orders

Suppose:

```
users

id | name
---+------
1  | Alice
2  | Bob
3  | Charlie
```

and:

```
orders

id | user_id | amount
---+---------+-------
1  | 2       | 500
2  | 1       | 300
3  | 2       | 700
```

We may frequently run:

```
SELECT *
FROM orders
WHERE user_id = 2;
```

We could create:

```
CREATE INDEX idx_orders_user_id
ON orders (user_id);
```

Now MySQL has an index specifically for looking up `user_id`.

# 19. How to See Indexes

You can use:

```
SHOW INDEX FROM users;
```

This displays information about the indexes on the table.

You can also use:

```
SHOW CREATE TABLE users;
```

to inspect the table definition, including indexes and constraints.

---

# 20. EXPLAIN

One of the most useful tools for understanding indexes is:

```
EXPLAIN
```

For example:

```
EXPLAIN
SELECT *
FROM users
WHERE email = 'alice@example.com';
```

MySQL can show information about how it plans to execute the query, including whether an index is being considered or used.

We'll explore `EXPLAIN` more when we get into **SQL optimization**.

---

# 21. When Should You Consider an Index?

Indexes are particularly useful for columns that are frequently used in:

```
WHERE
JOIN
ORDER BY
GROUP BY
```

For example:

```
SELECT *
FROM users
WHERE email = 'alice@example.com';
```

An index on:

```
email
```

may be useful.

Or:

```
SELECT *
FROM orders
WHERE user_id = 10;
```

An index on:

```
user_id
```

may be useful.

---

# 22. Indexes and Small Tables

Suppose your table contains:

```
10 rows
```

An index may provide little practical benefit.

But if your table contains:

```
10 million rows
```

efficient indexing can become extremely important.

So indexing decisions depend on things such as:

```
Table size
+
Query patterns
+
Data distribution
+
Read/write workload
```

---

# 23. Simple Mental Model

Remember this:

```
TABLE
│
├── Data
│
└── INDEX
      ↓
   Shortcut
      ↓
Find data faster
```

An index doesn't replace the table.

It provides an additional structure that helps MySQL locate rows efficiently.

---

# 24. A Real Example

Suppose:

```
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    age INT
);
```

We already have:

```
id
↓
PRIMARY KEY
↓
Indexed automatically
```

and:

```
email
↓
UNIQUE
↓
Unique index
```

If our application frequently searches by username:

```
SELECT *
FROM users
WHERE username = 'Alice';
```

we might add:

```
CREATE INDEX idx_username
ON users (username);
```

Now we have:

```
users
│
├── id
│    └── PRIMARY KEY / Index
│
├── username
│    └── Index
│
├── email
│    └── UNIQUE / Index
│
└── age
```

We don't automatically create an index on `age` just because the column exists.

---

# 25. The Most Important Idea

Don't think:

> **"Index = another copy of my table."**

Instead think:

> **"Index = a searchable shortcut that helps MySQL locate rows."**

Like a book:

```
Book
 │
 ├── Pages → Actual data
 │
 └── Index → Helps locate information
```

Database:

```
Table
 │
 ├── Rows → Actual data
 │
 └── Index → Helps locate rows
```

📌 **Index = Search shortcut.**

## Quick Summary

|Concept|Meaning|
|---|---|
|Index|Helps MySQL find data faster|
|Primary Key|Uniquely identifies a row and is indexed|
|Unique Index|Prevents duplicate values|
|Composite Index|Index involving multiple columns|
|Full-Text Index|Designed for text searching|
|`CREATE INDEX`|Creates an index|
|`SHOW INDEX`|Displays indexes|
|`EXPLAIN`|Helps analyze query execution|

Basic syntax:

```
CREATE INDEX index_name
ON table_name (column_name);
```

Example:

```
CREATE INDEX idx_email
ON users (email);
```

And remember the trade-off:

```
INDEX
 ↓
Faster reads
 +
More storage
 +
Potentially more work during writes
```
