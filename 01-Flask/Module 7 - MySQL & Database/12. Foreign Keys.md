A **Foreign Key** is a column that creates a **relationship between two tables**.

In simple words:

> **A Foreign Key stores the value of a Primary Key from another table.**

This allows MySQL to know how records in different tables are connected.

---

# 1. Start With a Simple Example

Suppose we have two tables:

```
users
orders
```

The `users` table:

```
users

┌────┬─────────┐
│ id │ name    │
├────┼─────────┤
│ 1  │ Alice   │
│ 2  │ Bob     │
│ 3  │ Charlie │
└────┴─────────┘
```

Here:

```
id → Primary Key
```

Now suppose we have an `orders` table:

```
orders

┌────┬─────────┐
│ id │ user_id │
├────┼─────────┤
│ 1  │ 2       │
│ 2  │ 1       │
│ 3  │ 2       │
└────┴─────────┘
```

Here:

```
user_id → Foreign Key
```

Why?

Because:

```
orders.user_id
       ↓
references
       ↓
users.id
```

---

# 2. What Does This Relationship Mean?

Look at:

```
orders

id | user_id
---+--------
1  | 2
2  | 1
3  | 2
```

The first order has:

```
user_id = 2
```

Look at `users`:

```
id | name
---+-------
1  | Alice
2  | Bob
3  | Charlie
```

So:

```
Order 1
   ↓
user_id = 2
   ↓
users.id = 2
   ↓
Bob
```

Therefore:

> **Order 1 belongs to Bob.**

That's what a foreign key allows us to represent.

---

# 3. Why Not Just Store the User's Name?

You might wonder why we don't do this:

```
orders

id | user_name
---+----------
1  | Bob
2  | Alice
3  | Bob
```

This creates problems.

Suppose Bob changes his name.

You may have to update it in many rows.

Instead:

```
users

id | name
---+-----
2  | Bob
```

and:

```
orders

id | user_id
---+--------
1  | 2
3  | 2
```

The orders only store:

```
2
```

which points to the user.

This avoids unnecessary duplication.

---

# 4. Creating a Foreign Key

First create the parent table:

```
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100)
);
```

Then create the child table:

```
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

The important part is:

```
FOREIGN KEY (user_id)
REFERENCES users(id)
```

Read it as:

> `user_id` in `orders` references `id` in `users`.

---

# 5. Parent Table and Child Table

You'll frequently hear these terms.

```
users
  ↓
Parent table
```

```
orders
  ↓
Child table
```

Why?

Because `orders` depends on `users` for its `user_id`.

Diagram:

```
┌──────────────┐
│    USERS     │
│              │
│ PK id        │
│ name         │
└──────┬───────┘
       │
       │
       │ FK user_id
       ▼
┌──────────────┐
│    ORDERS    │
│              │
│ PK id        │
│ FK user_id   │
└──────────────┘
```

---

# 6. Foreign Key Must Reference a Key

A foreign key normally references a column in another table that has a `PRIMARY KEY` or an appropriate `UNIQUE` constraint.

For example:

```
users
────────────
id ← PRIMARY KEY
```

Then:

```
orders
────────────
user_id ← FOREIGN KEY
```

Relationship:

```
orders.user_id
      ↓
users.id
```

---

# 7. Foreign Key Prevents Invalid References

This is one of its biggest advantages.

Suppose users are:

```
id | name
---+-------
1  | Alice
2  | Bob
```

There is no user `99`.

Now try:

```
INSERT INTO orders (id, user_id)
VALUES (1, 99);
```

MySQL can reject this because:

```
user_id = 99
```

doesn't correspond to an existing:

```
users.id = 99
```

So the database prevents a broken relationship.

---

# 8. Without a Foreign Key

Imagine the database allows:

```
users

1 | Alice
2 | Bob
```

and:

```
orders

1 | 2
2 | 99
3 | 1
```

What is:

```
user_id = 99
```

supposed to mean?

There is no such user.

This is called **referential integrity** problem.

A foreign key helps prevent this.

---

# 9. Foreign Key and Primary Key Together

These two work as a pair:

```
Primary Key
     ↓
Identifies a record

Foreign Key
     ↓
References that record
```

Example:

```
users
────────────
PK id
name
```

```
orders
────────────
PK id
FK user_id
```

Relationship:

```
users.id
   ▲
   │
   │
orders.user_id
```

Remember:

> **Primary Key identifies. Foreign Key connects.**

---

# 10. One-to-Many Relationship

Foreign keys are commonly used to create **one-to-many** relationships.

Example:

```
One User
   ↓
Many Orders
```

```
USER
 │
 ├── Order 1
 ├── Order 2
 └── Order 3
```

Database:

```
users
────────────
id | name
1  | Alice
2  | Bob
```

```
orders
────────────────
id | user_id
1  | 1
2  | 1
3  | 2
4  | 1
```

Here:

```
Alice → Order 1
Alice → Order 2
Alice → Order 4

Bob → Order 3
```

The foreign key `user_id` makes this relationship possible.

---

# 11. Foreign Key With `CREATE TABLE`

Complete example:

```
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

Then:

```
CREATE TABLE orders (
    id INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

Notice:

```
users
  │
  │ id
  ▼
orders
  │
  │ user_id
```

---

# 12. Naming the Foreign Key

You can give the foreign key constraint a name:

```
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    
    CONSTRAINT fk_orders_user
        FOREIGN KEY (user_id)
        REFERENCES users(id)
);
```

Here:

```
fk_orders_user
```

is the constraint name.

This can make larger databases easier to manage.

---

# 13. Foreign Key and DELETE

Here's an important situation.

Suppose:

```
users

id | name
---+------
1  | Alice
```

and:

```
orders

id | user_id
---+--------
1  | 1
2  | 1
```

Now you try to delete Alice:

```
DELETE FROM users
WHERE id = 1;
```

What should happen to her orders?

There are several possible rules.

MySQL lets you define these behaviors.

---

# 14. ON DELETE CASCADE

```
FOREIGN KEY (user_id)
REFERENCES users(id)
ON DELETE CASCADE
```

This means:

> If the parent user is deleted, automatically delete the related orders.

Before:

```
users
1 | Alice

orders
1 | 1
2 | 1
```

Delete Alice:

```
DELETE users WHERE id = 1;
```

After:

```
users
(empty)

orders
(empty)
```

The related orders are deleted automatically.

⚠️ This should be used carefully because deleting one parent record can delete many child records.

---

# 15. ON DELETE SET NULL

Another option:

```
FOREIGN KEY (user_id)
REFERENCES users(id)
ON DELETE SET NULL
```

This means:

> If the user is deleted, set `user_id` to `NULL`.

Before:

```
orders

id | user_id
---+--------
1  | 1
```

Delete user `1`.

After:

```
orders

id | user_id
---+--------
1  | NULL
```

For this to work, `user_id` generally needs to allow `NULL`:

```
user_id INT NULL
```

---

# 16. ON DELETE RESTRICT

Another behavior is to prevent deletion of the parent while related child records exist.

Conceptually:

```
User
 ↓
has orders
 ↓
Can't delete user yet
```

You must first deal with the related orders.

This is useful when deleting the parent would leave important data without its required relationship.

---

# 17. ON UPDATE CASCADE

You can also define behavior when a referenced key changes:

```
FOREIGN KEY (user_id)
REFERENCES users(id)
ON UPDATE CASCADE
```

If the referenced key changes, the related foreign-key values are updated accordingly.

However, with the common `AUTO_INCREMENT` integer ID design, primary keys usually don't need to change.

---

# 19. Foreign Key Does Not Have to Have the Same Name

These names:

```
users.id
orders.user_id
```

are conventional and easy to understand.

But technically, the foreign key column could have another name.

For example:

```
orders.customer_id
```

could reference:

```
users.id
```

```
FOREIGN KEY (customer_id)
REFERENCES users(id)
```

The names don't have to be identical.

What matters is the relationship.

---

# 20. A Foreign Key Can Reference Another Table

For example:

```
departments
────────────
id
name
```

and:

```
employees
────────────
id
name
department_id
```

Relationship:

```
departments.id
       ▲
       │
       │
employees.department_id
```

SQL:

```
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    department_id INT,
    FOREIGN KEY (department_id)
        REFERENCES departments(id)
);
```

Now each employee can be associated with a department.

---

# 21. Foreign Key vs Primary Key

This is the most important comparison:

|Primary Key|Foreign Key|
|---|---|
|Identifies a row|Connects to another table|
|Must be unique|Can usually repeat|
|Cannot be `NULL`|Can be `NULL` unless `NOT NULL` is specified|
|Usually exists in its own table|References a key in another table|
|One primary key constraint per table|A table can have multiple foreign keys|

For example:

```
users
────────────
PK id
name
```

```
orders
────────────
PK id
FK user_id
```

Notice something interesting:

```
orders.user_id
```

can repeat:

```
1
1
1
2
2
```

That's perfectly fine.

Why?

Because many orders can belong to the same user.

# 22. The Big Picture

Now connect everything you've learned:

```
              DATABASE
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
      USERS               ORDERS
   ┌─────────┐          ┌─────────┐
   │ PK id   │◄─────────│ FK user_id
   │ name    │          │ PK id   │
   └─────────┘          └─────────┘
```

The flow is:

```
Primary Key
    ↓
Uniquely identifies user
    ↓
Foreign Key
    ↓
References that user
    ↓
Relationship between tables
```

That's the heart of relational databases. 🔗

# Quick Summary

### Foreign Key

> A column that references a key in another table and helps maintain the relationship between tables.

Example:

```
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    FOREIGN KEY (user_id)
        REFERENCES users(id)
);
```

Meaning:

```
orders.user_id
      ↓
references
      ↓
users.id
```

### Remember:

```
PRIMARY KEY
↓
"Who is this?"

FOREIGN KEY
↓
"Which record in another table does this belong to?"
```
