**ER Diagram**, or **Entity-Relationship Diagram (ERD)**, is a visual representation of a database design.

It shows:

- **Entities** → what we store
- **Attributes** → information about those entities
- **Relationships** → how entities are connected

In simple words:

> **An ER diagram is a blueprint of the database.**

Before creating tables, we can draw an ER diagram to understand how everything fits together.

---

# 1. Why Do We Use ER Diagrams?

Imagine you're building a library database.

You need:

```
Students
Books
Authors
Borrowings
```

If you immediately start creating tables, you might make mistakes.

Instead, first create a diagram:

```
Students ──────── Borrowings ──────── Books
                                      │
                                      │
                                   Authors
```

Now we can visually understand the database structure.

---

# 2. ER Diagram Components

An ER diagram mainly contains:

```
Entity
Attribute
Relationship
```

Let's understand each one.

---

# 3. Entity

An **entity** is something about which we want to store information.

Examples:

```
Student
Book
Teacher
Course
Product
Order
User
```

In a database, entities generally become **tables**.

For example:

```
Entity              Table
────────────────────────────
Student       →     students
Book          →     books
Course        →     courses
```

In a traditional ER diagram, an entity is often represented using a rectangle:

```
┌─────────────┐
│   STUDENT   │
└─────────────┘
```

---

# 4. Attribute

An **attribute** describes an entity.

For example:

```
Student
│
├── id
├── name
├── email
└── age
```

These are attributes of the Student entity.

A traditional ER diagram represents attributes using ovals:

```
          (name)
             │
             │
(id) ──── STUDENT ──── (email)
             │
           (age)
```

In actual database design, these attributes usually become **columns**.

```
students
────────────
id
name
email
age
```

---

# 5. Relationship

A **relationship** describes how entities are connected.

For example:

```
Student ─── enrolls in ─── Course
```

This tells us:

> A student enrolls in a course.

Traditional ER diagrams often represent relationships using diamonds:

```
┌─────────┐      ◇───────────◇      ┌─────────┐
│ STUDENT │──────│  ENROLLS  │──────│ COURSE  │
└─────────┘      ◇───────────◇      └─────────┘
```

---

# 6. Entity + Attributes + Relationship

Let's put everything together.

Suppose we have:

```
Student
id
name
email
```

and:

```
Course
id
name
```

and the relationship:

```
Student enrolls in Course
```

The conceptual ER diagram is:

```
        (id)                    (id)
          │                       │
        (name)                  (name)
          │                       │
          ▼                       ▼
    ┌───────────┐            ┌───────────┐
    │  STUDENT  │            │  COURSE   │
    └─────┬─────┘            └─────┬─────┘
          │                         │
          │      ENROLLS IN         │
          └──────────◇──────────────┘
```

---

# 7. Cardinality

Now we need to answer an important question:

> **How many records can participate in a relationship?**

This is called **cardinality**.

The main types are:

```
1 : 1
1 : N
M : N
```

Let's understand them.

---

# 8. One-to-One (1:1)

One record from entity A is related to one record from entity B.

Example:

```
Person ───── Passport
```

One person has one passport.

Conceptually:

```
PERSON
   │
   │ 1
   │
   │ 1
   ▼
PASSPORT
```

So:

```
1 : 1
```

---

# 9. One-to-Many (1:N)

One record can be related to many records.

Example:

```
Teacher ───── Students
```

One teacher can teach many students.

But each student may belong to one teacher in this simplified example.

```
Teacher
   │
   │ 1
   │
   │ N
   ▼
Students
```

So:

```
1 : N
```

Another common example:

```
User ───── Orders
```

One user can have many orders.

```
User
 │
 ├── Order 1
 ├── Order 2
 └── Order 3
```

---

# 10. Many-to-Many (M:N)

Many records on one side can relate to many records on the other side.

Example:

```
Student ←→ Course
```

One student can take many courses:

```
Alice
 ├── Python
 ├── Java
 └── Database
```

And one course can have many students:

```
Python
 ├── Alice
 ├── Bob
 └── John
```

Therefore:

```
Student M : N Course
```

---

# 11. How Many-to-Many Works in MySQL

Here's something very important.

Relational databases normally don't directly store a many-to-many relationship in just two tables.

Instead, we introduce a **junction table** (also called an associative/intermediate table).

For example:

```
students
courses
student_courses
```

Diagram:

```
┌──────────┐          ┌─────────────────┐          ┌─────────┐
│ STUDENTS │          │ STUDENT_COURSES │          │ COURSES │
└────┬─────┘          └────────┬────────┘          └────┬────┘
     │                          │                        │
     │ 1                        │ N                      │
     └──────────────────────────┤                        │
                                │                        │
                                ├────────────────────────┘
                                │ N                    1
```

The junction table might contain:

```
student_courses
────────────────
student_id
course_id
```

Example:

```
student_id | course_id
-----------+----------
1          | 1
1          | 2
1          | 3
2          | 1
2          | 3
```

This is how the many-to-many relationship is represented.

We'll study this more when we reach **Foreign Keys** and **Relationships**.

---

# 12. Primary Key in an ER Diagram

Every entity/table generally has an identifier.

For example:

```
STUDENT
────────────
PK id
name
email
```

`PK` means **Primary Key**.

In an ER diagram, you may see:

```
Student
────────────
PK id
name
email
```

The primary key uniquely identifies each student.

---

# 13. Foreign Key in an ER Diagram

Suppose:

```
users
────────────
PK id
name
```

and:

```
orders
────────────
PK id
FK user_id
total
```

The relationship is:

```
┌─────────┐                 ┌─────────┐
│  USERS  │                 │ ORDERS  │
├─────────┤                 ├─────────┤
│ PK id   │◄───────────────┐│ PK id   │
│ name    │                └│ FK user_id
└─────────┘                 │ total
                            └─────────┘
```

Here:

```
orders.user_id
       ↓
users.id
```

So the foreign key connects the tables.

---

# 14. Crow's Foot Notation

When working with modern database tools, you'll often see **Crow's Foot notation**.

Instead of drawing diamonds and ovals, it uses symbols near the relationships.

For example:

```
USER ─────────────< ORDER
```

The crow's foot:

```
<
```

represents **many**.

So:

```
USER ─────────────< ORDER
  1                 N
```

means:

> One user can have many orders.

---

# 15. Common Crow's Foot Symbols

You'll commonly encounter:

```
│
│
```

means:

**one**

And:

```
<
```

means:

**many**

So:

```
USER │────────< ORDER
     1          N
```

means:

```
1 : N
```

---

# 16. Optional vs Mandatory Relationships

Sometimes a relationship isn't always required.

For example:

```
User ───── Order
```

A user might exist without having placed any orders.

So:

```
User
  │
  │ 0..N
  ▼
Order
```

means:

> A user can have zero or many orders.

On the other hand, every order might be required to belong to a user:

```
Order
  │
  │ exactly 1 user
  ▼
User
```

This distinction becomes important when designing constraints.

Let's design our earlier library system.

### Entities

```
STUDENT
BOOK
AUTHOR
BORROWING
```

### Relationships

```

```

```

├───────────┤
│ PK id     │
│ name      │
│ email     │
└─────┬─────┘
      │
      │ 1
      │
      │ N
┌─────▼────────┐
│  BORROWING   │
├──────────────┤
│ PK id        │
│ FK student_id│
│ FK book_id   │
│ borrowed_at  │
│ returned_at  │
└──────┬───────┘
       │
       │ N
       │
       │ 1
┌──────▼──────┐
│    BOOK     │
├─────────────┤
│ PK id       │
│ title       │
│ FK author_id│
└──────┬──────┘
       │
       │ N
       │
       │ 1
┌──────▼──────┐
│   AUTHOR    │
├─────────────┤
│ PK id       │
│ name        │
└─────────────┘
```

Now we can visually understand the entire database.

# 18. ER Diagram vs Database Tables

These are related but not exactly the same thing.

### ER Diagram

A **visual design**:

```
Student ─────── Course
```

### Database

The actual implementation:

```
students
courses
student_courses
```

So:

```
ER Diagram
    ↓
Database Design
    ↓
SQL
    ↓
Actual Tables
```

---

# 19. ER Diagram Example for an Online Store

Suppose we're designing an online store.

Entities:

```
User
Product
Order
```

Relationships:

```
User → places → Order
Order → contains → Product
```

But an order can contain many products, and a product can appear in many orders.

So we'd need:

```
users
orders
products
order_items
```

Conceptually:

```
┌─────────┐
│  USERS  │
└────┬────┘
     │ 1
     │
     │ N
┌────▼────┐
│ ORDERS  │
└────┬────┘
     │ 1
     │
     │ N
┌────▼─────────┐
│ ORDER_ITEMS  │
└────┬─────────┘
     │ N
     │
     │ 1
┌────▼──────┐
│ PRODUCTS  │
└───────────┘
```

This is a much cleaner design than putting everything into one giant table.

# 20. Why ER Diagrams Are Useful for Flask

Eventually, you'll build something like:

```
Flask Application
       │
       ▼
SQLAlchemy Models
       │
       ▼
MySQL Tables
```

Before writing those models, you can design:

```
ER Diagram
```

For example:

```
User
 │
 │ 1:N
 ▼
Post
 │
 │ 1:N
 ▼
Comment
```

Then implement those relationships using SQLAlchemy.

So ER diagrams become a bridge between:

```
Application requirements
          ↓
    Database design
          ↓
      SQLAlchemy
          ↓
         MySQL
```

# 21. The Most Important Things to Remember

If you remember only these, you're good:

### Entity

> Something we store information about.

```
Student
```

### Attribute

> Property of an entity.

```
name
email
age
```

### Relationship

> Connection between entities.

```
Student ─── enrolls in ─── Course
```

### Primary Key

> Uniquely identifies a record.

```
id
```

### Foreign Key

> Connects records between tables.

```
student_id → students.id
```

### Cardinality

> Describes how many records can be related.

```
1:1
1:N
```
