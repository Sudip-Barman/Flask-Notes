A **transaction** in MySQL is a group of one or more SQL operations that are treated as **one complete unit of work**.

The simplest definition:

> **Transaction = Either all required operations succeed, or the changes can be undone.**

This is especially important when several database operations depend on each other.

---

# 1. Why Do We Need Transactions?

Imagine a bank transfer.

You want to transfer ₹1,000 from **Account A** to **Account B**.

There are two operations:

```
1. Remove ₹1,000 from Account A
2. Add ₹1,000 to Account B
```

Suppose this happens:

```
Account A
₹10,000
   ↓
- ₹1,000
   ↓
₹9,000
```

But then the second operation fails:

```
Account B
₹5,000
   ↓
❌ Failed
   ↓
₹5,000
```

Now we have:

```
A → lost ₹1,000
B → didn't receive ₹1,000
```

The money has effectively disappeared from the system. 💸

A transaction prevents this kind of partial update.

---

# 2. Transaction Concept

We can treat both operations as **one unit**:

```
START TRANSACTION
      ↓
Remove money from A
      ↓
Add money to B
      ↓
Everything successful?
    ↙       ↘
  YES        NO
   ↓          ↓
COMMIT     ROLLBACK
   ↓          ↓
Save       Undo
changes    changes
```

So:

```
COMMIT
↓
Make changes permanent

ROLLBACK
↓
Undo changes
```

These two commands are the heart of transactions.

---

# 3. Basic Transaction Syntax

Start a transaction:

```
START TRANSACTION;
```

Perform your SQL operations:

```
UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;
```

If everything is successful:

```
COMMIT;
```

If something goes wrong:

```
ROLLBACK;
```

---

# 4. What Does COMMIT Mean?

`COMMIT` means:

> **Save the changes permanently.**

Example:

```
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

COMMIT;
```

After `COMMIT`, the update becomes permanent.

Conceptually:

```
UPDATE
  ↓
Temporary transaction changes
  ↓
COMMIT
  ↓
Permanent changes
```

---

# 5. What Does ROLLBACK Mean?

`ROLLBACK` means:

> **Undo changes made during the current transaction.**

Example:

```
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

ROLLBACK;
```

The update is undone.

The account goes back to its previous state.

```
Before
₹10,000

UPDATE
₹9,000

ROLLBACK
₹10,000
```

---

# 6. Complete Bank Transfer Example

Suppose:

```
Account 1 → ₹10,000
Account 2 → ₹5,000
```

We want to transfer ₹1,000.

```
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

After the transaction:

```
Account 1 → ₹9,000
Account 2 → ₹6,000
```

Both changes are saved.

---

# 7. What If Something Goes Wrong?

Suppose the first operation succeeds:

```
Account 1
₹10,000
   ↓
₹9,000
```

But the second operation fails.

Instead of leaving Account 1 at ₹9,000, we can:

```
ROLLBACK;
```

The transaction returns the database to the state before the transaction began.

```
Account 1
₹9,000
   ↓
ROLLBACK
   ↓
₹10,000
```

That's the power of transactions.

---

# 8. Transaction = All or Nothing

This is the most important idea.

Suppose we have:

```
Operation 1 ✓
Operation 2 ✓
Operation 3 ✓
Operation 4 ❌
```

Without a transaction:

```
Operation 1 → saved
Operation 2 → saved
Operation 3 → saved
Operation 4 → failed
```

The database may be left partially changed.

With a transaction:

```
Operation 1 ✓
Operation 2 ✓
Operation 3 ✓
Operation 4 ❌
       ↓
   ROLLBACK
       ↓
Everything undone
```

So the transaction gives us:

> **All operations succeed together, or the transaction can be rolled back.**

---

# 9. Transaction Example With Orders

Imagine placing an order.

Several things may need to happen:

```
1. Create order
2. Add order items
3. Reduce product stock
4. Record payment
```

For example:

```
START TRANSACTION;

INSERT INTO orders (...);

INSERT INTO order_items (...);

UPDATE products
SET stock = stock - 1
WHERE id = 10;

INSERT INTO payments (...);

COMMIT;
```

If everything succeeds:

```
COMMIT
```

If something fails:

```
ROLLBACK
```

This prevents situations such as:

```
Order created ✓
Stock reduced ✓
Payment record ❌
```

leaving the database in an inconsistent state.

# 10. Transaction Commands

The basic commands you need to know are:

### Start

```
START TRANSACTION;
```

### Save

```
COMMIT;
```

### Undo

```
ROLLBACK;
```

There are also:

```
SAVEPOINT
ROLLBACK TO SAVEPOINT
RELEASE SAVEPOINT
```

We'll look at those shortly.

---

# 11. START TRANSACTION

You can start a transaction with:

```
START TRANSACTION;
```

MySQL also supports:

```
BEGIN;
```

So:

```
START TRANSACTION;
```

and:

```
BEGIN;
```

can be used to start a transaction.

For notes, I'd recommend remembering:

```
START TRANSACTION;
```

because it makes the intention very clear.

---

# 12. COMMIT

Example:

```
START TRANSACTION;

INSERT INTO students (name, age)
VALUES ('Alice', 20);

COMMIT;
```

The new student is permanently saved.

---

# 13. ROLLBACK

Example:

```
START TRANSACTION;

INSERT INTO students (name, age)
VALUES ('Alice', 20);

ROLLBACK;
```

The insertion is undone.

So:

```
START TRANSACTION
      ↓
INSERT
      ↓
ROLLBACK
      ↓
INSERT disappears
```

---

# 14. Transaction With DELETE

Transactions work with `DELETE` too.

```
START TRANSACTION;

DELETE FROM students
WHERE id = 10;

ROLLBACK;
```

The deleted row can be restored by the rollback, assuming the operation is transactional and hasn't been committed.

If instead:

```
START TRANSACTION;

DELETE FROM students
WHERE id = 10;

COMMIT;
```

the deletion becomes permanent.

---

# 15. Transaction With INSERT

```
START TRANSACTION;

INSERT INTO students (name, age)
VALUES ('Bob', 21);

ROLLBACK;
```

The insertion is undone.

Or:

```
START TRANSACTION;

INSERT INTO students (name, age)
VALUES ('Bob', 21);

COMMIT;
```

The insertion is saved.

---

# 16. Transaction With UPDATE

```
START TRANSACTION;

UPDATE students
SET age = 25
WHERE id = 1;

ROLLBACK;
```

The age change is undone.

Or:

```
START TRANSACTION;

UPDATE students
SET age = 25
WHERE id = 1;

COMMIT;
```

The new age is saved.

---

# 17. SAVEPOINT

Sometimes you don't want to undo **the entire transaction**.

You can create a checkpoint using `SAVEPOINT`.

Example:

```
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

SAVEPOINT point1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;
```

Now imagine you want to undo only the changes after `point1`.

You can use:

```
ROLLBACK TO SAVEPOINT point1;
```

The transaction goes back to the savepoint.

---

# 18. Understanding SAVEPOINT

Think of it as a checkpoint in a game 🎮.

```
START TRANSACTION
       ↓
Operation A
       ↓
SAVEPOINT
       ↓
Operation B
       ↓
Operation C
       ↓
Something went wrong
       ↓
ROLLBACK TO SAVEPOINT
       ↓
Back to checkpoint
```

You don't necessarily lose everything.

---

# 19. Creating Multiple Savepoints

You can create multiple savepoints:

```
START TRANSACTION;

UPDATE ...;

SAVEPOINT step1;

INSERT ...;

SAVEPOINT step2;

DELETE ...;
```

Then you could go back to:

```
ROLLBACK TO SAVEPOINT step2;
```

or:

```
ROLLBACK TO SAVEPOINT step1;
```

depending on what you need.

---

# 20. Releasing a Savepoint

You can remove a savepoint:

```
RELEASE SAVEPOINT step1;
```

After releasing it, you can no longer roll back to that savepoint.

---

# 21. Transaction Properties: ACID

Transactions are commonly described using **ACID** properties.

This is an important database concept.

```
A → Atomicity
C → Consistency
I → Isolation
D → Durability
```

Let's understand each.

---

# 22. A = Atomicity

**Atomicity** means:

> The transaction is treated as one unit.

Either the entire transaction succeeds, or its changes can be rolled back.

Example:

```
Transfer ₹1,000

Remove money ✓
Add money ❌
     ↓
ROLLBACK
     ↓
Undo transfer changes
```

Think:

```
Atomicity
↓
All or nothing
```

---

# 23. C = Consistency

**Consistency** means:

> A transaction should take the database from one valid state to another valid state.

For example, suppose a rule says:

```
balance cannot be negative
```

A properly designed transaction should not leave the database violating that rule.

Before:

```
Account A → ₹10,000
Account B → ₹5,000
```

After a valid transfer:

```
Account A → ₹9,000
Account B → ₹6,000
```

The database remains logically valid.

Think:

```
Consistency
↓
Database rules remain valid
```

---

# 24. I = Isolation

**Isolation** means:

> Transactions running at the same time should not incorrectly interfere with each other.

Imagine:

```
Transaction A
       ↓
Changing account balance

Transaction B
       ↓
Reading/updating account balance
```

The database has mechanisms to control how these concurrent transactions interact.

This becomes particularly important when many users are accessing the database simultaneously.

Think:

```
Isolation
↓
Transactions don't improperly interfere
```

---

# 25. D = Durability

**Durability** means:

> Once a transaction has been successfully committed, its changes should survive afterward, including normal restarts or failures handled by the database's recovery mechanisms.

For example:

```
UPDATE
  ↓
COMMIT
  ↓
Saved
```

After a normal database restart, the committed change should still be there.

Think:

```
Durability
↓
Committed changes stay
```

---

# 26. ACID in One Table

|Property|Simple meaning|
|---|---|
|**Atomicity**|All or nothing|
|**Consistency**|Database remains valid|
|**Isolation**|Concurrent transactions don't improperly interfere|
|**Durability**|Committed changes persist|

Easy memory trick:

```
A → All or nothing
C → Correct/valid state
I → Independent transactions
D → Doesn't disappear after commit
```

---

# 27. Autocommit

MySQL commonly operates with **autocommit enabled by default** for many sessions.

That means individual SQL statements are automatically committed unless you explicitly start a transaction or otherwise change the transaction behavior.

For example:

```
UPDATE students
SET age = 25
WHERE id = 1;
```

With autocommit enabled, that statement is normally committed automatically.

If you want several operations to form one transaction:

```
START TRANSACTION;
```

Then:

```
UPDATE ...;
UPDATE ...;
INSERT ...;
```

and finally:

```
COMMIT;
```

or:

```
ROLLBACK;
```

---

# 28. Important: Not Every Storage Engine Behaves the Same

Transactions depend on the storage engine.

In modern MySQL usage, **InnoDB** is the standard transactional storage engine.

So when working with transactions, you generally want your tables to use InnoDB.

You can check a table's engine with:

```
SHOW TABLE STATUS;
```

or inspect the table definition:

```
SHOW CREATE TABLE students;
```

You may see something like:

```
ENGINE=InnoDB
```

# 29. A Complete Example

Suppose we have:

```
accounts

id | name  | balance
---|-------|--------
1  | Alice | 10000
2  | Bob   | 5000
```

Transfer ₹1,000 from Alice to Bob:

```
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

Final:

```
Alice → ₹9,000
Bob   → ₹6,000
```

If something goes wrong before `COMMIT`:

```
ROLLBACK;
```

Then the transaction's changes are undone.

# 30. Why Transactions Matter in Real Applications

Transactions are useful whenever several database operations must stay consistent.

Common examples include:

```
Bank transfers
Order processing
Inventory updates
Payment processing
Ticket booking
Account creation
Financial records
```

For example, ticket booking might involve:

```
1. Check seat
2. Reserve seat
3. Create booking
4. Record payment
```

If step 3 fails after step 2 succeeds, you don't want the seat to remain incorrectly reserved.

A transaction can group the related operations.

# 31. The Most Important Pattern

For your notes, remember this:

```
START TRANSACTION;

-- SQL operation 1
-- SQL operation 2
-- SQL operation 3

COMMIT;
```

If something goes wrong:

```
START TRANSACTION;

-- SQL operations

ROLLBACK;
```

So:

```
START TRANSACTION
        ↓
     Do work
        ↓
   ┌────┴────┐
   ↓         ↓
Success    Failure
   ↓         ↓
COMMIT    ROLLBACK
   ↓         ↓
 Save       Undo
```

---

# 32. Transaction vs CRUD

You learned CRUD earlier:

```
CREATE → INSERT
READ   → SELECT
UPDATE → UPDATE
DELETE → DELETE
```

A transaction isn't another CRUD operation.

Instead, it **controls a group of operations**.

For example:

```
START TRANSACTION;

INSERT ...;
UPDATE ...;
DELETE ...;

COMMIT;
```

So:

```
CRUD
↓
Operations on data

Transaction
↓
Controls a group of operations
```

---

# 33. One Important Warning

`ROLLBACK` only works for changes that are still part of the current transaction.

Once you do:

```
COMMIT;
```

you generally cannot simply:

```
ROLLBACK;
```

and expect the committed changes to disappear.

Think:

```
START
 ↓
Changes
 ↓
COMMIT
 ↓
Transaction finished
```

The rollback window has closed. 🚪

---

# 34. Final Mental Model

Imagine you're editing a document.

```
START TRANSACTION
        ↓
Make several changes
        ↓
        ├── Everything looks good
        │        ↓
        │      COMMIT
        │        ↓
        │      Save
        │
        └── Something went wrong
                 ↓
              ROLLBACK
                 ↓
             Undo changes
```

That's essentially what a database transaction does.

## Quick Revision

```
TRANSACTION
→ Group of database operations treated as one unit.

START TRANSACTION
→ Start a transaction.

COMMIT
→ Permanently save the transaction's changes.

ROLLBACK
→ Undo uncommitted transaction changes.

SAVEPOINT
→ Create a checkpoint inside a transaction.

ROLLBACK TO SAVEPOINT
→ Go back to that checkpoint.

ACID
→ Atomicity
→ Consistency
→ Isolation
→ Durability
```

### The golden rule 🧠

> **`COMMIT` = Save it. `ROLLBACK` = Undo it.**
