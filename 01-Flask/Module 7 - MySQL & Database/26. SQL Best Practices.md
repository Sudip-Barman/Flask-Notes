
**SQL Best Practices** are recommended ways of writing SQL so that your database code is:

- Easy to understand
- Safe
- Fast
- Maintainable
- Less prone to errors
- Scalable

In simple words:

> **SQL Best Practices = Rules for writing clean, safe, and efficient SQL.**

---

# 1. Use Meaningful Names

Use clear names for databases, tables, and columns.

### ❌ Bad

```
CREATE TABLE t1 (
    x INT,
    y VARCHAR(100)
);
```

It's difficult to understand what `t1`, `x`, and `y` represent.

### ✅ Better

```
CREATE TABLE students (
    id INT,
    name VARCHAR(100)
);
```

Now the purpose is obvious.

### Rule

Use names that describe the data:

```
students
orders
products
email
created_at
student_id
```

instead of:

```
t1
x
abc
data1
```

---

# 2. Use Primary Keys

Every important table should normally have a primary key that uniquely identifies each row.

Example:

```
CREATE TABLE students (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    age INT
);
```

Now every student can be uniquely identified:

```
id
↓
1 → Alice
2 → Bob
3 → Charlie
```

A primary key helps with:

- Uniqueness
- Relationships
- Searching
- Updating specific rows
- Joining tables

---

# 3. Use Foreign Keys for Relationships

When one table references another table, use a foreign key where appropriate.

Example:

```
CREATE TABLE orders (
    id INT PRIMARY KEY,
    student_id INT,
    amount DECIMAL(10,2),

    FOREIGN KEY (student_id)
        REFERENCES students(id)
);
```

This creates the relationship:

```
students.id
     ↑
     │
orders.student_id
```

It helps maintain **referential integrity**.

---

# 4. Choose Appropriate Data Types

Don't use unnecessarily large or inappropriate data types.

### ❌

```
age VARCHAR(100)
```

Age is a number, so storing it as text isn't ideal.

### ✅

```
age INT
```

Similarly:

```
Age           → INT
Price         → DECIMAL
Name          → VARCHAR
Date          → DATE
Date + time   → DATETIME
True/False    → BOOLEAN
```

Choosing suitable types can improve storage, validation, and query behavior.

---

# 5. Use `DECIMAL` for Money

For monetary values, don't normally use floating-point types such as `FLOAT` or `DOUBLE` when exact decimal arithmetic is required.

Prefer:

```
price DECIMAL(10,2)
```

For example:

```
999.99
1500.50
25.00
```

Why?

Floating-point numbers can introduce rounding/precision issues.

For financial data, exact decimal types are generally the safer choice.

---

# 6. Avoid `SELECT *` When You Don't Need Everything

You can write:

```
SELECT *
FROM students;
```

This means:

> Return every column.

It's convenient when exploring a table, but in application code it's often better to specify the columns you actually need.

### Instead:

```
SELECT id, name, age
FROM students;
```

Benefits:

- Makes the query clearer
- Returns less unnecessary data
- Avoids accidentally retrieving newly added columns
- Can reduce data transfer

Think:

```
SELECT *
↓
Give me everything

SELECT id, name
↓
Give me exactly what I need
```

---

# 7. Always Be Careful With `UPDATE`

This is a very important rule.

Never casually write:

```
UPDATE students
SET age = 25;
```

Without a `WHERE` clause, this can update **every row**.

For example:

```
Alice   → 25
Bob     → 25
Charlie → 25
David   → 25
```

Instead:

```
UPDATE students
SET age = 25
WHERE id = 1;
```

Now only the student with `id = 1` is updated.

---

# 8. Be Careful With `DELETE`

The same danger applies to `DELETE`.

### ⚠️ Dangerous

```
DELETE FROM students;
```

This removes all rows from the table.

### Safer

```
DELETE FROM students
WHERE id = 1;
```

Only the matching row is deleted.

Before running an important `DELETE`, it's often wise to first check what will be affected:

```
SELECT *
FROM students
WHERE id = 1;
```

Then perform:

```
DELETE FROM students
WHERE id = 1;
```

---

# 9. Use `WHERE` Carefully

`WHERE` determines which rows are affected or returned.

For example:

```
UPDATE products
SET price = 500
WHERE id = 10;
```

The `WHERE` condition is:

```
id = 10
```

Without it:

```
UPDATE products
SET price = 500;
```

every product could be changed.

A useful habit is:

> **Before UPDATE or DELETE, mentally ask: "Which rows will this affect?"**

---

# 10. Use Transactions for Related Operations

When multiple operations must succeed together, use a transaction.

For example:

```
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;
```

If something goes wrong:

```
ROLLBACK;
```

Remember:

```
Multiple related operations
          ↓
START TRANSACTION
          ↓
       Do work
          ↓
   ┌──────┴──────┐
   ↓             ↓
Success       Failure
   ↓             ↓
COMMIT        ROLLBACK
```

---

# 11. Use Indexes Wisely

Indexes can make searching faster.

For example:

```
CREATE INDEX idx_email
ON users(email);
```

Now searches involving `email` may be able to use that index.

For example:

```
SELECT *
FROM users
WHERE email = 'example@email.com';
```

However, don't create indexes on every column.

Indexes have costs:

```
More indexes
     ↓
Faster reads in suitable queries
     ↓
But
     ↓
More storage
     ↓
More work during INSERT/UPDATE/DELETE
```

So indexes should be added based on actual query patterns and constraints.

---

# 12. Primary Keys Are Indexed

When you create:

```
id INT PRIMARY KEY
```

MySQL automatically creates the required index for the primary key.

So you normally don't need to separately create:

```
CREATE INDEX ...
```

for the same primary-key column.

---

# 13. Index Columns Used Frequently for Searching

Suppose you frequently search:

```
SELECT *
FROM users
WHERE email = 'example@email.com';
```

An index on `email` may be useful:

```
CREATE INDEX idx_email
ON users(email);
```

Common candidates can include columns frequently used in:

```
WHERE
JOIN
ORDER BY
```

But indexing decisions depend on the actual workload and data distribution.

---

# 14. Don't Overuse Indexes

Imagine a table has:

```
id
name
email
age
city
phone
country
```

You shouldn't automatically create an index for all seven columns.

Instead, ask:

> Which columns are actually used frequently in important queries?

For example:

```
email → frequently searched
student_id → frequently joined
created_at → frequently filtered/sorted
```

Those may be good candidates.

---

# 15. Use `NOT NULL` When a Value Is Required

If a column must always have a value:

```
name VARCHAR(100) NOT NULL
```

This prevents:

```
name = NULL
```

when the column is required.

For example:

```
CREATE TABLE students (
    id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

Now a student must have a name.

---

# 16. Use Constraints to Protect Your Data

Constraints aren't just decoration. They help prevent invalid data.

For example:

```
CREATE TABLE students (
    id INT PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    age INT CHECK (age >= 0)
);
```

Here:

```
PRIMARY KEY
→ Unique row identifier

UNIQUE
→ Prevent duplicate values

NOT NULL
→ Value is required

CHECK
→ Value must satisfy a condition
```

The database itself helps enforce the rules.

---

# 17. Don't Store Multiple Values in One Column

Avoid designs like:

```
id | name  | phone_numbers
---|-------|-------------------
1  | Alice | 123,456,789
```

This makes searching and managing the individual phone numbers difficult.

Instead, depending on the requirements, use a separate table:

```
students
---------
id
name

student_phones
--------------
id
student_id
phone
```

Then:

```
students
   ↓
student_phones
```

This follows good relational database design.

---

# 18. Avoid Unnecessary Data Duplication

Suppose you have:

```
orders

id | student_name | amount
```

If the same student places 100 orders, their name could be repeated 100 times.

A normalized design can instead use:

```
students
---------
id
name
```

and:

```
orders
---------
id
student_id
amount
```

Then:

```
students.id
     ↑
     │
orders.student_id
```

Use a `JOIN` when you need the student's name.

This reduces unnecessary duplication.

---

# 19. Use Parameterized Queries

This is one of the **most important security practices**.

Never build SQL by directly concatenating untrusted user input into the SQL string.

### ❌ Dangerous approach

Conceptually:

```
query = "SELECT * FROM users WHERE name = '" + username + "'"
```

If `username` contains specially crafted SQL input, the query can be manipulated.

This is called **SQL Injection**.

### ✅ Better approach

Use parameterized queries provided by your database library.

For example, with Python's DB-API style:

```
cursor.execute(
    "SELECT * FROM users WHERE name = %s",
    (username,)
)
```

The database driver handles the value as data rather than treating it as part of the SQL command.

---

# 20. SQL Injection

SQL Injection happens when untrusted input is incorrectly inserted into SQL.

Imagine a login system doing something like:

```
User input
   ↓
Directly inserted into SQL
   ↓
SQL command gets manipulated
```

This can potentially allow an attacker to:

- Bypass authentication
- Read unauthorized data
- Modify data
- Delete data

Therefore:

> **Never trust user input. Use parameterized queries.**

This is especially important when you later connect MySQL with Flask.

---

# 21. Don't Store Passwords as Plain Text

Never store passwords like:

```
password = "mypassword123"
```

in a database.

Instead, passwords should be stored as **secure password hashes** using a password-hashing algorithm/library designed for passwords.

Conceptually:

```
User password
      ↓
Password hashing
      ↓
Password hash
      ↓
Database
```

When the user logs in:

```
Entered password
      ↓
Verify against stored hash
      ↓
Match?
```

The original password should not be recoverable from the stored hash under normal password-hashing design.

---

# 22. Keep SQL Formatting Clean

Compare these:

### ❌ Hard to read

```
SELECT s.name,o.amount FROM students s JOIN orders o ON s.id=o.student_id WHERE o.amount>500 ORDER BY o.amount DESC;
```

### ✅ Easier to read

```
SELECT
    s.name,
    o.amount
FROM students AS s
JOIN orders AS o
    ON s.id = o.student_id
WHERE o.amount > 500
ORDER BY o.amount DESC;
```

Both express the same basic query, but the second is much easier to understand.

---

# 23. Use Consistent Naming

Pick a naming style and stick with it.

For example:

```
student_id
created_at
updated_at
first_name
last_name
```

Instead of randomly mixing:

```
studentId
Student_ID
studentID
studentid
```

Consistency makes large projects much easier to maintain.

---

# 24. Use Comments for Complicated Queries

If a query is complicated, comments can explain why it exists.

Example:

```
-- Find students who placed at least two orders
SELECT
    s.name,
    COUNT(o.id) AS total_orders
FROM students AS s
JOIN orders AS o
    ON s.id = o.student_id
GROUP BY s.id, s.name
HAVING COUNT(o.id) >= 2;
```

Comments are particularly useful for unusual business rules or complicated logic.

---

# 25. Don't Make Queries More Complicated Than Necessary

If you need:

```
Student names
```

don't write a query involving five tables when one table is enough.

Prefer:

```
SELECT name
FROM students;
```

rather than unnecessarily complicated SQL.

Simple queries are generally easier to:

- Read
- Debug
- Maintain
- Optimize

---

# 26. Use `EXPLAIN` to Understand Query Performance

MySQL provides:

```
EXPLAIN
```

to show how MySQL plans to execute a query.

For example:

```
EXPLAIN
SELECT *
FROM students
WHERE email = 'example@email.com';
```

It can help you investigate:

- Which indexes are being considered or used
- How tables are accessed
- Join strategies
- Estimated rows examined

When a query becomes slow, `EXPLAIN` is one of the tools you should learn to use.

---

# 27. Don't Optimize Too Early

You might hear:

> "Indexes make queries faster, so add indexes everywhere!"

That's not a good rule.

First:

```
Write correct query
       ↓
Measure performance
       ↓
Find bottleneck
       ↓
Optimize
```

Use tools such as:

```
EXPLAIN
```

to understand what is happening.

Correctness comes first.

---

# 28. Back Up Important Databases

A database can contain extremely important information.

You should have a backup strategy.

Conceptually:

```
Database
   ↓
Backup
   ↓
Safe copy
```

If the database is accidentally damaged, deleted, or corrupted, a backup can help restore it.

For production systems, backups should be automated and regularly tested.

---

# 29. Use Least Privilege

Database users should have only the permissions they actually need.

For example, an application that only needs to read data shouldn't necessarily have permission to:

```
DROP DATABASE
DROP TABLE
```

The idea is:

> **Give each database user the minimum permissions required for its job.**

This reduces the potential damage if credentials are compromised.

---

# 30. Don't Give Your Application Excessive Database Permissions

Imagine your application only needs:

```
SELECT
INSERT
UPDATE
```

There may be no reason to give it unrestricted administrative privileges.

A safer architecture is:

```
Application
     ↓
Limited database user
     ↓
Only required permissions
```

rather than:

```
Application
     ↓
Database administrator
     ↓
Everything allowed
```

---

# 31. Use Transactions for Data Integrity

You've just learned transactions.

Best practice:

> Use a transaction when several database changes belong to one logical operation.

For example:

```
START TRANSACTION;

UPDATE ...;
INSERT ...;
UPDATE ...;

COMMIT;
```

If something fails:

```
ROLLBACK;
```

This prevents partially completed operations from leaving inconsistent data.

---

# 32. Don't Ignore NULL

`NULL` means:

> **Missing, unknown, or not applicable value.**

It is not the same as:

```
0
```

and not the same as:

```
''
```

For example:

```
age = NULL
```

means the age is unknown/missing.

To check for NULL, use:

```
WHERE age IS NULL
```

not:

```
WHERE age = NULL
```

Similarly:

```
WHERE age IS NOT NULL
```

checks for a non-NULL value.

---

# 33. Be Careful With `OR`

Consider:

```
SELECT *
FROM students
WHERE city = 'Kolkata'
   OR city = 'Delhi'
   AND age >= 18;
```

SQL operator precedence can make this behave differently from what you intended.

When logic gets complicated, use parentheses:

```
SELECT *
FROM students
WHERE
    (city = 'Kolkata' OR city = 'Delhi')
    AND age >= 18;
```

This makes your intention explicit.

---

# 34. Don't Use Reserved Words as Names

Some words have special meaning in SQL.

Examples include:

```
SELECT
TABLE
ORDER
GROUP
WHERE
INDEX
```

Avoid naming a table or column something confusing like:

```
CREATE TABLE order (...);
```

Prefer something like:

```
CREATE TABLE orders (...);
```

This avoids unnecessary quoting and confusion.

---

# 35. Use `LIMIT` When Exploring Large Tables

Suppose a table contains millions of rows.

Don't casually run:

```
SELECT *
FROM students;
```

when you're only exploring the data.

Instead:

```
SELECT *
FROM students
LIMIT 20;
```

This gives you a small sample.

You can also use:

```
SELECT id, name
FROM students
LIMIT 20;
```

This is especially useful while developing and debugging.

---

# 36. Test Dangerous Queries Before Executing Them

Before:

```
DELETE FROM students
WHERE age < 18;
```

first run:

```
SELECT *
FROM students
WHERE age < 18;
```

This lets you see exactly which rows you're about to delete.

Similarly, before:

```
UPDATE students
SET city = 'Kolkata'
WHERE age > 20;
```

first check:

```
SELECT *
FROM students
WHERE age > 20;
```

A very good habit:

```
SELECT first
      ↓
Check affected rows
      ↓
UPDATE / DELETE
```

# 38. The Golden SQL Rules 🧠

If you remember only a handful of rules, remember these:

```
1. Design tables properly.
2. Use Primary Keys.
3. Use Foreign Keys for relationships.
4. Choose appropriate Data Types.
5. Use Constraints.
6. Use Indexes where they actually help.
7. Never blindly UPDATE or DELETE without checking WHERE.
8. Use Parameterized Queries.
9. Use Transactions for related operations.
10. Back up important data.
11. Give users only necessary permissions.
12. Keep SQL readable.
```

And perhaps the most important safety rule:

```
Before UPDATE or DELETE
        ↓
Run SELECT with the same WHERE
        ↓
Check the rows
        ↓
Then modify them
```

That one habit can save you from a very unpleasant afternoon. 😄
