A **constraint** is a rule that controls what data can be stored in a database table.

In simple words:

> **Constraints prevent invalid or unwanted data from entering the database.**

For example, if every student must have a name, we can tell MySQL:

```
name VARCHAR(100) NOT NULL
```

Now MySQL won't allow a student record without a name.

---

# 1. Why Do We Need Constraints?

Suppose we have:

```
students

id | name | email
---+------+----------------
1  | Alice| alice@example.com
2  | Bob  | bob@example.com
```

Without proper rules, someone might accidentally insert:

```
id | name | email
---+------+----------------
3  | NULL | NULL
```

Maybe that's not allowed in our application.

Constraints allow the **database itself** to enforce these rules.

---

# 2. Main Types of Constraints

The important MySQL constraints are:

```
Constraints
│
├── PRIMARY KEY
├── FOREIGN KEY
├── NOT NULL
├── UNIQUE
├── DEFAULT
└── CHECK
```

You'll also often see `AUTO_INCREMENT`, but technically it is an attribute rather than a constraint.

Let's understand each one.

---

# 3. NOT NULL

`NOT NULL` means:

> This column must have a value.

Example:

```
CREATE TABLE students (
    id INT,
    name VARCHAR(100) NOT NULL
);
```

Here:

```
name → required
```

This is allowed:

```
INSERT INTO students (id, name)
VALUES (1, 'Alice');
```

But this isn't:

```
INSERT INTO students (id, name)
VALUES (2, NULL);
```

MySQL rejects it because:

```
name → NOT NULL
```

---

# 4. UNIQUE

`UNIQUE` means:

> A value cannot be duplicated in that column.

For example, suppose every student must have a unique email.

```
CREATE TABLE students (
    id INT,
    email VARCHAR(255) UNIQUE
);
```

This is allowed:

```
alice@example.com
bob@example.com
```

But this would fail:

```
alice@example.com
alice@example.com
```

because the same email appears twice.

### Think of it as:

```
UNIQUE
   ↓
No duplicate values
```

---

# 5. PRIMARY KEY

A **primary key** uniquely identifies each row.

Example:

```
CREATE TABLE students (
    id INT PRIMARY KEY,
    name VARCHAR(100)
);
```

Now:

```
id
↓
unique identity of each student
```

For example:

```
id | name
---+--------
1  | Alice
2  | Bob
3  | Charlie
```

You cannot have:

```
1 | Alice
1 | Bob
```

because two rows cannot have the same primary key.

A primary key also cannot be `NULL`.

---

# 6. PRIMARY KEY vs UNIQUE

These two can be confusing.

Both prevent duplicate values, but they serve different purposes.

### Primary Key

Usually identifies the **main identity** of the row.

```
students
────────────
id ← PRIMARY KEY
name
email
```

### UNIQUE

Prevents duplicates in another column.

```
students
────────────
id       ← PRIMARY KEY
name
email    ← UNIQUE
```

So:

```
id
↓
Who is this record?

email
↓
Can another record use this email?
```

A table has one primary key, although that key can consist of multiple columns. A table can have multiple `UNIQUE` constraints.

---

# 7. FOREIGN KEY

A **foreign key** creates a relationship between tables.

Suppose we have:

```
users
────────────
id
name
```

and:

```
orders
────────────
id
user_id
```

We can say:

```
orders.user_id
       ↓
users.id
```

SQL:

```
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100)
);
```

Then:

```
CREATE TABLE orders (
    id INT PRIMARY KEY,
    user_id INT,
    FOREIGN KEY (user_id) REFERENCES users(id)
);
```

Now MySQL knows:

> `orders.user_id` must refer to an existing user.

---

# 8. Why Foreign Keys Are Useful

Suppose the users table contains:

```
id | name
---+-------
1  | Alice
2  | Bob
```

Then this order is valid:

```
user_id = 1
```

because user `1` exists.

But:

```
user_id = 99
```

is invalid if user `99` doesn't exist.

The foreign key prevents this kind of broken relationship.

---

# 9. DEFAULT

`DEFAULT` provides a value automatically when one isn't supplied.

Example:

```
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    is_active BOOLEAN DEFAULT TRUE
);
```

Suppose we insert:

```
INSERT INTO users (id, name)
VALUES (1, 'Alice');
```

We didn't provide `is_active`.

MySQL uses:

```
is_active = TRUE
```

automatically.

So:

```
DEFAULT
   ↓
If no value is provided
   ↓
Use the specified value
```

Another common example:

```
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

This automatically records the creation time.

---

# 10. CHECK

`CHECK` ensures that a value satisfies a condition.

For example, age shouldn't be negative.

```
CREATE TABLE students (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    age INT CHECK (age >= 0)
);
```

This is valid:

```
age = 20
```

This is invalid:

```
age = -5
```

because:

```
age >= 0
```

must be true.

Another example:

```
price DECIMAL(10,2) CHECK (price >= 0)
```

This prevents negative prices.

---

# 11. Combining Constraints

We can use multiple constraints on the same table.

Example:

```
CREATE TABLE students (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    age INT CHECK (age >= 0),
    is_active BOOLEAN DEFAULT TRUE
);
```

Now the database has several rules:

```
id
→ PRIMARY KEY
→ AUTO_INCREMENT

name
→ NOT NULL

email
→ NOT NULL
→ UNIQUE

age
→ CHECK age >= 0

is_active
→ DEFAULT TRUE
```

That's a much safer table.

---

# 12. Column-Level vs Table-Level Constraints

Constraints can be written directly beside a column:

```
CREATE TABLE students (
    id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

This is called a **column-level constraint**.

You can also define some constraints separately:

```
CREATE TABLE students (
    id INT,
    name VARCHAR(100),
    PRIMARY KEY (id)
);
```

Here:

```
PRIMARY KEY (id)
```

is defined at the table level.

Both approaches can be useful.

---

# 13. Naming Constraints

You can give a constraint a name.

For example:

```
CREATE TABLE students (
    id INT,
    age INT,
    CONSTRAINT chk_age CHECK (age >= 0)
);
```

Here:

```
chk_age
```

is the constraint's name.

Naming constraints can make database maintenance easier, especially in larger projects.

---

# 14. Real-World Example

Imagine a simple `users` table:

```
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(255) NOT NULL UNIQUE,
    age INT CHECK (age >= 13),
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Let's translate this into plain English:

```
id
→ automatically generated
→ must be unique
→ identifies the user

username
→ required
→ cannot be duplicated

email
→ required
→ cannot be duplicated

age
→ must be 13 or greater

is_active
→ automatically TRUE if not provided

created_at
→ automatically gets current timestamp
```

The database is now enforcing these rules instead of relying entirely on the application.

---

# 15. Constraints Protect Data Integrity

This is an important concept.

**Data integrity** means that the data remains accurate, consistent, and valid.

For example:

```
NOT NULL
→ prevents missing required data

UNIQUE
→ prevents unwanted duplicates

PRIMARY KEY
→ uniquely identifies records

FOREIGN KEY
→ keeps relationships valid

CHECK
→ prevents invalid values

DEFAULT
→ provides sensible automatic values
```

Together, these rules protect the database.

---

# 16. Database vs Application Validation

You might wonder:

> "If Flask already validates the data, why do we need database constraints?"

Because validation can happen at multiple layers.

For example:

```
User
 ↓
Flask validation
 ↓
SQLAlchemy
 ↓
MySQL constraints
 ↓
Database
```

Suppose Flask accidentally sends:

```
age = -10
```

If MySQL has:

```
CHECK (age >= 0)
```

the database can still reject it.

So constraints provide a **final layer of protection**.

---

# 17. Quick Comparison

|Constraint|Purpose|
|---|---|
|`PRIMARY KEY`|Uniquely identifies a row|
|`FOREIGN KEY`|Connects tables|
|`NOT NULL`|Prevents missing values|
|`UNIQUE`|Prevents duplicates|
|`DEFAULT`|Supplies a value automatically|
|`CHECK`|Ensures a condition is satisfied|

A useful memory trick:

```
PRIMARY KEY → Who are you?
FOREIGN KEY → Who are you connected to?
NOT NULL    → You must provide this.
UNIQUE      → Don't duplicate this.
DEFAULT     → I'll provide this if you don't.
CHECK       → You must follow this rule.
```
