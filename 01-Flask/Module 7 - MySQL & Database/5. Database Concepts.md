
Before writing SQL or connecting Flask to MySQL, we need to understand the basic building blocks of a database.

This topic is important because almost everything later, including **tables, primary keys, foreign keys, relationships, and SQLAlchemy**, depends on these concepts.

---

# 1. What is a Database?

A **database** is an organized collection of data that can be stored, accessed, modified, and managed efficiently.

For example, a college application might have:

```
College Database
│
├── students
├── teachers
├── courses
└── results
```

A shopping application might have:

```
Shop Database
│
├── users
├── products
├── orders
└── payments
```

So a database is essentially a structured place for application data.

---

# 2. Database Management System

A **Database Management System (DBMS)** is software used to create, store, retrieve, update, and manage databases.

Examples:

```
MySQL
PostgreSQL
SQLite
Oracle Database
Microsoft SQL Server
```

For this course, we'll primarily use:

```
Flask
  ↓
MySQL
```

---

# 3. Relational Database

MySQL is a **relational database management system**.

In a relational database, information is primarily organized into **tables**.

For example:

```
students

┌────┬─────────┬─────┐
│ id │ name    │ age │
├────┼─────────┼─────┤
│ 1  │ Alice   │ 20  │
│ 2  │ Bob     │ 21  │
│ 3  │ Charlie │ 19  │
└────┴─────────┴─────┘
```

Another table:

```
courses

┌────┬──────────────┐
│ id │ course_name  │
├────┼──────────────┤
│ 1  │ Python       │
│ 2  │ Java         │
│ 3  │ Database     │
└────┴──────────────┘
```

The tables can be connected using relationships.

---

# 4. Database → Table → Row → Column

This is the fundamental hierarchy:

```
Database
   │
   ├── Table
   │     ├── Column
   │     ├── Column
   │     └── Rows
   │
   └── Table
```

Let's break it down.

### Database

```
college
```

### Table

```
students
```

### Columns

```
id
name
age
```

### Row

```
1 | Alice | 20
```

### Cell

```
Alice
```

So:

```
Database
   ↓
Table
   ↓
Row + Column
   ↓
Individual Data
```

---

# 5. Table

A **table** stores related data in rows and columns.

Example:

```
students

┌────┬─────────┬─────┐
│ id │ name    │ age │
├────┼─────────┼─────┤
│ 1  │ Alice   │ 20  │
│ 2  │ Bob     │ 21  │
│ 3  │ Charlie │ 19  │
└────┴─────────┴─────┘
```

The table represents one particular type of entity:

```
students → students
products → products
orders   → orders
```

---

# 6. Column

A **column** represents a particular attribute of the data.

For example:

```
students
```

might have:

```
id
name
email
age
```

Each column has a specific purpose.

```
id
↓
Student identifier

name
↓
Student name

email
↓
Student email

age
↓
Student age
```

---

# 7. Row

A **row** represents one complete record.

Example:

```
┌────┬───────┬─────┐
│ id │ name  │ age │
├────┼───────┼─────┤
│ 1  │ Alice │ 20  │ ← one row
│ 2  │ Bob   │ 21  │ ← another row
└────┴───────┴─────┘
```

The first row represents one student:

```
id = 1
name = Alice
age = 20
```

---

# 8. Cell

A **cell** is one individual value at the intersection of a row and column.

Example:

```
┌────┬───────┬─────┐
│ id │ name  │ age │
├────┼───────┼─────┤
│ 1  │ Alice │ 20  │
└────┴───────┴─────┘
```

`Alice` is a cell value.

`20` is another cell value.

---

# 9. Record

A **record** generally refers to one complete row of data.

For example:

```
1 | Alice | 20
```

is one student record.

You can think:

```
Row ≈ Record
```

---

# 10. Entity

An **entity** is something about which we want to store information.

For example, in a college system:

```
Student
Teacher
Course
Department
```

could all be entities.

In a shopping system:

```
User
Product
Order
Payment
```

could be entities.

Usually, entities eventually become tables.

For example:

```
Entity       Table
-----------------------
Student  →   students
Product  →   products
Order    →   orders
```

---

# 11. Attribute

An **attribute** describes a property of an entity.

For a Student:

```
Student
│
├── id
├── name
├── email
└── age
```

These are attributes of a student.

In a relational database, attributes generally become columns.

```
Attribute       Column
-------------------------
student id   →  id
student name →  name
student age  →  age
```

---

# 12. NULL

`NULL` means that a value is **missing, unknown, or not provided**.

For example:

```
┌────┬────────┬──────────────┐
│ id │ name   │ phone        │
├────┼────────┼──────────────┤
│ 1  │ Alice  │ 9876543210   │
│ 2  │ Bob    │ NULL         │
└────┴────────┴──────────────┘
```

Bob's phone number is not available.

That is represented by:

```
NULL
```

### Important

`NULL` is **not the same as**:

```
0
```

and it is not necessarily the same as:

```
''
```

They represent different things.

```
NULL
↓
No known/provided value

0
↓
Numeric value zero

''
↓
Empty string
```

---

# 13. Duplicate Data

Suppose we create this table:

```
students

┌────┬───────┬───────────────────┐
│ id │ name  │ email             │
├────┼───────┼───────────────────┤
│ 1  │ Alice │ alice@example.com │
│ 2  │ Alice │ alice@example.com │
└────┴───────┴───────────────────┘
```

We now have duplicated information.

This can cause problems when data becomes large.

For example, suppose Alice's information appears in 20 different places.

Changing her email could require changing it in many places.

Good database design tries to avoid unnecessary duplication.

This leads us toward **database normalization**, which we'll touch on as part of database design.

# 14. Relationships

One of the biggest advantages of a relational database is that tables can be related.

Suppose we have:

```
users

┌────┬───────┐
│ id │ name  │
├────┼───────┤
│ 1  │ Alice │
│ 2  │ Bob   │
└────┴───────┘
```

And:

```
orders

┌────┬─────────┬────────┐
│ id │ user_id │ total  │
├────┼─────────┼────────┤
│ 1  │ 1       │ 500    │
│ 2  │ 1       │ 300    │
│ 3  │ 2       │ 700    │
└────┴─────────┴────────┘
```

Here:

```
orders.user_id
       │
       ▼
users.id
```

This tells us who owns each order.

We'll study this in detail with **foreign keys and relationships**.

---

# 15. Primary Key

A **primary key** uniquely identifies each row in a table.

Example:

```
students

┌────┬────────┐
│ id │ name   │
├────┼────────┤
│ 1  │ Alice  │
│ 2  │ Bob    │
│ 3  │ John   │
└────┴────────┘
```

Here:

```
id
```

can be the primary key.

It allows us to distinguish:

```
Student 1
Student 2
Student 3
```

We'll cover primary keys separately.

---

# 16. Foreign Key

A **foreign key** connects one table to another.

Example:

```
users
────────────
id
name
```

```
orders
────────────
id
user_id
total
```

`orders.user_id` can reference `users.id`.

```
users.id
    ▲
    │
    │ referenced by
    │
orders.user_id
```

This creates a relationship between the tables.

---

# 17. Constraints

A **constraint** is a rule applied to data in a table.

Examples:

```
PRIMARY KEY
NOT NULL
UNIQUE
FOREIGN KEY
CHECK
DEFAULT
```

For example:

```
email VARCHAR(255) UNIQUE
```

means duplicate email values aren't allowed.

Constraints help maintain **data integrity**.

We'll study them later.

---

# 18. Data Integrity

**Data integrity** means keeping the data accurate, valid, and consistent.

For example, suppose we have:

```
students
```

and:

```
orders
```

If an order says:

```
user_id = 999
```

but user `999` doesn't exist, the database may contain an invalid relationship.

Foreign keys and other constraints help prevent these problems.

---

# 19. Database Schema

The term **schema** can be used in different ways depending on context.

In MySQL, a schema is commonly used essentially as a synonym for a **database**.

For example:

```
flask_learning
```

can be a MySQL schema/database containing:

```
students
users
posts
```

But in broader database terminology, "schema" can also refer to the **structure/design of a database**.

For our learning:

```
MySQL schema ≈ MySQL database
```

is a useful starting point.

# 20. Database Design

Before creating tables, we should decide:

```
What data do we need?
What tables do we need?
What columns should they have?
Which columns identify records?
Which tables are related?
```

For example, for a basic blog:

```
users
posts
comments
```

Then:

```
users
│
│ 1
│
│
│ N
▼
posts
│
│ 1
│
│
│ N
▼
comments
```

This design should ideally be planned before writing lots of SQL.

We'll cover **Database Design** next.

|**Row**|Represents one record|
|**Cell**|One individual value|
|**Entity**|Something we store information about|
|**Attribute**|Property of an entity|
|**Record**|One complete row|
|**NULL**|Missing/unknown value|
