
Logging and monitoring are essential when a Flask application moves beyond simple development.

Think of them as the application's **memory and health dashboard**:

- **Logging** tells you what happened.
- **Monitoring** tells you how the application is behaving.
- **Observability** helps you understand _why_ something happened.

---

# 1. What is Logging?

**Logging** means recording important events that happen inside an application.

For example:

```
User logged in
User created
Database query failed
Payment request failed
File uploaded
Server started
```

Instead of using:

```
print("User logged in")
```

production applications normally use Python's `logging` system.

### Simple example

```
import logging

logging.basicConfig(level=logging.INFO)

logging.info("Application started")
```

Output:

```
INFO:root:Application started
```

---

# 2. Why Do We Need Logging?

Imagine your Flask application suddenly returns:

```
500 Internal Server Error
```

The user only sees:

```
Something went wrong.
```

But the developer needs to know:

```
Which route failed?
When did it fail?
What exception occurred?
Which operation was running?
Was the database involved?
```

Logs provide this information.

### Without logging

```
Application crashed ❌
        ↓
"What happened?"
        ↓
Guessing
```

### With logging

```
Application crashed ❌
        ↓
Check logs
        ↓
Find exception
        ↓
Identify cause
        ↓
Fix problem
```

---

# 3. Logging vs `print()`

You may already use:

```
print("User logged in")
```

This is fine for quick debugging.

But `logging` is much more powerful.

|`print()`|Logging|
|---|---|
|Basic output|Structured system|
|No severity levels|DEBUG, INFO, WARNING, etc.|
|Difficult to control|Can filter levels|
|Usually console only|Console, files, external systems|
|Poor production support|Production friendly|
|No standard formatting|Custom formatting|

For real applications:

```
print()
  ↓
Development debugging

logging
  ↓
Application diagnostics
```

# 6. Logger

A **logger** is the object used to create log messages.

Instead of using the root logger:

```
logging.info("User created")
```

Flask applications commonly create a module-specific logger:

```
import logging

logger = logging.getLogger(__name__)
```

Then:

```
logger.info("User created")
logger.warning("Invalid request")
logger.error("Database error")
```

### Why `__name__`?

If the file is:

```
app/routes/users.py
```

then:

```
__name__
```

can identify the module.

This makes logs easier to understand.

---

# 7. Logger, Handler, Formatter

The logging system can be understood using three important components.

```
Logger
   ↓
Handler
   ↓
Formatter
```

### Logger

Creates the log message.

```
logger.info("User created")
```

### Handler

Decides where the message goes.

Examples:

```
Console
File
External logging system
```

### Formatter

Controls how the log looks.

Example:

```
2026-08-18 14:30:20 INFO User created
```

So:

```
Logger   → What happened?
Handler  → Where should it go?
Formatter → How should it look?
```

# 8. Basic Logging Configuration

Example:

```
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s"
)

logger = logging.getLogger(__name__)

logger.info("Application started")
```

Possible output:

```
2026-08-18 14:30:20 INFO __main__: Application started
```

The format contains:

```
%(asctime)s
```

Time of event.

```
%(levelname)s
```

Log level.

```
%(name)s
```

Logger name.

```
%(message)s
```

Actual message.

# 10. Logging Inside Routes

Example:

```
from flask import Flask

app = Flask(__name__)

@app.get("/users")
def users():
    app.logger.info("Users endpoint requested")

    return {
        "users": []
    }
```

Another example:

```
@app.post("/users")
def create_user():
    app.logger.info("Creating a new user")

    try:
        # database operation
        return {"message": "User created"}, 201

    except Exception:
        app.logger.exception("Failed to create user")
        return {"message": "Internal server error"}, 500
```

# 11. `logger.error()` vs `logger.exception()`

This distinction is important.

### `logger.error()`

```
try:
    result = 10 / 0
except Exception:
    logger.error("Calculation failed")
```

This logs the message.

### `logger.exception()`

```
try:
    result = 10 / 0
except Exception:
    logger.exception("Calculation failed")
```

This logs the message **and the exception traceback**.

For example:

```
ERROR Calculation failed
Traceback:
ZeroDivisionError: division by zero
```

Therefore:

```
except Exception:
    logger.exception("Operation failed")
```

is very useful when diagnosing unexpected exceptions.

---

# 12. Never Log Sensitive Information 🔐

This is extremely important.

Do **not** log:

```
Passwords
Password hashes unnecessarily
JWT tokens
Session cookies
API keys
Database passwords
Credit card information
Private personal information
```

Bad:

```
logger.info(f"Password entered: {password}")
```

Very bad:

```
logger.info(f"JWT token: {token}")
```

Better:

```
logger.info("User login attempt received")
```

If you need identification:

```
logger.info("User authentication successful")
```

Log the **event**, not the secret.

# 15. Rotating Logs

Imagine your application runs for one year.

If everything goes into:

```
app.log
```

the file could become huge.

Log rotation solves this problem.

Conceptually:

```
app.log
app.log.1
app.log.2
app.log.3
```

Python provides:

```
from logging.handlers import RotatingFileHandler
```

Example:

```
handler = RotatingFileHandler(
    "app.log",
    maxBytes=1_000_000,
    backupCount=5
)
```

Meaning:

```
Maximum size ≈ 1 MB
Keep 5 old log files
```

This prevents unlimited log growth.

# 16. Request Logging

A Flask application handles many requests.

You may want to know:

```
HTTP method
URL
Status code
Response time
```

Example desired log:

```
GET /users 200 45ms
POST /users 201 82ms
GET /products 404 12ms
```

You can use Flask hooks.

```
import time
from flask import request

@app.before_request
def start_timer():
    request.start_time = time.perf_counter()
```

Then:

```
@app.after_request
def log_request(response):
    duration = time.perf_counter() - request.start_time

    app.logger.info(
        "%s %s %s %.2fms",
        request.method,
        request.path,
        response.status_code,
        duration * 1000
    )

    return response
```

Now every request can be measured.

# 17. Request ID

In larger applications, many requests happen simultaneously.

A **request ID** helps connect all logs belonging to one request.

Example:

```
Request ID: 8f21a
```

Logs:

```
8f21a Request received
8f21a User authenticated
8f21a Database query started
8f21a Database query completed
8f21a Response returned
```

Without the request ID, logs from different users can become a giant bowl of spaghetti 🍝.

Concept:

```
Incoming Request
       ↓
Generate Request ID
       ↓
Store ID
       ↓
Every related log uses ID
       ↓
Response
```

This becomes particularly useful in distributed systems.

# 18. Structured Logging

Normal logging:

```
User created successfully
```

Structured logging represents information in a machine-readable format.

For example:

```
{
    "level": "INFO",
    "event": "user_created",
    "user_id": 25,
    "timestamp": "2026-08-18T14:30:00"
}
```

This is easier for logging systems to search and analyze.

For example:

```
Find all:
event = "user_created"
```

or:

```
Find:
level = "ERROR"
```

Structured logging becomes very useful in larger applications.

# 29. Observability

**Observability** is the broader concept of understanding the internal state of a system by examining its outputs.

The three major pillars are:

```
          Observability
               │
      ┌────────┼────────┐
      ↓        ↓        ↓
    Logs    Metrics   Traces
```

### Logs

Detailed events.

```
Database query failed
```

### Metrics

Numbers over time.

```
Error rate = 4%
```

### Traces

Follow one request through multiple components.

```
Client
 ↓
Flask
 ↓
Service
 ↓
Database
 ↓
External API
```

Tracing is particularly valuable in microservices.

# 30. Production Logging Configuration

A simplified structure can look like:

```
import logging
from logging.handlers import RotatingFileHandler

def configure_logging(app):
    handler = RotatingFileHandler(
        "app.log",
        maxBytes=1_000_000,
        backupCount=5
    )

    formatter = logging.Formatter(
        "%(asctime)s %(levelname)s %(name)s: %(message)s"
    )

    handler.setFormatter(formatter)
    handler.setLevel(logging.INFO)

    app.logger.addHandler(handler)
    app.logger.setLevel(logging.INFO)
```

Then inside the application factory:

```
def create_app():
    app = Flask(__name__)

    configure_logging(app)

    return app
```

This is a basic example. Production environments often use centralized logging infrastructure instead of only local files.

# 32. Logging Errors Correctly

Bad:

```
try:
    create_user()
except Exception:
    pass
```

The error disappears.

Better:

```
try:
    create_user()
except Exception:
    app.logger.exception("User creation failed")
    raise
```

If you intentionally return an error response:

```
try:
    create_user()
except Exception:
    app.logger.exception("User creation failed")

    return {
        "error": "Internal server error"
    }, 500
```

# 33. Logging HTTP Errors

You can create consistent error logging.

```
@app.errorhandler(500)
def internal_error(error):
    app.logger.error("Internal server error")

    return {
        "error": "Internal server error"
    }, 500
```

For unexpected exceptions, `logger.exception()` is generally more useful when called inside the exception-handling context.

# 36. Common Logging Mistakes

### ❌ Logging passwords

```
logger.info(password)
```

Never do this.

### ❌ Logging tokens

```
logger.info(token)
```

Never do this.

### ❌ Logging everything at ERROR

```
logger.error("User visited homepage")
```

That's not an error.

Use:

```
logger.info("Homepage requested")
```

### ❌ Using only `print()`

Use proper logging for application diagnostics.

### ❌ No log rotation

Logs can consume disk space.

### ❌ No timestamps

Timestamps are extremely useful when investigating incidents.

### ❌ Logging too much

Millions of unnecessary logs make important events harder to find.

---

# 37. Common Monitoring Mistakes

### ❌ Monitoring only CPU

CPU can be normal while the database is failing.

### ❌ No error-rate monitoring

Users may be receiving errors even when the server appears alive.

### ❌ No response-time monitoring

An application can technically work while being painfully slow.

### ❌ No alerts

Monitoring without alerts may require someone to manually stare at dashboards.

### ❌ Too many alerts

If everything sends an alert, eventually nothing feels important.

# 38. Recommended Flask Logging Structure

For a modular Flask project:

```
app/
├── __init__.py
├── extensions.py
├── routes/
├── services/
├── models/
└── utils/
    └── logging_config.py
```

`logging_config.py`:

```
import logging
from logging.handlers import RotatingFileHandler

def configure_logging(app):
    handler = RotatingFileHandler(
        "app.log",
        maxBytes=1_000_000,
        backupCount=5
    )

    formatter = logging.Formatter(
        "%(asctime)s %(levelname)s %(name)s: %(message)s"
    )

    handler.setFormatter(formatter)
    handler.setLevel(logging.INFO)

    app.logger.addHandler(handler)
    app.logger.setLevel(logging.INFO)
```

Then:

```
from .utils.logging_config import configure_logging

def create_app():
    app = Flask(__name__)

    configure_logging(app)

    return app
```

This keeps logging configuration separate from application routes.

# 44. One-Line Interview Definitions

**What is logging?**  
Logging is the process of recording application events for debugging, auditing, and troubleshooting.

**What is monitoring?**  
Monitoring is continuously observing application health, availability, performance, and resource usage.

**What is a logger?**  
A logger is an object used to create log messages at different severity levels.

**What is a handler?**  
A handler determines where log messages are sent, such as a console or file.

**What is log rotation?**  
Log rotation automatically limits log-file growth by creating new files and retaining older log files.

**What is a health check?**  
A health check is an endpoint or mechanism used to determine whether an application or service is functioning correctly.

**What is observability?**  
Observability is the ability to understand a system's internal behavior using outputs such as logs, metrics, and traces.
