Signals are one of Flask's more advanced features. They let different parts of an application **notify each other when something happens**, without tightly coupling the code together.

Think of a signal as a small announcement system:

```
Something happened
       ↓
    Signal
       ↓
"Anyone interested?"
       ↓
Connected receivers react
```

For example:

```
User registers
      ↓
Signal: user_registered
      ↓
 ┌───────────────┬────────────────┐
 ↓               ↓                ↓
Log event     Send email       Update analytics
```

---

# 1. What Is a Signal?

A **signal** is a notification mechanism that allows one part of an application to announce that an event has occurred.

Other functions can subscribe to that signal and react to it.

### Simple definition

> A signal is an event notification mechanism that allows different parts of an application to communicate without directly calling each other.

For example:

```
user_registered.send(...)
```

can notify every function that is listening to `user_registered`.

---

# 2. Why Do We Need Signals?

Suppose you have a registration route:

```
@app.post("/register")
def register():
    user = create_user()

    send_welcome_email(user)
    create_log(user)
    update_statistics(user)

    return {"message": "Registered"}
```

The registration route now knows about:

- email functionality
- logging
- statistics
- user creation

This creates **tight coupling**.

Instead, you can use a signal:

```
Register User
     ↓
Create User
     ↓
Send "user_registered"
     ↓
 ┌──────────────┬──────────────┐
 ↓              ↓              ↓
Logging      Email          Analytics
```

The registration code doesn't need to know who is listening.

# 3. Flask Signals

Flask provides several built-in signals.

Signals are provided through **Blinker**.

You can import Flask's built-in signals like this:

```
from flask import request_started
```

or:

```
from flask import request_finished
```

Depending on your Flask setup and version, Blinker provides the signal functionality.

---

# 4. Common Flask Signals

Some important Flask signals are:

|Signal|When it happens|
|---|---|
|`request_started`|Before a request is processed|
|`request_finished`|After a response is generated|
|`request_tearing_down`|When request context is being removed|
|`got_request_exception`|When an exception occurs during request handling|
|`appcontext_pushed`|When application context is pushed|
|`appcontext_popped`|When application context is removed|
|`appcontext_tearing_down`|When application context is being torn down|
|`template_rendered`|When a template is rendered|
|`message_flashed`|When a flash message is created|

These are useful for things such as:

- logging
- debugging
- monitoring
- auditing
- testing
- development tools

---

# 5. Signal Receiver

A function that listens to a signal is called a **receiver**.

Example:

```
from flask import request_started

def handle_request(sender, **extra):
    print("Request started")
```

Then connect it:

```
request_started.connect(handle_request)
```

Now whenever the signal is sent, `handle_request()` is called.

---

# 6. Understanding `sender`

Signals can provide information about **who sent the signal**.

Example:

```
def handle_request(sender, **extra):
    print(sender)
```

For Flask signals, the sender is often the Flask application instance.

Mental model:

```
Flask Application
       ↓
   sends signal
       ↓
 request_started
       ↓
    receiver
       ↓
 handle_request(sender, ...)
```

---

# 7. Using a Decorator

Instead of:

```
request_started.connect(handle_request)
```

you can use the signal's decorator style:

```
from flask import request_started

@request_started.connect
def handle_request(sender, **extra):
    print("Request started")
```

This is often cleaner.

---

# 8. Example: Request Logging

A simple signal receiver:

```
from flask import request_started, request

@request_started.connect
def log_request(sender, **extra):
    print("Request started:", request.path)
```

When someone visits:

```
/users
```

you might see:

```
Request started: /users
```

The route itself doesn't need to contain logging code.

---

# 9. `request_finished`

`request_finished` runs after Flask has generated a response.

Example:

```
from flask import request_finished

@request_finished.connect
def log_response(sender, response, **extra):
    print("Response status:", response.status_code)
```

A request such as:

```
GET /users
```

could produce:

```
Response status: 200
```

---

# 10. `got_request_exception`

This signal is useful for monitoring exceptions.

```
from flask import got_request_exception

@got_request_exception.connect
def log_exception(sender, exception, **extra):
    print("Exception:", exception)
```

If an unexpected exception occurs:

```
Route
  ↓
Exception
  ↓
got_request_exception
  ↓
log_exception()
```

This can be useful for:

- error logging
- monitoring
- debugging
- alerting systems

---

# 11. `template_rendered`

Flask also provides a signal for template rendering.

```
from flask import template_rendered

@template_rendered.connect
def log_template(sender, template, context, **extra):
    print("Template:", template.name)
```

For example:

```
return render_template("home.html")
```

could trigger:

```
template_rendered
      ↓
log_template()
      ↓
Template: home.html
```

This can be especially useful during testing and debugging.

---

# 12. `message_flashed`

Flask's flash system also has a signal.

```
from flask import message_flashed

@message_flashed.connect
def log_flash(sender, message, category, **extra):
    print("Flash:", category, message)
```

If your application executes:

```
flash("Profile updated", "success")
```

the receiver can observe that event.

---

# 13. Signals vs `before_request`

You might wonder:

> "Why not just use `before_request`?"

Good question.

### `before_request`

```
@app.before_request
def before():
    print("Before request")
```

This is Flask's request lifecycle hook.

It is generally used when the application itself needs to perform something as part of request processing.

For example:

```
@app.before_request
def load_user():
    ...
```

### Signal

```
@request_started.connect
def observe_request(sender, **extra):
    ...
```

Signals are more suitable when you want to **notify observers** about an event.

---

# 14. Signals vs Request Hooks

|Feature|Signals|Request Hooks|
|---|---|---|
|Main purpose|Notify observers|Control request lifecycle|
|Coupling|Lower|More directly tied to Flask app|
|Typical use|Logging, monitoring, auditing|Authentication, loading data|
|Can modify request flow?|Generally no|Yes|
|Can stop request?|Not their normal purpose|Yes|
|Application architecture|Event notification|Lifecycle control|

For example:

### Authentication

Use:

```
@app.before_request
```

### Request monitoring

Use:

```
request_started
```

---

# 15. Signals vs Decorators

These are also different.

### Decorator

A decorator modifies or wraps a specific function.

```
@login_required
def dashboard():
    ...
```

It affects:

```
dashboard()
```

### Signal

A signal notifies multiple listeners when an event happens.

```
Event
 ↓
Signal
 ↓
Receiver A
Receiver B
Receiver C
```

So:

```
Decorator → "Before/around this specific function, do something."

Signal → "Something happened. Anyone interested can react."
```

---

# 16. Signals vs Middleware

Middleware operates around the application's request/response system.

```
Client
  ↓
Middleware
  ↓
Flask
  ↓
Route
  ↓
Response
  ↓
Middleware
  ↓
Client
```

Signals operate as event notifications within Flask.

```
Event
 ↓
Signal
 ↓
Receivers
```

### Quick comparison

|Tool|Main purpose|
|---|---|
|Decorator|Modify a function|
|Request hook|Participate in Flask lifecycle|
|Middleware|Wrap application/server processing|
|Signal|Notify interested listeners|

# 17. Signal Arguments

Signal receivers commonly accept:

```
def receiver(sender, **extra):
    ...
```

For example:

```
@request_started.connect
def receiver(sender, **extra):
    print("Application:", sender)
```

Some signals provide additional arguments.

For example:

```
@request_finished.connect
def receiver(sender, response, **extra):
    print(response.status_code)
```

The exact arguments depend on the signal.

---

# 18. The `**extra` Pattern

You will frequently see:

```
def receiver(sender, **extra):
    ...
```

Why?

Because Flask signals can provide additional keyword arguments.

Using:

```
**extra
```

allows your receiver to accept them without explicitly declaring every possible argument.

Example:

```
def receiver(sender, **extra):
    print(extra)
```

You can inspect what the signal provides:

```
print(extra)
```

This is useful while learning and debugging.

---

# 19. Sender Filtering

A receiver can listen only when a particular sender emits the signal.

Example:

```
request_started.connect(
    handle_request,
    app
)
```

Conceptually:

```
App A ──→ request_started
              ↓
        handle_request()

App B ──→ request_started
              ↓
        not handled by this receiver
```

This becomes useful when an application contains multiple Flask application instances.

# 20. Custom Signals

You are not limited to Flask's built-in signals.

You can create your own signals using Blinker.

Example:

```
from blinker import signal

user_registered = signal("user-registered")
```

Now you have a custom signal called:

```
user-registered
```

---

# 21. Connecting to a Custom Signal

Create a receiver:

```
def handle_user_registered(sender, **extra):
    print("New user registered")
```

Connect it:

```
user_registered.connect(handle_user_registered)
```

Now the receiver is listening.

---

# 22. Sending a Custom Signal

After creating a user:

```
user_registered.send(
    "registration",
    user_id=10
)
```

The signal sends:

```
sender = "registration"

user_id = 10
```

The receiver can access them:

```
def handle_user_registered(sender, **extra):
    print("Sender:", sender)
    print("User ID:", extra["user_id"])
```

Output:

```
Sender: registration
User ID: 10
```

# 23. Custom Signal Mental Model

```
                Custom Signal
                     │
                     │ send()
                     ↓
             user_registered
              /      |       \
             ↓       ↓        ↓
          Logger   Email    Analytics
```

This is the heart of event-driven communication.

# 24. Practical Example

Suppose you have a product creation system.

Without signals:

```
def create_product():
    product = save_product()

    log_product_creation(product)
    update_statistics(product)
    notify_admin(product)

    return product
```

The service knows about everything.

With a signal:

```
def create_product():
    product = save_product()

    product_created.send(
        "product-service",
        product_id=product.id
    )

    return product
```

Then:

```
@product_created.connect
def log_product(sender, **extra):
    print("Product created:", extra["product_id"])
```

Another receiver:

```
@product_created.connect
def update_statistics(sender, **extra):
    print("Updating statistics")
```

And another:

```
@product_created.connect
def notify_admin(sender, **extra):
    print("Notify admin")
```

Now the product service doesn't need to directly know about these listeners.

# 25. Signals Are Synchronous

This is **very important**.

A signal is not automatically a background task.

Suppose:

```
product_created.send(...)
```

has three receivers:

```
Signal
  ↓
Receiver A
  ↓
Receiver B
  ↓
Receiver C
  ↓
Continue
```

The receivers normally execute as part of the same flow.

So if a receiver takes:

```
5 seconds
```

the request may also be delayed by that work.

Therefore:

> Signals do not automatically make slow operations asynchronous.

For expensive operations such as:

- sending large batches of emails
- video processing
- report generation
- large data processing

you may need a **background task system**.

That is why the next topic, **11.9 Background Tasks**, is important.

---

# 26. Don't Put Critical Business Logic Everywhere

Signals can be powerful, but they can also make an application confusing.

Imagine:

```
user_created.send(...)
```

and five different files secretly react to it.

A developer reading the registration code might not know what happens next.

This can make debugging difficult.

Therefore, avoid putting essential business rules into obscure signal receivers.

### Good uses

```
Logging
Auditing
Monitoring
Analytics
Notifications
Testing
Debugging
```

### Be careful with

```
Critical financial operations
Important database workflows
Security decisions
Essential business rules
```

For critical business logic, explicit service calls are often easier to understand.

---

# 27. Signals and Transactions

Consider:

```
user = User(...)
db.session.add(user)

user_created.send(...)
db.session.commit()
```

There is a problem.

The signal fires **before the transaction is committed**.

If the receiver sends an email or performs another action, the database transaction could later fail.

For example:

```
Create User
    ↓
Send Signal
    ↓
Send Email
    ↓
Database Commit
    ↓
ERROR
```

Now the email says the account exists, but the database transaction failed.

So you need to think carefully about **transaction boundaries** when using signals.

For important workflows, it may be better to trigger external side effects only after successful persistence, or use a reliable event/outbox architecture for more advanced systems.

# 28. Signals and Application Factory

With the application factory pattern, signal registration should be organized carefully.

For example:

```
project/
│
├── app/
│   ├── __init__.py
│   ├── extensions.py
│   ├── signals.py
│   └── routes/
│
└── run.py
```

`signals.py`:

```
from flask import request_started

def log_request(sender, **extra):
    print("Request started")

def register_signals():
    request_started.connect(log_request)
```

Then in the factory:

```
from flask import Flask
from .signals import register_signals

def create_app():
    app = Flask(__name__)

    register_signals()

    return app
```

This keeps signal setup organized.

---

# 29. Avoid Duplicate Signal Registration

Be careful when registering receivers.

If the same receiver is connected multiple times, you may get unexpected repeated execution.

For example:

```
Receiver registered
Receiver registered again
Receiver registered again
```

Then one signal could cause:

```
handle_event()
handle_event()
handle_event()
```

This is particularly important when working with:

- application factories
- development reloaders
- testing
- multiple application instances

Keep signal registration deliberate and predictable.

# 30. Signals in Testing

Signals can also be useful for testing.

Suppose you want to know whether a template was rendered.

You can listen for:

```
template_rendered
```

and inspect:

```
template
context
```

This can help verify:

```
Correct template
Correct context data
Correct rendering behavior
```

Signals can therefore be useful as an observation mechanism in tests.

# 31. When Should You Use Signals?

A useful decision rule:

### Use a signal when:

```
Something happened
        ↓
Other components may be interested
        ↓
They should not need to be tightly coupled
```

Examples:

```
Request started
Request finished
Exception occurred
Template rendered
User registered
Product created
Order completed
```

### Don't use a signal simply because you can.

If your code is:

```
create_user()
send_email()
```

and that relationship is essential and obvious, an explicit service call may actually be clearer.

# 32. Signals Architecture

A larger application might look like:

```
                  Flask Application
                         │
                         ↓
                       Event
                         │
                         ↓
                      Signal
                  ┌──────┼──────┐
                  ↓      ↓      ↓
                Logger  Audit  Analytics
```

The important idea is **loose coupling**.

The event producer doesn't need to know every consumer.

# 33. Signal vs Event Queue

Don't confuse Flask signals with a full event queue.

### Flask signal

```
Event
 ↓
Signal
 ↓
Receivers
```

Usually in the same application/process.

### Message queue

```
Application
     ↓
Message Queue
     ↓
Worker
     ↓
Task
```

Used for:

- asynchronous processing
- distributed systems
- retries
- long-running jobs
- background processing

That distinction will become important in the next topic.

# 34. Common Mistakes

### Mistake 1: Treating signals as background jobs

Wrong assumption:

```
signal = asynchronous
```

Not necessarily.

---

### Mistake 2: Putting critical business logic into signals

This can make application behavior difficult to discover.

---

### Mistake 3: Forgetting receiver arguments

For example:

```
def receiver():
    ...
```

A signal may provide arguments, causing problems.

Prefer:

```
def receiver(sender, **extra):
    ...
```

when appropriate.

---

### Mistake 4: Registering receivers repeatedly

This can cause an event to trigger the same function multiple times.

---

### Mistake 5: Ignoring transactions

A signal can trigger side effects before a database transaction is safely committed.

---

### Mistake 6: Using signals when a normal function call is clearer

Don't turn simple code into a secret event system.

Sometimes:

```
send_email(user)
```

is better than:

```
user_created.send(...)
```

with a hidden receiver somewhere else.
