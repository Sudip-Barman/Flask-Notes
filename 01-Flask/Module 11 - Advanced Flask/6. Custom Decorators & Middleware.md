
**Custom Decorators** and **Middleware** are two powerful techniques used in advanced Flask applications.

They solve different problems:

```
Decorator
   ↓
Controls or modifies a specific function

Middleware
   ↓
Controls or modifies requests/responses
across the application
```

A useful mental picture is:

```
Client
  ↓
Middleware
  ↓
Flask
  ↓
Decorator
  ↓
Route
  ↓
Response
  ↓
Middleware
  ↓
Client
```

---

# 1. What is a Decorator?

A **decorator** is a Python function that modifies or extends the behavior of another function without changing its original code.

Basic example:

```
def my_decorator(func):
    def wrapper():
        print("Before function")
        func()
        print("After function")

    return wrapper
```

Use it:

```
@my_decorator
def hello():
    print("Hello")
```

When you call:

```
hello()
```

Output:

```
Before function
Hello
After function
```

The `@my_decorator` syntax is shorthand for:

```
hello = my_decorator(hello)
```

---

# 2. Why Decorators Matter in Flask

Flask already uses decorators everywhere.

For example:

```
@app.route("/users")
def users():
    return "Users"
```

Here:

```
@app.route("/users")
```

is a decorator.

It tells Flask:

> "Associate this function with the `/users` URL."

Other Flask examples include:

```
@app.get("/")
```

```
@app.post("/users")
```

```
@app.errorhandler(404)
```

---

# 3. What is a Custom Decorator?

A **custom decorator** is a decorator that you create yourself.

For example:

```
def log_request(func):
    def wrapper(*args, **kwargs):
        print("Function called")
        return func(*args, **kwargs)

    return wrapper
```

Then:

```
@log_request
def profile():
    return "Profile"
```

Now `profile()` passes through your decorator before executing.

---

# 4. Why Use Custom Decorators?

Custom decorators are useful when the same logic needs to be applied to multiple functions.

Examples:

- Authentication
- Authorization
- Role checking
- Permission checking
- Logging
- Timing
- Validation
- Rate limiting
- Feature flags
- Request checks

Without a decorator:

```
def users():
    check_authentication()
    check_permission()
    ...
```

```
def products():
    check_authentication()
    check_permission()
    ...
```

```
def orders():
    check_authentication()
    check_permission()
    ...
```

This creates repetition.

With a decorator:

```
@permission_required("users.read")
def users():
    ...
```

Much cleaner.

---

# 5. `functools.wraps`

When creating custom decorators, you should normally use:

```
from functools import wraps
```

Example:

```
from functools import wraps

def my_decorator(func):

    @wraps(func)
    def wrapper(*args, **kwargs):
        print("Before")
        return func(*args, **kwargs)

    return wrapper
```

Why?

Because `@wraps(func)` preserves metadata from the original function.

For example:

```
__name__
__doc__
```

Without `wraps`, Flask and debugging tools may see the function as:

```
wrapper
```

instead of:

```
users
```

So remember:

> **Use `@wraps(func)` when writing custom decorators.**

# 7. Decorators With Flask Routes

Example:

```
from functools import wraps
from flask import session, redirect, url_for


def login_required(view):

    @wraps(view)
    def wrapped_view(*args, **kwargs):

        if "user_id" not in session:
            return redirect(url_for("login"))

        return view(*args, **kwargs)

    return wrapped_view
```

Then:

```
@app.get("/dashboard")
@login_required
def dashboard():
    return "Dashboard"
```

Now the route automatically checks whether the user is logged in.

---

# 8. Decorator Order Matters

This is important.

Consider:

```
@app.get("/dashboard")
@login_required
def dashboard():
    return "Dashboard"
```

Python applies decorators from the bottom upward.

Conceptually:

```
dashboard
   ↓
login_required
   ↓
app.get()
```

So the authentication decorator wraps the original function, and Flask registers the resulting callable.

Generally, Flask route decorators are placed above your custom decorators:

```
@app.get("/dashboard")
@login_required
def dashboard():
    ...
```

# 9. Authentication Decorator

Let's build a more complete example.

```
from functools import wraps
from flask import session, redirect, url_for


def login_required(view):

    @wraps(view)
    def wrapped_view(*args, **kwargs):

        user_id = session.get("user_id")

        if user_id is None:
            return redirect(url_for("login"))

        return view(*args, **kwargs)

    return wrapped_view
```

Use:

```
@app.get("/profile")
@login_required
def profile():
    return "Profile Page"
```

Flow:

```
Request
  ↓
/profile
  ↓
login_required
  ↓
Is user logged in?
  ├── No → Login
  └── Yes
       ↓
    profile()
```

# 10. Role-Based Decorator

Suppose your application has:

```
admin
manager
staff
customer
```

You can create:

```
def admin_required(view):

    @wraps(view)
    def wrapped_view(*args, **kwargs):

        user_id = session.get("user_id")

        if user_id is None:
            return "Login required", 401

        user = db.session.get(User, user_id)

        if user is None:
            return "User not found", 401

        if user.role != "admin":
            return "Access denied", 403

        return view(*args, **kwargs)

    return wrapped_view
```

Then:

```
@app.get("/admin")
@admin_required
def admin_dashboard():
    return "Admin Dashboard"
```

---

# 11. Multiple Allowed Roles

Sometimes several roles should access a route.

Instead of:

```
@admin_required
```

you can create:

```
def roles_required(*allowed_roles):

    def decorator(view):

        @wraps(view)
        def wrapped_view(*args, **kwargs):

            user_id = session.get("user_id")

            if user_id is None:
                return "Login required", 401

            user = db.session.get(User, user_id)

            if user is None:
                return "User not found", 401

            if user.role not in allowed_roles:
                return "Access denied", 403

            return view(*args, **kwargs)

        return wrapped_view

    return decorator
```

Now:

```
@app.get("/reports")
@roles_required("admin", "manager")
def reports():
    return "Reports"
```

This allows:

```
admin     ✅
manager   ✅
staff     ❌
customer  ❌
```

---

# 12. Permission Decorator

Roles are broad categories.

Permissions are more specific.

Example:

```
@permission_required("reports.export")
def export_report():
    ...
```

Implementation:

```
def permission_required(permission):

    def decorator(view):

        @wraps(view)
        def wrapped_view(*args, **kwargs):

            user = get_current_user()

            if user is None:
                return "Login required", 401

            if not has_permission(user, permission):
                return "Access denied", 403

            return view(*args, **kwargs)

        return wrapped_view

    return decorator
```

This is called a **decorator factory** because:

```
permission_required("reports.export")
```

first creates a decorator.

---

# 13. Decorator Factory

A normal decorator:

```
@my_decorator
```

A decorator factory:

```
@permission_required("users.delete")
```

Conceptually:

```
permission_required("users.delete")
             ↓
        creates decorator
             ↓
       wraps the route
```

This pattern is extremely useful for authorization.

# 14. Logging Decorator

You can create a decorator that logs function execution.

```
from functools import wraps


def log_execution(func):

    @wraps(func)
    def wrapper(*args, **kwargs):

        print(f"Calling {func.__name__}")

        result = func(*args, **kwargs)

        print(f"Finished {func.__name__}")

        return result

    return wrapper
```

Use:

```
@log_execution
def calculate_total():
    return 100
```

Output:

```
Calling calculate_total
Finished calculate_total
```

---

# 15. Timing Decorator

A decorator can measure execution time.

```
import time
from functools import wraps


def measure_time(func):

    @wraps(func)
    def wrapper(*args, **kwargs):

        start = time.perf_counter()

        result = func(*args, **kwargs)

        end = time.perf_counter()

        print(
            f"{func.__name__} took {end - start:.4f} seconds"
        )

        return result

    return wrapper
```

This can be useful for development and performance investigation.

For production systems, structured application logging and monitoring are generally better than relying on `print()`.

---

# 16. Important Decorator Rule

A decorator should normally preserve the original function's return value.

Good:

```
result = func(*args, **kwargs)
return result
```

Avoid accidentally doing:

```
func(*args, **kwargs)
```

without returning the result.

Otherwise:

```
return value
```

could become:

```
None
```

# 17. What is Middleware?

Now let's move to the second major concept.

**Middleware** is a layer that sits between the client and the Flask application.

It can inspect or modify requests and responses before they reach the application or after the application produces a response.

Basic model:

```
Client
  ↓
Middleware
  ↓
Flask Application
  ↓
Route
  ↓
Response
  ↓
Middleware
  ↓
Client
```

---

# 18. Why Middleware?

Middleware is useful for application-wide concerns.

Examples:

- Request logging
- Security headers
- Proxy handling
- Request transformation
- Response transformation
- Metrics
- Tracing
- Request IDs
- Authentication infrastructure
- Compression
- Rate limiting

Instead of putting the same logic into every route, middleware can handle it centrally.

---

# 19. WSGI Middleware

Flask is a **WSGI application**.

That means middleware can wrap the Flask WSGI application.

Conceptually:

```
Client
  ↓
Web Server
  ↓
Middleware
  ↓
Flask
  ↓
Route
```

The middleware receives the WSGI request environment and can pass it to Flask.

---

# 20. Basic WSGI Middleware

A very simple example:

```
class SimpleMiddleware:

    def __init__(self, app):
        self.app = app

    def __call__(self, environ, start_response):
        print("Request received")

        return self.app(environ, start_response)
```

Then:

```
app.wsgi_app = SimpleMiddleware(app.wsgi_app)
```

Now:

```
Request
   ↓
SimpleMiddleware
   ↓
Flask
```

---

# 21. Understanding `wsgi_app`

This line:

```
app.wsgi_app = SimpleMiddleware(app.wsgi_app)
```

may initially look strange.

Before:

```
app.wsgi_app
     ↓
Flask application
```

After:

```
app.wsgi_app
     ↓
SimpleMiddleware
     ↓
Original Flask application
```

The middleware wraps the original WSGI application.

---

# 22. Middleware Request Flow

Consider:

```
class SimpleMiddleware:

    def __init__(self, app):
        self.app = app

    def __call__(self, environ, start_response):

        print("Before Flask")

        response = self.app(
            environ,
            start_response
        )

        print("After Flask")

        return response
```

Flow:

```
Request
   ↓
"Before Flask"
   ↓
Flask
   ↓
Route
   ↓
Response
   ↓
"After Flask"
   ↓
Client
```

---

# 23. Middleware vs Decorator

This distinction is very important.

|Decorator|Middleware|
|---|---|
|Usually targets specific functions/routes|Usually targets application/request pipeline|
|Function-level|Application/server-level|
|Good for authorization|Good for request processing|
|Good for reusable route checks|Good for global behavior|
|Python function wrapping|WSGI/application wrapping|

### Example

Authentication for one route:

```
@login_required
def profile():
    ...
```

Application-wide request logging:

```
app.wsgi_app = LoggingMiddleware(app.wsgi_app)
```

---

# 24. Flask `before_request`

Flask provides a simpler mechanism for request-wide logic:

```
@app.before_request
def before_request():
    print("Request started")
```

This is often easier than writing raw WSGI middleware.

It runs before the request reaches the route.

Flow:

```
Request
  ↓
before_request
  ↓
Route
```

---

# 25. Flask `after_request`

You can also run logic after a response is created.

```
@app.after_request
def after_request(response):
    print("Response created")
    return response
```

Flow:

```
Request
  ↓
before_request
  ↓
Route
  ↓
Response
  ↓
after_request
  ↓
Client
```

---

# 26. Flask `teardown_request`

Flask also provides teardown hooks.

```
@app.teardown_request
def teardown_request(exception):
    ...
```

This runs when request processing is being torn down.

It is useful for cleanup tasks.

The callback receives an exception object when an exception occurred, or `None` otherwise.

---

# 27. Request Hook Mental Model

Flask provides several useful hooks:

```
Request
   ↓
before_request
   ↓
Route
   ↓
after_request
   ↓
Response
   ↓
teardown_request
```

The exact behavior around exceptions and teardown is important in advanced applications, but this is the basic mental model.

# 28. Global Request Logging

Instead of adding:

```
print("Request received")
```

to every route, use:

```
@app.before_request
def log_request():
    print(request.method, request.path)
```

You could see:

```
GET /
POST /users
GET /products
DELETE /users/10
```

For real applications, use the `logging` module rather than `print()`.

Conceptually:

```

  ↓
Generate Request ID
  ↓

  ↓
```

# 30. Adding Response Headers

A response hook can add headers.

```
@app.after_request
def add_headers(response):

    response.headers["X-App-Version"] = "1.0"

    return response
```

Now responses contain:

```
X-App-Version: 1.0
```

Security-related headers can also be managed this way, although dedicated security tooling can be preferable for complex applications.

# 31. Decorators and Middleware Solve Different Problems

Imagine a hospital with many doors.

A middleware is like the **building's main security checkpoint**.

A decorator is like a **special access badge required for one particular room**.

```
                    Building
                       │
                 Middleware
                       ↓
              Main Request Check
                       │
            ┌──────────┼──────────┐
            ↓          ↓          ↓
          Route      Route      Route
            │          │          │
        Decorator  Decorator  Decorator
```

This distinction helps you choose the right tool.

# 32. When Should You Use a Decorator?

Use a custom decorator when logic applies to **specific functions or routes**.

Good examples:

```
@login_required
@admin_required
@permission_required(...)
@rate_limit(...)
@validate_input(...)
```

---

# 33. When Should You Use Middleware?

Use middleware when logic belongs to the **request/response pipeline or infrastructure layer**.

Good examples:

```
Request logging
Request IDs
Tracing
Proxy handling
Global request transformation
Response processing
```

---

# 34. When Should You Use `before_request`?

If the logic is Flask-specific and should run before every request, `before_request` is often simpler than raw WSGI middleware.

Example:

```
@app.before_request
def check_application_status():
    ...
```

---

# 35. When Should You Use `after_request`?

Use it when you need to inspect or modify the response after the route executes.

Example:

```
@app.after_request
def add_custom_header(response):
    response.headers["X-App-Version"] = "1.0"
    return response
```

Remember:

> **An `after_request` function should return the response.**

---

# 36. Blueprint-Level Hooks

Blueprints can also have request hooks.

For example:

```
@users_bp.before_request
def before_users_request():
    ...
```

This allows logic to apply specifically to routes belonging to that blueprint.

This is useful when:

```
Global logic
    ↓
Application hooks

Feature-specific logic
    ↓
Blueprint hooks
```

---

# 37. Layering Decorators

You can use multiple decorators.

Example:

```
@app.get("/admin/reports")
@login_required
@admin_required
def admin_reports():
    return "Reports"
```

Conceptually:

```
Request
  ↓
login_required
  ↓
admin_required
  ↓
admin_reports()
```

This allows different responsibilities to remain separate.

---

# 38. Decorator Order

With multiple decorators:

```
@A
@B
def function():
    ...
```

Python conceptually does:

```
function = A(B(function))
```

Therefore, order can affect behavior.

For security-sensitive decorators, understand exactly which check happens first.

A common pattern is:

```
@app.get("/admin")
@login_required
@admin_required
def admin():
    ...
```

Authentication should be established before authorization.

---

# 39. Avoid Putting Too Much Logic in Decorators

A decorator should have a focused responsibility.

Good:

```
@login_required
```

Less ideal:

```
@do_everything()
```

where the decorator:

- checks login
- queries five tables
- sends emails
- modifies the database
- generates reports
- performs business calculations

That becomes difficult to understand and test.

---

# 40. Decorators vs Service Layer

Remember the architecture from **11.3**:

```
Route
  ↓
Service
  ↓
Repository / Model
  ↓
Database
```

A decorator should usually handle **cross-cutting concerns**.

The service layer should handle **business logic**.

For example:

```
@login_required
def create_order():
    return order_service.create_order(...)
```

Here:

```
Decorator
 ↓
Authentication

Service
 ↓
Order business logic
```

Nice and clean.

# 41. Common Mistakes With Decorators

### 1. Forgetting `@wraps`

Bad:

```
def decorator(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper
```

Better:

```
from functools import wraps

def decorator(func):

    @wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper
```

---

### 2. Forgetting `return`

Bad:

```
def wrapper(*args, **kwargs):
    func(*args, **kwargs)
```

Better:

```
def wrapper(*args, **kwargs):
    return func(*args, **kwargs)
```

---

### 3. Incorrect arguments

Routes can receive parameters:

```
@app.get("/users/<int:user_id>")
def user(user_id):
    ...
```

Your decorator should support:

```
def wrapper(*args, **kwargs):
```

rather than assuming the function has no arguments.

---

### 4. Putting business logic into decorators

Keep decorators focused.

---

# 42. Common Middleware Mistakes

### Mistake 1: Forgetting to call the wrapped application

Bad:

```
def __call__(self, environ, start_response):
    print("Request")
```

The request never reaches Flask.

Better:

```
def __call__(self, environ, start_response):
    print("Request")
    return self.app(environ, start_response)
```

---

### Mistake 2: Breaking the response

Middleware must respect the WSGI interface.

---

### Mistake 3: Using raw WSGI middleware unnecessarily

If Flask's:

```
before_request
after_request
```

already solves the problem, use the simpler Flask mechanism.

---

# 43. Security Considerations

Decorators are commonly used for authorization, but remember:

> **Authorization must happen on the backend.**

Never rely only on frontend UI restrictions.

For example, hiding:

```
Delete User
```

from a frontend does not protect:

```
DELETE /users/10
```

The Flask backend should enforce:

```
@permission_required("users.delete")
```

or equivalent authorization logic.

---

# 44. Middleware Security

Middleware can also be security-sensitive.

For example:

```
Proxy headers
Authentication infrastructure
Security headers
Request validation
Rate limiting
```

A badly configured middleware layer can affect every request, so keep global middleware simple, well-tested, and observable.

# 48. Quick Revision

### What is a decorator?

A function that modifies or extends another function's behavior.

### What is a custom decorator?

A decorator you create for your application's specific needs.

### Why use `@wraps`?

To preserve the wrapped function's metadata.

```
from functools import wraps
```

### What is middleware?

A layer that sits around the request/response pipeline.

### What is WSGI middleware?

Middleware that wraps a WSGI application.

### How can Flask wrap WSGI middleware?

```
app.wsgi_app = Middleware(app.wsgi_app)
```

### What is `before_request`?

A Flask hook that runs before request handling reaches the route.

### What is `after_request`?

A Flask hook that can inspect/modify the response after route processing.

### What is `teardown_request`?

A hook for request teardown and cleanup.

### Decorator or middleware for route authorization?

Usually **decorator**.

### Middleware or `before_request` for global request logging?

Either can work, but Flask's `before_request` is often simpler for Flask-specific application logic.

---

# 49. Golden Rules

Remember these:

> **Decorator = function/route-level behavior.**

> **Middleware = request/response pipeline behavior.**

> **`before_request` = run logic before Flask routes.**

> **`after_request` = process the response after the route.**

> **Use `@wraps` in custom decorators.**

> **Keep business logic in the service layer, not decorators or middleware.**
