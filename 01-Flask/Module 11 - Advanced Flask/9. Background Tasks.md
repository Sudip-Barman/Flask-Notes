Background tasks allow a Flask application to perform **long-running or delayed work outside the main request flow**.

The key idea is simple:

```
Without background task:

Client
  ↓
Flask
  ↓
Do everything
  ↓
Response
```

With a background task:

```
Client
  ↓
Flask
  ↓
Start task
  ↓
Quick response
  ↓
Background Worker
  ↓
Long-running work
```

This becomes important when an operation takes too long to complete during a normal HTTP request.

---

# 1. What Is a Background Task?

A **background task** is work that is executed separately from the normal request-response flow.

Examples:

- Sending emails
- Generating reports
- Processing large files
- Resizing images
- Sending notifications
- Generating PDFs
- Running scheduled jobs
- Processing uploaded data
- Calling slow external APIs
- Data cleanup

### Simple definition

> A background task is work that can be performed separately from the user's immediate HTTP request.

---

# 2. Why Do We Need Background Tasks?

Imagine an endpoint:

```
@app.post("/generate-report")
def generate_report():
    create_large_report()
    send_email()
    upload_file()
    return {"message": "Report ready"}
```

Suppose these operations take:

```
Generate report → 15 seconds
Send email     → 3 seconds
Upload file    → 5 seconds
```

The user could wait:

```
15 + 3 + 5 = 23 seconds
```

That's a poor user experience.

Instead:

```
POST /generate-report
        ↓
Create task
        ↓
Return quickly
        ↓
Background worker
        ↓
Generate report
        ↓
Send email
        ↓
Upload file
```

The user doesn't have to keep the HTTP request open for all 23 seconds.

---

# 3. Request-Response vs Background Processing

## Normal request

```
Browser
   ↓
GET /report
   ↓
Flask
   ↓
Generate report
   ↓
Return response
```

The request waits for the work.

---

## Background task

```
Browser
   ↓
POST /report
   ↓
Flask
   ↓
Create background job
   ↓
Return "Job started"
   
Meanwhile:

Worker
   ↓
Generate report
   ↓
Save result
```

This is much better for expensive operations.

---

# 4. Synchronous vs Asynchronous vs Background

These terms are related but **not identical**.

### Synchronous

The caller waits for the operation to finish.

```
A
↓
B
↓
C
↓
Done
```

### Asynchronous

The program can handle other work while waiting for an operation.

```
Start A
 ↓
Do other work
 ↓
A completes
```

### Background task

The work is moved outside the main request-processing path.

```
Request
  ↓
Queue job
  ↓
Response

Worker
  ↓
Process job
```

A background task is often implemented using asynchronous or distributed infrastructure, but the concepts should not be treated as interchangeable.

---

# 5. Simple Flask Background Thread

For very small applications, you might see:

```
from threading import Thread

def send_email():
    print("Sending email...")
```

Then:

```
@app.post("/send")
def send():
    thread = Thread(target=send_email)
    thread.start()

    return {"message": "Email task started"}
```

The HTTP request can return while the thread continues.

Conceptually:

```
Request
  │
  ├──→ Start Thread
  │
  └──→ Response

Thread
  ↓
Send Email
```

This can be useful for learning and small, non-critical tasks.

But it is **not usually the best production architecture**.

---

# 6. Why Threads Are Not Enough

Suppose your Flask application runs on several workers:

```
Worker 1
Worker 2
Worker 3
Worker 4
```

A background thread belongs to the process that created it.

If that process:

- crashes
- restarts
- is killed
- is redeployed

the task can disappear.

You also don't automatically get:

- persistent queues
- retries
- task monitoring
- failure tracking
- distributed workers

Therefore production applications often use a **task queue**.

---

# 7. Task Queue

A task queue stores jobs until a worker processes them.

Mental model:

```
Flask
  ↓
Task Queue
  ↓
Worker
  ↓
Task
```

For example:

```
User
 ↓
Flask API
 ↓
Redis / Message Broker
 ↓
Worker
 ↓
Send Email
```

The queue acts like a waiting line for jobs.

---

# 8. Popular Background Task Tools

Common technologies in the Python ecosystem include:

|Tool|Purpose|
|---|---|
|Celery|Distributed task queue|
|RQ|Redis-based task queue|
|Dramatiq|Background task processing|
|APScheduler|Scheduled/background jobs|
|Threading|Simple in-process background work|
|`asyncio`|Asynchronous programming|

You don't need all of these for every Flask project.

For larger applications, **Celery** is one of the most well-known choices.

---

# 9. Celery Mental Model

A typical Celery architecture:

```
                 Flask
                   │
                   ↓
              Create Task
                   │
                   ↓
             Message Broker
             ┌─────────────┐
             │    Redis    │
             └─────────────┘
                   │
                   ↓
               Celery
                Worker
                   │
                   ↓
              Execute Task
```

The broker stores/messages the job so workers can process it.

---

# 10. What Is a Worker?

A **worker** is a separate process that executes background tasks.

For example:

```
Flask Process
     │
     │ creates job
     ↓
Queue
     │
     ↓
Worker Process
     │
     ↓
send_email()
```

The Flask process doesn't need to perform the expensive operation itself.

---

# 11. What Is a Message Broker?

A **message broker** is a system that transports/stores messages between producers and consumers.

Examples include:

- Redis
- RabbitMQ

Mental model:

```
Producer
   ↓
Broker
   ↓
Consumer
```

In background processing:

```
Flask
   ↓
Broker
   ↓
Worker
```

Flask produces the task.

The worker consumes it.

---

# 12. Basic Celery Example

A simplified task:

```
from celery import Celery

celery = Celery(
    __name__,
    broker="redis://localhost:6379/0"
)

@celery.task
def send_email():
    print("Sending email...")
```

Then you can enqueue it:

```
send_email.delay()
```

Important:

```
send_email()
```

means:

> Run the function normally.

While:

```
send_email.delay()
```

means:

> Send the task to Celery for background execution.

---

# 13. Passing Arguments

You can pass data to a background task.

```
@celery.task
def send_welcome_email(email):
    print("Sending email to:", email)
```

Then:

```
send_welcome_email.delay("user@example.com")
```

The task queue receives something conceptually like:

```
Task:
send_welcome_email

Arguments:
"user@example.com"
```

The worker later executes it.

---

# 14. Flask + Celery

In a real Flask application, you generally want Celery to work cleanly with the application's configuration and application context.

A simplified architecture:

```
project/
│
├── app/
│   ├── __init__.py
│   ├── extensions.py
│   ├── routes/
│   └── tasks/
│       ├── __init__.py
│       └── email_tasks.py
│
├── celery_app.py
├── config.py
└── run.py
```

This keeps background-task code separate from routes.

---

# 15. Why Application Context Matters

Suppose a task needs:

```
from flask import current_app
```

or:

```
from app.extensions import db
```

A background worker isn't automatically inside a Flask request context.

Remember your previous topic:

```
Application Context
       ↓
current_app
g
```

A background worker may need an application context when accessing Flask-specific resources.

Conceptually:

```
with app.app_context():
    perform_task()
```

This is especially important when the task needs:

- Flask configuration
- database extensions
- application services
- other Flask-dependent resources

---

# 16. Background Tasks and Database Sessions

Suppose a task updates a database:

```
@task
def update_order(order_id):
    order = db.session.get(Order, order_id)

    order.status = "completed"

    db.session.commit()
```

You need to think about:

- application context
- database session lifecycle
- transaction boundaries
- errors
- rollback
- worker isolation

A worker should not blindly reuse a database session from a web request.

Each task should have a clean, controlled database interaction.

---

# 17. Task States

Background jobs often have states.

For example:

```
PENDING
   ↓
STARTED
   ↓
SUCCESS
```

Or:

```
PENDING
   ↓
STARTED
   ↓
FAILURE
```

You can think of a task like:

```
Task #123

Status: PROCESSING
```

Later:

```
Task #123

Status: SUCCESS
Result: report.pdf
```

This is useful when the user needs to track long-running operations.

---

# 18. Returning a Task ID

When a task is queued, you can return an identifier.

Conceptually:

```
{
    "message": "Task started",
    "task_id": "abc123"
}
```

Then the frontend can ask:

```
GET /tasks/abc123
```

and receive:

```
{
    "task_id": "abc123",
    "status": "PROCESSING"
}
```

Later:

```
{
    "task_id": "abc123",
    "status": "SUCCESS"
}
```

This creates a useful API pattern for long-running jobs.

---

# 19. Background Task API Pattern

A common design:

```
POST /reports
       ↓
Create task
       ↓
202 Accepted
       ↓
Return task ID
```

Then:

```
GET /tasks/{task_id}
       ↓
Check status
```

And eventually:

```
SUCCESS
   ↓
Get result
```

This is a good REST API pattern for asynchronous processing.

---

# 20. Why `202 Accepted`?

Remember your HTTP status codes.

For a task that has been accepted but **not completed yet**:

```
202 Accepted
```

can be appropriate.

Example:

```
{
    "success": true,
    "message": "Report generation started",
    "task_id": "abc123"
}
```

This tells the client:

> "I accepted your request, but the final work is still happening."

---

# 21. Retries

One of the major advantages of task queues is retry support.

Imagine:

```
Send email
   ↓
Network error
   ↓
Retry
   ↓
Success
```

For example, conceptually:

```
@task
def send_email():
    ...
```

If the operation fails temporarily, the task system can retry it.

Retries are especially useful for temporary failures such as:

- network problems
- temporary API failures
- service unavailability
- database connection problems

---

# 22. Retry Carefully

Retries can also cause problems.

Suppose a task:

```
Charge customer
```

runs successfully, but the worker crashes before recording success.

A retry could potentially charge again.

Therefore, important operations should consider **idempotency**.

For example:

```
Payment ID: PAY-12345
```

The system can check whether that payment was already processed before performing it again.

This is an important real-world distributed-systems concept.

---

# 23. Scheduled Tasks

Background systems can also execute tasks at specific times.

For example:

```
Every day at 12:00 AM
        ↓
Clean temporary files
```

Or:

```
Every Monday
      ↓
Generate weekly report
```

Or:

```
Every 10 minutes
      ↓
Check external service
```

This is different from a task that is simply triggered by an HTTP request.

---

# 24. Scheduler Mental Model

```
Scheduler
   ↓
Time arrives
   ↓
Create task
   ↓
Queue
   ↓
Worker
   ↓
Execute
```

Tools such as **APScheduler** can be used for scheduling, while Celery has its own ecosystem for scheduled tasks.

---

# 25. Background Tasks vs Signals

You just learned Signals, so this distinction is important.

### Signal

```
Something happened
       ↓
Signal
       ↓
Receivers
```

### Background task

```
Work needs to happen
       ↓
Queue
       ↓
Worker
       ↓
Execute later/separately
```

A signal itself does **not** automatically create a background job.

You could, however, use a signal receiver to enqueue a background task:

```
Event
 ↓
Signal
 ↓
Receiver
 ↓
Queue task
 ↓
Worker
```

This can be useful, but should be designed carefully.

---

# 26. Background Tasks vs `asyncio`

Another common confusion.

`asyncio` allows asynchronous programming within Python.

Example:

```
async def fetch_data():
    ...
```

This does not automatically mean:

> "Run this job in another worker process."

A background worker system provides a different architecture.

Think:

```
asyncio
→ asynchronous execution model

Celery/RQ
→ distributed/background task processing
```

They can sometimes be used together, but they solve different problems.

---

# 27. What Should Go Into a Background Task?

Good candidates:

```
Large report generation
Email sending
Image processing
PDF generation
File conversion
Bulk notifications
Data imports
External API synchronization
Scheduled cleanup
Large calculations
```

Poor candidates:

```
Simple database query
Simple validation
Small calculations
Normal CRUD operation
Authentication check
Basic response formatting
```

Don't turn every function into a background task.

# 29. Error Handling

Background tasks need their own error handling.

Normal request:

```
try:
    do_work()
except Exception:
    return {"error": "Failed"}, 500
```

But a background task doesn't necessarily have a browser waiting for a response.

Instead, the system may:

```
Task
 ↓
Exception
 ↓
Record FAILURE
 ↓
Log error
 ↓
Retry if appropriate
```

This is why background processing requires proper:

- logging
- monitoring
- retries
- task status
- failure handling

---

# 30. Logging Background Tasks

A task should produce useful logs.

For example:

```
import logging

logger = logging.getLogger(__name__)

def process_report(report_id):
    logger.info("Starting report %s", report_id)

    try:
        ...
        logger.info("Report %s completed", report_id)
    except Exception:
        logger.exception("Report %s failed", report_id)
        raise
```

Notice:

```
logger.exception(...)
```

is particularly useful because it records the exception traceback.

Logging will become more important later in **11.15 Logging & Monitoring**.

---

# 31. Security Considerations

Background tasks still need security.

Never assume:

> "It's a background task, so security doesn't matter."

For example, don't blindly trust:

```
user_id
file_path
order_id
```

provided to a task.

Validate the data and enforce authorization at the point where the operation is initiated.

Also avoid putting sensitive information into task payloads unnecessarily.

---

# 32. Important Production Principle

A background worker is a separate execution environment.

Therefore:

> Don't assume that the worker has the same request state as the Flask request.

For example, don't expect:

```
request
session
g
```

to automatically contain the original request's information.

Instead, pass the required identifiers explicitly:

```
process_order.delay(order_id)
```

rather than trying to pass an entire request object.

---

# 33. Don't Pass Huge Objects

Prefer:

```
process_report.delay(report_id)
```

instead of:

```
process_report.delay(huge_python_object)
```

Why?

Because the task system typically needs to serialize task arguments.

IDs and small values are much easier to:

- serialize
- store
- retry
- inspect
- transfer between processes

Then the worker can retrieve the required data.

```
Task
 ↓
report_id
 ↓
Database
 ↓
Report
```

---

# 34. Idempotency

This is an important concept for background systems.

An operation is **idempotent** if performing it multiple times has the same intended final effect as performing it once.

For example:

```
Set order status = "completed"
```

is generally easier to make idempotent than:

```
Add ₹100 to account
```

because repeated execution of the second operation could cause an incorrect balance.

Background tasks can be retried, so critical tasks should be designed with duplicate execution in mind.

---

# 35. Simple Architecture for Small Flask Apps

For a small project:

```
Flask
 ├── Routes
 ├── Services
 └── Thread
```

This may be enough for:

- development
- prototypes
- simple non-critical work

But for production-scale systems:

```
Flask
   ↓
Queue
   ↓
Worker
   ↓
Database / External Services
```

is generally more robust.

# 36. Common Mistakes

### Mistake 1: Doing expensive work inside a request

```
@app.post("/report")
def report():
    generate_huge_report()
```

This can make the request slow.

---

### Mistake 2: Thinking `async` automatically means background

It doesn't.

---

### Mistake 3: Using threads for critical jobs

A process restart can lose the task.

---

### Mistake 4: Ignoring retries

Temporary failures happen.

---

### Mistake 5: Ignoring duplicate execution

Retries can cause duplicate side effects.

---

### Mistake 6: Passing request/session objects

Background workers don't automatically share request context.

---

### Mistake 7: No task monitoring

If a task fails at 3 AM, you should have some way to know.

---

# 37. When Should You Use Background Tasks?

Use them when:

```
Operation is slow
       OR
Operation doesn't need immediate completion
       OR
Operation can safely run separately
```

For example:

```
User clicks "Generate Report"
          ↓
API returns quickly
          ↓
Worker generates report
          ↓
User checks status
          ↓
Report becomes available
```
