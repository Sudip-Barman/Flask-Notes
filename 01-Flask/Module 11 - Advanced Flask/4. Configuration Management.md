
Configuration Management is one of the most important parts of building a **professional Flask application**.

As your application grows, you will have many settings such as:

- Database URL
- Secret key
- Debug mode
- JWT settings
- Session settings
- File upload limits
- Email settings
- API keys
- Environment-specific settings

Instead of scattering these values throughout your code, Flask provides a centralized **configuration system**.

---

# 1. What is Configuration Management?

**Configuration Management** means managing application settings in a structured and centralized way.

For example, instead of writing:

```
app.config["SECRET_KEY"] = "my-secret-key"
app.config["DEBUG"] = True
app.config["MAX_CONTENT_LENGTH"] = 16 * 1024 * 1024
```

directly inside different parts of your application, we keep configuration in dedicated places.

### Simple idea

```
Application
     ↓
Configuration
     ↓
Settings
     ├── Database
     ├── Security
     ├── Sessions
     ├── Uploads
     ├── Email
     └── API
```

The application reads these settings when it starts.

---

# 2. Why Configuration Management is Important

Without proper configuration management, large applications can become difficult to maintain.

### Poor approach

```
app.config["SQLALCHEMY_DATABASE_URI"] = "mysql+pymysql://root:password@localhost/shop"

app.config["SECRET_KEY"] = "123456"

app.config["DEBUG"] = True
```

Problems:

- Secrets are exposed in source code.
- Changing environments becomes difficult.
- Development and production settings can get mixed.
- Configuration becomes scattered.
- Testing becomes harder.

### Better approach

```
config.py
    ↓
DevelopmentConfig
TestingConfig
ProductionConfig
    ↓
create_app()
    ↓
Flask Application
```

# 3. Flask `app.config`

Flask provides a configuration object through:

```
app.config
```

It behaves somewhat like a dictionary.

Example:

```
from flask import Flask

app = Flask(__name__)

app.config["DEBUG"] = True
app.config["SECRET_KEY"] = "example-key"
```

You can read values:

```
print(app.config["DEBUG"])
```

or:

```
print(app.config.get("DEBUG"))
```

---

# 4. `config` Works Like a Dictionary

You can think of:

```
app.config
```

as a special dictionary containing application settings.

Example:

```
app.config["DEBUG"] = True
app.config["APP_NAME"] = "Student Portal"
```

Then:

```
app.config["APP_NAME"]
```

returns:

```
Student Portal
```

# 6. Direct Configuration

For a very small application, you can configure Flask directly.

```
from flask import Flask

app = Flask(__name__)

app.config["SECRET_KEY"] = "example-key"
app.config["DEBUG"] = True
app.config["APP_NAME"] = "Student Portal"
```

This works, but it becomes inconvenient as the application grows.

For larger applications, **configuration classes** are better.

---

# 7. Configuration Classes

A configuration class stores related settings together.

Example:

```
class DevelopmentConfig:
    DEBUG = True
    TESTING = False
```

Another:

```
class TestingConfig:
    DEBUG = False
    TESTING = True
```

And:

```
class ProductionConfig:
    DEBUG = False
    TESTING = False
```

Now we have separate configurations for different environments.

---

# 8. Why Multiple Configurations?

A real application usually has different environments.

For example:

```
Development
Testing
Production
```

Each environment may require different settings.

|Setting|Development|Testing|Production|
|---|---|---|---|
|DEBUG|True|False|False|
|TESTING|False|True|False|
|Database|Development DB|Test DB|Production DB|
|Logging|Normal|Test|Detailed|
|Security|Development|Test|Strict|

This prevents development settings from accidentally being used in production.

# 10. Creating `config.py`

Example:

```
class DevelopmentConfig:
    DEBUG = True
    TESTING = False
    SECRET_KEY = "development-key"


class TestingConfig:
    DEBUG = False
    TESTING = True
    SECRET_KEY = "testing-key"


class ProductionConfig:
    DEBUG = False
    TESTING = False
    SECRET_KEY = "production-key"
```

Now we have three configuration classes.

# 11. Loading a Configuration Class

Flask provides:

```
app.config.from_object()
```

Example:

```
from flask import Flask
from config import DevelopmentConfig

app = Flask(__name__)

app.config.from_object(DevelopmentConfig)
```

Now Flask loads the configuration from `DevelopmentConfig`.

---

# 12. Configuration with Application Factory

This becomes especially useful with the **Application Factory Pattern**.

Example:

```
from flask import Flask
from config import DevelopmentConfig

def create_app():
    app = Flask(__name__)

    app.config.from_object(DevelopmentConfig)

    return app
```

The flow is:

```
create_app()
     ↓
Create Flask App
     ↓
Load Configuration
     ↓
Return App
```

---

# 13. Passing Configuration to the Factory

A better approach is to allow the factory to receive a configuration class.

```
from flask import Flask

def create_app(config_class):
    app = Flask(__name__)

    app.config.from_object(config_class)

    return app
```

Then:

```
from app import create_app
from config import DevelopmentConfig

app = create_app(DevelopmentConfig)
```

For production:

```
app = create_app(ProductionConfig)
```

This makes the application flexible.

---

# 14. Default Configuration

You can also provide a default.

```
from flask import Flask
from config import DevelopmentConfig

def create_app(config_class=DevelopmentConfig):
    app = Flask(__name__)

    app.config.from_object(config_class)

    return app
```

Now:

```
app = create_app()
```

uses:

```
DevelopmentConfig
```

while:

```
app = create_app(ProductionConfig)
```

uses:

```
ProductionConfig
```

# 16. Secret Key Configuration

Flask uses `SECRET_KEY` for security-related functionality such as sessions.

Example:

```
class DevelopmentConfig:
    SECRET_KEY = "development-secret"
```

However, sensitive production secrets should **not** be hardcoded.

Bad:

```
SECRET_KEY = "my-real-production-secret"
```

Better:

```
Environment Variable
       ↓
Configuration
       ↓
Flask
```

# 17. Environment Variables

Environment variables allow configuration to be supplied outside the source code.

For example:

```
SECRET_KEY=some-secret-value
```

Then Python can read it using:

```
import os

secret_key = os.environ.get("SECRET_KEY")
```

Example:

```
class ProductionConfig:
    SECRET_KEY = os.environ.get("SECRET_KEY")
```

Now the actual secret does not need to appear in your Git repository.

---

# 18. `.env` File

During local development, you may use a `.env` file.

Example:

```
SECRET_KEY=development-secret
DATABASE_URL=sqlite:///development.db
DEBUG=true
```

Your application can load environment variables using tools such as `python-dotenv`.

Flask development environments commonly work with `.env` files through this ecosystem.

### Important

Do not commit real secrets to Git.

A typical `.gitignore` includes:

```
.env
```

# 19. Sensitive vs Non-Sensitive Configuration

Not every configuration value is secret.

### Usually sensitive

```

```

### Usually non-sensitive

```
DEBUG
APP_NAME

```

The important distinction is:

```
Configuration
├── Public / non-sensitive settings
└── Secrets
       ↓
   Environment variables
```

# 20. `from_mapping()`

Flask also allows configuration from a dictionary-like mapping.

Example:

```
app.config.from_mapping(
    DEBUG=True,
    TESTING=False,
    APP_NAME="Student Portal"
)
```

Equivalent idea:

```
app.config["DEBUG"] = True
app.config["TESTING"] = False
app.config["APP_NAME"] = "Student Portal"
```

This is useful when configuration is already available as a dictionary.

# 22. Reading Configuration Inside a Route

You can access configuration through `current_app`.

```
from flask import Blueprint, current_app

main_bp = Blueprint("main", __name__)

@main_bp.get("/")
def home():
    app_name = current_app.config["APP_NAME"]

    return {
        "app": app_name
    }
```

Why `current_app`?

Because with the application factory pattern, you should avoid relying on a single global Flask application object.

---

# 23. `app.config` vs `current_app.config`

Inside application creation:

```
app.config["DEBUG"]
```

Inside a route or other application-context-aware code:

```
current_app.config["DEBUG"]
```

Think of it like:

```
Factory
   ↓
app.config

Running application code
   ↓
current_app.config
```

# 24. Configuration Selection Using Environment

A common pattern is:

```
import os

environment = os.environ.get("FLASK_ENV", "development")
```

Then choose configuration.

Conceptually:

```
configs = {
    "development": DevelopmentConfig,
    "testing": TestingConfig,
    "production": ProductionConfig
}
```

Then:

```
config_class = configs.get(environment, DevelopmentConfig)
```

And:

```
app.config.from_object(config_class)
```

Complete example:

```
import os
from flask import Flask

def create_app():
    app = Flask(__name__)

    environment = os.environ.get("APP_ENV", "development")

    configs = {
        "development": DevelopmentConfig,
        "testing": TestingConfig,
        "production": ProductionConfig
    }

    config_class = configs.get(
        environment,
        DevelopmentConfig
    )

    app.config.from_object(config_class)

    return app
```

# 25. Better Configuration Pattern

A clean `config.py` might look like:

```
import os


class BaseConfig:
    SECRET_KEY = os.environ.get("SECRET_KEY")
    SQLALCHEMY_TRACK_MODIFICATIONS = False


class DevelopmentConfig(BaseConfig):
    DEBUG = True


class TestingConfig(BaseConfig):
    TESTING = True
    DEBUG = False


class ProductionConfig(BaseConfig):
    DEBUG = False
```

This uses inheritance.

```
             BaseConfig
            /    |     \
           /     |      \
Development  Testing  Production
```

Common settings go into `BaseConfig`.

Environment-specific settings go into child classes.

# 26. Configuration Inheritance

Example:

```
class BaseConfig:
    SECRET_KEY = "example"
    APP_NAME = "Student Portal"


class DevelopmentConfig(BaseConfig):
    DEBUG = True


class ProductionConfig(BaseConfig):
    DEBUG = False
```

`DevelopmentConfig` automatically receives:

```
SECRET_KEY
APP_NAME
```

from `BaseConfig`.

It additionally has:

```
DEBUG = True
```

# 27. Testing Configuration

Testing should use a separate configuration.

Example:

```
class TestingConfig:
    TESTING = True
    SQLALCHEMY_DATABASE_URI = "sqlite:///test.db"
```

This prevents tests from accidentally modifying your real database.

For example:

```
Production Database
       ❌
       ↑
Tests

Testing Database
       ↑
      Tests
```

A good test environment should be isolated.

---

# 28. Configuration Overrides

Sometimes you need to override a setting temporarily.

Example:

```
app.config.from_mapping(
    TESTING=True
)
```

This is useful in automated tests.

For example:

```
app = create_app(TestingConfig)

with app.test_client() as client:
    response = client.get("/")
```

Testing configuration can also disable or replace external services.

# 34. Configuration Loading Order

A useful mental model is:

```
Start Application
       ↓
Create Flask App
       ↓
Load Base Configuration
       ↓
Load Environment Configuration
       ↓
Load Environment Variables / Secrets
       ↓
Initialize Extensions
       ↓
Register Blueprints
       ↓
Start Application
```

The exact loading strategy can vary, but the principle is that configuration should be available **before extensions and application components need it**.

# 35. Configuration Should Not Contain Business Logic

Configuration should contain settings, not application behavior.

### Good

```
class ProductionConfig:
    MAX_ITEMS_PER_PAGE = 50
    DEBUG = False
```

### Bad

```
class ProductionConfig:
    def calculate_order_total(self):
        ...
```

Business logic belongs in services or other application modules.

Remember:

```
Configuration
     ↓
"What settings should the application use?"

Service
     ↓
"What should the application do?"
```

# 36. Common Configuration Mistakes

### Mistake 1: Hardcoding secrets

```
SECRET_KEY = "real-secret"
```

Avoid this for production secrets.

---

### Mistake 2: Committing `.env`

Never commit:

```
.env
```

if it contains real credentials.

---

### Mistake 3: Production DEBUG

Never intentionally run production with:

```
DEBUG = True
```

Debug mode can expose sensitive information.

---

### Mistake 4: One configuration for everything

Using exactly the same settings for:

```
Development
Testing
Production
```

can cause serious problems.

---

### Mistake 5: Scattered configuration

Bad:

```
# file 1
MAX_SIZE = 10

# file 2
MAX_SIZE = 20

# file 3
MAX_SIZE = 30
```

Centralize it.

---

### Mistake 6: Configuration mixed with business logic

Do not turn `config.py` into a giant application module.

---

### Mistake 7: Missing defaults

If a setting may be optional, consider:

```
value = current_app.config.get("OPTIONAL_SETTING")
```

instead of assuming it always exists.

# 38. Complete Example

### `config.py`

```
import os


class BaseConfig:
    SECRET_KEY = os.environ.get("SECRET_KEY")

    SQLALCHEMY_TRACK_MODIFICATIONS = False

    ITEMS_PER_PAGE = 20

    SESSION_COOKIE_HTTPONLY = True
    SESSION_COOKIE_SAMESITE = "Lax"


class DevelopmentConfig(BaseConfig):
    DEBUG = True

    SQLALCHEMY_DATABASE_URI = "sqlite:///development.db"


class TestingConfig(BaseConfig):
    TESTING = True
    DEBUG = False

    SQLALCHEMY_DATABASE_URI = "sqlite:///testing.db"


class ProductionConfig(BaseConfig):
    DEBUG = False

    SQLALCHEMY_DATABASE_URI = os.environ.get(
        "DATABASE_URL"
    )

    SESSION_COOKIE_SECURE = True
```

### `app/__init__.py`

```
from flask import Flask
from config import DevelopmentConfig


def create_app(config_class=DevelopmentConfig):
    app = Flask(__name__)

    app.config.from_object(config_class)

    return app
```

### `run.py`

```
from app import create_app

app = create_app()
```

This gives you a clean foundation for a larger Flask application.

# 40. Configuration Management vs Environment Variables

These concepts are related but not identical.

### Configuration Management

The overall system for managing settings.

### Environment Variables

One mechanism for supplying settings.

Think:

```
Configuration Management
        │
        ├── Config Classes
        ├── app.config
        ├── Environment Variables
        ├── .env
        └── Configuration Files
```

Environment variables are therefore **one tool inside configuration management**.

---

# 41. Important Methods to Remember

|Method|Purpose|
|---|---|
|`app.config["KEY"] = value`|Set configuration|
|`app.config["KEY"]`|Read configuration|
|`app.config.get("KEY")`|Safely read configuration|
|`app.config.from_object()`|Load from class/object|
|`app.config.from_mapping()`|Load from dictionary-like values|
|`os.environ.get()`|Read environment variable|

# 42. Best Practices

For professional Flask applications:

1. Centralize configuration.
2. Separate development, testing, and production.
3. Keep secrets outside source code.
4. Use environment variables for sensitive values.
5. Add `.env` to `.gitignore` when appropriate.
6. Never expose production secrets in Git.
7. Never intentionally enable debug mode in production.
8. Use a base configuration for shared settings.
9. Keep configuration separate from business logic.
10. Load configuration before initializing extensions.
11. Use testing-specific configuration.
12. Use secure cookie settings in production.
13. Provide sensible defaults where appropriate.
14. Avoid scattering magic values throughout the application.
