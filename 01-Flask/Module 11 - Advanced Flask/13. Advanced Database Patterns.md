Advanced database patterns are techniques for designing and using databases effectively as Flask applications become larger.

At the beginner level, we mostly worked with:

```
Flask
  ↓
SQLAlchemy Model
  ↓
Database
```

In a larger application, we may need:

```
Flask Route
    ↓
Service Layer
    ↓
Repository / Data Access Layer
    ↓
SQLAlchemy
    ↓
Database
```

The goal is to make database code **clean, reusable, scalable, testable, and reliable**.

---

# 1. What Are Advanced Database Patterns?

A database pattern is a **reusable way of organizing database-related code or solving common database problems**.

Examples:

|Pattern|Main Purpose|
|---|---|
|Repository Pattern|Separate database access from business logic|
|Service Layer|Keep business operations outside routes|
|Unit of Work|Manage transactions as one logical operation|
|Transaction Pattern|Ensure related changes succeed/fail together|
|Soft Delete|Hide records instead of physically deleting them|
|Audit Trail|Track important changes|
|Optimistic Locking|Prevent conflicting updates|
|N+1 Prevention|Avoid excessive database queries|
|Pagination|Handle large datasets efficiently|
|Database Constraints|Enforce data integrity|
|Connection Pooling|Reuse database connections|
|Read/Write Separation|Scale database workloads|
|Repository + Service|Create cleaner architecture|

We will build these concepts one by one.

---

# 2. Why Do We Need Advanced Patterns?

Imagine a small Flask application.

A route might contain:

```
@app.post("/orders")
def create_order():
    data = request.get_json()

    order = Order(
        customer_id=data["customer_id"],
        total=data["total"]
    )

    db.session.add(order)
    db.session.commit()

    return {"message": "Order created"}
```

This works.

But as the application grows, the route may become:

```
Validate request
↓
Check customer
↓
Check product stock
↓
Calculate price
↓
Create order
↓
Create order items
↓
Update inventory
↓
Create payment record
↓
Create audit record
↓
Commit transaction
↓
Send notification
```

Now the route becomes huge.

That's where architecture patterns become useful.

---

# 3. Route vs Service vs Database

A clean architecture separates responsibilities.

```
Route
  ↓
HTTP handling

Service
  ↓
Business logic

Repository / Model
  ↓
Database operations

Database
  ↓
Persistent data
```

For example:

```
POST /orders
      ↓
create_order_route()
      ↓
OrderService.create_order()
      ↓
OrderRepository
      ↓
SQLAlchemy
      ↓
Database
```

# 4. Repository Pattern

The **Repository Pattern** separates database access from business logic.

Instead of writing queries everywhere:

```
user = User.query.filter_by(email=email).first()
```

we can create a repository.

Example:

```
class UserRepository:

    @staticmethod
    def find_by_email(email):
        return User.query.filter_by(email=email).first()

    @staticmethod
    def find_by_id(user_id):
        return db.session.get(User, user_id)

    @staticmethod
    def save(user):
        db.session.add(user)
```

Now the service can use:

```
user = UserRepository.find_by_email(email)
```

---

# 5. Why Use a Repository?

Without repository:

```
Route 1 → SQL
Route 2 → SQL
Route 3 → SQL
Service → SQL
Task → SQL
```

Database logic becomes scattered everywhere.

With repository:

```
Routes
   ↓
Services
   ↓
Repository
   ↓
Database
```

This gives one place for many database operations.

---

# 6. Repository Example

```
class ProductRepository:

    @staticmethod
    def get_by_id(product_id):
        return db.session.get(Product, product_id)

    @staticmethod
    def get_all():
        return Product.query.all()

    @staticmethod
    def find_by_name(name):
        return Product.query.filter_by(name=name).first()

    @staticmethod
    def save(product):
        db.session.add(product)
```

Service:

```
class ProductService:

    @staticmethod
    def create_product(name, price):
        product = Product(
            name=name,
            price=price
        )

        ProductRepository.save(product)
        db.session.commit()

        return product
```

Route:

```
@app.post("/products")
def create_product():
    data = request.get_json()

    product = ProductService.create_product(
        data["name"],
        data["price"]
    )

    return {
        "id": product.id,
        "name": product.name
    }, 201
```

Now each layer has a clear responsibility.

---

# 7. Service Layer Pattern

The **Service Layer** contains business logic.

For example:

```
class OrderService:

    @staticmethod
    def create_order(customer_id, product_id, quantity):
        product = ProductRepository.get_by_id(product_id)

        if product is None:
            raise ValueError("Product not found")

        if product.stock < quantity:
            raise ValueError("Insufficient stock")

        total = product.price * quantity

        order = Order(
            customer_id=customer_id,
            total=total
        )

        product.stock -= quantity

        db.session.add(order)
        db.session.commit()

        return order
```

The route doesn't need to know how the order is calculated.

---

# 8. Why Service Layer?

A service layer helps keep business rules in one place.

For example:

```
OrderService
    ↓
Create Order
Calculate Total
Check Stock
Update Inventory
Create Order Items
```

The same service can be used by:

```
HTTP API
CLI
Background Task
Admin Panel
Tests
```

without duplicating business logic.

---

# 9. Repository + Service Pattern

This is a common combination:

```
                Flask Route
                     │
                     ▼
               Service Layer
                     │
                     ▼
              Repository Layer
                     │
                     ▼
                 SQLAlchemy
                     │
                     ▼
                  Database
```

Responsibilities:

|Layer|Responsibility|
|---|---|
|Route|HTTP request/response|
|Service|Business rules|
|Repository|Database operations|
|Model|Data structure/ORM mapping|
|Database|Persistent storage|

# 10. Don't Overuse Repositories

Repository Pattern is useful, but don't create unnecessary abstraction.

For a tiny Flask application:

```
User.query.all()
```

may be perfectly fine.

You don't need:

```
Route
 ↓
Service
 ↓
Repository
 ↓
DAO
 ↓
Repository Factory
 ↓
Database Adapter
 ↓
Database
```

That's architectural lasagna. 🍝

Use abstraction when it actually improves the project.

---

# 11. Unit of Work Pattern

The **Unit of Work** represents a group of database changes that should be treated as one logical operation.

For example, creating an order might involve:

```
Create Order
Create Order Items
Reduce Stock
Create Payment
Create Audit Log
```

These should normally succeed together.

```
All succeed → COMMIT
Any critical failure → ROLLBACK
```

---

# 12. Transaction Pattern

Example:

```
try:
    order = Order(...)
    db.session.add(order)

    product.stock -= quantity

    payment = Payment(...)
    db.session.add(payment)

    db.session.commit()

except Exception:
    db.session.rollback()
    raise
```

This protects the operation from partial database changes.

---

# 13. Why Transactions Matter

Without a transaction:

```
Create order       ✅
Create order item  ✅
Update stock       ❌
Create payment     ❌
```

Now the database is inconsistent.

With a transaction:

```
Create order       ✅
Create order item  ✅
Update stock       ❌
       ↓
ROLLBACK
       ↓
Nothing committed
```

This follows the **atomicity** principle from ACID.

---

# 14. Flush vs Commit

SQLAlchemy provides:

```
db.session.flush()
```

and:

```
db.session.commit()
```

They are not the same.

### `flush()`

Sends pending changes to the database within the current transaction.

Example:

```
order = Order(customer_id=10)

db.session.add(order)
db.session.flush()

print(order.id)
```

The database may now have generated the ID, but the transaction has **not necessarily been committed**.

### `commit()`

Makes the transaction permanent.

```
db.session.commit()
```

Mental model:

```
add()
 ↓
flush()
 ↓
database sees changes
 ↓
commit()
 ↓
transaction becomes permanent
```

---

# 15. Soft Delete

Normally:

```
db.session.delete(user)
```

physically removes a record.

With **soft delete**, we don't actually delete it.

Instead:

```
class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100))
    is_deleted = db.Column(db.Boolean, default=False)
```

Then:

```
user.is_deleted = True
db.session.commit()
```

---

# 16. Why Soft Delete?

Useful when you need:

- history
- recovery
- auditability
- regulatory records
- accidental deletion protection

Instead of:

```
DELETE
```

we do:

```
is_deleted = TRUE
```

Normal query:

```
users = User.query.filter_by(is_deleted=False).all()
```

---

# 17. Soft Delete Warning

Soft delete creates an important problem:

You must remember to exclude deleted records.

Bad:

```
User.query.all()
```

Potentially returns deleted records.

Better:

```
User.query.filter_by(is_deleted=False).all()
```

For larger systems, you can centralize this filtering rather than relying on developers to remember it everywhere.

# 18. Audit Trail

An **audit trail** records important changes.

Example:

```
User 10
changed Product 25
price
₹500 → ₹550
```

Audit table:

```
audit_logs
----------------
id
user_id
action
entity_type
entity_id
old_value
new_value
created_at
```

Example:

```
class AuditLog(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    user_id = db.Column(db.Integer)
    action = db.Column(db.String(100))
    entity_type = db.Column(db.String(100))
    entity_id = db.Column(db.Integer)
    created_at = db.Column(db.DateTime)
```

---

# 19. What Should Be Audited?

Usually important actions:

```
Login
Logout
Password change
Role change
User deletion
Financial changes
Permission changes
Important configuration changes
Sensitive data updates
```

Don't necessarily audit every trivial database read.

# 20. Timestamps

Most important tables benefit from timestamps.

Example:

```
from datetime import datetime

class Product(db.Model):
    id = db.Column(db.Integer, primary_key=True)

    name = db.Column(
        db.String(100),
        nullable=False
    )

    created_at = db.Column(
        db.DateTime,
        default=datetime.utcnow
    )

    updated_at = db.Column(
        db.DateTime,
        default=datetime.utcnow,
        onupdate=datetime.utcnow
    )
```

Conceptually:

```
created_at
    ↓
When record was created

updated_at
    ↓
When record was last modified
```

For modern applications, timezone-aware timestamps are preferable.

# 21. Database Constraints

Application validation is useful.

But important rules should also be enforced by the database.

Example:

```
email = db.Column(
    db.String(120),
    unique=True,
    nullable=False
)
```

This gives database-level protection against duplicate emails.

Useful constraints include:

```
PRIMARY KEY
FOREIGN KEY
UNIQUE
NOT NULL
CHECK
```

---

# 22. Why Database Constraints Matter

Imagine two requests arrive simultaneously:

```
Request A → check email → available
Request B → check email → available
```

Both might try:

```
INSERT email
```

Application-level checking alone may not be enough.

A database `UNIQUE` constraint provides the final protection.

```
Application validation
       +
Database constraint
       ↓
Stronger data integrity
```

---

# 23. N+1 Query Problem

This is one of the most important advanced database concepts.

Suppose we have:

```
100 users
```

and each user has orders.

You run:

```
users = User.query.all()

for user in users:
    print(user.orders)
```

Depending on relationship loading, this can result in:

```
1 query → get users

100 queries → get orders for each user

Total = 101 queries
```

This is called the **N+1 query problem**.

---

# 24. Why N+1 Is Bad

Imagine:

```
10 users
→ 11 queries

100 users
→ 101 queries

10,000 users
→ 10,001 queries
```

Database traffic can explode.

The application may become slow even though the Python code looks simple.

---

# 25. Eager Loading

SQLAlchemy provides loading strategies to fetch related data efficiently.

For example:

```
from sqlalchemy.orm import joinedload

users = (
    User.query
    .options(joinedload(User.orders))
    .all()
)
```

The idea is:

```
Instead of:

Users
 ↓
Query orders
 ↓
Query orders
 ↓
Query orders
 ↓
...

Use:

Users + related data
        ↓
Efficient database loading
```

Other loading strategies include:

```
lazy loading
joined loading
select-in loading
```

---

# 26. `joinedload` vs `selectinload`

High-level distinction:

### `joinedload`

Uses a SQL join-style strategy.

```
joinedload(User.orders)
```

Useful when joining related data is efficient.

### `selectinload`

Typically loads the parent records and then fetches related records using an `IN` query.

```
from sqlalchemy.orm import selectinload

users = (
    User.query
    .options(selectinload(User.orders))
    .all()
)
```

For collections, `selectinload` is often a very useful strategy.

Don't choose blindly. Check query behavior and dataset size.

---

# 27. Pagination

Never blindly return thousands or millions of records.

Bad:

```
users = User.query.all()
```

for a huge table.

Instead:

```
page = request.args.get("page", 1, type=int)
per_page = 20

users = (
    User.query
    .paginate(
        page=page,
        per_page=per_page,
        error_out=False
    )
)
```

Conceptually:

```
Database
   ↓
Page 1 → 20 records
Page 2 → 20 records
Page 3 → 20 records
```

---

# 28. Pagination Metadata

An API can return:

```
{
    "data": [],
    "pagination": {
        "page": 1,
        "per_page": 20,
        "total": 150,
        "pages": 8
    }
}
```

This allows the frontend to build:

```
Previous
1 2 3 4 5
Next
```

# 29. Indexing

Indexes improve lookup performance.

Example:

```
email = db.Column(
    db.String(120),
    unique=True,
    index=True
)
```

Or:

```
name = db.Column(
    db.String(100),
    index=True
)
```

Conceptually:

```
Without index
Database
 ↓
Check many rows
 ↓
Find record

With index
Database
 ↓
Index
 ↓
Find location quickly
```

---

# 30. Don't Index Everything

Indexes consume:

- storage
- memory
- write/update resources

If you create unnecessary indexes:

```
Too many indexes
      ↓
INSERT/UPDATE becomes more expensive
```

Index columns that are frequently used for:

- filtering
- searching
- joins
- sorting

based on actual workload.

---

# 31. Composite Indexes

Sometimes queries use multiple columns.

For example:

```
__table_args__ = (
    db.Index(
        "idx_user_status",
        "user_id",
        "status"
    ),
)
```

Useful for queries such as:

```
WHERE user_id = 10
AND status = 'active'
```

Index design should match common query patterns.

# 32. Query Optimization

Suppose you need only two columns:

```
id
name
```

but retrieve:

```
id
name
email
address
phone
created_at
updated_at
...
```

Unnecessary data can increase overhead.

SQLAlchemy can select specific columns.

Conceptually:

```
users = db.session.query(
    User.id,
    User.name
).all()
```

The principle is:

> Retrieve only what you actually need.

# 33. Database Transactions + Services

A service operation can define the transaction boundary.

Example:

```
class OrderService:

    @staticmethod
    def create_order(customer_id, product_id, quantity):

        try:
            product = ProductRepository.get_by_id(product_id)

            if product is None:
                raise ValueError("Product not found")

            if product.stock < quantity:
                raise ValueError("Not enough stock")

            order = Order(
                customer_id=customer_id,
                total=product.price * quantity
            )

            product.stock -= quantity

            db.session.add(order)
            db.session.commit()

            return order

        except Exception:
            db.session.rollback()
            raise
```

The service controls the business operation.

---

# 34. Optimistic Locking

Consider two administrators editing the same product.

```
Admin A reads price = 500
Admin B reads price = 500

Admin A changes → 550
Admin B changes → 600
```

Admin B may accidentally overwrite Admin A's change.

**Optimistic locking** helps detect this.

A version field can be used:

```
version = db.Column(
    db.Integer,
    nullable=False,
    default=1
)
```

Conceptually:

```
Record version = 1

Admin A reads version 1
Admin B reads version 1

Admin A updates
version → 2

Admin B tries update using version 1
       ↓
Conflict detected
```

This is useful when concurrent updates are possible.

---

# 35. Pessimistic Locking

Another approach is **pessimistic locking**.

The application tells the database:

> "I am working with this row. Prevent conflicting changes while my transaction is running."

Conceptually:

```
Transaction A
     ↓
Lock row
     ↓
Update row
     ↓
Commit
     ↓
Release lock
```

SQLAlchemy supports database locking patterns such as:

```
query = (
    db.session.query(Product)
    .with_for_update()
    .filter_by(id=product_id)
)
```

Exact behavior depends on the database and transaction isolation.

---

# 36. Optimistic vs Pessimistic Locking

||Optimistic|Pessimistic|
|---|---|---|
|Assumption|Conflicts are uncommon|Conflicts may happen|
|Lock|Usually no lock|Locks resource|
|Conflict|Detect later|Prevent during transaction|
|Performance|Often lighter|Can be heavier|
|Use case|Collaborative editing|Critical concurrent updates|

---

# 37. Connection Pooling

We studied connection pooling earlier, but it is also an important database architecture pattern.

Instead of:

```
Request
 ↓
Create DB connection
 ↓
Query
 ↓
Close connection
```

every time, a pool maintains reusable connections.

```
            Connection Pool
          /       |       \
      Conn 1    Conn 2    Conn 3
          \       |       /
                 Flask
```

Benefits:

- reduced connection overhead
- better performance
- controlled database connections
- better concurrency

# 38. Read/Write Separation

Large applications sometimes separate:

```
Writes
  ↓
Primary Database
```

and:

```
Reads
  ↓
Read Replicas
```

Conceptually:

```
                 Flask
                   │
          ┌────────┴────────┐
          ▼                 ▼
       WRITE              READ
          ↓                 ↓
       Primary         Read Replica
```

This is useful at larger scale.

For a normal college project or small application, you usually don't need this complexity.

# 39. Database Migrations

Schema changes should be tracked.

Example:

Initial:

```
users
id
name
email
```

Later:

```
users
id
name
email
phone
```

Instead of manually modifying production databases, use migrations.

With Flask-Migrate:

```

```

# 40. Database Transactions and External Services

Be careful when combining database transactions with external APIs.

Example:

```
Database update
      ↓
Payment API
      ↓
Email API
```

Suppose:

```
Database → SUCCESS
Payment → SUCCESS
Email → FAILURE
```

You cannot simply rollback the external payment using:

```
db.session.rollback()
```

because database rollback doesn't undo external actions.

This is where concepts such as:

- background tasks
- retry mechanisms
- idempotency
- transactional outbox

become important.

---

# 41. Transactional Outbox Pattern

This is a more advanced pattern.

Suppose an order is created and you need to send an event/email.

Instead of:

```
Create order
 ↓
Call external service
```

you can:

```
Create order
     +
Create outbox event
     ↓
COMMIT
     ↓
Background worker
     ↓
Process outbox event
     ↓
External service
```

Example:

```
orders
outbox_events
```

Both database records are committed together.

Then a worker processes:

```
outbox_events
```

This reduces the chance of losing important events when external services fail.

---

# 42. Idempotency

An operation is **idempotent** if repeating it produces the same intended final result.

This is particularly important for APIs and payments.

Imagine:

```
POST /payment
```

The network fails after the server processes the payment.

The client retries.

Without protection:

```
Payment 1 → ₹100
Payment 2 → ₹100
```

The customer gets charged twice.

With an idempotency key:

```
Request
Idempotency-Key: abc123
```

The server remembers:

```
abc123 → already processed
```

and doesn't process the same operation twice.

---

# 43. Database Connection Lifecycle

A database operation should have a controlled lifecycle:

```
Request
   ↓
Acquire connection/session
   ↓
Execute queries
   ↓
Commit or rollback
   ↓
Release resources
```

SQLAlchemy's session system helps manage this.

Don't leave database transactions open unnecessarily.

Long transactions can cause:

- locks
- contention
- resource usage
- performance problems

---

# 44. Avoid Database Calls in Loops

Potentially problematic:

```
for user_id in user_ids:
    user = User.query.get(user_id)
```

This may generate many queries.

Prefer bulk/query-based operations where appropriate.

Conceptually:

```
❌ 100 IDs → 100 queries

✅ 100 IDs → one suitable query
```

For example:

```
users = User.query.filter(
    User.id.in_(user_ids)
).all()
```

---

# 45. Bulk Operations

SQLAlchemy supports bulk-style database operations.

For example, instead of:

```
for product in products:
    product.active = False
```

you may perform a suitable bulk update:

```
Product.query.update(
    {"active": False},
    synchronize_session=False
)

db.session.commit()
```

Bulk operations can be faster, but be careful:

- ORM events may behave differently
- in-memory objects may become stale
- business logic may be bypassed

Use them when appropriate, not automatically.

---

# 46. Database Constraints + Application Validation

Use both.

```
Application Validation
        +
Database Constraints
        ↓
Strong Data Integrity
```

Example:

Application:

```
if not email:
    return {"error": "Email required"}, 400
```

Database:

```
email = db.Column(
    db.String(120),
    nullable=False,
    unique=True
)
```

The application provides a friendly error.

The database provides the final integrity guarantee.

---

# 47. Normalization

Database normalization reduces unnecessary duplication.

Bad design:

```
orders
--------------------------------
order_id
customer_name
customer_email
product_name
product_price
```

The same customer information may be duplicated across many orders.

Better:

```
customers
products
orders
order_items
```

Relationships:

```
Customer
   ↓
Orders
   ↓
Order Items
   ↓
Products
```

---

# 48. Denormalization

Sometimes duplication is intentionally introduced for performance.

For example:

```
orders
----------------
customer_id
customer_name_snapshot
```

Why?

Because historical records may need to preserve information as it was at the time of the order.

For example, if a customer changes their name later, an old invoice might still need the original billing name.

So:

```
Normalization
    ↓
Reduce duplication

Denormalization
    ↓
Intentional duplication for specific reasons
```

---

# 49. Database Pattern Selection

Don't use every pattern in every application.

A practical guide:

|Problem|Possible Pattern|
|---|---|
|Huge route functions|Service Layer|
|SQL scattered everywhere|Repository|
|Multiple related DB changes|Transaction / Unit of Work|
|Need deletion recovery|Soft Delete|
|Need change history|Audit Trail|
|Too many queries|Eager Loading|
|Huge result sets|Pagination|
|Slow searches|Indexing|
|Concurrent edits|Optimistic Locking|
|Critical row conflicts|Pessimistic Locking|
|Duplicate API operations|Idempotency|
|External event reliability|Transactional Outbox|
|Very large read workload|Read Replicas|

# 51. Complete Example Architecture

Let's combine the concepts.

### Repository

```
class ProductRepository:

    @staticmethod
    def get_by_id(product_id):
        return db.session.get(Product, product_id)

    @staticmethod
    def save(product):
        db.session.add(product)
```

### Service

```
class ProductService:

    @staticmethod
    def update_price(product_id, new_price):

        product = ProductRepository.get_by_id(product_id)

        if product is None:
            raise ValueError("Product not found")

        if new_price <= 0:
            raise ValueError("Price must be positive")

        old_price = product.price

        product.price = new_price

        audit = AuditLog(
            action="price_updated",
            entity_type="product",
            entity_id=product.id
        )

        db.session.add(audit)

        try:
            db.session.commit()
        except Exception:
            db.session.rollback()
            raise

        return product
```

### Route

```
@app.patch("/products/<int:product_id>")
def update_product(product_id):

    data = request.get_json()

    try:
        product = ProductService.update_price(
            product_id,
            data["price"]
        )

        return {
            "id": product.id,
            "price": product.price
        }

    except ValueError as error:
        return {
            "error": str(error)
        }, 400
```

Notice what happened:

```
Route
 ↓
Receives HTTP input

Service
 ↓
Applies business rules
 ↓
Starts/controls database operation
 ↓
Creates audit record

Repository
 ↓
Finds database object

SQLAlchemy
 ↓
Database
```

This is much easier to maintain than putting everything into the route.

# 53. Golden Rules 🗄️

Remember these:

1. **Keep database logic organized.**
2. **Use a service layer for business logic when the application becomes complex.**
3. **Use repositories when separating database access genuinely helps.**
4. **Use transactions for related changes that must succeed or fail together.**
5. **Use database constraints, not only Python validation.**
6. **Watch for N+1 queries.**
7. **Use eager loading when appropriate.**
8. **Paginate large datasets.**
9. **Add indexes based on real query patterns.**
10. **Don't retrieve data you don't need.**
11. **Use soft deletes only when they provide a real benefit.**
12. **Keep audit records for important operations when required.**
13. **Think about concurrent updates.**
14. **Use idempotency for operations that must not happen twice.**
15. **Don't over-engineer small applications.**
