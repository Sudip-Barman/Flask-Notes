# 1. What Are Best Practices?

A best practice is a recommended way of designing or implementing something that generally leads to better:

- maintainability
- security
- readability
- reliability
- performance
- scalability
- testability

For example, this works:

```
@app.route("/users")
def users():
    # 300 lines of code
    ...
```

But this is usually better:

```
Route
  ↓
Service
  ↓
Repository
  ↓
Database
```

The second approach separates responsibilities.

# 2. Keep Routes Thin

One of the most important Flask practices is:

> **Routes should handle HTTP concerns, not contain the entire business logic.**

### ❌ Bad

```
@app.post("/orders")
def create_order():
    data = request.get_json()

    if not data.get("product_id"):
        return {"error": "Product required"}, 400

    product = Product.query.get(data["product_id"])

    if not product:
        return {"error": "Product not found"}, 404

    if product.stock <= 0:
        return {"error": "Out of stock"}, 400

    order = Order(
        product_id=product.id,
        quantity=data["quantity"]
    )

    db.session.add(order)
    db.session.commit()

    return {"message": "Order created"}, 201
```

It works, but the route is doing too much.

### Better

```
@app.post("/orders")
def create_order():
    data = request.get_json()

    order = order_service.create_order(data)

    return {
        "message": "Order created",
        "order_id": order.id
    }, 201
```

Business logic:

```
def create_order(data):
    product = find_product(data["product_id"])

    validate_stock(product)

    order = create_order_record(product, data)

    db.session.commit()

    return order
```

The route becomes easier to understand.

# 5. Use Blueprints

Instead of placing every route in one file:

```
@app.get("/users")
@app.get("/products")
@app.get("/orders")
@app.get("/login")
@app.get("/reports")
```

organize routes:

```
routes/
├── auth.py
├── users.py
├── products.py
└── orders.py
```

Each module can expose a Blueprint.

```
users_bp = Blueprint(
    "users",
    __name__,
    url_prefix="/users"
)
```

Then register it:

```
app.register_blueprint(users_bp)
```

# 6. Use the Application Factory

For larger Flask applications:

```
def create_app():
    app = Flask(__name__)

    configure_app(app)
    initialize_extensions(app)
    register_blueprints(app)

    return app
```

Benefits:

- easier testing
- cleaner configuration
- fewer circular imports
- multiple app instances
- better deployment flexibility

You already learned this in **11.1**.

```

    database_url = "mysql://root:password@localhost/app"

```


# 12. Use Correct HTTP Status Codes

Don't return:

```
return {"error": "Not found"}, 200
```

Use:

```
return {"error": "User not found"}, 404
```

Useful codes:

|Code|Meaning|
|---|---|
|200|Successful request|
|201|Resource created|
|204|Successful, no content|
|400|Bad request|
|401|Authentication required/failed|
|403|Permission denied|
|404|Resource not found|
|409|Conflict|
|422|Validation error|
|429|Too many requests|
|500|Server error|
|503|Service unavailable|

Correct status codes make APIs easier to use.

---

# 13. Use Consistent API Responses

Don't make every endpoint return a completely different structure.

For example:

```
{
    "success": true,
    "data": {
        "id": 10,
        "name": "Rahul"
    },
    "message": "User retrieved successfully"
}
```

Errors:

```
{
    "success": false,
    "error": {
        "code": "USER_NOT_FOUND",
        "message": "User not found"
    }
}
```

Consistency makes frontend development much easier.

---

# 14. Centralize Error Handling

Instead of repeating error responses everywhere:

```
return {"error": "Something went wrong"}, 500
```

you can create centralized handlers.

Example:

```
@app.errorhandler(404)
def not_found(error):
    return {
        "success": False,
        "error": {
            "code": "NOT_FOUND",
            "message": "Resource not found"
        }
    }, 404
```

This produces predictable errors.

---

# 15. Never Expose Internal Errors

Bad production response:

```
Traceback...
SQLAlchemy error...
Database password...
Internal file path...
```

Better:

```
{
    "success": false,
    "error": {
        "code": "INTERNAL_ERROR",
        "message": "An unexpected error occurred"
    }
}
```

Meanwhile, detailed information goes into logs.

```
User → Safe response
Developer → Detailed logs
```

# 16. Use Parameterized Queries

Never construct SQL using string concatenation.

### ❌ Bad

```
query = f"SELECT * FROM users WHERE name = '{name}'"
```

This can create SQL injection vulnerabilities.

### Better

With SQLAlchemy ORM:

```
user = User.query.filter_by(name=name).first()
```

Or parameterized raw SQL:

```
from sqlalchemy import text

query = text(
    "SELECT * FROM users WHERE name = :name"
)

db.session.execute(
    query,
    {"name": name}
)
```

Never trust user input.

---

# 17. Use Transactions Properly

When multiple database operations belong together:

```
try:
    create_order()
    update_inventory()
    create_payment_record()

    db.session.commit()

except Exception:
    db.session.rollback()
    raise
```

The goal:

```
Everything succeeds
       ↓
COMMIT

Something fails
       ↓
ROLLBACK
```

This prevents partially completed operations.

---

# 18. Don't Put External APIs Inside Unprotected Transactions

Suppose:

```
Database update
       ↓
External API
       ↓
External API fails
```

Your database transaction cannot automatically undo something that happened outside the database.

For more complex systems, patterns such as the **Transactional Outbox** can help:

```
DB transaction
   ↓
Business record + Outbox event
   ↓
COMMIT
   ↓
Background worker
   ↓
External API
```

You learned this pattern in **11.13**.

---

# 19. Avoid N+1 Queries

Imagine:

```
users = User.query.all()

for user in users:
    print(user.orders)
```

Depending on relationship loading, this can result in:

```
1 query for users
+
1 query per user
```

For 1,000 users:

```
1 + 1,000 = 1,001 queries
```

This is the **N+1 problem**.

Use appropriate eager loading:

```
from sqlalchemy.orm import selectinload

users = (
    User.query
    .options(selectinload(User.orders))
    .all()
)
```

Always understand what SQL your ORM code produces.

---

# 20. Don't Query More Data Than Needed

Avoid retrieving huge datasets when you only need a few fields.

Instead of:

```
users = User.query.all()
```

when you only need names, select the required columns.

Concept:

```
Need 2 columns
     ↓
Don't retrieve 30 columns
```

This can reduce:

- database work
- memory usage
- network transfer
- serialization time

---

# 21. Use Pagination

Never return thousands of records unnecessarily.

Bad:

```
GET /users
 ↓
500,000 users
 ↓
Huge response
```

Better:

```
GET /users?page=1&limit=20
```

Response:

```
{
    "data": [],
    "pagination": {
        "page": 1,
        "limit": 20,
        "total": 500000
    }
}
```

Also enforce a maximum page size.

For example:

```
limit <= 100
```

# 22. Add Database Indexes Carefully

Indexes improve lookup performance.

Example:

```
email = db.Column(
    db.String(120),
    unique=True,
    index=True
)
```

But don't index every column.

Indexes consume:

```
Storage
Write/update overhead
Maintenance cost
```

Index fields that are frequently used for:

```
Search
Filtering
Joining
Sorting
Uniqueness
```

# 23. Use Database Constraints

Application validation is useful, but the database should also protect its own integrity.

For example:

```
email = db.Column(
    db.String(120),
    unique=True,
    nullable=False
)
```

Possible constraints:

```
PRIMARY KEY
FOREIGN KEY
UNIQUE
NOT NULL
CHECK
```

Think:

```
Application validation
        +
Database constraints
        ↓
Stronger data integrity
```

# 24. Use Secure Authentication

Authentication should include:

```
Password hashing
Secure sessions/tokens
Expiration
Logout
Rate limiting
Account protection
```

Never store:

```
password = "mypassword"
```

# 25. Authorization Must Be Server-Side

Don't rely on frontend restrictions.

For example, hiding:

```
Delete User
```

from a normal user does not provide security.

A malicious user can directly send:

```
DELETE /users/10
```

The backend must check:

```
Is authenticated?
      ↓
Has permission?
      ↓
Can access this resource?
      ↓
Perform operation
```

# 26. Protect Against IDOR / BOLA

Suppose:

```
GET /users/25
```

A logged-in user shouldn't automatically be allowed to access every user's data.

Check ownership or permissions:

```
if current_user.id != requested_user.id:
    return {"error": "Forbidden"}, 403
```

This is an example of **object-level authorization**.

# 27. Use CSRF Protection When Appropriate

If authentication relies on cookies, state-changing requests can require CSRF protection.

Typical methods include:

```
CSRF token
SameSite cookies
Origin/Referer validation where appropriate
```

For example:

```
POST
PUT
PATCH
DELETE
```

should be considered carefully when using cookie-based authentication.

# 28. Configure Secure Cookies

For cookie-based authentication:

```
SESSION_COOKIE_SECURE = True
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = "Lax"
```

Meaning:

```
Secure
 ↓
HTTPS only

HttpOnly
 ↓
JavaScript cannot directly read cookie

SameSite
 ↓
Helps reduce cross-site request risks
```

Configuration should match your application's architecture.

# 29. Use HTTPS

Production applications should use:

```
https://
```

rather than:

```
http://
```

HTTPS protects data in transit.

Especially important for:


# 30. Configure CORS Carefully

Avoid blindly allowing every origin:

```
CORS(app, origins="*")
```

when your application requires restricted cross-origin access.

Instead, specify trusted origins where appropriate:

```
CORS(
    app,
    origins=[
        "https://example.com"
    ]
)
```

Remember:

> CORS controls browser cross-origin behavior. It is **not an authentication mechanism**.

# 41. Keep Functions Small and Focused

Bad:

```
def process_everything():
    # 500 lines
    ...
```

Better:

```
def validate_order():
    ...

    ...

    ...

    ...
```

# 42. Use Meaningful Names

Bad:

```
def x(a, b):
    ...
```

Better:

```
def calculate_order_total(price, quantity):
    ...
```

# 43. Don't Overuse Comments

Comments should explain **why**, not simply repeat **what**.

Bad:

```
# Add 1 to count
count += 1
```

Useful:

```
# Retry because the external service occasionally returns temporary failures.
retry_count += 1
```

The code explains what happens.

The comment explains why.

---

# 44. Keep Business Logic Testable

A service like:

```
def calculate_order_total(items):
    ...
```

is easier to test than logic buried inside:

```
@app.post("/orders")
def create_order():
    ...
```

This is another reason to separate routes and services.

# 45. Avoid Circular Imports

```

 ↓
services.py
 ↓

 ↓

```

```
  ↓

  ↓

  ↓
```

```
       ↓
```

# 47. Use `g` Correctly

Flask's:

```
g
```

is useful for temporary context-local data.

For example:

```
g.current_user = user
```

But don't treat `g` as permanent storage.

It disappears when the application context ends.

Remember:

```
g
 ↓
Temporary context data
```

not:

```
g
 ↓
Database
```

# 48. Avoid Global Mutable State

Be careful with:

```
users = []
```

as application-wide state.

With multiple workers:

```
Worker 1 → users list A
Worker 2 → users list B
```

They are not necessarily synchronized.

Use appropriate shared storage:

```
Database
Redis
Object storage
```

when state must be shared.

# 49. Cache Carefully

Caching improves performance:

```
Request
 ↓
Cache
 ↓
Hit → Return
```

But stale data can become a problem.

Always consider:

```
What is the cache key?
How long should it live?
When should it be invalidated?
Is the data user-specific?
```

Never blindly cache sensitive personalized responses.

# 50. Use Background Tasks for Long Work

Don't make users wait for expensive operations.

Bad:

```
Request
 ↓
Generate huge report
 ↓
Send email
 ↓
Process images
 ↓
Response after 60 seconds
```

Better:

```
Request
 ↓
Create background task
 ↓
Return quickly
 ↓

```

You learned this in **11.9**.

# 51. Make Background Jobs Idempotent

Suppose a job is retried:

```
Job
 ↓
Fails
 ↓
Retry
```

If it creates the same record twice, that's a problem.

Design jobs so repeated execution doesn't create unintended duplicate effects.

Example concept:

```
Payment request ID = 123

First execution → Process
Retry           → Detect 123 already processed
                  ↓
                Don't duplicate
```

---

# 52. Use Timeouts for External Services

Never assume an external API will respond instantly.

Bad:

```
response = external_api.request()
```

with no sensible timeout.

Better conceptually:

```
response = external_api.request(
    timeout=10
)
```

External services can:

```
Become slow
Become unavailable
Return errors
Hang
```

Your application should fail gracefully.

---

# 53. Retry Carefully

Retries are useful for temporary failures.

Example:

```
Request
 ↓
Temporary failure
 ↓
Retry
 ↓
Success
```

But don't retry forever.

Use:

```
Maximum retries
Backoff
Timeouts
Idempotency
```

A common strategy is **exponential backoff**:

```
1 sec
 ↓
2 sec
 ↓
4 sec
 ↓
8 sec
```

```

     ↓
```

# 60. Use Database Migrations

```

     ↓

     ↓

     ↓
```

# 63. Keep Production Debugging Safe

When production fails:


# 65. Keep Performance Optimization Evidence-Based

Don't optimize everything just because it _looks_ slow.

# 67. Prefer KISS

**KISS = Keep It Simple, Stupid**

The idea:

> Prefer the simplest design that correctly solves the problem.

For example:

```
Small application
     ↓
Simple architecture
```

rather than:

```
Small application
     ↓
17 services
 ↓
8 queues
 ↓
4 databases
 ↓
Kubernetes
 ↓
Nobody knows why 😵
```

---

# 68. Follow DRY Carefully

**DRY = Don't Repeat Yourself**

If the same logic appears repeatedly:

```
validate_email(...)
```

you can centralize it.

But don't create abstractions merely because two lines look similar.

Good DRY:

```
Repeated business logic
       ↓
Reusable function/service
```

Bad DRY:

```
Two similar lines
       ↓
Create giant abstraction framework
```

Again, balance matters.

---

# 69. Use High Cohesion and Low Coupling

### High cohesion

A module should have closely related responsibilities.

```
auth/
 ↓
Authentication-related functionality
```

### Low coupling

Modules shouldn't depend heavily on unrelated modules.

Ideal:

```
Auth ──────→ User
Orders ────→ Product
Reports ───→ Services
```

rather than everything importing everything.

---

# 70. Use Single Responsibility

A module/class/function should have a clear responsibility.

For example:

```
UserService
 ↓
User-related business logic
```

Not:

```
UserService
 ↓
Users
 ↓
Emails
 ↓
PDFs
 ↓
Payments
 ↓
Database backups
```

That becomes a "god object".

# 75. Final Interview Revision 🎯

### What are Flask best practices?

> Flask best practices are design and development practices that improve an application's maintainability, security, reliability, performance, scalability, and testability.

### Why should routes be thin?

> Thin routes keep HTTP handling separate from business logic, making the application easier to test and maintain.

### Why use a service layer?

> A service layer centralizes business logic and prevents routes from becoming unnecessarily complex.

### Why use application factories?

> Application factories improve configuration, testing, modularity, and application initialization.

### Why use Blueprints?

> Blueprints organize related routes and functionality into modular components.

### Why use environment variables?

> They separate configuration and secrets from application source code.

### Why use database constraints?

> They provide a final database-level guarantee of data integrity.

### Why use pagination?

> Pagination prevents APIs from loading and returning unnecessarily large datasets.

### Why are tests important?

> Tests verify application behavior and help prevent regressions when code changes.

### Why is monitoring needed?

> Monitoring helps detect availability, performance, resource, and operational problems in production.

### Why should applications not run with DEBUG enabled in production?

> Debug mode can expose sensitive internal application information and is not appropriate for production operation.

### What does "don't overengineer" mean?

> Use the simplest architecture that properly solves the current problem, and introduce additional complexity only when it provides real value.

### ⭐ The most important lesson from Module 11

> **A good Flask application is not just one that works. It should be structured so that another developer can understand it, tests can verify it, security controls can protect it, failures can be diagnosed, and the application can safely evolve over time.**
