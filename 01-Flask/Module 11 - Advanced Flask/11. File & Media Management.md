
File handling is a common requirement in Flask applications.

Users may need to upload:

- Profile pictures
- Documents
- PDFs
- Images
- CSV files
- Videos
- Audio
- Attachments

A Flask application therefore needs a proper strategy for **uploading, validating, storing, serving, and deleting files**.

The basic architecture is:

```
Client
   ↓
Upload File
   ↓
Flask
   ↓
Validate File
   ↓
Generate Safe Filename
   ↓
Store File
   ↓
Save File Metadata
   ↓
Database
```

---

# 1. What Is File Management?

**File management** is the process of handling files within an application.

It includes:

```
Upload
Validation
Storage
Retrieval
Serving
Renaming
Deleting
Security
Access control
```

**Media management** is similar, but usually focuses on media files such as:

```
Images
Videos
Audio
Documents
```

---

# 2. Why File Management Needs Special Attention

Uploading a file sounds simple:

```
file = request.files["file"]
file.save(...)
```

But real applications have many questions:

```
Is a file actually provided?
Is the file type allowed?
Is the filename safe?
Is the file too large?
Where should it be stored?
Can another user access it?
Can the file overwrite another file?
Could the file contain malicious content?
How should it be deleted?
```

So file uploads are both a **functionality problem** and a **security problem**.

# 3. Basic Flask File Upload

Flask provides uploaded files through:

```
request.files
```

Example HTML:

```
<form method="POST" enctype="multipart/form-data">
    <input type="file" name="document">
    <button type="submit">Upload</button>
```

The important part is:

```
enctype="multipart/form-data"
```

# 4. Receiving the File

In Flask:

```
from flask import request

@app.post("/upload")
def upload():
    file = request.files.get("document")

    if not file:
        return {"error": "No file provided"}, 400

    return {"message": "File received"}
```

The uploaded object is usually a Werkzeug `FileStorage` object.

# 7. Never Trust the Filename

Suppose a user uploads:

```
profile.jpg
```

That seems harmless.

But a malicious filename might contain path components such as:

```
../../something
```

You should never blindly use a user-provided filename as a filesystem path.

Flask/Werkzeug provides:

```
from werkzeug.utils import secure_filename
```

Then:

```
filename = secure_filename(file.filename)
```

Example:

```
original = file.filename
safe_name = secure_filename(original)
```

The purpose is to turn an unsafe filename into a safer filesystem filename.

---

# 8. `secure_filename()`

Example:

```
from werkzeug.utils import secure_filename

filename = secure_filename("../../my file.jpg")

print(filename)
```

The result will be normalized into a safer filename rather than preserving the dangerous path structure.

The important principle is:

> **Never directly trust `file.filename`.**

---

# 9. File Extension Validation

Suppose your application only accepts:

```
.jpg
.jpeg
.png
.pdf
```

You can check the extension.

```
ALLOWED_EXTENSIONS = {
    "jpg",
    "jpeg",
    "png",
    "pdf"
}
```

Helper:

```
def allowed_file(filename):
    return (
        "." in filename
        and filename.rsplit(".", 1)[1].lower()
        in ALLOWED_EXTENSIONS
    )
```

Then:

```
if not allowed_file(file.filename):
    return {"error": "File type not allowed"}, 400
```

---

# 10. Why Extension Checking Isn't Enough

This is important for security.

A file could be named:

```
photo.jpg
```

but its actual content may not be a valid JPEG.

Therefore:

```
Filename extension
        ≠
Actual file content
```

For security-sensitive applications, validate the actual file type/content as well.

For images, libraries such as Pillow can help inspect image content.

For documents and other file types, appropriate parsers or MIME/content validation may be needed.

---

# 11. MIME Type

A file may have a MIME type such as:

```
image/jpeg
image/png
application/pdf
text/csv
```

You may inspect:

```
file.mimetype
```

For example:

```
print(file.mimetype)
```

But don't blindly trust a client-provided MIME type either.

The client can lie.

For security-sensitive uploads, combine:

```
Extension
+
Declared MIME type
+
Actual file/content validation
```

# 12. File Size Validation

Large files can consume:

- memory
- disk space
- bandwidth
- processing time

Flask lets you configure a request size limit:

```
app.config["MAX_CONTENT_LENGTH"] = 16 * 1024 * 1024
```

This represents:

```
16 MB
```

Conceptually:

```
Upload
  ↓
Size > limit?
  ├── YES → Reject
  └── NO → Continue
```

---

# 13. Why Upload Limits Matter

Imagine an endpoint allowing unlimited uploads.

An attacker could repeatedly upload:

```
500 MB
500 MB
500 MB
500 MB
...
```

Your server's storage could disappear quickly.

So file size limits are an important security and resource-management measure.

# 14. Unique Filenames

Suppose two users upload:

```
profile.jpg
```

If you save both as:

```
uploads/profile.jpg
```

the second upload could overwrite the first.

Instead, generate a unique name.

For example:

```
import uuid

extension = filename.rsplit(".", 1)[1]
unique_name = f"{uuid.uuid4()}.{extension}"
```

You could get:

```
a8b2c9d4-....jpg
```

Then:

```
file.save(path)
```

Now filenames don't collide.

---

# 15. UUID-Based Filenames

A common pattern:

```
Original:
profile.jpg

Stored:
8f2d3a1c-....jpg
```

The database can remember:

```
original_name = profile.jpg
stored_name   = 8f2d3a1c-....jpg
```

This gives you both:

- user-friendly original filename
- safe unique storage name

# 16. File Metadata

You generally shouldn't store the actual file inside your database unless there is a specific reason.

Instead, store **metadata**.

For example:

```
files
--------------------------------
id
original_name
stored_name
mime_type
size
path
uploaded_by
created_at
```

Then:

```
Database
   ↓
File metadata
   ↓
Actual file storage
```

# 17. Database + Filesystem Architecture

A common design:

```
                 Flask
                   │
          ┌────────┴────────┐
          ↓                 ↓
      Database           File Storage
          │                 │
      Metadata           Actual File
```

For example:

```
Database:

original_name = "resume.pdf"
stored_name = "abc123.pdf"
size = 240KB
user_id = 10
```

Filesystem:

```
uploads/abc123.pdf
```

---

# 18. Why Not Store Everything in the Database?

You technically can store files as binary data using things such as BLOBs.

But for many web applications, storing large files directly in a relational database can create problems:

- database size grows rapidly
- backups become larger
- database operations become heavier
- file delivery can become less convenient

For many applications:

```
Database → metadata
Object/File storage → actual files
```

is a cleaner architecture.

# 22. Public vs Private Files

This is a major architectural decision.

### Public file

Anyone with the URL can access it.

Examples:

```
Public profile images
Website logos
Public product images
```

### Private file

Only authorized users can access it.

Examples:

```
Private documents
Invoices
Personal records
Internal reports
```

Never assume:

> "If someone knows the filename, they should be able to download it."

Private files need authorization.

# 24. Authentication vs Authorization

Remember Module 9.

Authentication:

```
"Who are you?"
```

Authorization:

```
"Are you allowed to access this file?"
```

Example:

```
if file.owner_id != current_user.id:
    return {"error": "Forbidden"}, 403
```

For role-based systems:

```
if not has_permission(user, "files.read"):
    return {"error": "Forbidden"}, 403
```

# 26. Path Traversal

Path traversal is a security problem where an attacker tries to access files outside the intended directory.

For example, conceptually:

```
../../secret.txt
```

The attacker attempts to move upward through directories.

This is why directly constructing paths from user input is dangerous.

Bad:

```
path = os.path.join("uploads", user_input)
```

without appropriate validation.

Use safe filename/path handling and controlled storage identifiers.

---

# 27. Better Download Architecture

Instead of exposing arbitrary filenames:

```
/files/<filename>
```

a safer design can use a database ID:

```
/files/123
```

Then:

```
123
 ↓
Database lookup
 ↓
stored object key
 ↓
authorization check
 ↓
serve/download
```

This keeps storage details behind your application.

---

# 28. File Deletion

When a file is deleted:

```
Delete database record
+
Delete actual file
```

You need to keep both sides consistent.

For example:

```
os.remove(file_path)
db.session.delete(file_record)
db.session.commit()
```

But think carefully about failure order.

Suppose:

```
Delete physical file
        ↓
Database commit fails
```

Now the database still thinks the file exists.

Or:

```
Database deleted
        ↓
Physical file deletion fails
```

Now you have an orphaned file.

For important systems, file deletion often needs a deliberate cleanup/retry strategy.

---

# 29. Orphaned Files

An **orphaned file** is a file that exists in storage but no longer has a valid database record.

Example:

```
Storage:
report123.pdf

Database:
No record
```

Over time, thousands of orphaned files can waste storage.

A cleanup job can periodically detect and remove them.

This connects nicely with the previous topic:

```
Background Task
      ↓
Find orphaned files
      ↓
Delete them
```

# 30. Temporary Files

Some files only need to exist temporarily.

For example:

```

Generate result
  ↓
```

These should be stored in a temporary location rather than permanent storage.

Python provides tools such as:


# 39. File Metadata Model

A simple SQLAlchemy model might look like:

```
class File(db.Model):
    id = db.Column(db.Integer, primary_key=True)

    original_name = db.Column(
        db.String(255),
        nullable=False
    )

    stored_name = db.Column(
        db.String(255),
        unique=True,
        nullable=False
    )

    mime_type = db.Column(
        db.String(100)
    )

    size = db.Column(
        db.Integer
    )

    path = db.Column(
        db.String(500),
        nullable=False
    )

    uploaded_by = db.Column(
        db.Integer,
        db.ForeignKey("users.id"),
        nullable=False
    )
```

This stores metadata rather than the file contents themselves.

# 49. Common Mistakes

### Mistake 1: Trusting `file.filename`

Always sanitize filenames.

---

### Mistake 2: Allowing unlimited file sizes

This can exhaust server resources.

---

### Mistake 3: Checking only the extension

A malicious or invalid file can use a misleading extension.

---

### Mistake 4: Using original filenames as storage names

This can cause collisions and security problems.

---

### Mistake 5: Storing uploads inside executable application directories

This can increase security risk.

---

### Mistake 6: Forgetting authorization on downloads

A file URL isn't permission.

---

### Mistake 7: Storing huge files directly in the database without a reason

Object storage is often a better fit.

---

### Mistake 8: Processing huge files inside the request

Use background processing when appropriate.

---

### Mistake 9: Forgetting orphaned files

Database and storage can become inconsistent.

# 51. A Simple Secure-ish Upload Example

For learning purposes:

```
import os
import uuid

from flask import Flask, request, jsonify
from werkzeug.utils import secure_filename

app = Flask(__name__)

UPLOAD_FOLDER = "uploads"

app.config["UPLOAD_FOLDER"] = UPLOAD_FOLDER
app.config["MAX_CONTENT_LENGTH"] = 16 * 1024 * 1024

ALLOWED_EXTENSIONS = {
    "jpg",
    "jpeg",
    "png",
    "pdf"
}


def allowed_file(filename):
    return (
        "." in filename
        and filename.rsplit(".", 1)[1].lower()
        in ALLOWED_EXTENSIONS
    )


@app.post("/upload")
def upload():
    file = request.files.get("file")

    if file is None or file.filename == "":
        return jsonify({
            "error": "No file selected"
        }), 400

    if not allowed_file(file.filename):
        return jsonify({
            "error": "File type not allowed"
        }), 400

    original_name = secure_filename(file.filename)

    extension = original_name.rsplit(".", 1)[1].lower()

    stored_name = f"{uuid.uuid4()}.{extension}"

    os.makedirs(
        app.config["UPLOAD_FOLDER"],
        exist_ok=True
    )

    path = os.path.join(
        app.config["UPLOAD_FOLDER"],
        stored_name
    )

    file.save(path)

    return jsonify({
        "message": "File uploaded",
        "filename": stored_name
    })
```

This is a **learning example**, not a complete production-grade upload system. Production applications may need deeper content validation, malware scanning, access control, object storage, logging, quotas, and safer processing depending on the file types involved.

# 52. Why the Example Uses UUID

Imagine:

```
User A → photo.jpg
User B → photo.jpg
```

Without unique names:

```

```

Potential collision.

With UUIDs:

```

uploads/8d9e0f....jpg
```

Much safer for storage organization.

# 53. Don't Expose Internal Paths

Avoid returning:

```
{
    "path": "C:\\server\\project\\uploads\\abc123.pdf"
}
```

This reveals internal filesystem information.

Instead return something like:

```
{
    "file_id": 123,
    "filename": "abc123.pdf"
}
```

or an appropriate application-level download URL.

```
                              Database
                                  │
                                  ↓
                         Background Worker
                              │       │
                              ↓       ↓

                              │       │

```

This is the larger picture.

You don't need all of it for a small Flask project, but understanding the architecture is valuable.

# 56. Three Things to Keep Separate

This is one of the most useful concepts from this topic:

```
                FILE SYSTEM
                     │
              Actual file
                     │
                     ↓
                DATABASE
                     │
                Metadata
                     │
                     ↓
                APPLICATION
                     │
             Access control
```

Don't confuse:

```
File
```

with:

```
File metadata
```

or:

```
File URL
```

They are three different things.

# 57. Quick Revision

### Where are uploaded files found?

```
request.files
```

### What encoding does a file upload form need?

```
enctype="multipart/form-data"
```

### How do you make a filename safer?

```
secure_filename()
```

### Why generate unique filenames?

To prevent collisions and overwrites.

### Why limit file size?

To protect memory, storage, bandwidth, and processing resources.

### Should you trust the file extension?

**No.**

### Should you trust the MIME type blindly?

**No.**

### Where should metadata go?

Usually the **database**.

### Where should large actual files go?

Often **filesystem/object storage**.

### What protects private downloads?

**Authentication + authorization.**

### What is an orphaned file?

A stored file without a valid database record.

### What is path traversal?

An attack attempting to access files outside the intended directory.

### When should file processing move to a background worker?

When processing is expensive or long-running.
