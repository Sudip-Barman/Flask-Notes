
**Contexts and Proxies** are some of the most confusing concepts in Flask at first, but they become much easier once you understand the problem they solve.

You have already used objects like:

```
request
session
current_app
g
```

You may have wondered:

> "Where did Flask get the current request from?"

> "How does `current_app` know which Flask application is running?"

The answer involves **contexts** and **proxies**.

---

# 1. What is a Context?

A **context** is information Flask makes available while a particular operation is being processed.

For example, when Flask handles a request, it needs to know:

```
Which application?
Which request?
Which user/session?
Which request-specific data?
```

Flask creates a context around that operation.

Think of a context as a temporary **working environment**.

```
Request arrives
      ↓
Flask creates context
      ↓
Route executes
      ↓
Route can access request/session/current_app
      ↓
Request finishes
      ↓
Context is removed
```

---

# 2. Why Does Flask Need Contexts?

Imagine your application has:

```
app1 = Flask(__name__)
app2 = Flask(__name__)
```

Which application should this code refer to?

```
current_app
```

And if thousands of requests are being processed, which request should:

```
request
```

refer to?

Flask needs a mechanism to keep track of the **currently active application/request**.

That's where contexts come in.

---

# 3. Two Important Flask Contexts

Flask mainly has two contexts:

```
1. Application Context
2. Request Context
```

They are related, but they are **not the same thing**.

---

# 4. Application Context

The **application context** contains information related to the current Flask application.

It makes objects such as:

```
current_app
g
```

available.

Example:

```
from flask import current_app

print(current_app.name)
```

This only works when an application context is active.

---

# 5. Request Context

The **request context** contains information about the current HTTP request.

It makes objects such as:

```
request
session
```

available.

Example:

```
from flask import request

print(request.method)
```

This works while Flask is processing an HTTP request.

---

# 6. Application Context vs Request Context

|Context|Main Purpose|Common Objects|
|---|---|---|
|Application Context|Current Flask application|`current_app`, `g`|
|Request Context|Current HTTP request|`request`, `session`|

Mental model:

```
Application Context
        │
        ├── current_app
        └── g

Request Context
        │
        ├── request
        └── session
```

A request context is associated with an application context.

---

# 7. The Four Objects You Should Know

These four are especially important:

```
current_app
g
request
session
```

Let's understand each.

---

# 8. `current_app`

`current_app` represents the Flask application that is currently handling the operation.

Example:

```
from flask import current_app

print(current_app.name)
```

You can access configuration:

```
current_app.config["APP_NAME"]
```

You can access extensions indirectly through application-related structures depending on the extension architecture.

---

# 9. Why Not Just Use `app`?

With a simple application, you might write:

```
from flask import Flask

app = Flask(__name__)
```

Then:

```
print(app.config["APP_NAME"])
```

But in a factory-based application, the application is created inside:

```
def create_app():
    app = Flask(__name__)
    return app
```

There may not be one global `app` object that every module should import.

Instead, use:

```
from flask import current_app
```

Then:

```
current_app.config["APP_NAME"]
```

This fits naturally with the Application Factory Pattern.

---

# 10. `current_app` Mental Model

Think:

```
create_app()
     ↓
Flask application
     ↓
Current application context
     ↓
current_app
```

So:

```
current_app
```

basically means:

> "Give me the Flask application currently associated with this context."

---

# 11. `g`

`g` is a Flask object used to store **data during the current application context**.

The name comes from "global", but it is important not to interpret it as a permanent global variable.

Example:

```
from flask import g

g.username = "Alex"
```

Later:

```
print(g.username)
```

The data is available during the current context.

---

# 12. What is `g` Useful For?

Common uses include storing data that multiple functions need during one request.

For example:

```
Request
  ↓
Load current user
  ↓
Store user in g
  ↓
Multiple functions use g.user
```

Example:

```
g.user = user
```

Then another function can access:

```
g.user
```

without querying the database again.

---

# 13. `g` Is Not a Database

This is important.

If you do:

```
g.user = user
```

that does **not** permanently save the user.

When the relevant context ends:

```
g data
   ↓
Context ends
   ↓
Data disappears
```

So don't use `g` as permanent storage.

---

# 14. `g` Is Not a Session

These are different:

### `g`

Temporary server-side context data.

### `session`

Data associated with the user's session.

Example:

```
g.user = user
```

means:

> "Make this user available during the current context."

While:

```
session["user_id"] = user.id
```

means:

> "Remember this user's authenticated session."

---

# 15. `request`

`request` represents the current HTTP request.

Example:

```
from flask import request

print(request.method)
```

Possible values:

```
GET
POST
PUT
PATCH
DELETE
```

You can access:

```
request.args
request.form
request.get_json()
request.files
request.headers
request.cookies
request.path
request.method
```

All of these refer to the **current request**.

---

# 16. `session`

`session` represents the current user's Flask session.

Example:

```
from flask import session

session["user_id"] = 10
```

Then:

```
user_id = session.get("user_id")
```

You already learned sessions in Module 9.

Now you can understand why:

```
session
```

is available inside request handling.

It is connected to the active request context.

---

# 17. The Context Relationship

A simplified model:

```
Flask Application
      ↓
Application Context
      │
      ├── current_app
      └── g
      │
      ↓
Request Context
      │
      ├── request
      └── session
```

This is not meant as an exact implementation diagram, but it is an excellent mental model.

---

# 18. What is a Proxy?

Now comes the second half.

Objects like:

```
current_app
request
session
g
```

are **context-local proxies**.

The word "proxy" means that the object acts as a representative for the actual object associated with the current context.

Think of:

```
request
   ↓
Proxy
   ↓
Find current request
   ↓
Actual request object
```

---

# 19. Why Use Proxies?

Without proxies, you would have to explicitly pass the current application/request everywhere.

For example:

```
def some_function(app, request):
    ...
```

Then:

```
some_function(app, request)
```

and potentially:

```
some_function(app, request, session)
```

This would become cumbersome.

Flask lets you write:

```
def some_function():
    print(request.method)
```

The proxy resolves the appropriate object from the current context.

---

# 20. Simple Proxy Mental Model

Think of:

```
request
```

as a receptionist saying:

> "Give me the request belonging to the current request context."

Similarly:

```
current_app
```

means:

> "Give me the application belonging to the current application context."

The variable looks like an ordinary object, but Flask resolves it dynamically.

---

# 21. Why `request` Works in a Route

Consider:

```
@app.get("/users")
def users():
    print(request.method)
    return "Users"
```

When Flask receives:

```
GET /users
```

Flask creates the appropriate request context.

Then:

```
request.method
```

can resolve to:

```
GET
```

After the request finishes, that request context is removed.

---

# 22. Outside a Request Context

Consider:

```
from flask import request

print(request.method)
```

If no request is active, Flask cannot determine which request you're talking about.

You will get an error similar to:

```
RuntimeError:
Working outside of request context.
```

This is one of the most common Flask errors beginners encounter.

---

# 23. Outside an Application Context

Similarly:

```
from flask import current_app

print(current_app.name)
```

outside an application context can produce:

```
RuntimeError:
Working outside of application context.
```

The problem is not that `current_app` is missing.

The problem is:

> There is no active application context from which Flask can determine the current application.

---

# 24. Why `db.session` Sometimes Gives Context Errors

You may encounter something like:

```
RuntimeError:
Working outside of application context.
```

when using Flask-SQLAlchemy.

For example:

```
User.query.all()
```

outside an appropriate Flask application context.

Why?

Because the Flask-integrated database extension needs to know:

```
Which Flask application?
Which configuration?
Which database connection?
```

The application context provides that association.

---

# 25. `app.app_context()`

If you need to perform application-related work outside a request, Flask allows you to manually create an application context.

Example:

```
with app.app_context():
    print(current_app.name)
```

Now:

```
current_app
```

works inside the block.

---

# 26. Application Context Example

```
from flask import Flask, current_app

app = Flask(__name__)

with app.app_context():
    print(current_app.name)
```

Flow:

```
app
 ↓
app.app_context()
 ↓
Application Context Created
 ↓
current_app works
 ↓
Block ends
 ↓
Context Removed
```

---

# 27. Why Is This Useful?

Application contexts are useful for tasks such as:

- Database operations
- CLI commands
- Background jobs
- Initialization tasks
- Scripts
- Testing
- Accessing configuration outside a request

Example:

```
with app.app_context():
    users = User.query.all()
```

---

# 28. Request Context Manually

You can also create a request context.

```
with app.test_request_context("/users"):
    print(request.path)
```

Now:

```
request.path
```

can work.

Output:

```
/users
```

This is particularly useful in testing and debugging.

---

# 29. Application Context vs Request Context

Let's make this very clear.

### Application Context

Answers:

> "Which Flask application am I working with?"

Provides:

```
current_app
g
```

### Request Context

Answers:

> "Which HTTP request am I currently handling?"

Provides:

```
request
session
```

---

# 30. Does Every Request Have an Application Context?

In normal Flask request handling, yes, Flask pushes an application context associated with the request.

Conceptually:

```
Incoming Request
      ↓
Application Context
      ↓
Request Context
      ↓
Route
      ↓
Response
      ↓
Contexts Removed
```

---

# 31. Context Lifetime

A request context exists only while the request is being processed.

For example:

```
10:00:00
Request arrives
      ↓
Context created
      ↓
Route executes
      ↓
Response generated
      ↓
Context removed
10:00:01
```

Therefore:

```
g.some_value
```

is temporary.

---

# 32. `g` Example With Current User

A common pattern:

```
from flask import g, session

@app.before_request
def load_user():

    user_id = session.get("user_id")

    if user_id:
        g.user = User.query.get(user_id)
    else:
        g.user = None
```

Then routes can use:

```
@app.get("/profile")
def profile():

    if g.user is None:
        return "Login required", 401

    return {
        "name": g.user.name
    }
```

The flow is:

```
Request
  ↓
before_request
  ↓
Find user
  ↓
g.user
  ↓
Route
  ↓
Use g.user
```

---

# 33. Why Use `g` Here?

Without `g`, you might repeatedly write:

```
user_id = session.get("user_id")
user = User.query.get(user_id)
```

in many places.

Instead:

```
before_request
      ↓
Find user once
      ↓
g.user
      ↓
Routes/services can access it
```

This can make request-scoped data easier to share.

Be mindful of query behavior and application architecture. Don't use `g` simply to hide expensive database operations.

---

# 34. `g` and Cleanup

`g` can also be useful for resources that should be cleaned up after the request.

A common conceptual pattern is:

```
@app.teardown_appcontext
def cleanup(exception):
    ...
```

For example, a resource stored in `g` can be closed during teardown.

This pattern is useful for request/app-context-scoped resources.

---

# 35. `teardown_appcontext`

Flask provides:

```
@app.teardown_appcontext
def cleanup(exception):
    ...
```

This runs when the application context is being removed.

Conceptually:

```
Application Context
       ↓
Application Work
       ↓
Cleanup
       ↓
Context Removed
```

---

# 37. Context and Application Factory

Contexts become especially important with the Application Factory Pattern.

Suppose:

```
def create_app():
    app = Flask(__name__)
    return app
```

You don't want every module to import a single global:

```
app
```

Instead, Flask can determine the active application through:

```
current_app
```

This works beautifully with factories.

```
create_app()
    ↓
Flask App
    ↓
Application Context
    ↓
current_app
```

# 38. `current_app` in a Service

Suppose you have:

```
app/
├── routes/
└── services/
```

A service might need a configuration value.

Instead of:

```
def send_report(app):
    api_url = app.config["API_URL"]
```

you can use:

```
from flask import current_app

def send_report():
    api_url = current_app.config["API_URL"]
```

As long as the function executes within an application context.

# 39. Context Errors

These messages are extremely important to recognize.

### Error 1

```
Working outside of application context.
```

Usually means you tried to access:

```
current_app
g
```

or an extension requiring application context without an active application context.

### Error 2

```
Working outside of request context.
```

Usually means you tried to access:

```
request
session
```

without an active request context.

---

# 40. How to Fix Application Context Errors

If you already have an app:

```
with app.app_context():
    ...
```

Example:

```
with app.app_context():
    users = User.query.all()
```

In an application factory:

```
app = create_app()

with app.app_context():
    users = User.query.all()
```

---

# 41. How to Fix Request Context Errors

For testing:

```
with app.test_request_context("/users"):
    print(request.path)
```

This creates a simulated request context.

Don't use this as a way to fake requests in normal application logic. Use proper request handling or the Flask test client when testing endpoints.

---

# 42. Test Client and Contexts

Flask's test client can create the appropriate contexts while making requests.

Example:

```
with app.test_client() as client:
    response = client.get("/users")
```

During that request:

```
request
session
current_app
```

can be available as appropriate.

---

# 43. `with client` and Context Lifetime

You can also use:

```
with app.test_client() as client:
    response = client.get("/")

    # context-related assertions can be made here
```

This is useful in tests where you need to inspect request/session-related state.

# 44. Application Context Stack Concept

Internally, Flask must keep track of active contexts.

A useful conceptual model is a stack:

```
Top
 ↓
Current Context
 ↓
Previous Context
 ↓
Older Context
```

When a context is pushed:

```
Push
 ↓
New context becomes current
```

When removed:

```
Pop
 ↓
Previous context becomes current
```

Modern Flask uses Python's context-local machinery to manage this safely across concurrent execution.

You don't normally need to manipulate the underlying machinery directly.

---

# 45. Why Contexts Are Safe for Concurrent Requests

Imagine:

```
User A → Request A
User B → Request B
User C → Request C
```

Each request needs its own:

```
request
session
g
```

Flask's context-local system ensures each execution context gets the appropriate current objects rather than all requests sharing one ordinary global variable.

Conceptually:

```
Request A → request_A
Request B → request_B
Request C → request_C
```

while your code can simply write:

```
request
```

# 47. Common Flask Proxies

Important Flask context-local objects include:

```
current_app

```

They provide convenient access to context-specific data.

---

# 48. Proxy vs Normal Variable

Normal variable:

```
user = some_user
```

This refers directly to the assigned object.

Context proxy:

```
request
```

does not simply mean one globally stored request object.

It resolves the object associated with the current context.

This distinction is fundamental.

---

# 49. `current_app` Does Not Mean "The App Variable"

This is a subtle but important point.

Don't think:

```
current_app == global app
```

Instead think:

```
current_app
     ↓
"The Flask application associated
 with the currently active context"
```

That distinction becomes especially useful when working with:

- Application factories
- Testing
- Multiple applications
- CLI commands
- Background tasks

---

# 50. Context in CLI Commands

Flask CLI commands can work with an application context.

For example, a command may need:

```
current_app.config
```

or:

```
User.query.all()
```

because the command is associated with the Flask application.

This is one reason Flask's context system is useful beyond HTTP requests.

---

# 51. Context in Background Tasks

Suppose you eventually run a background task:

```
def generate_report():
    current_app.config["REPORT_PATH"]
```

If the task runs outside Flask's application context, this can fail.

You may need:

```
with app.app_context():
    generate_report()
```

This is an important concept when you reach background processing.

---

# 52. Don't Store Long-Lived Data in `g`

Bad idea:

```
g.all_users = User.query.all()
```

and expecting it to remain available tomorrow.

It won't.

`g` is tied to the current context.

Use a proper database, cache, or other persistent storage for long-lived data.

---

# 53. Don't Pass Context Objects Everywhere

You generally don't want functions like:

```
def process_user(app, request, session, g):
    ...
```

everywhere.

Instead, context-aware Flask code can use:

```
current_app
request
session
g
```

when appropriate.

However, don't overuse Flask globals in business logic. Passing explicit values into pure service functions can often make code easier to test and reuse.

---

# 54. Context-Aware vs Context-Independent Code

This is an important architecture distinction.

### Context-aware

```
def get_page_size():
    return current_app.config["PAGE_SIZE"]
```

This requires an application context.

### Context-independent

```
def calculate_total(price, quantity):
    return price * quantity
```

This requires no Flask context.

Generally, keeping core business logic context-independent makes it easier to test.

---

# 55. Good Architecture

A clean architecture might look like:

```
Route
  ↓
Read request
  ↓
Extract data
  ↓
Service
  ↓
Business logic
  ↓
Database
```

For example:

```
@app.post("/orders")
def create_order():
    data = request.get_json()

    return order_service.create_order(data)
```

Here:

```
request
  ↓
Route layer
```

while:

```
order_service
  ↓
Business logic
```

doesn't need to know about the Flask request.

# 56. Common Mistakes

### Mistake 1: Using `request` outside a request

```
print(request.args)
```

in a normal standalone script.

Result:

```
Working outside of request context.
```

---

### Mistake 2: Using `current_app` outside application context

```
print(current_app.config)
```

without an application context.

---

### Mistake 3: Treating `g` as permanent storage

```
g.user = user
```

doesn't permanently store the user.

---

### Mistake 4: Confusing `session` with `g`

```
session → user session state
g       → temporary context data
```

---

### Mistake 5: Passing Flask context into every service

Don't make your entire application dependent on:

```
request
current_app
session
```

when ordinary Python parameters would be cleaner.

# 63. Final Rules to Remember

> **Application Context = current Flask application environment.**

> **Request Context = current HTTP request environment.**

> **`current_app` = current application.**

> **`g` = temporary context-scoped data.**

> **`request` = current HTTP request.**

> **`session` = current user session.**

> **These are context-local proxies, not ordinary global variables.**

> **Context exists for a limited lifetime.**

> **Use `app.app_context()` when application-context-dependent work needs to happen outside a request.**

> **Use `app.test_request_context()` mainly for testing/request simulation.**

> **Keep core business logic as context-independent as practical.**
