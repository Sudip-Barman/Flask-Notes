As Flask applications grow, the biggest problem is often no longer Flask itself. The problem becomes **where to put everything**.

A beginner project may have:

```
app.py
```

But a real application can contain:

```
Routes
Models
Services
Authentication
API
Database
Configuration
Validation
Templates
Static files
Tests
```

If everything is placed in a few files, the project becomes difficult to understand and maintain.

**Modular architecture** solves this by dividing the application into logical components, where each component has a clear responsibility.

---

# 1. What is Project Structure?

**Project structure** means how files and folders are organized inside your application.

For example:

```
project/
│
├── app.py
├── models.py
├── routes.py
├── config.py
└── requirements.txt
```

This is a simple structure.

A larger application might use:

```
project/
│
├── app/
│   ├── __init__.py
│   ├── extensions.py
│   ├── models/
│   ├── routes/
│   ├── services/
│   ├── schemas/
│   └── utils/
│
├── tests/
├── config.py
├── run.py
└── requirements.txt
```

The second structure is more suitable for a growing application.

---

# 2. What is Modular Architecture?

**Modular architecture** means dividing an application into separate modules based on responsibility or feature.

Instead of:

```
One giant file
      ↓
Everything
```

we create:

```
Application
│
├── Authentication
├── Users
├── Products
├── Orders
├── Services
├── Database
└── Configuration
```

Each module handles a particular part of the application.

### Mental model

```
Large Application
       ↓
Break into Modules
       ↓
Each Module has One Responsibility
       ↓
Connect Modules Together
       ↓
Complete Application
```

Think of it like a machine made from replaceable components. If the gearbox needs work, you should not have to dismantle the radio. 🔧

---

# 3. Why Do We Need Modular Architecture?

Without modularization:

```
app.py
 ├── 500 lines
 ├── routes
 ├── database
 ├── authentication
 ├── business logic
 ├── validation
 ├── utilities
 └── everything else
```

Problems:

- Difficult to find code
- Difficult to test
- Difficult to debug
- Difficult for multiple developers
- More chance of circular imports
- Difficult to reuse code
- Difficult to add new features
- Difficult to maintain

With modular architecture:

```
routes/
services/
models/
schemas/
utils/
```

Each area has a clear purpose.

# 7. Understanding Each Folder

## `app/`

This is the main Python package containing the application.

```
app/
```

It contains the application's actual code.

---

## `__init__.py`

Usually contains the application factory.

```
from flask import Flask


def create_app():
    app = Flask(__name__)

    return app
```

As we learned in **11.1**, this is where the application gets assembled.

---

# 8. `extensions.py`

This contains Flask extensions.

For example:

```
from flask_sqlalchemy import SQLAlchemy
from flask_jwt_extended import JWTManager

db = SQLAlchemy()
jwt = JWTManager()
```

Then the factory initializes them:

```
db.init_app(app)
jwt.init_app(app)
```

This prevents extensions from being tightly coupled to a specific application instance.

---

# 9. `models/`

Models represent database entities.

Instead of:

```
models.py
```

containing 30 different models, you can divide them:

```
models/
├── user.py
├── product.py
├── order.py
└── category.py
```

For example:

```
class Product(db.Model):
    __tablename__ = "products"

    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(100), nullable=False)
    price = db.Column(db.Float, nullable=False)
```

The model's job is primarily to represent and interact with persistent data.

---

# 10. `routes/`

Routes contain HTTP endpoint definitions.

Example:

```
routes/
├── auth.py
├── users.py
├── products.py
└── orders.py
```

A Blueprint might live inside `products.py`:

```
from flask import Blueprint

products_bp = Blueprint(
    "products",
    __name__,
    url_prefix="/api/products"
)


@products_bp.get("/")
def get_products():
    return {
        "data": []
    }
```

Routes should generally be responsible for handling the HTTP layer.

---

# 11. `services/`

This is where **business logic** can live.

This is an important architectural concept.

Suppose you have:

```
@products_bp.post("/")
def create_product():
    # 100 lines of validation,
    # pricing,
    # database logic,
    # notifications...
```

That route becomes difficult to maintain.

Instead:

```
@products_bp.post("/")
def create_product():
    data = request.get_json()

    product = create_product_service(data)

    return {
        "data": product
    }, 201
```

And the business logic lives in:

```
def create_product_service(data):
    # validation
    # business rules
    # database operation
    # other logic

    ...
```

The route handles HTTP.

The service handles business logic.

---

# 12. Route vs Service

This distinction is extremely useful.

### Route

```
HTTP Request
     ↓
Route
     ↓
Read request
     ↓
Call service
     ↓
Return response
```

### Service

```
Business Logic
     ↓
Validation
     ↓
Rules
     ↓
Database operations
     ↓
Return result
```

So:

```
Route
  ↓
"What did the client request?"

Service
  ↓
"How should the application handle it?"
```

---

# 13. `schemas/`

Schemas are commonly used to define and validate data structures.

For example, a product input might require:

```
name
price
category
```

A schema can define what the API expects and how data should be serialized.

Popular tools include:

- Marshmallow
- Pydantic
- Flask-specific validation libraries

For simple projects, manual validation may be enough.

For larger APIs, schema-based validation can improve consistency.

---

# 14. `utils/`

Utility functions are reusable helpers.

For example:

```
utils/
├── validators.py
├── helpers.py
└── decorators.py
```

Possible functions:

```
def is_valid_email(email):
    ...
```

or:

```
def format_response(data):
    ...
```

Be careful with `utils`.

Don't put random code there simply because you don't know where else it belongs.

A utility should generally be:

> Small, reusable, and not strongly tied to one business feature.

---

# 15. `templates/`

For Flask applications that render HTML:

```
templates/
├── base.html
├── index.html
├── auth/
│   ├── login.html
│   └── register.html
└── products/
    ├── list.html
    └── details.html
```

This keeps templates organized according to their feature.

---

# 16. `static/`

Static resources:

```
static/
├── css/
├── js/
├── images/
└── fonts/
```

For example:

```
static/
├── css/
│   └── style.css
│
├── js/
│   └── app.js
│
└── images/
    └── logo.png
```

---

# 17. `tests/`

Tests should be separated from application code.

```
tests/
├── conftest.py
├── test_auth.py
├── test_users.py
├── test_products.py
└── test_orders.py
```

For example:

```
def test_get_products(client):
    response = client.get("/api/products")

    assert response.status_code == 200
```

This keeps your test suite organized.

---

# 18. `config.py`

Configuration should have its own place.

For example:

```
class DevelopmentConfig:
    DEBUG = True


class TestingConfig:
    TESTING = True


class ProductionConfig:
    DEBUG = False
```

Then:

```
app.config.from_object(config_class)
```

This works nicely with the Application Factory pattern.

---

# 19. `run.py`

`run.py` can be a simple entry point:

```
from app import create_app

app = create_app()


if __name__ == "__main__":
    app.run()
```

The application logic should not be placed here.

# 20. Separation of Concerns

One of the most important principles behind modular architecture is **Separation of Concerns**.

It means:

> Different parts of the application should handle different responsibilities.

For example:

```
Routes
  ↓
HTTP

Services
  ↓
Business Logic

Models
  ↓
Database

Schemas
  ↓
Data Validation / Serialization

Utils
  ↓
Reusable Helpers
```

This prevents one component from becoming responsible for everything.

---

# 21. Example of Poor Architecture

Imagine:

```
@app.post("/api/products")
def create_product():

    # Read JSON
    # Validate data
    # Check permissions
    # Calculate price
    # Create database object
    # Save database
    # Send email
    # Format response
    # Handle errors

    ...
```

This might work initially.

But the route has too many responsibilities.

---

# 22. Better Architecture

Instead:

```
@products_bp.post("/")
def create_product():

    data = request.get_json()

    result = product_service.create(data)

    return {
        "success": True,
        "data": result
    }, 201
```

Then:

```
Route
  ↓
Product Service
  ↓
Validation
  ↓
Business Rules
  ↓
Model
  ↓
Database
```

Now each layer has a clearer responsibility.

# 23. Layered Architecture

A common structure is:

```
┌──────────────────────┐
│      HTTP Layer      │
│       Routes         │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│    Service Layer     │
│   Business Logic     │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│     Data Layer       │
│ Models / Repository  │
└──────────┬───────────┘
           ↓
┌──────────────────────┐
│       Database       │
└──────────────────────┘
```

This is often called **layered architecture**.

It is not mandatory for every Flask project, but it is useful for larger applications.

---

# 24. Feature-Based Structure

There is another useful approach.

Instead of organizing everything by technical layer:

```
routes/
models/
services/
```

you can organize by **feature**.

For example:

```
app/
│
├── auth/
│   ├── routes.py
│   ├── service.py
│   ├── models.py
│   └── schemas.py
│
├── users/
│   ├── routes.py
│   ├── service.py
│   ├── models.py
│   └── schemas.py
│
└── products/
    ├── routes.py
    ├── service.py
    ├── models.py
    └── schemas.py
```

This can work very well for large applications.

---

# 25. Layer-Based vs Feature-Based

### Layer-based

```
app/
├── routes/
├── services/
├── models/
└── schemas/
```

### Feature-based

```
app/
├── users/
├── products/
├── orders/
└── auth/
```

### Which is better?

There is no universal winner.

For a smaller/medium Flask application:

```
Layer-based
```

is often easier to understand.

For a large application with many independent features:

```
Feature-based
```

can provide stronger modularity.

You can also combine both approaches.

# 27. Avoid Over-Engineering

Modular architecture is powerful, but don't create 40 folders for a 200-line application.

### Small application

```
app.py
templates/
static/
```

### Medium application

```
app/
├── __init__.py
├── extensions.py
├── models.py
└── routes/
```

### Large application

```
app/
├── models/
├── routes/
├── services/
├── schemas/
├── utils/
└── ...
```

The structure should grow **with the complexity of the application**.

---

# 28. Dependency Direction

A good architecture should have predictable dependencies.

For example:

```
Route
  ↓
Service
  ↓
Repository / Model
  ↓
Database
```

Avoid unnecessary reverse dependencies:

```
Database
  ↓
Route
  ↓
Service
```

The second structure makes the system harder to reason about.

---

# 29. Circular Import Problem

Poor organization can create:

```
routes.py
   ↓
models.py
   ↓
services.py
   ↓
routes.py
```

This can cause:

```
ImportError
Circular import
Partially initialized module
```

Application factories and modular architecture help reduce these problems.

A common dependency pattern is:

```
extensions
    ↑
    │
models
    ↑
    │
services
    ↑
    │
routes
    ↑
    │
application factory
```

The exact dependency graph depends on the project, but keeping dependencies directional is a useful goal.

# 31. Application Startup Flow

With this architecture:

```
run.py
   ↓
create_app()
   ↓
Load Configuration
   ↓
Initialize Extensions
   ↓
Register Blueprints
   ↓
Register Error Handlers
   ↓
Flask App
```

Then when a request arrives:

```
HTTP Request
     ↓
Blueprint / Route
     ↓
Validation
     ↓
Service
     ↓
Model / Repository
     ↓
Database
     ↓
Service Result
     ↓
Route
     ↓
JSON Response
```

# 32. Important Principles

### 1. Single Responsibility

A module should have a clear responsibility.

### 2. Separation of Concerns

Don't mix HTTP, business logic and database logic unnecessarily.

### 3. DRY

**Don't Repeat Yourself.**

Move genuinely reusable logic into appropriate functions/modules.

### 4. KISS

**Keep It Simple.**

Don't create unnecessary architectural complexity.

### 5. Low Coupling

Modules should not depend heavily on unrelated modules.

### 6. High Cohesion

Related code should stay together.

### 7. Explicit Dependencies

Make dependencies clear instead of relying on hidden global behavior.

---

# 33. Common Mistakes

### ❌ One giant `app.py`

Everything ends up in one file.

### ❌ Giant route functions

Routes contain business logic, database operations and validation.

### ❌ Random `utils`

Anything that doesn't have a home gets thrown into `utils.py`.

### ❌ Too many tiny files

Splitting every five lines into a new file makes the project harder, not easier.

### ❌ Circular imports

Modules depend on each other in a loop.

### ❌ Over-engineering

Using complex architecture before the application actually needs it.

### ❌ Mixing unrelated responsibilities

For example:

```
User authentication
Product pricing
Email sending
Database connection
```

all inside one function.
